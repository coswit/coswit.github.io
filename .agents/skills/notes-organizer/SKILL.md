# 笔记整理

维护本仓库（coswit.github.io，docsify 笔记站，导航在根目录 `_sidebar.md`）的技术读书笔记。三类任务：

1. **新书入库**（最常见）：用户提供书名或原始摘录，整理成按章组织的系列笔记
2. **格式清理**：修订已有笔记的格式、表述与术语
3. **合并与拆分**：重叠笔记合并、过长笔记拆成编号系列

## 硬性约束（每次都要遵守）

1. **先提方案，确认后执行。** 任何写文件、移动、删除之前，先给出方案：目标文件夹、每个新文件的完整文件名、章节划分。用户确认后才动手。用户提供的材料本身已明确的（如指定了文件名），照办，不再反复确认。
2. **不自动 git commit。** 只改文件，提交由用户自己完成。
3. **永远不要手动编辑 `_sidebar.md`。** 它由 GitHub Actions（`.github/workflows/main.yml`：push 时运行 docsify-file-generate-slidebar，按文件树生成并回写仓库）自动维护，手动改动会被下次生成覆盖。侧边栏的内容与顺序完全由文件名和目录结构决定。
4. **不做跨笔记的关联引用。** 笔记内不添加指向其他笔记/章节的"参见"链接或指引（如"详见 Java虚拟机/03"），每篇笔记保持自包含；整理时遇到错位到他篇主题的内容，直接移动或删除，不用引用代替。

## 任务一：新书入库

### 第 1 步：搞清书的版本与结构

- 用户只给书名时，先确认版次（很多书有多个版本，内容差异大，如《TCP/IP详解》卷1的 v1/v2）。不确定就问。
- **在线搜索**（WebSearch/WebFetch），按优先级：
  1. 原书完整目录（出版社、豆瓣、英文版官网/O'Reilly 等）——**章节划分以原书目录为准**
  2. GitHub 上别人整理的该书笔记仓库（搜"书名 + notes / 读书笔记"）
  3. 博客上的系列解读文章
- **多源综合主题（C 主题综述式）**：搜索并甄别来源（优先级：官方文档 > 权威博客/论文 > 论坛与问答摘录），方案中列出采信的来源清单；不同来源说法冲突时交叉验证，正文注明分歧与采信理由。
- **搜不到原书内容时**，用模型已有的知识重建全书结构，并在方案中明确说明："基于模型知识整理，章节划分与示例可能与原书有出入"。书中具体细节（示例代码、页码、数字）不确定时不要编造——示例按概念重写并注明改写。
- **用户提供了原始摘录/草稿时**，以它为内容骨架，用目录或模型知识补全结构；用户材料没覆盖的章节，在方案中标注"该章基于模型知识补写"，让用户知情。

### 第 2 步：盘点仓库

- 看根目录已有哪些主题文件夹，复用最贴切的；都不贴切才在方案中提出新建文件夹。
- 这本书是否已有笔记？已有则视为**增量更新**：沿用其文件命名与风格，不另起炉灶。

### 第 3 步：提方案

方案必须具体到文件名，包含：

- 目标文件夹及归属理由
- 文件清单：每个文件的名字 + 覆盖的原书章节
- 每章的篇幅与形态预期（是否含代码示例、mermaid 图、表格）
- 选用的页面骨架范式（A 原书跟读 / B 源码剖析 / C 主题综述，见「写作风格」）

### 第 4 步：写笔记

风格见下文「写作风格」与「语言规则」。侧边栏无需任何处理——push 后 Actions 自动按新文件树生成。

### 第 5 步：自审（review）

写完不等于完成。对每个新写的文件**逐篇复查**后再汇报，检查清单：

- **风格一致性**：标题层级与小节编号是否和系列/原书对齐；文件名编号与覆盖章节是否对应；标题是否直白、小节之间是否有衔接过渡；实践要点是否配了代码示例
- **内容条理与可读性**：章节推进是否条理清晰——先概念后代码、先定义后使用，链路按因果或调用顺序展开，不前后跳跃；论述是否连贯——概念首现即解释、结论有依据、前后内容互相呼应不留断链；行文是否可读——一段一个重点，段落不过长，解说与代码交替，不堆砌密集长句
- **语言规则**：有没有专有名词被意译（JNI→"java 本地方法"、monolithic→"巨石"式的错误）；有没有文学化比喻代称技术概念（"讣告""老朽""紧箍咒"）；同一术语全文是否统一；括注格式是否规范；带缩写的术语首现是否带了英文全称；中文段落标点是否全部全角、有无中英文符号混用（见「语言规则」）
- **事实与时效**：不确定的细节有没有编造；"基于模型知识/已改写"的标注是否如实；成书早于当前版本的内容（已废弃的 API、机制）是否补了时效性注解
- **渲染可用性**：代码块语言标注齐全；mermaid 代码块语法正确（docsify 要能渲染，节点文本里别用圆括号）；表格结构完整；确认没有新增跨笔记关联引用（见「硬性约束」第 4 条）
- 自查出的问题**直接修复**，并在最终汇报里说明"review 发现并修改了什么"；拿不准、需要用户判断的单独列出

## 语言规则（最重要）

笔记是给未来的自己看的：**中文为主，方便理解优先，不强行翻译**。

- **专有名词、API、类名、方法名、模式名、协议名一律保留英文，绝不意译。** JNI 就是 JNI，不写"java 本地方法"；Observer、Factory Method、Binder、Handler 都不翻译。
- **技术行话不意译成比喻，不用文学化代称。** monolithic、death notification、B List service 这类行话直接用英文原词，不译成"巨石""讣告""老朽"，更不用"加冕礼""紧箍咒"式的自造比喻指代技术概念——直接说它是什么。确实通用的中文词（惊群、队头阻塞）可作首现括注：thundering herd（惊群）、head-of-line blocking（队头阻塞）。
- **已有通用中文译名的术语用中文**：垃圾回收、死锁、线程池、闭包。拿不准译名是否通用时，中文后全角括号附英文：协变的（covariant）、活跃性（liveness）、竞态条件（Race Condition）。
- **带缩写的术语要保留英文全称**：首次出现时展开为「中文译名（English Full Name，缩写）」或「缩写（English Full Name，中文译名）」，如 闪存翻译层（Flash Translation Layer，FTL）、MMU（Memory Management Unit，内存管理单元）；后文沿用缩写即可。裸缩写（SRAM、ASLR、COW 这类）同样在首现处补全称，如 SRAM（Static Random-Access Memory）。代码块与 mermaid 图内不展开；缩写出现在全角括注内部时不再另套括号，改用逗号并列，如「（必须 IPC，Interprocess Communication，进程间通信）」。
- **关键定义与金句**：英文原文放引用块，紧跟中文翻译。范式：

  ```markdown
  > A design pattern names, abstracts, and identifies the key aspects of ...
  >
  > 设计模式命名、抽象并标识出一类常见设计结构中的关键方面……
  ```

- 中英文混排时中英文之间加空格，括号用全角：如"示例语言为 C++ 与 Smalltalk"。
- **中文语境用全角标点，不混用英文符号**：逗号、冒号、分号、问叹号、括号在中文句子里一律用全角（，、：、；、？、！、（）），如「进程孵化与登记，持有 mLruProcesses（原在 AMS）」。代码块、行内反引号代码、mermaid 图、表格对齐行、markdown 链接括号保持半角不动；直引号（"）沿用全库既有惯例。
- 中文翻译说不清、有翻译腔的地方，直接保留英文原句，不要硬译。

## 写作风格

命名归「命名与目录约定」管；页面骨架按材料类型从下列三范式中选，提方案时确定、系列内不混用，骨架之外的元素级风格三式通用：

### 页面骨架范式（三选一）

**A 原书跟读式**——教材、语言类（如 cpp、CSAPP）：一页 = 原书一章，标题紧跟原书目录。

```markdown
## 3. 复合类型             ← 原书小节号 + 名，概念重述一两句开场
### 指针和引用             ← 原书子节，### 不带编号
> 关键定义英文原文
> 中文翻译                 ← 引用块；代码示例 + 行内中文注释
```

**B 源码剖析式**——源码、框架机制类（如 深入理解Android卷II、Android源码分析 系列）。有原书时一页 = 原书一章，独立分析时一页 = 一个流程/组件主题；小节用 N.M / N.M.K 编号，按「概述与版本说明 → 整体类关系 → 阶段/专题剖析 → 注意点」推进：

```markdown
## N.1 概述与版本说明       ← 首句承接上一篇；基准声明（AOSP 树/版本）+ 阶段总览表格（阶段、所在进程、核心调用链）
> 版本注意（引用块）        ← 声明级差异："Android 10 起迁移到 ATMS，核心思路不变，骨架仍适用"
> 摘编声明（引用块）        ← "文中代码为摘编版：保留主干、省略日志与样板，可对照 AOSP"——一次声明全局有效
（全局调用链 flowchart）
## N.2 整体类关系           ← 独立大节：角色/Record 的职责表格，点破关键关系（如双界对应）
## N.3 阶段①：App 进程发起  ← 主干：按阶段推进，阶段名带进程/职责边界
### N.3.1 Activity.startActivity ← 子节用 类.方法 命名；局部时序图开头；承接语开场再进源码
### 支线：异常分支与边界     ← 支线收进子节，不打断主干推进
## N.5 专题：非流程内容     ← 链路之外的内容（如前台服务、进程优先级）单独成节
## N.k-1 演进备注（可选）    ← 细节级新旧差异集中收纳，标明"可跳过，不影响主线"
## N.k 使用时要注意的点      ← 固定收尾：每条先语义后代码演示；篇末一句呼应收束
```

- **源码引用**：基准与摘编原则在 N.1 一次性声明，代码块只标来源（如 `ActiveServices#startServiceLocked`）与截取说明；调用链用行内箭头表示：`scheduleCreateService` → `H.CREATE_SERVICE`，不逐跳画图。
- **图示选择**：开篇放唯一一张全局调用链图（flowchart）；局部按需选型——调用链路 → 时序图、生命周期 → 状态图、数据结构关系 → 关系图；一图一职责，节点文本不用圆括号（docsify）。
- **主线/支线**：主干按阶段推进不被打断，异常分支、历史细节收进「支线」子节；并行链路（如 start 与 bind）各自成节、共享 N.2 的类关系；链路小节前后呼应成闭环（客户端的异常对应服务端的检查）。
- **版本差异两级**：章首「版本注意」引用块管声明级差异（骨架是否仍适用）；细节级差异少时行内括注、多时进章末「演进备注」——当前源码独立阅读、自成主体，主干不展开旧版本写法。

**C 主题综述式**——多源综合类：材料来自书籍、网页、博客等多种来源，按内容主题重新梳理总结，不必跟随任何单一来源的结构；一页 = 一个主题，页内小节不编号、按主题逻辑排序：

```markdown
## 导读：这篇讲什么        ← 一段定位 + 覆盖范围 + 一张心智模型 mermaid 图
## 核心概念                ← 逐个展开：定义 → 机制 → 代码
### 概念 A
### 概念 B
## 全景流程                ← 完整链路：时序图/状态图 + 逐步解说
## 对比与选型              ← 决策表格
## 实践要点                ← 每条配代码
## 来源                    ← 文末可选：书名/链接列表
```

跨来源内容合并去重、按主题取舍；不同来源说法冲突时交叉验证，在正文注明分歧与采信理由。

三式共同不变量：

- **每页结构**：不写页面总标题、不开装点性/文学化的开篇引用块（B 式概述内的版本注意、摘编声明等功能性引用块不受此限），一页笔记一个单元（A 式为原书一章，B 式为原书一章或一个流程/组件主题，C 式为一个主题）；标题层级与编号跟随所选范式。
- **标题直白**：小节标题直接说内容（如 `CachedAppOptimizer:cached 进程冻结`、`启动时序与 4.0 对比`），不用比喻、排比、悬念式标题（如"杀不死你的，先冻住你"）。
- **小节之间要有叙事衔接**：每小节开头用一两句引入，承接上一小节、交代本节讲什么，然后再进代码；不要小节之间没有过渡、代码块直接罗列。前后有关联的内容（如客户端的异常与服务端的检查）要互相呼应，形成完整链路。
- **代码注释写事实**：注释说明该行代码做什么、为什么，写清机制（如「返回包名为 `?` 的错误标记，客户端据此抛异常」）；原代码自带的英文注释分级处理——简短通用的（// no-op 这类）保留即可，承载机制信息的优先在其后补中文解说，翻译会失真的保留英文原文、不强译（与「语言规则」的不硬译一致）；不用"看的是 X——不是 Y"式的对比腔，不用含糊代称（"占位 ComponentName""办前台化"这类）。
- **实践要点配代码示例**：核心条目（易错、语义复杂）必须配基于源码核实的最小示例（如 ServiceConnection 的四个回调逐一演示），优先正反例对照（错误写法 vs 正确写法）；纯认知型条目（概念澄清）可用文字 + 表格，不为凑数硬写示例；先讲清概念语义（如返回值表格），再上代码。
- **紧跟原书结构**：按原书小节顺序推进，每个概念用中文重述；难懂处加对比表格（如指针 vs 引用这类易混概念的对照）或 mermaid 图，帮助理解优先。
- **代码块必须标注语言**；原书示例代码尽量原样保留（含原有英文注释），在行内追加中文注释，或在代码前后用中文解说。原书示例语言与实际开发语言不一致、确无保留价值时才改写，并注明改写。
- **原书表格保留英文原文**，必要时在单元格内加中文括注（如 `6 significant digits(有效数字)`）。
- **关键定义加粗**，中文重述后紧跟英文原文括注，与「语言规则」一致。
- **图**：结构/流程/关系图用 mermaid（站点已配置 mermaid、KaTeX，数学公式用 `$...$`），不画 ASCII 图。
- 站点 markdown 开启 `breaks: true`：单个换行即成段，行尾不需要补两个空格。
- 笔记配图放**笔记所在文件夹的 `images/` 子目录**（如 `Java虚拟机/images/`），引用用相对路径 `./images/文件名.png`（文件名用 ASCII，避免 URL 编码问题）。清理旧笔记时，把外链图下载到本地 `images/` 并替换引用，消除外链失效风险。

## 命名与目录约定

- **新系列**（这本书还没有笔记）：在主题文件夹下建书名子文件夹，章节文件用两位数编号。两种等价范式，任选其一但系列内统一：**连字符式** `00-导读.md`、`01-标题.md`（如 `设计模式/GoF/`、`AI/oh-my-openagent/`），或**两空格式** `01  标题.md`（如 `cpp/`）。
- **已有系列**：文件命名严格沿用既有惯例，如 `Effective Java/1.对像的创建和销毁.md`、`Java并发编程/01线程安全性.md`、`cpp/01  变量和基本类型.md`；但内容风格仍按「写作风格」执行。
- **编号必须用 ASCII 数字**：`_sidebar.md` 按文件名排序自动生成，`00`、`01`…`10` 能正确排序，而中文数字按 Unicode 排序会乱序（一 < 七 < 三 < 九 < 二 < 五 < 八 < 十）。给中文数字编号的已有系列补笔记时，在方案中指出这一冲突，由用户决定：沿用中文数字（接受侧边栏乱序）还是整个系列迁移为 ASCII 编号。
- 章节标题可中文可英文，与内容匹配（英文原著章节名可保留英文，如 `01-Creational-Patterns.md`）。

## 任务二/三：清理、合并、拆分

与任务一相同，先提方案、确认后执行（「硬性约束」第 1 条）。方案要素：

- **文件清单**：受影响的每个文件，标注动作（修改/移动/重命名/删除）。
- **改动说明**：清理列出要校正的问题类型与示例；合并说明保留哪个文件、内容如何取舍；拆分给出新系列文件名与章节分配，原文件删除还是留作索引进方案里定。
- **影响面**：移动/重命名的文件，全局搜索旧路径，列出引用它的其他文件。

执行要点：

- **格式清理**：统一标题层级（对齐该系列选用的骨架范式，见「写作风格」；三式通用的不变量：不写页面总标题、一页一个单元）、补代码块语言标注、修失效的图片与链接、全文术语一致、全文标点统一（中文段落一律全角，消除中英文符号混用）——按「语言规则」校正误译（如把"java 本地方法"改回 JNI）。
- **合并**：只合并主题明显重叠的笔记，取舍理由写进方案。
- **拆分**：单文件过长且天然分章的，拆成编号系列（命名见上）。
- **移动/重命名文件后**：全局搜索旧路径，更新其他笔记中指向它的链接（`_sidebar.md` 由 Actions 自动重新生成，无需处理）。
