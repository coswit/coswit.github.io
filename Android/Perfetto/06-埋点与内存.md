## 导读：补上业务语义与内存调用栈两块拼图

系统 Trace 能告诉你线程什么时候运行、CPU 在哪个核、哪一帧超时，但它不知道播放器正在解哪一帧、游戏引擎在加载哪个场景、一个业务任务在队列里排了多久。这篇讲两个互补的能力：**用 Perfetto SDK 的 Track Event 把业务语义写进 Trace**（当时在 decode 哪个 frame、哪个队列堵了、请求怎么跨线程流转），**用 heapprofd 把 native 分配的调用栈写进 Trace**（谁在 malloc/new）。两者都能与 sched、Binder、FrameTimeline 放在同一时间轴上分析。

## 埋点选型：先看要不要接 SDK

没有业务语义缺口就不需要接 SDK。按场景选工具：

| 场景 | 建议 |
|---|---|
| Java/Kotlin 层临时标记函数耗时 | android.os.Trace 或 AndroidX tracing（抓取时配 atrace_apps 或 -a 包名） |
| Android native / C++ 模块长期埋点 | Perfetto SDK Track Event |
| 跨平台引擎、游戏、播放器、Camera pipeline | Track Event + 稳定参数与 counter |
| 需要复杂结构化状态，slice/counter 表达不了 | 再考虑自定义 DataSource |
| 只想看系统线程、Binder、频率 | 系统数据源即可，不接 SDK |

几点边界：**Perfetto SDK 只有 C/C++ 形态，没有 Java/Kotlin 版**——纯 Java App 想要带参数和 flow 的结构化事件，要么把埋点下沉到 native 层走 JNI（Java Native Interface），要么退回 android.os.Trace 的纯 slice 表达；Android-only 的简单 section 场景，官方也建议继续用 android.os.Trace（走 atrace 路径进 Perfetto）。App 侧 tracing 的版本资格：API 31 起 App tracing 对所有 App 默认可用；API 29/30 非 debuggable App 需要 profileable 或 AndroidX Trace.forceEnableAppTracing() 二选一；API 28 及以下只能靠 forceEnableAppTracing()（API 31+ 上是 no-op）。NDK ATrace_* 从 API 23 起可用。另外 ATrace 也有开销：热循环、每次锁尝试、每个对象都打点，会通过 JNI、trace_marker 与内核路径扰动结果——粗粒度 section 用 ATrace，高频状态用 SDK 的 category gating 或默认关闭的 debug category。

SDK 里有两层能力：**Track Event**（函数耗时、业务阶段、队列长度、跨线程关系，接入成本低，Trace Processor 与 UI 原生支持）与**自定义 DataSource**（自定义 protobuf 状态、高频结构化数据，要维护 schema 还要给 Trace Processor 补解析）。能用 slice、counter、flow 和参数表达的问题，第一版一律先用 Track Event。

### 业务阶段字典先于代码

Track Event 不是把宏塞进每个函数。先定义业务阶段字典，让后续 SQL、报告、看板都知道事件叫什么、属于哪个阶段、单位是什么、缺字段怎么降级：

| event_name | category | phase | 必填参数 | 单位/基数 | 报告指标 |
|---|---|---|---|---|---|
| DecodeFrame | player | decode | frame_id、stream_id、codec | frame_id 在 stream_id 内唯一 | decode_dur_ms |
| UploadTexture | rendering | upload | frame_id、texture_bytes | texture_bytes 用 bytes | upload_dur_ms、upload_bytes |
| RenderSubmit | rendering | submit | frame_id、surface_id | queue_depth 用 items | submit_dur_ms |
| WaitForBuffer | camera | wait | request_id、buffer_queue | request_id 在 session 内唯一 | wait_for_buffer_ms |

字段改名、删字段、改单位都要提升 arg_schema_version；长期报告字段不要叫 debug.frame_id 而应叫业务 schema 的 frame_id。缺 RenderSubmit 时报告只能输出 decode/upload 阶段，写 missing_marker=RenderSubmit、evidence_grade=partial，不能写端到端结论。

### Backend 选择

| Backend | 谁控制 Trace | 适用 |
|---|---|---|
| kInProcessBackend | App 自己创建 tracing session | 单进程验证、离线测试 |
| kSystemBackend | 外部 perfetto 命令或系统服务控制 | 与 sched、freq、Binder、FrameTimeline 合并分析（Android 性能分析最常用） |

system backend 下 App 只是 producer，session 的启停由系统控制；App 不能自己读取整份系统 Trace。Android 9 已有 traced，但命令行 --txt 配置从 Android 10 起才好用，P 设备通常要走二进制 TraceConfig；非 Pixel 的 P/Q 设备要验证 traced 是否启用。

### 最小接入骨架

native 模块接入只解决三件事：稳定 category、system backend、可查询的事件名。

```cpp
// tracing_categories.h：只声明 category，名字要稳定，
// 不要把动态 id、页面实例号塞进 category 名
PERFETTO_DEFINE_CATEGORIES(
    perfetto::Category("rendering").SetDescription("Rendering pipeline"),
    perfetto::Category("player").SetDescription("Media pipeline"),
    perfetto::Category("pipeline.debug")
        .SetDescription("Verbose pipeline events")
        .SetTags("debug"));

// tracing_categories.cc：静态存储只出现在一个 .cc 文件，避免多重定义
PERFETTO_TRACK_EVENT_STATIC_STORAGE();

// tracing_init.cc：全进程只做一次，放进程入口确定路径（如 JNI_OnLoad），做好幂等
void InitPerfetto() {
  perfetto::TracingInitArgs args;
  args.backends |= perfetto::kSystemBackend;
  perfetto::Tracing::Initialize(args);
  perfetto::TrackEvent::Register();
}
```

业务代码里打点。TRACE_EVENT 是作用域事件（进作用域开始、出作用域结束），适合包住同步工作；跨函数的阶段用 TRACE_EVENT_BEGIN/END，但别把 begin/end 分散到不相关调用路径，容易嵌套错配：

```cpp
void DecodeFrame(int frame_id) {
  TRACE_EVENT("player", "DecodeFrame", "frame_id", frame_id);
  DecodeFrameImpl(frame_id);
}
```

初始化的几个坑：注册之前发出的 Track Event 会被静默丢弃（事后难与真丢包区分）；多进程 App 的每个进程都要各自 Initialize + Register，:remote、:player 子进程不继承主进程的初始化；system backend 下进程在 session 开始后才启动也没关系，producer 连上 traced 后数据源自动启用，但连接之前的事件不存在，别把这段空白当业务空闲。C++ SDK 是 C++17 库，发布形态通常是合并版 perfetto.h + perfetto.cc，接入时确认编译标准、线程库、符号裁剪与包体增量。

### category 是线上开关

category 决定哪些事件被打开，要按配置接口来设计而不是随手起名：按子系统和开关粒度划分（player/rendering/camera/pipeline.debug/pipeline.slow），页面、实验组、请求类型放参数或 metadata。注意 C++ SDK 未命中规则时非 debug/slow category 默认打开，C SDK 默认关闭——线上 preset 统一用「先全关再白名单」避开默认行为差异：

```protobuf
data_sources {
  config {
    name: "track_event"
    target_buffer: 0
    track_event_config {
      disabled_categories: "*"
      enabled_categories: "player"
      enabled_categories: "rendering"
    }
  }
  producer_name_filter: "com.example.app"
}
```

system backend 下 track_event 可能来自多个 producer，现场 preset 用 producer_name_filter 收住范围（先从 trace 里确认实际 producer name）。debug/slow tag 的 category 默认关闭，专项分析再显式打开。现场抓 Trace 不必换包，改配置即可控制业务事件。

## 和系统 Trace 合抓

业务事件解释「业务在做什么」，系统事件解释「为什么慢」。合抓时按频率分 buffer，ftrace 与 track_event 各归各的：

```protobuf
buffers { size_kb: 131072 fill_policy: RING_BUFFER }  # 0: sched / ftrace
buffers { size_kb: 32768  fill_policy: RING_BUFFER }  # 1: app track event

data_sources {
  config {
    name: "linux.ftrace"
    target_buffer: 0
    ftrace_config {
      ftrace_events: "sched/sched_switch"
      ftrace_events: "sched/sched_waking"
      ftrace_events: "power/cpu_frequency"
      ftrace_events: "power/cpu_idle"
      atrace_categories: "gfx"
      atrace_categories: "view"
      atrace_categories: "binder_driver"
      atrace_apps: "com.example.app"
    }
  }
}
data_sources {
  config {
    name: "android.surfaceflinger.frametimeline"
    target_buffer: 0
  }
}
data_sources {
  config {
    name: "track_event"
    target_buffer: 1
    track_event_config {
      disabled_categories: "*"
      enabled_categories: "player"
      enabled_categories: "rendering"
    }
  }
  producer_name_filter: "com.example.app"
}
```

抓完先用 SQL 确认事件进来（thread_slice 是 stdlib 提供的关联视图，参数用 EXTRACT_ARG 读 debug.* annotation）：

```sql
INCLUDE PERFETTO MODULE slices.with_context;
INCLUDE PERFETTO MODULE time.conversion;
SELECT
  time_to_ms(ts) AS ts_ms,
  time_to_ms(dur) AS dur_ms,
  name, thread_name, process_name,
  EXTRACT_ARG(arg_set_id, 'debug.frame_id') AS frame_id
FROM thread_slice
WHERE process_name = 'com.example.app'
  AND name IN ('DecodeFrame', 'RenderScene', 'UploadTexture')
ORDER BY ts;
```

两个注意点：独立 track、process track 的事件不一定有 utid，可能不出现在 thread_slice，改用 process_slice / thread_or_process_slice 或直接 JOIN track；业务 frame_id 是业务帧、FrameTimeline 的 frame/vsync 是系统帧，只靠时间重叠容易把排队、预渲染归到错误帧，最终要结合 Choreographer doFrame、RenderThread slice 与 actual/expected_frame_timeline_slice 确认。

## 跨线程 flow、独立 track 与 counter

业务慢常不在单个函数而在队列之间——UI 线程提交、decoder 处理、render 消费，同线程 slice 看不出它们属于同一个 frame。用 flow 连接（不要直接拿容易复用的业务 frame_id 当 flow id，先 hash 成 Trace 内唯一的进程内 token）：

```cpp
uint64_t MakeFlowId(uint64_t session_id, uint64_t stream_id, uint64_t frame_id) {
  return Hash64(session_id, stream_id, frame_id);
}
void EnqueueFrame(uint64_t session_id, uint64_t stream_id, uint64_t frame_id) {
  TRACE_EVENT("player", "EnqueueFrame",
              perfetto::Flow::ProcessScoped(MakeFlowId(session_id, stream_id, frame_id)),
              "frame_id", frame_id);
}
void RenderFrame(uint64_t session_id, uint64_t stream_id, uint64_t frame_id) {
  // 最终消费阶段用 TerminatingFlow 结束 flow
  TRACE_EVENT("player", "RenderFrame",
              perfetto::TerminatingFlow::ProcessScoped(MakeFlowId(session_id, stream_id, frame_id)),
              "frame_id", frame_id);
}
```

跨多函数、跨线程持续很久的任务（任务队列、异步加载）也可以放独立 track——track id 要在一次 Trace 内对该并发任务唯一，线上 request id 容易复用，复用后不同任务会合到同一条 track 假装成一个长任务，稳的做法是加 session namespace 或生成专用 64-bit track id：

```cpp
void StartRequest(uint64_t request_id) {
  perfetto::Track track(request_id);
  auto desc = track.Serialize();
  desc.set_name("player.request");
  perfetto::TrackEvent::SetTrackDescriptor(track, desc);
  TRACE_EVENT_BEGIN("player", "Request", track, "request_id", request_id);
}
void FinishRequest(uint64_t request_id) {
  TRACE_EVENT_END("player", perfetto::Track(request_id));
}
```

**counter 只放状态，不放日志**：队列长度、in-flight 请求数这类随时间变化的数值适合 counter；frame id 是标识符不是可聚合指标，放 slice 参数或 flow id。counter 要固定单位与聚合口径（峰值、窗口均值、增长斜率），绝不对标识符求 avg/max：

```cpp
void ReportDecodeQueueDepth(int depth) {
  TRACE_COUNTER("player",
                perfetto::CounterTrack("DecodeQueueDepth", "items"),
                depth);
}
```

**事件名是 SQL 接口**：一旦进了 SQL、看板与回归报告，事件名就不能变，动态信息放参数——

```cpp
// 不建议：每个 frame 生成不同事件名，SQL 无法稳定统计
TRACE_EVENT("player", perfetto::DynamicString{"DecodeFrame_123"});
// 建议：事件名稳定，动态信息放参数
TRACE_EVENT("player", "DecodeFrame", "frame_id", frame_id);
```

命名采用「阶段 + 动作」（DecodeFrame、UploadTexture、RenderScene、SubmitRequest、WaitForBuffer）。事件名稳定后 SQL 才稳定：

```sql
INCLUDE PERFETTO MODULE slices.with_context;
INCLUDE PERFETTO MODULE time.conversion;
SELECT process_name, thread_name, name,
       COUNT(*) AS count,
       ROUND(AVG(dur) / 1e6, 1) AS avg_ms,
       time_to_ms(MAX(dur)) AS max_ms
FROM thread_slice
WHERE process_name = 'com.example.app'
  AND name IN ('DecodeFrame', 'UploadTexture', 'RenderScene')
GROUP BY process_name, thread_name, name
ORDER BY max_ms DESC;
```

## 控制写入量

Track Event 开销低但不免费，两条丢数据路径要分清：android.os.Trace / ATrace 写太密压 ftrace per-CPU buffer；SDK Track Event 写太密压 producer 共享内存、central buffer 与增量状态——ATrace 丢事件时不要只盯 track_event stats，SDK 丢包时也不要去调 ftrace buffer。给每类埋点设预算：

- **事件密度**：按 events/sec、每帧事件数、参数字节数与 Trace 时长估算写入量；120Hz、多线程、多阶段叠加后，每帧一次也可能过密
- **数据形状**：小对象、每次锁尝试、像素级循环不默认开启；高频 debug category 默认关，专项时用 1/N 采样或触发后短窗口开启
- **参数开销**：便宜标量直接传；昂贵字符串、JSON、容器遍历、锁内状态快照放进 enabled 判断或 lambda——参数在宏调用前已拼好时，category gating 救不了
- **采集验收**：业务 Track Event 放独立 central buffer；抓完跑 stats 验收（traced_buf_chunks_overwritten/discarded、traced_buf_trace_writer_packet_loss、track_event_parser_errors、track_event_tokenizer_errors、track_hierarchy_missing_uuid 等）；Ring Buffer 场景配合 incremental_state_config.clear_period_ms 防止后半段事件缺名字

报告里单独给 track_event_trust_level：packet loss 为 0 但 tokenizer_errors 或 track_hierarchy_missing_uuid 非零，业务事件仍要降级。

## App 侧现场 Trace 协议

普通 App 没有随意启动系统 tracing 的权限，也不适合线上动态下发高开销 TraceConfig。现场方案拆三层：**平台侧**预置受控 TraceConfig（trigger、Ring Buffer、数据源白名单、配额）；**App 侧**记录埋点与页面状态，检测慢帧、卡死、超时后按约定激活 trigger；**服务端**接收 Trace package，跑 stats 与摘要 SQL。

核心机制是 STOP trigger：trace 先以 Ring Buffer 循环记录，App 检测到问题后触发一个已声明的名字，系统在 stop_delay_ms 后收尾——问题发生前的现场和触发后的尾巴都能保住：

```protobuf
trigger_config {
  trigger_mode: STOP_TRACING
  trigger_timeout_ms: 1800000   # 最长等待 trigger 的窗口
  triggers {
    name: "app_ui_jank"
    stop_delay_ms: 1000
    max_per_24_h: 8             # 兜底限频，平台侧还要做用户/设备/版本/天维度限频
    skip_probability: 0.8
  }
}
```

trigger 的模型是：有权限的 consumer 预先声明名字，App 这类 producer 只能激活已声明的名字。测试设备可用 `/system/bin/trigger_perfetto app_ui_jank` 验证；接了 SDK 的 native 模块用 `perfetto::Tracing::ActivateTriggers({"app_ui_jank"}, 10000)`（第二参数是 TTL，避免无限期 pending）。线上 App 不应假设自己能执行 trigger_perfetto 命令，更推荐平台提供受控接口：App 只提交受限请求（preset 名、trigger 名、触发原因、场景与动作 id、慢帧列表），平台按白名单、采样率、设备状态与配额决定是否触发。

触发策略要靠近用户感知而不是实现细节：UI 慢帧（JankStats 连续慢帧）→ 看主线程、RenderThread、FrameTimeline、CPU；主线程卡死前兆（2s/4s/8s watchdog）→ 看主线程状态、Binder、锁、IO；业务 timeout（Camera open、播放器 prepare）→ 看 App marker、Binder、HAL。触发名进平台 preset 后保持稳定，改名会断开服务端聚合与历史数据。

### Trace package 最小集

一份现场包最小必需四件：Trace 本体、业务 metadata（app_metadata.json，字段固定带 schema_version：app_version、page/action、trigger 与 reason、scenario_id/session_id/action_id、refresh_rate_hz、thermal_state、trace_preset）、采集 preset（trace_preset.txt）、stats 可信度结果（trace_stats.json，含 trace_quality_status 与逐项 stats 及决策）。app_events.jsonl 存触发点事件，与 Track Event 共享 scenario_id/session_id/action_id。

两个工程红线：**时间戳统一用 elapsedRealtimeNanos / CLOCK_BOOTTIME 语义并写进字段名**——Perfetto 能同步带 ClockSnapshot 的时间域，外部 JSON 不会自动归一，metadata 里记录 trace 起止的 elapsed realtime 供服务端对齐；**不要直接截断 trace.perfetto-trace**——它是 protobuf 流，二进制裁剪会破坏 packet、时钟同步与增量状态，裁剪发生在采集侧（Ring Buffer 控触发前窗口、stop_delay_ms 控触发后窗口、trigger 限频控重复抓取），max_file_size_bytes 是落盘硬上限而非窗口裁剪工具。平台化后再补上传策略（Wi-Fi 条件、每日配额、白名单 tag、加密与 TTL）。

## 内存问题先分账

heapprofd 之前先把内存数据分成几张账，很多误判源于混账：

| 数据 | 来源 | 回答什么 |
|---|---|---|
| 进程 RSS（Resident Set Size，常驻内存）/ swap 趋势 | linux.process_stats | RSS、anon/file、swap、oom_score_adj 变化 |
| PSS（Proportional Set Size，按比例分摊内存）/ Private Dirty | dumpsys meminfo、smaps_rollup | PSS、SwapPss 是否上涨 |
| 系统内存压力 | linux.sys_stats | MemAvailable、ZRAM、vmstat、PSI（Pressure Stall Information，压力失速信息） |
| native allocation 调用栈 | android.heapprofd | 哪些 malloc/new 栈在分配、哪些没释放 |
| Java 对象保留关系 | Java heap dump、MAT（Memory Analyzer Tool） | 哪些 Java 对象被谁持有 |

**heapprofd 统计的是目标进程向 libc malloc/free、new/delete 请求的字节数，不等于 RSS**：GraphicBuffer、dma-buf、GPU texture、驱动分配、直接 mmap/memfd、绕过 libc 的自研 allocator 都不在这张账里（自研 allocator 要用 custom allocator API 专项接入）。反过来 heapprofd 里某条栈累计分配很高也不代表 RSS 同涨——那可能是分配 churn（频繁申请快速释放，Total 高、Unreleased 不高）。内存问题先分清「占住不放」和「反复制造临时对象」。按现象选入口：Java 对象保留明显 → HPROF/MAT；Native Heap 涨 → heapprofd；Graphics/GL/dmabuf 涨 → meminfo/GPU 计数/SurfaceFlinger；RSS 涨而 heapprofd 不高 → 先用 smaps_rollup、mmap syscall 拆账，不要判 heapprofd 抓错（allocator 线程缓存、碎片、ZRAM、page 粒度都会造成差异）。

## heapprofd 快速上手

前置资格：Android 10+；user build 上抓目标 App 需要 debuggable 或 `<profileable android:shell="true"/>`；userdebug/eng 可抓大多数 App 与系统服务（少量 critical 服务被 SELinux 策略禁止）。Android 15 起 App 可经 ProfilingManager 请求 heap profile（结果脱敏、限流、不保证满足），与 adb/实验室路径分开设计。

官方推荐先用 tools/heap_profile 脚本（处理设备侧细节，适合单进程定位）：

```bash
tools/heap_profile android \
  -n com.example.app \
  -d 15000 \      # 抓 15 秒
  -i 4096 \       # 采样间隔 4096 bytes
  -c 5000 \       # 每 5 秒一个 continuous dump
  -o /tmp/heapprofd-com-example-app
```

输出目录的 raw-trace 拖进 Perfetto UI 即可看到 Heap Profile 轨道。按进程名（-n）抓会命中已运行的同名进程并等待后续新进程，能覆盖启动早期（zygote specialize 最早一小段仍可能没记到）；按 PID 抓适合稳定运行现场但错过启动段。多进程 App 要分别写多个 -n（com.example.app、com.example.app:remote…），否则子进程的 malloc 不进 profile。

### 与系统 Trace 合抓的配置要点

| 配置 | 建议 |
|---|---|
| sampling_interval_bytes | 4096 是常用起点；手写配置必须显式设非 0 值（0 无效，Android 12 之前还可能让目标进程崩溃） |
| continuous_dump_config | dump_phase_ms + dump_interval_ms，周期性产生累计快照 |
| shmem_size_bytes | 分配密集时调大 |
| block_client | true：共享内存满时阻塞目标进程换数据完整，适合实验室 leak 复现（配 block_client_timeout_us）；false：交互性能分析默认值，避免反向影响 jank/latency |
| buffer 策略 | heapprofd 放独立大 buffer；用 DISCARD 时必须足够大——heap profile 在 dump 点集中写入，DISCARD 满后丢新数据，对末尾 diamond 危险 |
| 业务 marker | 至少四类：operation_start、steady_state、operation_end、release_done/gc_idle_done；没有 release marker 只能写「操作后保留增加」，不能写「泄漏」 |

heapprofd + ftrace 会互相增加扰动，heap + 系统上下文的 preset 只适合短窗口实验室复现，并记录目标场景耗时是否被 profiler 改变。

## 读 Profile：UI 与 SQL

Heap Profile 轨道上每个 diamond 是一次 dump（continuous dump 的每个 diamond 都是从开始到该时刻的累计结果），点击后下方出 flamegraph。读图顺序：先看连续几个 diamond 的 **Unreleased malloc size** 是否持续增加（占住不放）；再看 **Total malloc size** 判断是不是高 churn；用 Left Heavy 视图找最大调用栈；找 allocator/ART glue 之上的第一个业务帧；回时间轴关联触发操作。

**不要用单个 diamond 判泄漏**，至少看「操作前、操作后、回收后」三点：操作后涨、回收后仍不降才偏泄漏；操作中升高但释放后回落是峰值；长期保留但有容量上限、复用证据与压力回收策略才可能写成缓存。实验室可用 `adb shell killall -USR1 heapprofd` 在关键业务点手动触发 snapshot（进页面前、页面稳定后、退出并 release 后各一次），比固定间隔更容易与业务动作对齐。

SQL 侧，单目标快速读图用标准库 summary tree（沿 callsite 父子关系聚合，接近 flamegraph 的 cumulative 视图；没有进程列，别用于多进程回归统计）：

```sql
INCLUDE PERFETTO MODULE android.memory.heap_profile.summary_tree;
SELECT name, mapping_name AS map_name,
       cumulative_size / 1024.0 / 1024.0 AS unreleased_mb
FROM android_heap_profile_summary_tree
WHERE cumulative_size > 0
ORDER BY cumulative_size DESC
LIMIT 50;
```

泄漏三点对比的骨架（baseline / after_action / after_release 三个 dump 时刻，按调用栈对比未释放量）：

```sql
WITH selected_dumps(label, dump_ts) AS (
  VALUES
    ('baseline', 100000000000),
    ('after_action', 120000000000),
    ('after_release', 150000000000)
),
alloc_by_dump AS (
  SELECT d.label, a.callsite_id,
         SUM(a.size) / 1024.0 / 1024.0 AS unreleased_mb
  FROM heap_profile_allocation a
  JOIN selected_dumps d ON a.ts = d.dump_ts
  WHERE a.upid = (SELECT upid FROM process WHERE name = 'com.example.app'
                  ORDER BY start_ts DESC LIMIT 1)
  GROUP BY d.label, a.callsite_id
)
SELECT
  callsite_id,
  SUM(CASE WHEN label = 'baseline' THEN unreleased_mb ELSE 0 END) AS baseline_mb,
  SUM(CASE WHEN label = 'after_action' THEN unreleased_mb ELSE 0 END) AS after_action_mb,
  SUM(CASE WHEN label = 'after_release' THEN unreleased_mb ELSE 0 END) AS after_release_mb
FROM alloc_by_dump
GROUP BY callsite_id
ORDER BY after_release_mb DESC
LIMIT 50;
```

原始表查询把调用栈拆成 frame 行，容易只看到 malloc/realloc 这类 leaf frame，最终归因回 summary tree 或 flamegraph 取完整调用栈；写稳定脚本前用 `PRAGMA table_info(heap_profile_allocation);` 确认字段。

## 采样间隔与符号化

sampling_interval_bytes: 4096 的含义是平均每分配 4096 bytes 采一个样本再按概率归因到调用栈——不是「低于就估算、高于就精确」的硬分界。怀疑大量小对象时调低间隔（开销上升）；buffer overrun 时先增大共享内存或提高间隔。报告措辞上不要写「精确分配了 12.34MB」，写「4096 bytes 采样间隔下，未释放分配主要集中在 A/B/C 三条调用栈」——采样 profiler 的价值是找方向和排序。before/after 比较必须保持同一采样间隔、相近负载与同一窗口；样本少、窗口短、调用栈分散时 top 栈排名不稳定，weak 证据只写「候选调用栈」。

Java 侧补充：heapprofd 在 Android 12+ 可通过 `heaps: "com.android.art"` 切到 Java allocation sampling（记录对象创建调用栈，不记录 GC、不等价于 heap dump 的保留关系）；「谁持有 Java 对象」仍然只有 Java heap dump 能回答。

符号化：flamegraph 里全是地址、unknown 或混淆名时先修符号——保留未裁剪 so 或 build id 对得上的符号文件，补 ProGuard/R8 mapping；Build ID mismatch 降级为地址级证据。读栈时别盲滤 libart.so、allocator glue——ART 常是 Java 调 native、NativeAllocationRegistry 路径的关键上下文；DEDUPED、ICF 折叠、单帧栈先按符号化问题处理。heapprofd 专用 stats 单独跑一遍（name GLOB 'heapprofd_*'），重点看 heapprofd_buffer_overran、heapprofd_non_finalized_profile、heapprofd_client_error、heapprofd_sampling_interval_adjusted——命中后不要把数字写成精确账本。

## 发布报告前的检查

- **采集条件**：Android 10+（Java allocation sampling 需 12+）；user build 的 profileable/debuggable；按进程名抓才覆盖启动早期；runtime profiling 不是立刻生效（目标进程很空闲时，下一波分配前可能还没启用）；同一目标进程同时只能被一个 session profile
- **数据可信度**：32 位程序在部分旧版本有限制（空 profile 查 Known Issues）；heapprofd/stackprofile/symbolization stats 过一遍；heapprofd 数字与 RSS 对不上很常见（碎片、线程缓存、ZRAM）
- **结论归类**：leak（释放后仍保留）/ peak（操作中升高释放后回落）/ cache（有上限、复用证据、压力回收）/ churn（Total 高 Unreleased 低）/ 图形内存账外问题 / 证据不足，每类对应不同下一步
