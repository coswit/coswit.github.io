## 导读：从「抓 10 秒」到「守住现场」

很多性能问题不是点一下就能复现：开机慢、偶发卡顿、温升后降频、几小时后音频断续、车机周期性抖动。这些都不适合 10 秒手工 trace，需要现场长 Trace——提前定义证据窗口、用 trigger 封存现场、让文件安全写完、拿回来后判断可信度。这篇分两半：前半讲**怎么把偶发问题变成可复查的证据**，后半讲**当问题疑似压到硬件层时，GPU、devfreq、电池与电源轨信号怎么进同一段分析**。先立一条总纲：现场方案的质量取决于能否用可控开销换到可复查证据，把所有开关打开抓一小时只会更快撞上文件、开销与丢数据问题。

## 证据窗口先行

写配置前先把问题窗口问清楚，每个答案都映射到具体配置项：

| 问题 | 影响的配置 |
|---|---|
| 问题多久复现一次 | duration_ms、是否后台运行、是否周期 snapshot |
| 根因在问题前还是问题后 | STOP trigger 还是 START trigger |
| 问题前要保留多少秒 | Ring Buffer 大小、数据源宽度、写文件周期 |
| 用户能否手工停止 | 自动 trigger、是否接 bugreport |
| 早期 ADB 不可用 | Boot Trace、平台预置、init/service 触发 |
| 抓取中可能断 USB | --background-wait、snapshot、后台服务 |
| 文件最大能多大 | max_file_size_bytes、上传策略、本地 TTL（Time To Live，留存期限） |
| 数据是否敏感 | log tag 白名单、禁用 atrace_apps: "*" |

常见场景到模式的映射：UI 偶发卡顿与 ANR 前兆用 Ring Buffer + STOP trigger（验证 App marker、FrameTimeline 覆盖目标窗口）；温升降频用 write_into_file 或 snapshot 按分钟级保留趋势；业务 timeout 根因在前用 STOP、要看恢复过程用 START；音频 underrun 用 Ring Buffer + STOP 且 audio/sched/binder/underrun marker 同步在场。

## 三种长 Trace 模式

| 模式 | 行为 | 适合 | 风险 |
|---|---|---|---|
| Ring Buffer + STOP trigger | 循环记录最近窗口，异常发生后停止 | 掉帧、ANR 前兆、音频 underrun | buffer 太小覆盖根因；trigger 未命中就没有现场 |
| write_into_file 长录制 | 周期把 buffer 写到文件 | 几十分钟到数小时趋势 | I/O 开销、文件过大 |
| --clone-by-name snapshot | 原 session 继续跑，按需克隆当前窗口 | 调参、温控、电源策略实验 | 需 Android 14(U)+ 或厂商合入新版 perfetto |

不要把三种模式混成一个「大而全配置」，先选模式再定数据源。

### Ring Buffer + STOP trigger 基线（UI 偶发卡顿 preset）

关键结构（完整配置含 unique_session_name、数据源明细，此处保留骨架）：

```protobuf
unique_session_name: "ui_jank_flight_recorder"
buffers {
  size_kb: 65536
  fill_policy: RING_BUFFER      # 0: 高频 ftrace/atrace
}
buffers {
  size_kb: 8192
  fill_policy: RING_BUFFER      # 1: FrameTimeline、process stats、App Track Event
}
trigger_config {
  trigger_mode: STOP_TRACING
  trigger_timeout_ms: 3600000
  triggers {
    name: "app_ui_jank"
    producer_name_regex: "com\\.example\\.app"   # 只允许声明的 producer 激活
    stop_delay_ms: 1000
    max_per_24_h: 10
  }
}
incremental_state_config {
  clear_period_ms: 10000
}
```

双 buffer 的原因：图形问题里如果 sched 事件保住了、但 FrameTimeline、App marker、进程描述被覆盖，仍然无法判断是 App、SurfaceFlinger、BufferQueue 还是调度导致卡顿——语义数据要放小 buffer 保护。`trigger_config` **不会自己根据 FrameTimeline 自动触发**，必须有 App 侧 marker 与 trigger emitter（JankStats/FrameMetrics/自研阈值检测）接入；没有 emitter，session 只会等到 trigger_timeout_ms 被清理，不能当「末尾窗口兜底」。

ftrace 的 buffer_size_kb、buffer_size_lower_bound、drain_period_ms 会增加内核 per-CPU buffer 占用与 drain 唤醒频率，只留在短窗口 preset 并上线前验证开销。Ring Buffer 能保留多久不由 trigger_timeout_ms 决定，由写入速率与 buffer 大小决定：**保留窗口（秒）≈ buffer MB ÷ 写入速率（MB/s）**——ftrace 2MB/s 时 64MB 只剩约 32 秒。且要对三层 buffer 都有数：kernel per-CPU ftrace buffer、producer 共享内存、central buffer，central buffer 加大救不了 kernel buffer 来不及 drain 的早期丢事件。

抓完先验收 FrameTimeline 是否真的存在（查 expected/actual_frame_timeline_slice 行数），再确认目标窗口内 App 与 SurfaceFlinger 都有帧记录。怀疑 hardirq/softirq/kworker 抢 CPU 时，不要把这些事件放进默认长 Trace——先做短窗口专项 preset，按结果决定是否进现场方案。

### 长录制：周期写文件

```protobuf
duration_ms: 3600000
prefer_suspend_clock_for_duration: true   # 亮灭屏/车机休眠场景按 wall-clock 计时长
write_into_file: true
file_write_period_ms: 10000
max_file_size_bytes: 2147483648
flush_period_ms: 30000                    # 10~30s 起试，减少低频数据源乱序
buffers {
  size_kb: 32768
  fill_policy: RING_BUFFER
}
```

注意 duration_ms 默认不计算系统 suspend 时间。Android scheduler tracing 典型写入 1~2MB/s，可录制秒数 ≈ max_file_size_bytes ÷ 实测速率——2GB 上限只有约 17~34 分钟，撑不到 1 小时；log、syscall、page fault、camera/audio、过宽的 Track Event 会把速率放大一个数量级。要抓更久就缩数据源、提上限或改 summary/snapshot 策略。

### 后台运行与安全停止

现场常断 USB。普通长 Trace 优先 `--background-wait`（等数据源启动后返回 PID，比 --background 少丢开头）：

```bash
adb push field.pbtxt /data/misc/perfetto-configs/field.pbtxt
PID=$(adb shell perfetto --background-wait --txt \
  -c /data/misc/perfetto-configs/field.pbtxt \
  -o /data/misc/perfetto-traces/field.perfetto-trace | tr -d '\r')
```

Android 10/11 非 root user build 不要假设能读 /data/misc/perfetto-configs，改走 stdin（`cat config | perfetto -c -`）。停止时不要 kill 后立刻 pull——Perfetto 还要把尾部写完，等进程退出且文件大小连续稳定再拉：

```bash
adb shell "kill -INT $PID"
adb shell "while kill -0 $PID 2>/dev/null; do sleep 1; done"
# 再轮询 stat -c %s 确认文件大小连续 3 次不变后 adb pull
```

### trigger 的权限模型与收尾语义

Perfetto trigger 的价值是权限隔离：有权限的一方提前声明 trigger 名称与行为，App 或系统组件只能报告「事件发生了」，不能决定抓什么、抓多大、传哪里。emitter 协议建议固定成一条 JSON 事件（event_id、trigger_name、trigger_source、page/action、reason、threshold 与 observed value、时间窗、dedupe_key），并同时写入同 event_id 的 Track Event，服务端靠 event_id 与时间窗把外部记录、trace 内事件、FrameTimeline 慢帧对上；对不上时这份 Trace 只能当系统侧上下文。测试环境可用 `adb shell /system/bin/trigger_perfetto app_ui_jank` 或 `echo 'activate_triggers: "app_ui_jank"' | adb shell perfetto --txt -c -` 验证。

STOP trigger 适合「根因在触发之前」（慢帧、ANR 前兆）；START trigger 适合「事件发生后继续观察」（如温度进入 hot 后再抓 10 秒），用 START 时不要再配普通 duration_ms。两个收尾语义要写进工具链：**trigger 未命中时 session 停止且不返回数据，输出文件是空的，这是设计行为**——脚本要记录 trigger_matched=false 并清理空文件，别把空 trace 当「没有发生问题」的证据；**trigger 命中后 stop_delay_ms 就结束 session**，要维持长期 flight recorder 覆盖，平台侧需守护逻辑重启下一轮并生成新 case id，避免覆盖上一次现场。

### snapshot 与 detached

snapshot（--clone-by-name，Perfetto v49.0 入口、平台需 Android 14+）：配置里给 session 起名 unique_session_name，之后 `perfetto --clone-by-name thermal_snapshot -o ...` 随时克隆当前 Ring Buffer，原 session 继续跑。适合反复观察趋势的调参实验，不适合一次性封存事故现场。

detached mode（--detach）让 session 脱离命令生命周期由 traced 持有，官方不推荐常规使用——容易泄漏 session 让设备长时间处于 tracing 状态。必须用时打开 write_into_file，并配合 --is_detached 检查、--attach --stop 停止，脚本里做启动前查旧 session、结束停 session、超 TTL 自动停的兜底。

### Bugreport 兜底

用户/测试/运维常先触发 bugreport。要与 bugreport 合包的 Trace 显式声明：

```protobuf
unique_session_name: "field_ui_jank_bugreport"
bugreport_score: 100
bugreport_filename: "field-ui-jank.pftrace"   # Android V / v42+ 的可读文件名
```

bugreport_score > 0 才会成为候选，分数越高越优先保存。版本行为不同：Android S/T 上保存会取走 trace 内容并提前停止 session；Android U+ 上创建只读 snapshot，原 session 继续。报告里写清版本与验证命令（--save-for-bugreport / --save-all-for-bugreport）。

## Boot Trace：特殊现场窗口

Boot Trace 处理设备级开机问题（开机到桌面慢、OTA（Over-The-Air，空中升级）后首启慢、Launcher 首帧晚、某服务开机阻塞），**App 冷启动不走这条路线**。边界先讲清：Android boot tracing 是 Android 13+ 能力；它在 persistent properties 加载后（/data 挂载后）才启动，**不覆盖 PMIC 上电、bootloader、kernel early boot、first-stage init**（更早阶段靠 pstore、kernel cmdline 或厂商 init 埋点）；Trace 的 0 点是 tracing 开始而非电源键按下；「开机完成」没有唯一标准（Launcher 首帧、可输入、网络可用可能是不同团队的指标）；persist.debug.perfetto.boottrace 是 one-shot，每次 boot 前要重设。

第一版配置别贪心：抓 init、sched、freq、idle、进程生命周期、process stats 与 am/wm/gfx 的 ATrace，log 只在 userdebug 按白名单开。buffer 策略与 ready 点匹配：DISCARD 容易保住早期 init/zygote 但满了丢后续；RING 保住最近窗口但可能覆盖早期事实——90 秒启动窗口不要用 32MB DISCARD 硬扛，优先加大 buffer、缩窄数据源或开周期写文件并验收 traced_buf_chunks_discarded。抓取流程：

```bash
adb root
adb push boottrace.pbtxt /data/misc/perfetto-configs/boottrace.pbtxt
adb shell setprop persist.debug.perfetto.boottrace 1
adb reboot && adb wait-for-device && adb root
# 等待 duration 结束 + 文件大小连续稳定后再 pull（不要只等文件非空）
```

验收清单：覆盖 /data 挂载后到目标 ready 点；stats 无 data loss/setup error；init、system_server、surfaceflinger、launcher 可见；记录按键方式、boot id、ready 标准、设备 build。分析顺序固定：init/service 启动 → zygote → system_server → PackageManager/ATMS（ActivityTaskManagerService，活动任务管理服务）→ SurfaceFlinger → Launcher → 首帧/可输入 ready 点。报告写清 ready 标准，否则「开机慢 3 秒」会变成跨团队争论。

## 现场证据包与收尾

只拿 .perfetto-trace 不够，证据包要能回答「什么场景、何时触发、文件是否完整」：

```text
case-20260504-153012/
  trace.perfetto-trace
  config.pbtxt          # 当次实际配置
  metadata.json         # case_id、preset、trigger 与来源、触发时刻、trace 起止、
                        # boot_id、build、app_version、battery、thermal、upload_reason
  stats.sql.txt         # 质量体检结果
  log_excerpt.txt       # 白名单 tag 短窗口摘要
  summary.json          # 机器可读状态，驱动 triage/上传/留存
```

summary.json 不写结论作文，写机器可读状态：trigger_matched、file_complete、stats_status、affected_sources、usable_metrics、evidence_grade、upload_mode、next_action。evidence_grade 分级：A = 窗口、关键数据源、stats、metadata 都完整；B = 轻微 data loss 但核心判断可用；C = 只保留方向性判断；D = 只能当环境记录。长 Trace 还要写清时钟域：ftrace 用 CLOCK_BOOTTIME、log 带 wall time，外部 metadata 同时记录 elapsed realtime、wall time 与 boot id；更稳的做法是把 trigger 本身也写成 trace 内 Track Event；看到 clock sync failure 时跨数据源同步降级处理。

**裁剪优先发生在采集侧**：用 Ring Buffer 控制「只保留最近窗口」、stop_delay_ms 控触发后窗口、max_file_size_bytes 控上限，上传完整问题窗口的原始 Trace，服务端生成 summary 作为轻量索引。不要事后硬切二进制文件（增量状态、track descriptor、stats 会被破坏），必须离线裁剪时按 TracePacket 重写并保留 descriptor 与 stats，绝不用 dd 或文本截断。上传策略默认收窄：Wi-Fi/充电/用户授权才传；超阈值先传 summary；log 白名单 + 脱敏；trace 设 TTL（如 3 天）；不允许服务端向用户设备下发任意 text proto 配置，只允许选审核过的 preset。

分析前固定检查两道门：时长是否符合预期（`SELECT trace_start()/1e9, trace_dur()/1e9`；不符先查 trigger_timeout_ms、max_file_size、进程被杀、文件未 close、suspend 语义），stats 全局体检 + per-buffer 检查（traced_buf_* 按 idx 判断是高频 buffer、语义 buffer 还是写文件路径的问题；RING_BUFFER 下的 chunks_overwritten 不一定是错误——它通常只表示窗口外旧数据被覆盖，要单独确认是否把 trigger 前的根因覆盖掉）。现场若开了 ftrace，还要记录 trace_clock 与 available_events，跨 trace 比较时 clock 或事件集不同会直接影响结论可信度。

## 硬件 counter：GPU、devfreq 与功耗

FrameTimeline 标出一帧晚了，主线程、RenderThread、SurfaceFlinger 看着都没越界时，很容易顺手写一句「可能是 GPU 瓶颈」——这句话风险很高。GPU 频率、GPU counter、电池电流、电源轨都不是 App 单帧归因工具，只能判断问题是否已进入 GPU、内存互联、功耗或温控层。先分清五个术语：**frequency** 是调频策略给的档位，不等于利用率；**counter** 是硬件/驱动采样值（百分比、字节数、事件次数或厂商自定义单位）；**render stage** 是 GPU 工作时间片（依赖 producer 与驱动支持）；**battery current** 是整机电池口径；**power rail** 是子系统能量口径（GPU/Display/Memory/WLAN rail），也不是进程口径。

| 数据 | 采集入口 | 能回答 | 边界 |
|---|---|---|---|
| GPU render stages | gpu.renderstages（或厂商后缀名） | GPU 工作是否跨过目标窗口 | 依赖 GPU producer 与驱动 |
| GPU frequency | ftrace power/gpu_frequency 或 sys_stats 轮询 | 调频、上限、温控后状态 | 频率不是利用率，单位依设备 |
| GPU memory | ftrace gpu_mem/gpu_mem_total | 进程 GPU 内存趋势 | 不是带宽，不是单帧忙 |
| GPU counters | gpu.counters / gpu.counters.adreno 等 | fragment、vertex、texture 等硬件事件 | counter ID/名称依设备 |
| Battery counters | android.power | 电池电流、电压、电量 | 整机口径，受 USB/充电影响 |
| Power rails | android.power + collect_power_rails | 各 rail 能量变化 | 依赖 ODPM 硬件与 IPowerStats HAL |

### 设备能力是第一关

GPU counter 不是 Android 通用能力：producer 可能注册带硬件后缀的数据源名（gpu.counters.adreno、gpu.renderstages.mali），TraceConfig 必须写 descriptor 实际暴露的精确名称；counter 用 counter_ids 或 counter_names 二选一（后者仅部分 producer 支持）。power rails 依赖 ODPM（on-device power rail monitor）这类专用硬件，很多量产设备没有。抓取前先确认能力：

```bash
adb shell perfetto --query --long   # 查 data source 名、counter id、unit、supports_counter_names
```

报告保留能力清单（has_gpu_renderstages、has_power_rails、missing_reason 等字段），避免把「设备不支持」「配置名不匹配」「buffer 丢了」「信号没升高」混为一谈。preset 分层：baseline_jank（FrameTimeline + marker + sched + freq，第一轮现场）→ gpu_suspect_short（追加 render stages、GPU memory、devfreq、power 短轮询，仅 10~30 秒复现窗口）→ gpu_counter_lab（实验室专项，写明 counter id/name/unit 与 descriptor）。

### 短 Trace 的最小信号集

在 UI jank 基线之上追加硬件信号（普通 App 不能自行开启这些数据源，只能经 Track Event/ATrace 暴露业务阶段）：

```protobuf
data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "sched/sched_switch"
      ftrace_events: "sched/sched_waking"
      ftrace_events: "power/cpu_frequency"
      ftrace_events: "power/cpu_idle"
      ftrace_events: "power/gpu_frequency"
      ftrace_events: "power/gpu_work_period"
      ftrace_events: "gpu_mem/gpu_mem_total"
      ftrace_events: "devfreq/devfreq_frequency"
      atrace_categories: "gfx"
      atrace_categories: "hal"
      atrace_apps: "com.example.app"
    }
  }
}
data_sources {
  config {
    name: "linux.sys_stats"
    sys_stats_config {
      stat_period_ms: 1000
      stat_counters: STAT_CPU_TIMES    # 必须显式：留空时新版本采全量 /proc/stat，旧版本可能什么都不采
      cpufreq_period_ms: 500
      gpufreq_period_ms: 500
      devfreq_period_ms: 500
      thermal_period_ms: 1000
    }
  }
}
data_sources {
  config {
    name: "android.power"
    android_power_config {
      battery_poll_ms: 250
      battery_counters: BATTERY_COUNTER_CAPACITY_PERCENT
      battery_counters: BATTERY_COUNTER_CHARGE
      battery_counters: BATTERY_COUNTER_CURRENT
      battery_counters: BATTERY_COUNTER_VOLTAGE
      collect_power_rails: true
    }
  }
}
```

两条路径的区别：power/gpu_frequency 与 devfreq_frequency 是事件路径（精确变化点，窗口开头要向前找前一条状态）；gpufreq_period_ms 等是轮询路径（持续趋势，可能漏短暂尖峰）。thermal zone 名称与可用性依设备而定，没采到只能写「本 trace 无 thermal 证据」，不能写「没有温控影响」。GPU counters 按 descriptor 的 counter ID 选择（counter_period_ns: 1000000 即 1ms 采样，开销与数据量都高，只在实验室短窗口开）。AGI 与 Perfetto 分工：AGI 回答图形内部问题（render pass、draw call、shader、专项 counter 解释），Perfetto 回答系统时间关系（帧前后线程/SF/Binder 是否异常、GPU stage 是否晚于目标窗口、频率与功耗是否同窗变化）——重图形场景常需要两份证据。

### 分析流程与关键查询

固定顺序：FrameTimeline 找问题帧 → 主线程/RenderThread/SF 是否已越界 → GPU render stages / completion 是否跨过目标窗口 → GPU frequency 变化（抬频、降频、温控压上限）→ GPU counters 或 AGI 判方向 → power rails / battery 判约束 → 回系统 Trace 看 Binder、CPU 竞争、后台动画、刷新率变化。所有专项查询绑定同一问题窗口（来源写进报告：frametimeline / track_event / trigger / 人工标注；窗口缺失时只能做全局趋势扫查）。

先跑领域专属 stats 补查（通用体检之外）：gpu_counters_invalid_spec、gpu_render_stage_parser_errors、power_rail_empty_packet 等——缺轨道先分清「设备没暴露」「配置没匹配」「被 buffer 丢掉」三种情况，再谈降级。然后盘点这份 Trace 里实际有哪些 counter（counter_track 全列、gpu_counter_track 单列、android_power_rails_metadata 列 rail 元数据；元数据表为空时写「本 trace 无可用 power rail 元数据」，不要写「GPU rail 没升高」）。

render stages 的第一步永远是确认轨道存在：`SELECT id, name FROM gpu_track WHERE scope = 'gpu_render_stage'`——0 行就到此为止，报告写 gpu_stage_status=unavailable，不要拿频率或 rail 补位。轨道存在时把窗口内 stage slice 按重叠时长排序，看哪个 queue 上哪类 stage 压满窗口；stage 名与 args key 由 GPU producer 决定（Adreno 与 Mali 输出不同），跨设备脚本不要硬编码。GPU 频率高只说明策略抬了频率，不等于满载；GPU memory 高只是纹理/buffer 方向提示。power rails 是累计能量计数，标准库换算出 average_power（mW）与 energy_delta（uWs）；按问题窗口聚合而不是全 trace 峰值排序，报告同时给 valid_samples 与覆盖时长，覆盖不足不要用 rail 排名做结论。battery current 是整机口径（负数放电、正数充电），**实验室大坑：插着 USB 会看到正电流与电量上升**——功耗对比要么控制 USB 供电，要么把 current 只当趋势参考。

### 报告规范与结论分级

GPU/Power 结论必须带最小 schema 方便复查（trace/device/GPU 型号、window_source 与起止、app_frame_count/jank_count、各信号 status、stats_quality_level、evidence_grade、next_tool）。信号到 App 动作的映射：fragment/shader 压力 → 降 overdraw、shader 复杂度、特效占比；texture/bandwidth → 降纹理尺寸格式与上传频率；GPU memory 高 → 查 Surface/texture/buffer 生命周期；SF 合成压力 → 查 layer 数量、透明层、HWC/GPU composition；功耗温升趋势 → 降帧率、动画占空比、后台渲染。结论分三级：**强结论**（同窗内 frame、线程/SF、GPU stage、counter 多源一致）可写；**相关方向**（频率、rail、thermal 与窗口同步但缺 GPU stage/counter）只能写方向；**缺证据**（descriptor/stats/关键轨道缺失）禁止把缺轨道写成没有问题。功耗分析是 A/B 实验不是单次定罪：控制亮度、刷新率、网络、温度、USB 供电后比较同一设备两个版本。三个典型场景的边界：GPU 压力与帧晚同窗出现（需 token/layer/process 校验归属，render stage 不能替代 present fence）；提频后仍慢（查 GPU 内部、内存互联、SF 合成变复杂、温控压频，需 AGI）；功耗异常（先看屏幕/刷新率/持续动画，短时电流峰值不下结论，多次复现才稳）。
