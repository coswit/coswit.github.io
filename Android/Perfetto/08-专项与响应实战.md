## 导读：专项场景的通用打法

Camera open 慢、Audio underrun、WebView 首屏卡住、游戏掉帧——这类问题的证据散落在 App、system_server、cameraserver/audioserver、HAL、SurfaceFlinger 和调度轨道里，只在 UI 里多看几条轨道很容易漏掉关键时间点。这篇分两半：前半用 Camera/Audio 举例讲**领域专项分析的可复用方法**（对象字典 → 阶段/周期 SQL → 能回 UI 复查的报告 → 平台建设），后半把**交互首帧响应**单独拎出来拆解（从输入事件到第一帧反馈）。方法本身是通用的，可迁移到 WebView、Flutter、游戏与厂商自定义服务，差别只在对象字典和指标模板。

## 对象字典：领域分析的第一步

Camera 和 Audio 的难点不在「有没有这个 atrace category」，而在 Trace 里到底有哪些对象：

| 领域 | 对象 | 为什么要识别 |
|---|---|---|
| Camera | App client、cameraserver、provider、HAL、request/session id | open、configure、preview、capture 分散在不同进程 |
| Audio | App audio thread、audioserver、MixerThread、FastMixer、audio HAL、蓝牙路由 | underrun 往往来自周期抖动、写入不稳、HAL 阻塞或调度延迟 |

自动化分析的第一步是生成**对象字典**：相关进程、线程、track、slice 名称、log tag、request/session id。做法是先用关键词（camera/audio/media、cameraserver/audioserver/surfaceflinger）把候选对象列成一张表，再由领域负责人人工确认归属——注意用普通 `CREATE TABLE` 而不是 `CREATE PERFETTO TABLE`（后者只读，无法写回确认结果），字段至少覆盖 role、进程/线程、track_id、厂商别名、置信度 confidence 与 owner_confirmed。**后续 SQL 只使用 owner_confirmed = 1 的对象**：vendor HAL、provider、codec、蓝牙路由一漂移，靠 LIKE 的自动化就会退回模糊匹配。固定 role 枚举如 camera_app_client、camera_service、camera_provider、camera_hal、display_service、audio_app、audio_server、audio_mixer、audio_hal、bluetooth_audio。

领域 schema 是 App、平台、SQL 与报告之间的协作接口，要版本化而不是散在口头约定里。schema 至少定义：object_roles（角色枚举）、stable_events（稳定事件名 + owner + required_args，如 Camera#OpenStart/Camera#ConfigureStreamsEnd/Camera#FirstPreviewFrame）、stage_definitions（阶段 = 起止事件对，如 open_api = OpenStart→OpenEnd）、report_fields。注意**两层命名**：CameraService#Open、CameraHAL#FirstResult 是各服务里的埋点实现名，Camera#OpenStart 是分析和报告使用的接口名，两层靠 schema 的 owner 字段与映射表对上；埋点实现改名时只更新映射，不动分析层。

## 领域 preset 与采集边界

| 能力 | 谁能做 |
|---|---|
| App marker / metadata | 普通 App（android.os.Trace、NDK ATrace、Track Event） |
| 已登记 trigger | 普通 App 或测试 harness（只能激活平台预先声明的名称） |
| App profiling | shell + profileable（release 性能对比优先）或 debuggable（仅调试） |
| ftrace / process stats / FrameTimeline / system log | shell、Traceur、平台/OEM 受信 consumer |
| 上传、限频、隐私、preset 选择 | 平台/OEM 诊断流程 |

实验室领域 preset（lab_domain_debug）在基线上加开 camera/audio/hal/binder_driver 等 atrace category、FrameTimeline、process_stats 与 android.log（filter_tags 白名单 CameraService/CameraProvider/AudioFlinger 等）。三个易错点：**atrace_categories 打开的是系统 category，不会自动带上 App 侧 android.os.Trace**——App ATrace 共享 ATRACE_TAG_APP，要按包名配 atrace_apps；**android.log 只在 userdebug 构建可靠**，user build 要用外部 logcat/bugreport 替代；central buffer 的 size_kb 不等于 ftrace per-CPU kernel ring buffer，sched 丢失看 stats 的 ftrace overrun/dropped。category 列表以目标设备 Record 页或 `perfetto --query` 输出为准，不要复制别人机器上的列表。

质量门禁在通用的 stats 非零项体检（error、data_loss、loss/drop/parse 类计数）之上，领域再补 graphics_frame_event_parser_errors、systrace_parse_failure 等解析项，按 affected_signal 分组降级；RING_BUFFER 下的 overwritten 要单独解释——可能只是窗口外旧数据被覆盖，也可能说明问题前证据不够长。

## Camera：拆阶段，别写「camera 慢」

| 阶段 | owner | 关注点 |
|---|---|---|
| App 发起 open | App marker | 用户操作、权限、UI 线程是否等待 |
| App 到 cameraserver | App + service | Binder 往返、服务端线程池拥塞 |
| cameraserver 到 provider/HAL | platform event | provider 进程、HAL 线程、设备等待 |
| configure streams | platform/HAL | stream 数量、分辨率、HAL configure 耗时 |
| first HAL buffer | HAL/provider | request 提交、buffer 从 HAL 返回 |
| first presented frame | FrameTimeline/SF + App marker | buffer 经 SurfaceFlinger 后被用户看到 |
| capture/result | platform/HAL | request id、result callback |

三个口径必须分清：**API 调用返回、第一帧从 HAL 返回、第一帧被用户看到**——前两个偏 framework/HAL，第三个还要经过 BufferQueue、SurfaceFlinger 与 FrameTimeline。报告写清量的是哪一个，否则「open 变快了」可能只是 API 更早返回，预览首帧并没有提前。专项 SQL 绑定问题窗口（来自 trigger metadata、业务 marker 或人工选区）；缺稳定事件时，阶段状态输出 stage_unavailable、耗时留空，**不要把 LIKE 候选查询升级成阶段结论**——退路是补 android.os.Trace/Track Event 或让平台在 CameraService、provider、HAL 关键阶段补稳定事件名。

## Audio：看周期，别只看 Top slice

Audio 问题比 Camera 更强调周期性：一次长 slice 不一定导致听感问题，连续几个 mixer 周期抖动、App 写入间隔不稳、HAL 写入阻塞才接近 underrun。对 audioserver 的 Mixer/FastMixer 线程，输出 start-to-start 周期与 off-CPU gap：

```sql
WITH target_window AS (SELECT 120e9 AS start_ts, 126e9 AS end_ts),
mixer_runs AS (
  SELECT ss.ts, ss.dur, th.name AS thread_name,
         LEAD(ss.ts) OVER (PARTITION BY ss.utid ORDER BY ss.ts) AS next_ts
  FROM sched ss
  JOIN thread th USING (utid)
  JOIN process p USING (upid)
  CROSS JOIN target_window
  WHERE p.name = 'audioserver'
    AND (LOWER(th.name) LIKE '%mixer%' OR LOWER(th.name) LIKE '%fastmixer%')
)
SELECT ts / 1e9 AS ts_s, thread_name,
       dur / 1e6 AS running_ms,
       (next_ts - ts) / 1e6 AS start_to_start_period_ms,
       (next_ts - (ts + dur)) / 1e6 AS off_cpu_gap_ms
FROM mixer_runs
WHERE next_ts IS NOT NULL
ORDER BY start_to_start_period_ms DESC
LIMIT 100;
```

周期异常只说明节奏变了，原因（被锁、Binder、HAL 写入打断还是正常 idle）还要关联 thread_state、HAL slice、underrun log 与 route metadata。**不要给 period_ms 写跨设备固定阈值**——它与 sample rate、buffer size、fast path、蓝牙路由、offload 都有关；正确做法是同设备同 route 下拿一段干净播放做基线，比较异常现场的周期尾部是否变长、是否连续变长、是否与 underrun log 或听感时间点重合。

Running 与 Runnable 分开算的原则在专项里同样适用，区别只是统计对象来自 domain_objects 字典中 owner_confirmed = 1 的线程而不是靠线程名猜：Runnable 高先看 CPU 竞争、优先级、频率与唤醒源；Running 高再上 CPU profiling。log 负责补阶段语义（request id、route change、underrun、错误码），限定在问题窗口内查 android_logs，且不当唯一证据——耗时与阻塞仍回到 slice、sched、thread_state、Binder。

## 报告要能回 UI

自动化报告固定四块：数据质量（时长、stats 异常、关键数据源在场）、对象字典、阶段指标（Camera open/config/HAL buffer/presented frame；Audio 周期）、复查点（ts、dur、进程、线程、slice/log 名称）。报告里每个异常都要能跳回 Perfetto UI——只有结论没有时间点，别人没法复查。结论分级四档：**确认**（X 在窗口 A 内阻塞了 Y；要求 required_signals_available=true、data_quality=clean、ui_review_points≥1）；**倾向**（更像 X 方向；missing_evidence 列出缺什么）；**排除**（signal_present 且指标不支持，不能来自数据缺失）；**降级**（degrade_reason 写明 data loss、数据源缺失或样本不足）。工程讨论里很多争议不来自 Trace 本身，而是只有「倾向」的证据被写成了「确认」。

## 从专项到问题清单与平台建设

把常见现象翻译成采集 preset、分析路径与输出证据，团队的问题清单大致是：

| 问题 | 基础数据源 | 专项加开 | 默认输出 |
|---|---|---|---|
| UI 卡顿 | sched/freq/idle/gfx/view/wm/input/process_stats/FrameTimeline | binder_driver、App ATrace/Track Event | 问题帧、App/HWUI/SF 阶段、线程状态 |
| 点击响应慢 | input、sched、view、wm、binder_driver、FrameTimeline | 视觉状态 counter、高速相机对照 | input 到首个可见变化 |
| App 启动 | sched/freq/am/wm/view/binder_driver/FrameTimeline | log、CPU profiling | 启动阶段、首帧、Top wait |
| ANR | sched/freq/binder_driver/am/wm/log | lock、IO、CPU profiling | 主线程等待证据 |
| Binder 慢 | sched、binder_driver、binder_lock、process_stats | system_server log | 慢事务 TopN、server 状态 |
| Native 内存 | process_stats | heapprofd、业务 trigger | 分配栈和增长趋势 |
| Camera / Audio | sched/freq + 领域 category + hal + binder + FrameTimeline/log | CPU profiling、平台事件 | 阶段耗时 / underrun 前后周期抖动 |
| 功耗温控 | sched/freq/idle/android.power/thermal/log | GPU counters、devfreq、power rails | 资源趋势和异常窗口 |

每个 preset 要有负责人、版本、用途、默认窗口、采集方、构建边界、数据源、开销等级（实测写入速率，不用一个 cost_level 代替真实预算）、隐私等级与质量门禁——没有这些字段，preset 很快变成一堆没人敢删的配置。平台体系分三层：**field**（user build 线上/灰度，平台诊断组件或 Traceur 持有 session，App 只发 marker/trigger，低开销 Ring Buffer + 短窗口 stop trigger）；**lab**（实验室复现与版本对比，可控可重复）；**deep**（userdebug/root 专项，heapprofd、linux.perf、GPU counters 这类高开销能力）。**deep preset 不要放到线上**；field 层禁止 linux.perf、heapprofd、GPU counters、高频 syscall/pagefault 事件。trigger 名字收敛登记（App 代理、Framework watchdog、AudioFlinger、CameraService、Thermal 都只能发已登记名称），进入平台后不改名，否则服务端索引与历史趋势断开；bugreport_score > 0 把运行中的 session 标记为 bugreport 候选（S/T 保存并停原 session，U+ 只读快照）。服务端处理用显式状态机约束证据来源：ingested → quality_checked → scenario_classified → assignee_selected → evidence_graded → issue_linked → fix_build_recorded → same_preset_rerun → before_after_compared → regression_rule_updated，字段改名或数据源失效在 quality_checked 阶段直接降级。

## 交互首帧响应：只看操作后的第一帧

点一个按钮多久出现按压态、点会话多久看到第一帧在动、滑动多久内容跟手——这类问题与启动和流畅度相关，但口径要单独拎出来。主指标 **input_to_present_ms**：从 InputReader 读到事件（read_time）到关联帧 present，对应 android_input_events 表的 end_to_end_latency_dur。它不覆盖触控 IC、驱动上报前延迟、显示扫描与面板响应；只有关联帧存在且 is_speculative_frame = false 时才是强证据，否则降级为 estimated 或不输出。响应慢拆成四个指标：

| 指标 | 起点 → 终点 | 回答什么 |
|---|---|---|
| Dispatch latency | InputDispatcher 发出 → App 收到 | 系统分发与 InputChannel 是否慢 |
| Handling latency | App 收到 → App 发出 ACK | App input 处理是否慢 |
| input_to_present_ms | input read → 关联帧 present | 用户多久看到第一帧反馈 |
| Completion latency | 业务触发点 → 页面/动画稳定 | 整个操作多久完成 |

三个「输入时间」别混用：event_time（事件发生时间）、read_time（InputReader 读到，end-to-end 的起点）、dispatch_ts/receive_ts（派发与接收，用来拆系统与应用段）。报告写清起点口径——用 read_time 起算就写 input read，用业务 click handler 起算就写 App marker，起点不同数字不能比。分析前把场景对象字典固定：包名、InputChannel、目标窗口与 layer（TX - 包名/Activity#0 形态）、业务 marker、预期终点；多显示器与折叠屏按 display_id 区分事件归属，折叠姿态（posture）作为独立维度，跨形态不合基线。

### 采集配置与降级

| preset | 环境 | 数据源 | 输出 |
|---|---|---|---|
| lab_input_debug | debuggable system、实验室短窗口 | android.input.inputevent、FrameTimeline、sched、App marker | input round trip + input_to_present_ms |
| field_input_response | user build、平台受控 | App marker、可得信号、trigger metadata | app_marker_to_present_ms，不输出 input_to_present_ms |

核心数据源 android.input.inputevent 面向 debuggable system build：

```protobuf
data_sources {
  config {
    name: "android.input.inputevent"
    android_input_event_config {
      mode: TRACE_MODE_TRACE_ALL          # 记录系统处理的输入事件，仅限本地/测试
      trace_dispatcher_input_events: true
      trace_dispatcher_window_dispatch: true
    }
  }
}
```

user build 不要依赖它（规则模式也变不成线上采集能力）；input 事件可能同时发给前台窗口、SystemUI、IME（Input Method Editor，输入法）与 spy window，采集范围要过隐私评审。缺失信号时的 fallback 提前固定：缺 inputevent → 只能输出 App marker 到 present，不能输出 read/dispatch/handling 与 input_to_present_ms；缺 FrameTimeline → 只有 input round trip；SurfaceView/游戏/视频场景 → FrameTimeline 本就不支持 SurfaceView，要靠 layer、marker、外部视频。另外 FrameTimeline 需要 Android 12+。

### UI 排查顺序与点击场景

拿到 Trace 按顺序看七条轨道：InputReader/InputDispatcher（事件是否读到、派发给谁）→ App 主线程（事件到达后是否马上 Running）→ Choreographer#doFrame（状态变化经 Input/Animation/Traversal 哪条路径推进）→ RenderThread（syncFrameState/DrawFrame/dequeueBuffer/queueBuffer 是否卡）→ FrameTimeline（关联帧 expected/actual、token、layer）→ SurfaceFlinger（buffer 是否及时 latch、fence 与合成影响）→ CPU 调度与频率（Runnable 等待、频率不足、迁核）。不要从最长的 slice 开始猜，先把输入事件和第一帧反馈连起来。

点击场景先定义起点终点：按钮按压态用 DOWN/read → 按压态第一帧 present；页面跳转用 click handler/业务 marker → 转场第一帧 present；内容可用用 marker → 首屏内容 marker。以「点会话进聊天页」为例的链路：找 ACTION_UP → 看 dispatch 到 receive 的耗时 → 看主线程是否被及时调度 → 看 click handler 里有无 Binder/IO/锁/同步布局/图片解码 → 看 startActivity Binder、窗口创建、focus 切换、starting window 是否插入等待 → 看下一帧 doFrame → 看 RenderThread 与 FrameTimeline 确认 present → 回对象字典确认这帧就是用户可见的第一帧。

最容易误判的一点：**Perfetto 显示 App 画了一帧 ≠ 用户看到了变化**——App actual timeline 的结束点是提交帧，不等于上屏。确认首帧要回到关联帧、SF actual/display frame、layer_name 与外部证据。App 侧补三个业务 marker（事件名固定，动态 id 不进 section 名）：

```kotlin
fun onConversationClick(conversationId: String) {
    Trace.beginSection("Conversation#Click")
    try {
        openConversation(conversationId)
    } finally {
        Trace.endSection()
    }
}
fun onConversationTransitionStart() {
    Trace.beginSection("Conversation#TransitionStart")
    Trace.endSection()
}
fun onConversationFirstContentDrawn() {
    Trace.beginSection("Conversation#FirstContentDrawn")
    Trace.endSection()
}
```

marker 是业务状态，present 时间来自关联帧，报告里 business_marker_ts、associated_frame_id、present_ts、association_method 分开写。

### 滑动场景：从第一个有效 MOVE 到内容位移

手指刚动时系统收到大量 MOVE，但 App 可能还没越过 touch slop，也可能因事件合并与 Vsync 节奏，只有某一帧真的产生位移。推荐口径：**第一个业务有效 ACTION_MOVE → 内容第一次可见位移的 present**。分析步骤：找 MOVE 序列 → 排除 slop 内的小幅 MOVE → 看 App 是否收到并及时 ACK → 看 doFrame 的 Input 阶段是否更新 scroll offset → 看下一帧提交与 FrameTimeline present → 用 App counter 或外部视频确认位移。Perfetto 自己不知道「内容动了多少」，自研 App 加一个轻量 counter（只在值变化时记录、每帧最多一次）：

```kotlin
recyclerView.addOnScrollListener(object : RecyclerView.OnScrollListener() {
    override fun onScrolled(rv: RecyclerView, dx: Int, dy: Int) {
        val offset = rv.computeVerticalScrollOffset()
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
            Trace.setCounter("Feed#ScrollOffsetY", offset.toLong())
        } else {
            androidx.tracing.Trace.setCounter("Feed#ScrollOffsetY", offset)
        }
    }
})
```

Trace.setCounter 从 API 29 起可用，低 minSdk 用 AndroidX tracing。有了它，「第一帧开始动」从主观描述变成可查时间点：先算 move_to_offset_change_ms，再算 offset_change_to_present_ms。

### 用 SQL 量化输入延迟

Trace 含 android.input.inputevent 时用标准库 android.input 模块（WebView/Chrome 场景另按 Chrome 模块分析，不用 Chrome EventLatency）。先选目标事件——按包名、channel、action 过滤，并用业务 marker 就近匹配，避免 DOWN/MOVE/UP、IME、多窗口混进来；然后看 round trip：

```sql
INCLUDE PERFETTO MODULE android.input;
SELECT
  input_event_id, event_action,
  (dispatch_ts - read_time) / 1e6 AS read_to_dispatch_ms,
  dispatch_latency_dur / 1e6 AS dispatch_ms,
  handling_latency_dur / 1e6 AS handling_ms,
  ack_latency_dur / 1e6 AS ack_ms,
  total_latency_dur / 1e6 AS total_ms,
  end_to_end_latency_dur / 1e6 AS input_to_present_ms,
  frame_id,
  is_speculative_frame
FROM android_input_events
WHERE process_name = 'com.example.app'
  AND normalized_event_channel LIKE '%ChatActivity%';
```

字段语义：dispatch_latency_dur 是 Dispatcher 发出到 App 收到；read_to_dispatch_ms 是 Reader 读到到 Dispatcher 发出（暴露分发前排队与 policy 拦截）；handling_latency_dur 是 App 收到到 finish/ACK 的框架口径——**不是 click handler 专属耗时**，定位业务处理要再用 ViewRootImpl/InputStage slice 或 marker 切分；ack_latency_dur 是 ACK 回程；end_to_end_latency_dur 是 input read 到关联帧 present，无关联帧时为 NULL。NULL 不代表没有视觉反馈——可能反馈发生在 SurfaceView、游戏引擎或另一 layer，回 marker 与外部证据，不要把 NULL 写成「没有绘制」；is_speculative_frame 为 true 时结论降级。排查时先查 round-trip 慢事件（不过滤 end_to_end），调度部分 Running/Runnable 分开算且前置检查 sched 数据完整。

### 五条归因路径

**Read/dispatch 慢**（read_to_dispatch 或 dispatch 高）：InputReader 到 Dispatcher 排队、Dispatcher 忙、system_server Runnable、窗口焦点/InputChannel 异常、policy/interception、IME/overlay、CPU 被 RT（Real-Time，实时）任务/cgroup/thermal 挤压——偏平台侧。**Handling 慢**（handling 高）：主线程收到后长 Running、Input 阶段重计算、click handler 同步 Binder/IO/等锁、同步布局、图片解码、Compose 重组、RecyclerView 大量 bind——App marker 加主线程 slice 可定位。**ACK 快但第一帧慢**（最常见）：ACK 只说明输入处理完，不等于帧已显示；查是否没请求下一帧或请求太晚、是否在等 Binder/Activity transaction/数据回调、Animation/Traversal 排到后一个 Vsync、RenderThread 卡在 syncFrameState/DrawFrame、BufferQueue backpressure、GPU fence、SF/HWC 合成、线程 Runnable。**ANR 与亚 ANR**：交互慢多数是亚 ANR；Input ANR 两类——事件已发但长时间没 ACK（handling/ACK 异常），或 focused event 等不到 focused window（查 WindowManager/ATMS、窗口创建与焦点切换）；ACK 快第一帧慢一般不触发 input ANR。**滑动不跟手**：常表现为第一帧位移晚、后续恢复稳定；查有效 MOVE 到 offset 变化、offset 变化到 present、MOVE 合并、主线程 Runnable 错过 Vsync、后续 FrameTimeline 是否稳定——用户说「不跟手」，说的常常是输入到第一帧的延迟，别只看 jank count。

### 高速相机与 Perfetto 的边界

Perfetto 记录的是系统内部时间；用户眼睛看到的时间还包含触控采样、固件处理、显示扫描、面板响应与拍摄误差。做竞品对比或验收时三者组合：**外部测量给结果**（高速相机/机械手定义可见起点终点），**Perfetto 给原因**（拆内部哪一段慢），**App marker 给业务语义**。没有外部测量时，报告只能写系统内部延迟，不能写用户可见绝对延迟。

报告固定结构：scenario、config 版本、采集模式与 build 类型、data_quality、对象字典、起点终点定义、输入事件（input_event_id、各时间戳、selection_reason）、业务 marker、关联帧（frame_id、association_method、speculative 与否）、breakdown（read_to_dispatch/dispatch/handling/ack/frame_after_ack）、evidence（线程 Runnable、DrawFrame 耗时、FrameTimeline miss 几个 vsync）、review_points（可回 UI 的时间点）、boundary（fallback、缺信号、外部测量方式与误差）、owner_hint。证据等级统一：confirmed / likely / excluded / degraded / unknown——is_speculative_frame=true、缺 FrameTimeline、缺外部视频、data loss 都降级。最小 walkthrough 示例：handling 18ms、dispatch 4ms、read_to_dispatch 3ms、ACK 后第一帧晚 53ms，其中主线程 doFrame 前 Runnable 21ms、FrameTimeline 关联帧 miss 1 个 vsync——这可以写「倾向主线程调度等待导致首帧晚一拍」，但 speculative 或没有外部视频时不能写「确认用户可见延迟 76ms」。
