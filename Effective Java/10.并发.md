### 条目 78：同步访问共享的可变数据

```java
// 反例：后台线程永远退不出去——没有同步，观察不到 stopRequested 的修改
private static boolean stopRequested;

public static void main(String[] args) throws InterruptedException {
    Thread backgroundThread = new Thread(() -> {
        int i = 0;
        while (!stopRequested)
            i++;
    });
    backgroundThread.start();
    TimeUnit.SECONDS.sleep(1);
    stopRequested = true;   // 无同步：JVM 可能做提升优化（hoisting），循环变成 while(true)
}
```

修复：**volatile**（保证可见性与 happens-before 顺序）：

```java
private static volatile boolean stopRequested;
```

volatile 的限制：不保证原子性。`count++` 是"读-改-写"三步，并发会丢更新：

```java
private static volatile int nextSerialNumber = 0;
public static int generateSerialNumber() {
    return nextSerialNumber++;   // 反例：竞态！
}

// 正确：synchronized（同步既保证互斥也保证可见性）
private static int nextSerialNumber = 0;
public static synchronized int generateSerialNumber() {
    return nextSerialNumber++;
}
// 更好：AtomicLong
```

最佳方案：**不共享可变数据**——不可变对象或根本不修改（有效不可变则必须安全发布：static 初始化或 volatile/锁）。

### 条目 79：避免过度同步

条目 78 的反面：过度同步（在同步区域内做外来调用）会导致死锁/数据破坏：

```java
// 观察者模式：在同步区域内调用外来的观察者方法
private void notifyElementAdded(E element) {
    synchronized (observers) {
        for (SetObserver<E> observer : observers)
            observer.added(this, element);   // 外来方法！
    }
}

// 攻击1：观察者的 added 里再 addObserver → 在同一线程重复加锁
//         （可重入不死锁，但破坏一致性）
// 攻击2：观察者的 added 里 removeObserver 自己 → 死锁（线程在等待自己持有的锁）
```

修复：**把外来调用移出同步块**（open call）：

```java
private void notifyElementAdded(E element) {
    List<SetObserver<E>> snapshot = null;
    synchronized (observers) {
        snapshot = new ArrayList<>(observers);   // 拷贝在锁内
    }
    for (SetObserver<E> observer : snapshot)     // 调用在锁外
        observer.added(this, element);
}
```

更好的替代：**CopyOnWriteArrayList**（每次写都拷贝底层数组，读完全无锁，适合观察者列表这类读多写少）。

一般原则：**在同步区域内做尽量少的工作**；获取锁→处理数据→释放。可变类的设计要么完全同步（文档说明）、要么完全不同步（外部同步），前者代表 `BlockingQueue`、后者代表 `ArrayList`。

### 条目 80：executor、task 和 stream 优先于线程

```java
// 直接用线程：任务与执行耦合
Thread t = new Thread(() -> doWork());
t.start();

// Executor：任务提交与执行机制解耦
ExecutorService exec = Executors.newSingleThreadExecutor();
exec.submit(() -> doWork());
exec.shutdown();   // 让已提交任务完成后退出

// 常用工厂：
// newFixedThreadPool(n)     固定大小
// newCachedThreadPool()     弹性（短命小任务）
// newSingleThreadExecutor() 单线程（任务顺序执行）
// newScheduledThreadPool()  定时/周期
```

要点：

- **工作队列 + 拒绝策略**：`ThreadPoolExecutor` 手动配置（队列满时的行为：CallerRunsPolicy 等）；
- 定时任务用 `ScheduledThreadPoolExecutor`（不要 Timer——对时钟敏感、异常会杀死整个定时线程）；
- ForkJoinPool/parallel stream 处理分治并行（条目 48）；
- **守护线程别用于可能要写持久状态的逻辑**（JVM 退出时直接被杀）；
- 线程池大小：小任务多线程别超过 `Runtime.getRuntime().availableProcessors()`。

### 条目 81：并发工具优先于 wait 和 notify

正确使用 wait/notify 极易出错（虚假唤醒、忘检查条件、notifyAll vs notify）。`java.util.concurrent` 提供了更高层的工具：

| 需求 | 工具 |
| --- | --- |
| 计数等待 | `CountDownLatch` |
| 资源限流 | `Semaphore` |
| 阶段同步 | `CyclicBarrier` |
| 高性能并发 Map | `ConcurrentHashMap` |
| 阻塞队列 | `BlockingQueue`（工作队列、生产者消费者） |
| 延迟队列 | `DelayQueue` |

```java
// 并行执行多个任务并等待完成：CountDownLatch
public static long time(Executor executor, int concurrency,
                        Runnable action) throws InterruptedException {
    CountDownLatch ready = new CountDownLatch(concurrency);
    CountDownLatch start = new CountDownLatch(1);
    CountDownLatch done  = new CountDownLatch(concurrency);
    for (int i = 0; i < concurrency; i++) {
        executor.execute(() -> {
            ready.countDown();       // 就绪
            try {
                start.await();       // 等待统一发令
                action.run();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            } finally {
                done.countDown();    // 完成
            }
        });
    }
    ready.await(); start.countDown();
    long startNanos = System.nanoTime();
    done.await();
    return System.nanoTime() - startNanos;
}
```

确实要用 wait/notify 时：**永远在循环内 wait**（检查条件——防虚假唤醒），一般优先 notifyAll：

```java
synchronized (obj) {
    while (<condition does not hold and timeout not exceeded>)
        obj.wait(timeout);
    ... // Perform action appropriate to condition
}
```

### 条目 82：文档化线程安全性，或使用注解

线程安全级别（要写进文档，`@GuardedBy` 标注同步策略）：

| 级别 | 说明 | 例子 |
| --- | --- | --- |
| 不可变 immutable | 无需外部同步 | String、Long |
| 无条件线程安全 | 内部同步，任意并发调用 | ConcurrentHashMap、AtomicLong |
| 有条件线程安全 | 部分方法需要外部同步 | `Collections.synchronizedMap` 的复合操作 |
| 非线程安全 | 调用方必须全部外部同步 | ArrayList、HashMap |
| 线程对立 | 即使外部同步也不能安全并发（应避免） | 未同步修改静态可变状态的类；平台中罕见，发现即视为 bug |

文档要说明：哪些方法需要锁、需要哪把锁（客户端锁定风险高）。`synchronized` 修饰符 本身**不是**线程安全文档。无条件的类要用私有锁对象（`private final Object lock = new Object();`）防止客户端/子类干扰。

### 条目 83：谨慎地使用延迟初始化

延迟初始化是把双刃剑（收益有限，风险不小）。按字段类型选择：

```java
// 1. 普通实例字段：同步的简单访问器（性能可接受）
private FieldType field;
synchronized FieldType getField() { return field; }

// 2. 静态字段：holder class 模式（JVM 类加载保证，最优雅）
private static class FieldHolder {
    static final FieldType field = computeFieldValue();
}
static FieldType getField() { return FieldHolder.field; }

// 3. 实例字段、需要避免同步开销：double-check 模式（必须 volatile！）
private volatile FieldType field;
FieldType getField() {
    FieldType result = field;         // 第一次读（绝大多数在此返回）
    if (result == null) {             // 第一次检查
        synchronized (this) {
            if (field == null)        // 第二次检查
                field = computeFieldValue();
            result = field;
        }
    }
    return result;
}
```

对于**可以接受重复初始化**的静态字段，也可用简单 racy single-check（不带 volatile 但字段要能容忍重复写）。局部技巧：**long/double 之外的基本类型字段**延迟初始化可以不同步（原子写）。

大多数场景：**直接急切初始化**（eager）更简单安全。

### 条目 84：不要依赖线程调度器

线程调度器无保证（任何依赖调度顺序/优先级/时间片的程序都不可移植）。要点：

- **能运行的线程不应长期处于等待**（让线程池/任务结构本身可推进）；
- 线程不应**忙等**（busy-wait）——反复检查共享对象状态；等待条件用 wait/notify 或并发工具；
- **Thread.yield 和线程优先级不可移植**：yield 在 JVM 间行为差异巨大，优先级被部分 JVM 忽略；
- 自测性能时不要用 sleep/循环凑数，要真实负载；
- 如果程序因线程过少而无法推进，**增加线程**或让每个线程做更多**独立**工作，而不是调优先级。

单线程的 executor 在死锁场景救不了（任务互相等待同一线程池）——线程池要留有余量或用有界工作队列+拒绝策略。
