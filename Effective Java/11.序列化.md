### 条目 85：其他替代方案优于 Java 序列化

Java 原生序列化（`ObjectOutputStream`/`ObjectInputStream`）的历史问题：

- **安全漏洞的温床**：反序列化炸弹（Gadget Chain）——构造恶意的对象图导致资源耗尽或任意代码执行（如 `HashSet` 嵌套导致的 billion-laugh 式 DoS；Log4j 之外最著名的反序列化漏洞家族都源于此）；
- 反序列化是"隐式构造器"——输入不可信时无法校验；
- 跨版本脆弱（serialVersionUID 漂移）。

**优先选择跨平台的序列化形式**：JSON（Jackson/Gson，人类可读）或 Protocol Buffers（二进制、高效、schema 演进友好）。

必须用 Java 序列化时：

- **永远不要反序列化不可信的数据**；
- 用**对象输入过滤（ObjectInputFilter，Java 9）**白名单限制反序列化的类：

```java
ObjectInputStream in = new ObjectInputStream(fileIn);
in.setObjectInputFilter(new ObjectInputFilter() {
    // 只允许白名单里的类
    ...
});
```

注意：即使有过滤，也不保证安全（历史 gadget 链里有过滤绕过），最佳策略仍然是别用。

### 条目 86：谨慎地实现 Serializable

实现 Serializable 的代价：

- **降低类的灵活性**：一旦发布，序列化形式就成为 API 的一部分（内部实现被"冻结"）；
- **隐藏的构造器**：反序列化是创建对象的另一个通道，绕过正常构造器的校验（条目 88）；
- **bug 与安全漏洞的概率上升**；
- **测试负担**：发布新版本要测试新老序列化形式的互操作。

经验法则：

- **值类**（如 Date、BigInteger）与**很少使用的类**适合实现；
- 为继承设计的类尽量不要实现（子类被迫承担）；
- 接口尽量不要 extends Serializable；
- 内部类（条目 24）不要实现（隐式外部引用会被一起序列化）；

**必须声明 serialVersionUID**（private static final long），不写则编译器按类结构生成——类一改就全部不兼容：

```java
private static final long serialVersionUID = 234098243823485285L;
```

### 条目 87：考虑使用自定义的序列化形式

默认的序列化形式是对象物理结构的快照，只有当**物理结构与逻辑内容一致**时才合适。String 的逻辑内容就是字符数据——但物理上还有 hash 缓存字段，不应序列化：

```java
// String 的自定义序列化形式：只写实际字符
private void writeObject(ObjectOutputStream s) throws IOException {
    s.defaultWriteObject();          // 写可序列化的元数据
    s.writeInt(length());            // 逻辑内容：长度
    for (int i = 0; i < length(); i++)
        s.writeChar(charAt(i));
}
```

自定义形式的收益：更紧凑、解耦内部实现、避免序列化无关字段（如缓存）。

**对象图 vs 树**：默认形式会序列化整个可达对象图（引用字段递归），共享/循环引用导致：重复数据、栈溢出（深图）。合理做法是只序列化**逻辑状态**（抽象数据），如 `HashSet` 只序列化元素集合而不序列化桶数组（物理实现）：

```java
// writeObject 里用 putFields / writeFields 自定义字段
private void writeObject(ObjectOutputStream s) throws IOException {
    s.defaultWriteObject();
    s.writeInt(size);       // 逻辑内容
    for (Object e : this)   // 迭代元素而不是序列化桶
        s.writeObject(e);
}
```

transient 修饰不需要序列化的字段（缓存、派生数据）。无论哪种形式，都要**自测序列化-反序列化的往返（round-trip）**。

### 条目 88：保护性地编写 readObject

readObject 相当于"字节流构造器"——**必须做正常构造器的一切校验与防御**：

```java
public final class Period {
    private Date start;
    private Date end;

    // 反序列化时同样要做保护性拷贝 + 不变式校验
    private void readObject(ObjectInputStream s)
            throws IOException, ClassNotFoundException {
        s.defaultReadObject();

        // 保护性拷贝（防御伪造的流中共享/后续被修改的 Date）
        start = new Date(start.getTime());
        end   = new Date(end.getTime());

        // 不变式校验（伪造的流可以违反任何约束）
        if (start.compareTo(end) > 0)
            throw new InvalidObjectException(start + " after " + end);
    }
}
```

要点：

- readObject 中**先 defaultReadObject 再校验/拷贝**；
- 对可变字段做防御性拷贝（无法用构造器，只能字段替换）；
- 检查不变式，**抛 InvalidObjectException**（不是 IllegalArgumentException）；
- 默认 readObject 之后如果不变式涉及字段间关系，**可以抛异常阻止反序列化完成**；
- 静态工厂类序列化时要防止反序列化产生额外实例（条目 89）。

### 条目 89：对于实例控制，枚举类型优于 readResolve

```java
// readResolve：反序列化完成后用已有实例替换新创建的实例
private Object readResolve() {
    // Return the one true Elvis and let the garbage collector
    // take care of the Elvis impersonator
    return INSTANCE;
}
```

readResolve 的局限：

- **依赖被忽略**：readResolve 前对象已经生成，若类可被继承或有可变的实例字段，攻击者可以在反序列化的对象与 readResolve 替换之间拿到引用（Elvis 窃取攻击——通过一个"支架类"窃取实例）；
- 需要**所有实例字段为 transient 或类声明 final** 才安全；
- 单例的正确解法仍是**枚举**（条目 3）：JVM 保证每个枚举常量唯一实例，序列化免费且防伪造：

```java
public enum Elvis {
    INSTANCE;
    private String[] favoriteSongs = { "Hound Dog", "Heartbreak Hotel" };
    public void printFavorites() { System.out.println(Arrays.toString(favoriteSongs)); }
}
```

readResolve 的合理用途：无法用枚举的实例控制场景（如序列化代理不可行时的兼容），此时务必配合 writeReplace 与 final 类。

### 条目 90：考虑用序列化代理代替序列化实例

**序列化代理模式（serialization proxy pattern）**：为可序列化类提供一个私有静态嵌套"代理"，承载逻辑状态：

```java
public final class Period {
    private final Date start;
    private final Date end;
    ...
    // 序列化代理：Period 的逻辑表示
    private static class SerializationProxy implements Serializable {
        private final Date start;
        private final Date end;

        SerializationProxy(Period p) {
            this.start = p.start;
            this.end = p.end;
        }

        // 反序列化时通过"正常构造器"重建外围实例——所有校验/防御自动生效
        private Object readResolve() {
            return new Period(start, end);   // 走公有构造器！
        }
    }

    // 写入时换成代理
    private Object writeReplace() {
        return new SerializationProxy(this);
    }

    // 防止伪造的流直接反序列化 Period 本身
    private void readObject(ObjectInputStream stream) throws InvalidObjectException {
        throw new InvalidObjectException("Proxy required");
    }
}
```

优势：

- 把反序列化**收口到正常构造器**——不变式校验、保护性拷贝自动生效，杜绝条目 88 的攻击面；
- 物理表示与序列化形式完全解耦。

局限：

- 不能与**可被客户端继承的类**兼容；
- 不能与**对象图中含循环引用的类**兼容（代理反序列化时外围实例还不存在）；
- 性能开销（EnumSet 的例子：代理模式慢约 14%）。

**总结**：需要 Java 序列化时，序列化代理是安全的第一选择；配合枚举单例（条目 89）与 ObjectOutputStream 的输入过滤（条目 85）使用。
