
### 条目 42：lambda 优先于匿名类

```java
// 匿名类（Java 8 前的函数对象）
Collections.sort(words, new Comparator<String>() {
    public int compare(String s1, String s2) {
        return Integer.compare(s1.length(), s2.length());
    }
});

// lambda：类型推断，按长度排序
Collections.sort(words,
        (s1, s2) -> Integer.compare(s1.length(), s2.length()));

// 更进一步：比较器构造方法（见条目 43）
Collections.sort(words, comparingInt(String::length));
```

lambda 的注意点：

- **没有名称和文档**——超过三行就该考虑提取方法；
- **类型推断依赖上下文**：目标类型必须明确（泛型方法/变量声明），`Object o = () -> {}` 非法；
- lambda 中 `this` 指外围实例（匿名类中指匿名类自身）；
- **lambda 只能用于函数式接口**；需要抽象类实例或多个抽象方法时还得匿名类；
- lambda 不能可靠地序列化（不要序列化 lambda）。

枚举的特定于常量方法体也可以换成构造器中的 lambda（`Operation` 枚举用 `DoubleBinaryOperator`）。

### 条目 43：方法引用优于 lambda

lambda 越短，参数名本身越能表达语义；但任何**已有方法能做的**，方法引用更直接：

```java
map.merge(key, 1, (count, incr) -> count + incr);  // lambda
map.merge(key, 1, Integer::sum);                     // 方法引用
```

五种方法引用：

| 类型 | 示例 | lambda 等价 |
| --- | --- | --- |
| 静态 | `Integer::parseInt` | `str -> Integer.parseInt(str)` |
| 已绑定实例方法（bound） | `Instant.now()::isAfter` | `t -> Instant.now().isAfter(t)` |
| 未绑定实例方法（unbound） | `String::toLowerCase` | `str -> str.toLowerCase()` |
| 类构造器 | `TreeMap<K,V>::new` | `() -> new TreeMap<K,V>()` |
| 数组构造器 | `int[]::new` | `len -> new int[len]` |

选择标准：**方法引用更短更清晰就用它**；当参数名恰好能表达语义而方法名不能时（`service.execute(Gadget::shutdown)` vs `gadget -> gadget.shutdown()`）用 lambda。

### 条目 44：坚持使用标准的函数接口

`java.util.function` 提供了 43 个标准函数接口，六大基本类型（按参数/返回/是否抛异常/返回 boolean）：

| 接口 | 签名 | 示例 |
| --- | --- | --- |
| `UnaryOperator<T>` | T -> T | `String::toLowerCase` |
| `Predicate<T>` | T -> boolean | `String::isEmpty` |
| `Function<T,R>` | T -> R | `Arrays::asList` |
| `Supplier<T>` | () -> T | `Instant::now` |
| `Consumer<T>` | T -> void | `System.out::println` |
| `BinaryOperator<T>` | (T, T) -> T | `Integer::max` |

基本类型有专门变体（`IntPredicate`、`LongFunction<R>` 等）避免装箱。

**何时自定义函数接口**：需要约定（类型名能表达"这是做什么的"，如 `Comparator<T>`）；或要求多重签名方法标识。自定义时务必加 `@FunctionalInterface`（编译器校验单抽象方法）。

### 条目 45：谨慎使用 Stream

Stream 不是所有场景都更简洁。适合流水线式的**序列转换**（过滤/映射/切片/搜索/分组），不适合"中间值依赖前后状态"的读逻辑。

```java
// 词频统计（适合 Stream 的经典场景）
Map<String, Long> freq = words.stream()
        .collect(groupingBy(String::toLowerCase, counting()));
```

**要警惕的陷阱**：

- `chars()` 返回的是 `IntStream<Character>`（装箱的 Character 而不是 char）：

```java
// "Hello world!" 中出现频率最高的字母（chars 是 IntStream，可读性差）
"Hello world!".chars().boxed()...
// 更好的做法：charAt 循环，或 chars() 慎用
```

- Stream 版的"读"代码可能把一个 for 循环拆成三段难以阅读的管道（书中 Anagram 的对比：Stream 版反而绕）；
- Stream 中不该处理 char 流、不该访问闭包外可变状态。

经验法则：Stream 适合集合/数组转换、不适合需要检查元素间关系的场景（状态依赖）。老式代码与 Stream 混用是正常的，不要为流而流。

### 条目 46：优先选择 Stream 中无副作用的函数

forEach 应该只用于**呈现**（打印、加入既有结果），不要用于计算：

```java
// 反例：在 forEach 里改外部 map——"味道糟糕的代码"
Map<String, Long> freq = new HashMap<>();
words.forEach(word -> freq.merge(word.toLowerCase(), 1L, Long::sum));

// 正例：用收集器
Map<String, Long> freq = words.stream()
        .collect(groupingBy(String::toLowerCase, counting()));
```

常用收集器：`toList/toSet/toMap/joining/groupingBy/partitioningBy/counting/summingInt`。

`toMap` 注意点：多个键冲突要提供合并函数（`BinaryOperator`），否则抛 IllegalStateException；值可能为 null 时用 `toMap` 的三参数重载或收集成 list。

### 条目 47：返回类型：Stream 还是 Iterable（Collection 优先）

返回 `Stream` 的 API 用 for-each 遍历不便，返回 `Iterable` 的 API 用 Stream 不便——**`Collection`（或其子类型）是最佳的公共返回类型**：

- 既支持 Stream（`stream()`），又支持 for-each（Iterable）；
- `size()` 有限时甚至可提示用户不用拉全部元素。

无法返回 Collection 的场景（数据量可能巨大）：返回 Stream（或 Iterable，面向老式循环）。小元素序列用 `List.of(...)` 返回（标准实现高效）。

### 条目 48：谨慎使用 Stream 并行

并行化收益来自**并行处理任务的速度 > 任务拆分/合并的开销**。可预测并行的场景：

- `ArrayList`、`HashMap`、`HashSet`、`ConcurrentHashMap`、数组、`IntStream.range`、机器码 buffer——**数据源可均匀切分，且与结果的合并廉价**；

```java
// 可以并行：int 均匀切分 + 机器接近的计算
primes().map(p -> TWO.multiply(p).subtract(ONE))
        .parallel()
        .filter(mersenne -> mersenne.isProbablePrime(50))
        .limit(20)
        .forEach(System.out::println);
```

- 遍历、组合、合并的**成本高或不可切分**（如 iterate、bufferedReader.lines）不要并行；
- **limit 遇到并行流时要小心**（无序 source 上 limit 语义弱化）；
- 终端操作（forEach/count）合并开销大的要避免；
- 并行流默认用公共 ForkJoinPool，IO 阻塞型任务会饿死其他任务。

除非有把握（可测量），否则不要并行——数据源可切分 + 足够多元素 + 每元素操作昂贵，三者齐备才有收益。
