### 条目 69：针对异常情况才使用异常

```java
// 反例：用异常做循环终止（慢且遇修改并发修改时行为错误）
try {
    int i = 0;
    while (true)
        range[i++].climb();
} catch (ArrayIndexOutOfBoundsException e) { }
```

异常**设计用于异常情况**：JVM 不做优化假设、栈捕获成本高。标准模式是**状态检测方法 + 访问方法**：

```java
for (Mountain m : range)
    m.climb();

// 状态检测 vs 异常驱动的选择：
// 1. 并发外部访问时，"检测再操作"有竞态——异常更稳；
// 2. 检测成本高且预期常失败时，异常驱动更快。
for (Iterator<Foo> i = collection.iterator(); i.hasNext(); ) { Foo foo = i.next(); ... }
```

### 条目 70：对可恢复的情况使用受检异常，对编程错误使用运行时异常

三类 throwable 的选择：

| 种类 | 用途 | 客户端处理 |
| --- | --- | --- |
| 受检异常（checked） | **可恢复**的情况 | 必须 catch 或传播，可尝试恢复 |
| 运行时异常（runtime） | **编程错误**（违反前提约定） | 不应该 catch（修复代码） |
| 错误（Error） | JVM 资源不足等致命错误 | 不要自定义 Error 子类 |

受检异常要提供**恢复条件的访问方法**（如 `InsufficientFundsException.getAmount()` + `deficit()`），让调用方能编程式处理。

### 条目 71：避免不必要地使用受检异常

受检异常强迫调用方 catch/传播，过度使用让 API 使用困难。可以：

- **改抛非受检异常 + 提供检测方法**（`if (obj.isEmpty()) ... else obj.pop()`）；
- **拆分方法**让"正常路径"无需处理异常。

```java
// 受检版
try { actionPermitted(); ... }
catch (ActionDeniedException e) { ... }

// 更好：状态检测法
if (actionPermitted()) { ... }
```

### 条目 72：善于使用标准异常

| 异常 | 场景 |
| --- | --- |
| `IllegalArgumentException` | 非 null 参数值不合适 |
| `IllegalStateException` | 对象状态不适合方法调用 |
| `NullPointerException` | 参数为 null（`Objects.requireNonNull` 自动化） |
| `IndexOutOfBoundsException` | 索引越界 |
| `ConcurrentModificationException` | 检测到并发修改（已是 best-effort） |
| `UnsupportedOperationException` | 对象不支持该操作（接口方法的可选操作） |

复用标准异常的好处：API 易学、可读性好、性能（已预实例化）。**不要复用 Exception/RuntimeException/Throwable/Error**；不确定时抛 IllegalArgumentException。

### 条目 73：抛出与抽象相对应的异常

上层捕获底层异常时要**异常转译（exception translation）**——抛出上层抽象对应的异常：

```java
// AbstractSequentialList 中的转译
try {
    ...
} catch (NoSuchElementException e) {
    throw new IndexOutOfBoundsException("Index: " + index);
}
```

更好的是**异常链（exception chaining）**——把底层异常作为 cause 传入，保留完整堆栈：

```java
} catch (LowerLevelException cause) {
    throw new HigherLevelException(cause);   // 高层构造器把 cause 传给 super
}
```

`Throwable.getCause()` 取因。注意：无脑 catch 并转译（不提供高层语义）反而不如直接让底层异常传播——除非高层方法保证其承诺。

### 条目 74：为每个方法记录文档中抛出的异常

- 每个方法单独声明**受检异常**并 `@throws` 文档化**何时**抛出（不要用 `throws Exception` 聚合声明）；
- 非受检异常也**应该**文档化（同 @throws），但不建议用 throws 关键字声明；
- 类级别的文档可以统一声明所有方法共有的前置条件（如"所有参数为 null 时抛 NullPointerException"，类注释写一次即可覆盖全部方法）。

### 条目 75：在详细信息中包含失败捕获信息

异常的 `toString`/消息应包含**导致失败的所有参数和字段值**：

```java
// 反例：空消息或 "Assertion Error"
// 正例：包含索引、长度、运算细节
public IndexOutOfBoundsException(int lowerBound, int upperBound, int index) { ... }
// 消息形如 "Index: 9, Lower bound: 0, Upper bound: 8"
```

为确保安全和跨版本，消息内容**不要**包含口令/密钥等敏感信息；服务端日志记录完整失败信息比客户端可见的异常消息更重要。

### 条目 76：保持失败原子性

失败的方法调用应让对象**保持在调用前的状态**。实现手段（按优先程度）：

- **参数检查先行**（在修改状态前抛出）：

```java
public Stack pop() {
    if (size == 0)
        throw new EmptyStackException();   // 先检查再修改
    ...
}
```

- **先计算后赋值**：调整大小的操作先做"临时的不可变计算"（如 `TreeMap.remove` 之前先查找）；
- **在临时副本上执行操作**，成功后替换（如 `Collections.sort` 先拷贝数组再排序，中途比较器抛异常不影响原集合）；
- **写恢复代码**（ catch 后回滚）——很少用。

不可变对象天然失败原子。失败原子性是**期望而非强制**（如并发容器迭代器的 `ConcurrentModificationException` 是 best-effort），文档应说明。

### 条目 77：不要忽略异常

```java
// 空 catch 块把异常"吞掉"——问题在后续以无关方式爆发
try { ... } catch (SomeException e) { }
```

确实无法处理时也要记录或转译传播：

```java
} catch (SomeException e) {
    e.printStackTrace();        // 至少留痕（生产应走日志）
    // 或者：Thread.currentThread().interrupt()（InterruptedException 的正确处理，条目 82）
}
```

每个空 catch 块都应该有注释说明为什么可以安全忽略。
