### 导论（第 1 章精要）：线程的收益与风险

**为什么需要多线程**：

- **资源利用**：程序阻塞在 IO/等待时，CPU 可以跑别的线程（单线程进程在 IO 期间只能空转）；
- **公平性**：多个用户/任务轮流使用资源，而不是一个长任务霸占到底；
- **便利性**：某些问题用多线程建模更自然（服务器"一个连接一个任务"、模拟、异步事件）。

**线程带来的三类风险**（也是全书的主线）：

| 风险 | 含义 | 对应篇章 |
| --- | --- | --- |
| **安全性（safety）** | 不破坏数据与不变式 | 第 1~4 篇 |
| **活跃性（liveness）** | 该发生的事最终会发生（死锁/饥饿/活锁） | 第 8 篇 |
| **性能（performance）** | 服务时间、延迟、吞吐量、可伸缩性 | 第 9 篇 |

**线程无处不在**：即使不显式创建线程，程序也几乎必然运行在多线程环境——JVM 自身（GC、JIT）、Timer、Servlet 容器（一个 Servlet 可能同时被多个请求线程调用）、RMI、Swing 事件派发线程。**"我的代码没有创建线程"不能作为不处理并发的理由**——框架替你创建了线程，同步责任依然在你。

### 什么是线程安全性

**线程安全性定义：当多个线程访问某个类时，这个类始终都能表现出正确的行为，无论运行时如何调度、交替执行，且不需要调用端做任何额外的同步。**

- "正确的行为"指类的**不变式（invariant）**与后置条件不被破坏；
- 无状态对象（没有实例字段）一定线程安全——Servlet 的无状态实现是天然安全的；
- 线程安全的类封装了所有需要的同步，调用者不需要自己加锁（如 ConcurrentHashMap）；
- 线程安全性是关于**正确性**的概念：在多线程环境下"表现得和文档描述的语义一样"，而不是"在测试中没出过错"。

任何"适度线程安全"的中间地带都不存在——要么所有路径都安全，要么它不是线程安全的。

### 竞态条件（Race Condition）

**竞态条件：正确性取决于多个线程的交替执行时序。** 最常见的两种形态：

**1. 检查再运行（check-then-act）**：判断与动作之间，条件可能已被其他线程改变。最典型的是延迟初始化（LazyInitRace）：

```java
if (instance == null)   // 检查
    instance = new Instance();  // 运行——两个线程可能都通过了检查，创建两个实例
```

竞态并不总是导致错误——**它只是"可能"出错**。这正是并发 bug 最诡异的地方：测试十万次都通过，不代表竞态不存在；bad timing 一旦出现就是数据损坏。

**2. 读取-修改-写入（read-modify-write）**：三步不是原子的：

```java
count++;   // 读取 count、加 1、写回：并发下丢失更新
```

书中例子：无同步的因数分解 Servlet（UnsafeCountingFactorizer），并发访问时统计数偏小——数值偏小还不算最糟，**失效/不一致的数据沿调用链继续传播才是**。

**复合操作（compound action）**：check-then-act 与 read-modify-write 都是由多步构成的复合操作，要保证线程安全，**必须把复合操作作为不可分割的原子操作来执行**。这是下一节加锁的目标，也是后面原子变量（第 11 篇）的目标。

### 原子变量：单状态变量的轻量方案（预告）

当**状态只有一个变量**，且操作恰好有原子形式时，`java.util.concurrent.atomic` 的原子变量可以替代锁：

```java
// 计数器版因数分解 Servlet：用 AtomicLong 修复丢失更新
public class AtomicCountingFactorizer implements Servlet {
    private final AtomicLong count = new AtomicLong(0);

    public void service(ServletRequest req, ServletResponse resp) {
        BigInteger i = extractFromRequest(req);
        BigInteger[] factors = factor(i);
        count.incrementAndGet();              // 原子的读-改-写（底层 CAS，第 11 篇）
        encodeIntoResponse(resp, factors);
    }
    public long getCount() { return count.get(); }
}
```

**局限**：原子变量只救得了"单个独立变量"。一旦状态由多个变量组成不变式（比如后面缓存的 `lastNumber` 与 `lastFactors` 必须彼此匹配），单个原子变量无能为力——要么把两个状态放进一个不可变对象原子替换，要么加锁。

### 加锁机制

#### 内置锁（监视器锁）

Java 每个对象都有一把内置锁，`synchronized` 块自动获取/释放：

```java
synchronized (lock) {   // 访问和修改共享状态前，先获得锁
    // 临界区：同一时刻只有一个线程能进入
}
```

- 以**对象为粒度**互斥：同一把锁保护的所有代码块串行执行；
- 自动释放（异常也会），不会忘记 unlock；
- synchronized 方法是"锁住整个方法体"的语法糖：静态方法锁 Class 对象，实例方法锁 this。

#### 锁是可重入的

内置锁可重入：**同一线程可以再次获取自己已持有的锁**（按"持有计数"管理，获取一次加一、退出一次减一，归零才释放）。否则下面的代码会自死锁——子类覆写方法又调 super 的同步方法：

```java
public class Widget {
    public synchronized void doSomething() { ... }
}
public class LoggingWidget extends Widget {
    @Override
    public synchronized void doSomething() {   // 先获取 Widget 的锁
        System.out.println(...);
        super.doSomething();    // 再次获取同一把锁——可重入所以不会死锁
    }
}
```

可重入的代价是"拥有锁的线程可以反复进入"，它把锁封装在了线程所有权的概念里。

#### 用锁保护状态

**锁保护的含义是互斥访问，并非魔法隔离**：

- 对每个**可变的共享变量**，所有访问它的路径都必须由**同一把锁**保护；
- 每个共享的**不变式**涉及多个变量时，这些变量的读写必须在**同一个原子操作**（同一锁的同一临界区）内完成——把 `if (a > b) b = a;` 拆成两个同步块就破坏了不变式；
- 不是所有字段都需要锁保护（不可变字段、被封闭的字段、未被共享的字段不需要）；
- **锁与状态的关系是"约定"而非"强制"**：synchronized 不会阻止未加锁的代码访问该字段——获得锁的约定必须写进类的文档并贯彻到每一行访问代码（见第 3 篇文档化同步策略）。

常见误区：只用 synchronized 修饰写方法不修饰读方法——**读写都要同步**。写同步读不同步，读到的是失效数据，等于还是没同步（可见性见第 2 篇）。

**并非所有数据都需要锁**：判断标准只有三条——变量是否被多线程共享？是否可变？是否已有其他机制（不可变、封闭、并发容器）保护？三者皆否才需要。

### 活跃性与性能

锁粒度的两难：

- **粗粒度**：整个方法同步（SynchronizedFactorizer）——安全但性能差，并发度退化为串行，多线程反而不如单线程（还多了上下文切换）；
- **太细**：多个锁交叉保护相关状态——容易出错甚至死锁；

**原则：合理地在原子操作内尽快完成（快进快出）**。缩小同步块的范围，把与状态无关的耗时操作（I/O、计算）移出锁外，但要保持原子性不能牺牲：

```java
// 缓存了因数结果的 Servlet：只锁"读写缓存"这一复合操作
public class CachedFactorizer implements Servlet {
    private BigInteger lastNumber;
    private BigInteger[] lastFactors;
    private long hits;          // 命中数与命中分解数也用同一把锁保护
    private long cacheHits;

    public void service(ServletRequest req, ServletResponse resp) {
        BigInteger i = extractFromRequest(req);
        BigInteger[] factors = null;
        synchronized (this) {                       // 原子地检查并更新缓存
            ++hits;
            if (i.equals(lastNumber)) {
                ++cacheHits;
                factors = lastFactors.clone();
            }
        }
        if (factors == null) {
            factors = factor(i);                    // 耗时计算在锁外！
            synchronized (this) {                   // 原子地更新结果
                lastNumber = i;
                lastFactors = factors.clone();
            }
        }
        encodeIntoResponse(resp, factors);
    }
}
```

简单性与性能之间优先选择简单（先正确，再按测量结果优化）。

### 本章案例的演进小结

书用"因数分解 Servlet"贯穿了第 2 章，一步步走向线程安全：

| 版本 | 状态策略 | 结论 |
| --- | --- | --- |
| StatelessFactorizer | 无状态 | 天然线程安全 |
| UnsafeCountingFactorizer | 普通计数器 ++ | 丢失更新（read-modify-write） |
| AtomicCountingFactorizer | AtomicLong | 单变量场景够用，复合状态不行 |
| SynchronizedFactorizer | 所有方法整体同步 | 安全但过度串行化 |
| CachedFactorizer | 只锁缓存复合操作 | 正确 + 并发度好 |

**这一章建立了全书的第一原则：保护可变的共享状态，要么封装同步（锁/原子变量），要么不共享（不可变/封闭）。**

> 【演进】书中成书于 Java 5/6 时代，当时 synchronized 是重量级操作，大家倾向于减小锁范围。JDK 6 之后内置锁经历了锁升级优化（轻量级锁、自适应自旋等，偏向锁 JDK 15 起移除），**现代 JVM 上无竞争的 synchronized 开销已经很低**——优先用它，有测量数据再考虑优化（Effective Java 条目 67）。另外，书成书时的 Servlet 接口是 javax.servlet，如今已迁到 jakarta.servlet，但例子背后的原理不变。
