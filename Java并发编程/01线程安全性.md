### 什么是线程安全性

**线程安全性定义：当多个线程访问某个类时，这个类始终都能表现出正确的行为，无论运行时如何调度、交替执行，且不需要调用端做任何额外的同步。**

- "正确的行为"指类的**不变式（invariant）**与后置条件不被破坏；
- 无状态对象（没有实例字段）一定线程安全——Servlet 的无状态实现是天然安全的；
- 线程安全的类封装了所有需要的同步，调用者不需要自己加锁（如 ConcurrentHashMap）。

### 竞态条件（Race Condition）

**竞态条件：正确性取决于多个线程的交替执行时序。** 最常见的两种形态：

**1. 检查再运行（check-then-act）**：判断与动作之间，条件可能已被其他线程改变。最典型的是延迟初始化：

```java
if (instance == null)   // 检查
    instance = new Instance();  // 运行——两个线程可能都通过了检查，创建两个实例
```

**2. 读取-修改-写入（read-modify-write）**：三步不是原子的：

```java
count++;   // 读取 count、加 1、写回：并发下丢失更新
```

书中例子：无同步的因数分解 Servlet（UnsafeCountingFactorizer），并发访问时统计数偏小——**并发程序最诡异的地方：bug 不一定每次都出现**，测试通过不代表没有竞态。

### 加锁机制

#### 内置锁（监视器锁）

Java 每个对象都有一把内置锁，`synchronized` 块自动获取/释放：

```java
synchronized (lock) {   // 访问和修改共享状态前，先获得锁
    // 临界区：同一时刻只有一个线程能进入
}
```

- 以**对象为粒度**互斥：同一把锁保护的所有代码块串行执行；
- 自动释放（异常也会），不会忘记 unlock。

#### 锁是可重入的

内置锁可重入：**同一线程可以再次获取自己已持有的锁**（按"持有计数"管理，退出一次减一）。否则下面的代码会自死锁——子类覆写方法又调 super 的同步方法：

```java
public class Widget {
    public synchronized void doSomething() { ... }
}
public class LoggingWidget extends Widget {
    @Override
    public synchronized void doSomething() {   // 先获取 Widget 的锁
        System.out.println(...);
        super.doSomething();    // 再次获取同一把锁——可重入所以不会死锁
    }
}
```

#### 用锁保护状态

**锁保护的含义是互斥访问，并非魔法隔离**：

- 对每个**可变的共享变量**，所有访问它的路径都必须由**同一把锁**保护；
- 每个共享的**不变式**涉及多个变量时，这些变量的读写必须在**同一个原子操作**（同一锁的同一临界区）内完成——把 `if (a > b) b = a;` 拆成两个同步块就破坏了不变式；
- 不是所有字段都需要锁保护（不可变字段、被封闭的字段不需要）。

常见误区：只用 synchronized 修饰写方法不修饰读方法——读写都要同步（可见性，见第 3 章）。

### 活跃性与性能

锁粒度的两难：

- **粗粒度**：整个方法同步（SynchronizedFactorizer）——安全但性能差，并发度退化为串行；
- **太细**：多个锁交叉保护相关状态——容易出错甚至死锁；

**原则：合理地在原子操作内尽快完成（快进快出）**。缩小同步块的范围，把与状态无关的耗时操作（I/O、计算）移出锁外，但要保持原子性不能牺牲：

```java
// 缓存了因数结果的 Servlet：只锁"读写缓存"这一复合操作
public class CachedFactorizer implements Servlet {
    private BigInteger lastNumber;
    private BigInteger[] lastFactors;
    private long hits;          // 命中数与命中分解数也用同一把锁保护
    private long cacheHits;

    public void service(ServletRequest req, ServletResponse resp) {
        BigInteger i = extractFromRequest(req);
        BigInteger[] factors = null;
        synchronized (this) {                       // 原子地检查并更新缓存
            ++hits;
            if (i.equals(lastNumber)) {
                ++cacheHits;
                factors = lastFactors.clone();
            }
        }
        if (factors == null) {
            factors = factor(i);                    // 耗时计算在锁外！
            synchronized (this) {                   // 原子地更新结果
                lastNumber = i;
                lastFactors = factors.clone();
            }
        }
        encodeIntoResponse(resp, factors);
    }
}
```

简单性与性能之间优先选择简单（先正确，再按测量结果优化）。

> 【演进】书中成书于 Java 5/6 时代，当时 synchronized 是重量级操作，大家倾向于减小锁范围。JDK 6 之后内置锁经历了锁升级优化（轻量级锁、自适应自旋等，偏向锁 JDK 15 起移除），**现代 JVM 上无竞争的 synchronized 开销已经很低**——优先用它，有测量数据再考虑优化（Effective Java 条目 67）。
