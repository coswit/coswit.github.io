### 可见性（Visibility）

加锁不仅能互斥，还能保证**可见性**。但只把写同步、读不同步，读到的可能是**失效数据**：

```java
// 没有同步的共享可变数据
public class NoVisibility {
    private static boolean ready;
    private static int number;

    private static class ReaderThread extends Thread {
        public void run() {
            while (!ready)
                Thread.yield();      // 可能永远循环！
            System.out.println(number);  // 也可能打印 0（失效数据）！
        }
    }
    public static void main(String[] args) {
        new ReaderThread().start();
        number = 42;
        ready = true;    // 写入顺序可能与代码顺序不一致（重排序）
    }
}
```

两种诡异现象的根源都是**重排序（reordering）**：

- **读线程永远循环**：JIT 判定 `while (!ready)` 中 ready 不变，提升为 `while (true)`；
- **打印 0 而不是 42**：写线程的 `number = 42` 与 `ready = true` 可能被重排；读线程也可能先看到 ready=true 后看到 number=42（无数据竞争保证）。

**重排序不仅发生在编译器，CPU 的乱序执行与缓存也都会造成。在没有同步的情况下，推断"内存操作发生的顺序"是徒劳的。**幸运的是，没有同步的读能看到的"怪事"被 JMM 限定在一个范围内——失效数据、部分构造的对象，但不会凭空捏造一个值（详见第 12 篇）。

**失效数据（stale data）比崩溃更危险**：NoVisibility 最多是死循环或打印错值；若是"订单对象读到旧余额、新状态"，脏数据会沿着调用链继续传播，损坏的范围远超线程边界。大多数框架（如 Servlet 容器）会复用线程/对象，一个请求留下的脏状态可能被后续请求读到。

非原子的 64 位操作：不加 volatile 的 long/double 读写（JVM 允许）可能拆成两次 32 位——读到"高位新值+低位旧值"的随机值。加锁或 volatile 可解决（现代 64 位 JVM 基本都保证 64 位读写原子，但规范不保证——跨平台代码别依赖这个）。

### 加锁与可见性

内置锁的意义有两层，缺一不可：

1. **互斥**：同一时刻只有一个线程在临界区；
2. **可见性**：线程 A 释放锁 M 前写入的所有变量，线程 B 获得 M 后都能看到正确值。

所以**读写必须在同一把锁上同步**——写同步、读不同步，只是半个同步，读到失效数据。锁的可见性依据是 happens-before 规则"解锁 happens-before 后续对同一把锁的加锁"（第 12 篇）。

### volatile 变量

**volatile 保证：可见性 + 有序性（禁止重排），不保证原子性。**

- 写 volatile：刷新到主内存并使其他核的缓存失效；
- 读 volatile：从主内存读取最新值；
- volatile 变量相当于"轻量级的同步"：不挂起线程，但只解决可见性；
- 适当使用：**一个线程写、多个线程读**的标志位/状态发布：

```java
volatile boolean asleep;     // 兔子线程
while (!asleep) countSomeSheep();   // 每次循环都能看到最新值
```

**限制**：`count++` 这类依赖当前值的操作依然不安全（读改写三步不原子）。只有满足"**变量的写不依赖当前值，且不与其他变量组成不变式**"才适合只靠 volatile：

```java
// 反例：volatile 不足以保证下面这个"上限"不变式
private volatile int lower, upper;   // lower ≤ upper 的约束会被并发交错破坏——需要锁
```

加锁与 volatile 的选择：**加锁可以同时保证原子性与可见性，volatile 只保证可见性**。当能用volatile 就够时（单一标志位、发布不可变快照），volatile 更轻。

### 发布与逸出（Publish and Escape）

**发布（publish）**：使对象能在当前作用域之外被使用（存到静态字段、传给外部方法、注册监听器、作为方法返回值…）。**逸出（escape）**：对象在**构造完成之前**发布——危险，其他线程会看到未构造完的对象。

**发布的边界问题——发布内部可变状态就等于失去控制**：

```java
// 发布了内部可变数组：任何拿到引用的代码都能改你的状态，
// "不可变"的伪装瞬间崩塌——这属于类自己的封装失败，与调用者无关
class UnsafeStates {
    private String[] states = new String[] { "AK", "AL", ... };
    public String[] getStates() { return states; }   // 应返回拷贝！
}
```

同样，发布一个内部可变对象的引用（比如 getter 返回内部 Set 的引用），就把该对象的修改权拱手让出——"封闭"（见第 3 篇）随之瓦解。

**this 逸出的典型场景**：

```java
// 1. 构造器中启动线程：内部类隐式持有 this，新线程立刻能看到未构造完的对象
public class ThisEscape {
    public ThisEscape(EventSource source) {
        source.registerListener(new EventListener() {
            public void onEvent(Event e) {
                doSomething(e);   // 可能通过外部类引用访问未初始化的字段
            }
        });
    }
}

// 2. 构造器中调用可被覆写的方法（子类状态未初始化——父类构造期间子类字段还是默认值）
// 3. 构造器中把 this 传给外部方法（显式逸出）
// 4. 在构造器内启动线程（内部类的 run 天然携带 this 的隐式引用）
```

**修复：工厂方法 + 私有构造器**，只有构造完成后才发布：

```java
public class SafeListener {
    private final EventListener listener;
    private SafeListener() {                       // 私有构造
        listener = e -> doSomething(e);            // 内部类只是保存，不发布 this
    }
    public static SafeListener newInstance(EventSource source) {
        SafeListener safe = new SafeListener();    // 完全构造后
        source.registerListener(safe.listener);    // 才发布
        return safe;
    }
}
```

### 线程封闭（Thread Confinement）

**访问共享的可变数据才需要同步——不共享就不需要。**线程封闭是"以不共享换安全"的策略，三种方式：

1. **Ad-hoc 线程封闭**：由使用方自行维护（完全靠约定，脆弱，尽量避免——一旦有更严格的封装技术可用就该替换它）；
2. **栈封闭（stack confinement）**：变量只存在于局部变量/局部对象，天然封闭——**最简单也最常用的线程安全方式**。注意方法内创建的对象只要没逸出就安全（哪怕作为参数传给外部方法，只要对方不发布它；基本类型参数传值天然不逸出，引用类型要看被调用方行为）；
3. **ThreadLocal**：把值与线程绑定，每线程一份副本：

```java
// JDBC 连接不线程安全——用 ThreadLocal 让每个线程持有自己的 Connection
private static ThreadLocal<Connection> connectionHolder = ThreadLocal.withInitial(() -> DriverManager.getConnection(DB_URL));
```

适合：全局单例按线程隔离（SimpleDateFormat、用户上下文、事务上下文）。原理类似 `Map<Thread, T>`（实际存在 Thread 对象的 ThreadLocalMap 里）。风险：生命周期长 + 不 remove 会泄漏（线程池中的线程不死，副本一直可达——副本持有的大对象也连带泄漏），**用完务必 finally 里 remove**。

ThreadLocal 另一个用途是"**串行线程封闭（serial thread confinement）**"：对象通过安全发布（如 BlockingQueue）从一个线程移交给另一个线程，之后只有接收线程可以碰它——对象池、生产者-消费者传递缓冲对象都是这个模式（见第 4 篇）。

### 不可变性

**不可变对象一定是线程安全的**，不需要任何同步。不可变的三个要求：

- 状态创建后不能修改；
- 所有字段 final（**强烈要求**，保证安全的初始化过程，见第 12 篇 final 的初始化安全）；
- **正确构造**（this 没有逸出）。

> 注意"不可变"不等于"被 final 修饰的对象"——字段 final 但指向可变对象，状态仍可变。`final List<X>` 只是引用不可变。不可变性与"被声明为 final"的区别，正是第 4 篇"事实不可变"概念的基础。

```java
// 不可变的三剑客容器：构造后状态完全确定
public final class ThreeStooges {
    private final Set<String> stooges = new HashSet<>();
    public ThreeStooges() { stooges.add("Moe"); stooges.add("Larry"); stooges.add("Curly"); }
    public boolean isStooge(String name) { return stooges.contains(name); }
}
```

可变的构造器参数要在构造时**拷贝**（防止调用者后续修改引用的数据，如 OneValueCache 中 `factors.clone()`）。若构造器接收可变参数，`this` 没逸出 + 参数拷贝，才能担保"构造完成后状态永远有效"。

**volatile 的正确用法之一：发布不可变对象**——"不可变对象 + volatile 引用"是多线程共享可变状态的轻量替代：

```java
// 因式分解缓存：OneValueCache 不可变，用 volatile 保证引用的可见性
@Immutable
class OneValueCache {
    private final BigInteger lastNumber;
    private final BigInteger[] lastFactors;
    public OneValueCache(BigInteger i, BigInteger[] factors) {
        lastNumber = i;
        this.lastFactors = factors != null ? factors.clone() : null;   // 防御性拷贝
    }
    public BigInteger[] getFactors(BigInteger i) {
        return (lastNumber == null || !lastNumber.equals(i)) ? null : lastFactors.clone();
    }
}

public class VolatileCachedFactorizer implements Servlet {
    private volatile OneValueCache cache = new OneValueCache(null, null);  // volatile 引用
    public void service(ServletRequest req, ServletResponse resp) {
        BigInteger i = extractFromRequest(req);
        BigInteger[] factors = cache.getFactors(i);
        if (factors == null) {
            factors = factor(i);
            cache = new OneValueCache(i, factors);   // 原子地"替换"整个缓存（引用读写是原子的）
        }
        encodeIntoResponse(resp, factors);
    }
}
```

没有锁，没有 CAS——靠"不可变 + volatile 引用"达到线程安全。局限：只能保证**单次**读/替换的原子性，复合状态更新（check-then-act 跨多次）仍需加锁或原子引用。**每当需要修改不可变对象的状态时，就创建一个新的实例整体替换**（类似函数式的"值语义"）。

### 安全发布

不正确的发布 = 其他线程看到"半成品"对象。**要安全地发布一个对象，引用与对象的状态必须同时对其他线程可见。**

**不正确的发布**（无同步的公有静态字段）的问题：看到引用不为 null ≠ 看到构造完成的状态（重排序）。经典的 Holder 例子：

```java
// 未安全发布时，另一个线程调用 assertSanity 可能抛 AssertionError！
public class Holder {
    private int n;
    public Holder(int n) { this.n = n; }
    public void assertSanity() {
        if (n != n)   // 两次读 n，中间被写入或读到失效值——"n 不等于 n"竟然成立
            throw new AssertionError("This statement is false.");
    }
}
```

`n != n` 之所以可能：非同步的读没有 happens-before 关系，第一次读看到失效值 0、第二次读到新值 42。（把 n 声明为 final 即可免同步安全。）

**不可变对象与初始化安全**：JMM 的初始化安全保证——正确构造（不逸出）的不可变对象，**不需要任何同步**就能被任意线程安全使用，**即使用不安全的方式发布**（final 字段语义，第 12 篇）。这是"不可变"比"不修改"更强的根本原因。

**安全发布的常用模式**：

1. **静态初始化函数**中初始化引用：`public static Holder holder = new Holder(42);`（类初始化由 JVM 保证，有内部锁）；
2. **volatile 字段**引用；
3. **final 字段**（正确构造下，保证初始化安全性）；
4. **锁保护的字段**（读写都在 synchronized / Lock 内）；
5. 并发容器（ConcurrentHashMap、BlockingQueue）内部已保证（put happens-before take）。

发布后的三类对象：

| 类型 | 含义 | 发布后能否共享 |
| --- | --- | --- |
| 不可变对象 | 状态不可变 + 安全发布 | 自由共享（含无同步） |
| 事实不可变（effectively immutable） | 技术上可变，但发布后不再改 | 安全发布后可共享（读多线程也行） |
| 可变对象 | 状态可变 | **不仅发布要同步，每次访问都要同步** |

发布的需求取决于对象的**可变程度**：不可变对象任意发布；事实不可变要求安全发布；可变对象要求"安全发布 + 每次访问都同步"。

### 本章小结

- **加锁的两个理由：互斥 + 可见性**（读写都要同步）；
- volatile 只保证可见性和有序性，不保证原子性，只适用于"写不依赖当前值、不参与不变式"的场景；
- 构造未完成就发布（this 逸出）是定时炸弹——工厂方法模式修复；
- 不共享（栈封闭、ThreadLocal、串行封闭）与不可变是同步之外的两大支柱；
- **共享可变状态才需要同步；能不可变就不可变；要发布就得安全发布。**

> 【演进】书中成书时（2006）volatile 的实现还很贵；现代 JVM 的 volatile 读开销几乎与普通读相当，写需要一个内存屏障（x86 上是带 lock 前缀的指令）。另外，Java 9 的 VarHandle 提供了比 volatile 更细的内存序模式（acquire/release/opaque），供库作者使用（第 11 篇）。
