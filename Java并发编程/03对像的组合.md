### 设计线程安全的类

设计线程安全类的三要素：

1. **确定对象状态由哪些变量构成**（实体字段 + 引用到的可变对象，"对象的逻辑状态"可能跨越物理字段——例如 LinkedHashMap 的逻辑状态既包含哈希表又包含链表顺序）；
2. **找出不变式**：约束状态变量的取值关系（如计数器上下界、区间 [lower, upper] 的 lower ≤ upper）；
3. **制定并发访问策略**：哪些锁保护哪些状态、哪些变量是不可变的、哪些被线程封闭。

**收集同步需求**：不变式涉及多个变量时，必须作为**一个不可分割的原子操作**来维护。约束条件（如下界 ≤ 上界）限制了状态取值，更新也必须原子：

```java
// NumberRange 的不变式 lower ≤ upper：两个字段必须"捆绑"更新，
// 各自加锁（或不加锁）都会让线程观察到 lower > upper 的非法中间态
public class NumberRange {
    private final AtomicInteger lower = new AtomicInteger(0);
    private final AtomicInteger upper = new AtomicInteger(0);
    public void setLower(int i) { lower.set(i); }        // 错误：没有同时约束 upper
    public void setUpper(int i) { upper.set(i); }
    // 不变式跨字段，纯委托失效——需要同一把锁保护两个字段
}
```

同样，**后置条件**（如"计数器 +1 后不小于原值"）也意味着"先检查后行动"必须原子。类对状态约束越多，并发审计的工作量越大。

**状态所有权**：类并不总是拥有自己的状态——所有权与封装总是一起出现（拥有 = 在封装之内，由该类决定何时可变）。容器拥有其内部元素；发布引用等于共享所有权（发布可变对象的引用即放弃对它的独占控制——别的代码也能改它）。所有权与"由谁负责同步"直接挂钩：共享所有权意味着同步责任也共享（或交由容器本身承担）。

### 实例封闭（Instance Confinement）

**封闭：把数据封装在对象内部，把访问数据的路径限制在锁保护的范围内。**封闭简化了线程安全——哪怕被封装的对象本身不是线程安全的：

```java
// PersonSet 内部的 HashSet 非线程安全，但被封闭后只通过加锁方法访问——整体线程安全
@ThreadSafe
public class PersonSet {
    @GuardedBy("this") private final Set<Person> mySet = new HashSet<>();

    public synchronized void addPerson(Person p) { mySet.add(p); }
    public synchronized boolean containsPerson(Person p) { return mySet.contains(p); }
}
```

注意：**PersonSet 的线程安全性建立在 Person 不会被外部修改的前提上**（封闭的前提：被封闭对象不逸出）。如果 Person 可变且被共享，封闭就被破坏——封闭"我的 HashSet"容易，封闭"HashSet 里的元素"需要额外的纪律。

**平台类库的封闭**：`Collections.synchronizedXxx` 的实现原理就是封闭 + 监视器模式——把非线程安全的容器（HashMap）封闭在包装类里，所有方法用同一把锁（容器自身）串行化：

```java
Map<K, V> m = Collections.synchronizedMap(new HashMap<>());  // 迭代仍需手动 synchronized (m)
```

**监视器模式（monitor pattern）**：用对象自身的内置锁（this）保护所有状态的封闭方式。私有锁是它的变体——**客户端无法拿到你的锁，无法发动长时间持锁的攻击**（恶意或无意地长时间持有你的锁，让你的类卡死）：

```java
public class PrivateLock {
    private final Object lock = new Object();    // 私有锁：外界无法拿到
    public void doSomething() {
        synchronized (lock) { ... }              // 子类与客户端都无法干扰这把锁
    }
}
```

代价：子类与客户端无法参与同步策略（无法和你的操作做原子组合）——但这本来就该避免。

### 委托线程安全性（Delegating）

**把线程安全性委托给现有的线程安全类**——自己不写锁，状态交给线程安全的容器管理。

**车辆追踪器（全书经典案例）：同一个需求的多种实现，体现"委托"的适用边界。**

**方案一：监视器模式（MonitorVehicleTracker）**——可变的 MutablePoint + 全方法同步 + 返回**快照**：

```java
@ThreadSafe
public class MonitorVehicleTracker {
    @GuardedBy("this") private final Map<String, MutablePoint> locations;

    public synchronized Map<String, MutablePoint> getLocations() {
        return deepCopy(locations);                        // 返回深拷贝快照——调用者改的是副本
    }
    public synchronized MutablePoint getLocation(String id) {
        MutablePoint loc = locations.get(id);
        return loc == null ? null : new MutablePoint(loc); // 每次调用都拷贝
    }
    public synchronized void setLocation(String id, int x, int y) {
        MutablePoint loc = locations.get(id);
        if (loc == null) throw new IllegalArgumentException("No such ID: " + id);
        loc.x = x;
        loc.y = y;
    }
}
```

**方案二：委托给 ConcurrentHashMap（DelegatingVehicleTracker）**——不可变 Point + 原子替换：

```java
// 委托给 ConcurrentHashMap：位置数据全部保存在并发容器中
@ThreadSafe
public class DelegatingVehicleTracker {
    private final ConcurrentMap<String, Point> locations;
    private final Map<String, Point> unmodifiableMap;

    public DelegatingVehicleTracker(Map<String, Point> points) {
        locations = new ConcurrentHashMap<>(points);
        unmodifiableMap = Collections.unmodifiableMap(locations);
    }
    public Point getLocation(String id) { return locations.get(id); }   // Point 不可变
    public void setLocation(String id, int x, int y) {
        locations.replace(id, new Point(x, y));   // 不可变 Point 的"替换"更新
    }
    public Map<String, Point> getLocations() { return unmodifiableMap; }  // 弱一致性的实时视图
}
```

两种方案的**语义差异**（不是谁对谁错，而是接口契约不同）：

- 返回快照（深拷贝 / `new HashMap<>(locations)` 再包装）：拿到的是"**某一时刻**"的一致视图，但拷贝有开销，且数据马上过期；
- 返回实时视图（unmodifiableMap 包着 ConcurrentHashMap）：拿到的是"**最新但未必一致**"的视图（遍历中某辆车可能移动了两次）；
- 监视器版还把可变的 MutablePoint 交给了调用者（拷贝保护了内部状态）；委托版返回的 Point 不可变，天然无此顾虑。

**委托生效的条件**：状态真正独立，且涉及的多变量不变式没有被跨字段地表达。

- 委托给**单个**线程安全容器：安全；
- 委托给**多个**独立的状态变量（彼此无不变式约束）：也安全：

```java
// 两个独立的计数器，分别委托给 AtomicLong——组合不出跨字段不变式，因此安全
@ThreadSafe
public class DelegatingStats {
    private final AtomicInteger upper = new AtomicInteger(0);
    private final AtomicInteger lower = new AtomicInteger(0);
    // lower ≤ upper 的约束如果存在，就不能纯委托——这是两个变量组成的不变式，需要锁
}
```

如果存在**复合不变式**（如 lower ≤ upper），纯委托失效——修改 lower 与 upper 必须原子，要么加锁，要么用不可变对象承载组合状态再原子替换。

**发布底层状态**：委托时还可以选择把底层容器直接发布（返回 unmodifiableMap 的实时视图）vs 返回快照——取决于不变式是否允许外部观察者看到中间态、以及数据新鲜度的要求。若类的部分状态可以暴露、部分必须守护（如不允许别人往 locations 里加车），就要精细设计发布的边界。

### 扩展已有的线程安全类

给线程安全类添加原子操作（如给 Vector 加"没有才添加"）的四种途径：

1. **修改类**（加入新原子方法）——通常做不到（没有源码/平台类）；

2. **继承（extends）**——脆弱：实现细节的同步策略（锁哪个对象、粒度）变了就失效，且把实现与基类锁死；非 final 的类才能继承，同步策略无法自我说明；

3. **客户端加锁**——把外部代码用目标对象的锁包起来：

```java
// 错误做法：不同步——size 与 get 之间列表可能被别的线程清空，抛 ArrayIndexOutOfBoundsException
public static Object getLast(Vector list) {
    int lastIndex = list.size() - 1;
    return list.get(lastIndex);
}

// 正确：客户端加锁——必须用 Vector 自身的锁（list 就是它的锁）
public static Object getLast(Vector list) {
    synchronized (list) {
        int lastIndex = list.size() - 1;
        return list.get(lastIndex);
    }
}
// 正确的"没有才添加"：
public static void putIfAbsent(Vector v, Object x) {
    synchronized (v) {                        // 客户端加锁：与 Vector 内部同一把锁
        if (!v.contains(x)) v.add(x);
    }
}
```

客户端加锁脆弱在：**你必须精确知道目标类的锁是哪个对象、加锁的粒度**——破坏了封装，是"侵入式的猜测"（"以毒攻毒"地依赖实现细节）。更糟的是 lock 的是哪个对象常常没有文档（见下节）。

4. **组合（推荐）**——用组合包装，用自己的锁：

```java
// 组合：内部委托给线程安全类，复合操作用自己的锁保护
@ThreadSafe
public class ImprovedList<T> implements List<T> {
    private final List<T> list;
    public ImprovedList(List<T> list) { this.list = list; }

    public synchronized boolean putIfAbsent(T x) {
        boolean absent = !list.contains(x);    // contains/add 各自线程安全
        if (absent) list.add(x);               // 但组合起来要靠自己的锁保证原子
        return absent;
    }
    // 其余方法委托给 list（自己的锁保护一层，比内部锁略粗，但简单可靠）
}
```

组合不需要知道底层锁的细节，只保护自己的复合逻辑——**"简单粗暴但正确"，比聪明的客户端加锁更好**。即使底层 list 的锁策略将来改变，ImprovedList 依然正确（自己这层锁永远成立）。它维持了"一层加锁的包装"的额外开销，但换来的是对底层实现的零假设。

### 文档化同步策略

为类和使用者写下同步策略：哪些状态由哪些锁保护、哪些是 volatile/不可变/封闭、发布条件。**没有文档的线程安全类是"能用但危险"的**——常见平台的坑：继承 Thread 安全类的"部分线程安全"（如 Hashtable：单个方法安全，复合操作要客户端加锁，但文档没说）。

**给类的线程安全性分级**（文档应明确说明属于哪一级）：

| 级别 | 含义 | 例子 |
| --- | --- | --- |
| 不可变（immutable） | 无可变状态 | String、Integer、OneValueCache |
| 无条件线程安全 | 内部充分同步，复合操作也是原子的 | ConcurrentHashMap、AtomicLong、ConcurrentLinkedQueue |
| 有条件线程安全 | 个别复合操作需要客户端加锁 | synchronizedCollection（迭代要外部锁）、Hashtable |
| 线程兼容（thread-compatible） | 自身不同步，可由外部加锁保护 | ArrayList、HashMap（配 Collections.synchronizedXxx） |
| 线程敌对（thread-hostile） | 即使外部加锁也不安全 | 类内有自己的数据竞争/发布漏洞的坏例子 |

文档化还包括：**哪些操作持锁、持多久**（客户端加锁需要知道锁对象）；无副作用的方法是否真的无副作用；javadoc 的 @ThreadSafe / @GuardedBy("lock") 注解（jcip-annotations，第 1 篇提过的标注体系）可以把同步策略落到代码里。

### 小结（第 2~4 篇主线）

| 共享数据形态 | 策略 |
| --- | --- |
| 不共享 | 栈封闭 / ThreadLocal / 串行封闭 |
| 不可变对象 | final + 正确构造 + 安全发布 |
| 少量独立的状态 | 原子变量 / 委托给并发容器 |
| 有复合不变式 | 锁保护（快进快出）或不可变对象原子替换 |
| 复合操作扩展 | 组合优先于继承与客户端加锁 |
