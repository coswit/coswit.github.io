### 同步容器类的问题

Vector、Hashtable 及 Collections.synchronizedXxx 是"早期"的同步容器：**每个方法各自同步**，单个方法线程安全，**复合操作不安全**。复合操作的三大类：

- **迭代**（遍历时别的线程修改）抛 ConcurrentModificationException（fail-fast 是"尽力而为"的启发式检测——它检测到修改就抛，但没有义务及时发现）；
- **check-then-act**（没有才添加、取最后一个元素）——原子性跨度大于单个方法；
- **复合调用**（如"先 contains 再 remove"之间的窗口）。

```java
// Vector 上"取最后一个元素"的竞态：size 与 get 之间列表被清空 → 越界异常
public static Object getLast(Vector list) {
    int lastIndex = list.size() - 1;
    return list.get(lastIndex);
}
// 修复：synchronized (list) 把两步包成原子（客户端加锁，见第 3 篇）
```

**迭代与 CME**：同步容器的迭代器在其他线程并发修改时抛 ConcurrentModificationException。在迭代期间持锁可以保安全——但代价是**整个迭代期都持锁**（别的线程连读都进不来），且容器大时锁持有时间过长：

```java
// 迭代同步容器的"正确但笨重"写法：锁内迭代
synchronized (vector) {
    for (int i = 0; i < vector.size(); i++) doSomething(vector.get(i));
}
// forEach 等语法糖不会替你做这件事——它底层还是迭代器
```

更常见的做法是**在锁内先克隆容器，再对副本迭代**（复制期间持锁短，迭代无锁）——代价是拷贝开销。

**隐藏迭代器（hidden iterator）**：最阴险的 CME 来源——迭代藏在"看起来无害"的方法里：

```java
// 看起来加锁了，其实没有：toString 底层调 StringBuilder.append(Set) 会迭代整个 set——
// 无锁迭代 + 另一个线程 add → ConcurrentModificationException
@NotThreadSafe
public class HiddenIterator {
    @GuardedBy("this") private final Set<Integer> set = new HashSet<>();

    public synchronized void add(Integer i) { set.add(i); }
    public synchronized void remove(Integer i) { set.remove(i); }

    public void addTenThings() {
        Random r = new Random();
        for (int i = 0; i < 10; i++)
            add(r.nextInt());
        System.out.println("DEBUG: added ten elements to " + set);   // 隐藏的迭代！
    }
}
```

toString、hashCode、equals、containsAll、removeAll、retainAll，甚至把容器传给构造器（如 `new ArrayList<>(set)`），都会隐式迭代。**教训一：所有持锁访问该容器的地方都要锁——包括"看似只读"的调试打印；教训二：这类需求直接换并发容器，别用同步容器。**

**新代码不要再用同步容器，用并发容器。**

### 并发容器

针对并发访问重新设计的容器，**大幅提高吞吐的同时保证安全**：

**ConcurrentHashMap**

- 代替同步 HashMap/Hashtable。Java 8 前采用**锁分段（lock striping）**（默认 16 段，不同段可并行写），Java 8 起改为 **CAS + 少量 synchronized 桶级锁**（链表头/红黑树根）；
- **读操作无锁**（volatile 读表与节点）；
- 迭代器**弱一致性（weakly consistent）**：不抛 CME，反映"开始迭代时或之后的部分"状态，不保证实时；
- size()/isEmpty() 是**估计值**（并发下精确统计代价大）；
- 复合操作原子化：**putIfAbsent、replace、computeIfAbsent** 等，替代"客户端加锁"；
- 注意：**批量操作（size、containsAll）语义弱化**——并发环境下的精确瞬时值本身意义有限。

**CopyOnWriteArrayList**

- 代替同步 List，适合**读多写极少**（监听器列表、配置）；
- 每次修改复制底层数组，**读永远无锁**且迭代是快照（不抛 CME、不会看到中间态）——迭代器持有的引用永远不变，"事实不可变"的典型应用；
- 写代价高（复制 + 可能引发 GC 压力），写频繁时性能很差；
- 迭代器**不支持 remove**（快照没有"对应的底层元素"）。

**ConcurrentSkipListMap / Set**：跳表实现的有序并发容器（对应同步 TreeMap），并发性优于锁式的有序容器（插入/删除只影响局部）。

> 【演进】Java 8 的 ConcurrentHashMap 还提供了并行批量操作（forEach/search/reduce），支持并行流（parallelStream）的底层基石。

### 阻塞队列与生产者-消费者

**BlockingQueue**：put/take 在满/空时**阻塞等待**，天然的流量控制与解耦：

| 实现 | 特点 |
| --- |
| ArrayBlockingQueue | 有界，环形数组 |
| LinkedBlockingQueue | 可选有界，链表（默认无界——用之前想清楚） |
| PriorityBlockingQueue | 按优先级出队，无界 |
| SynchronousQueue | **零容量**——put 直接交给 take（交接点，直接握手） |
| DelayQueue | 延迟到期才能取走 |

生产者-消费者模式的价值：**解耦**（生产与消费速率互不依赖，互相不直接持有引用，一切通过队列说话）+ **削峰**（有界队列提供"背压"：队列满时生产者阻塞，而不是内存爆掉）。桌面搜索的经典结构——爬虫与索引器之间隔一条阻塞队列：

```java
// 生产者：遍历文件树，把文件塞进队列
public class FileCrawler implements Runnable {
    private final BlockingQueue<File> fileQueue;
    private final FileFilter fileFilter;
    private final File root;
    ...
    public void run() {
        try {
            crawl(root);
        } catch (InterruptedException e) {          // 爬取被中断：退出
            Thread.currentThread().interrupt();
        }
    }
    private void crawl(File root) throws InterruptedException {
        File[] entries = root.listFiles(fileFilter);
        if (entries != null)
            for (File entry : entries)
                if (entry.isDirectory()) crawl(entry);
                else if (!alreadyIndexed(entry)) fileQueue.put(entry);
    }
}

// 消费者：从队列取文件建索引
public class Indexer implements Runnable {
    private final BlockingQueue<File> queue;
    ...
    public void run() {
        try {
            while (true) indexFile(queue.take());   // 队列空则阻塞——消费者不需要知道生产者的存在
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
// 启动：几个爬虫 + 几个索引器，通过一条有界队列连接
```

队列的选择也是设计决策：有界队列（背压、稳定）、无界队列（生产快于消费时内存膨胀）、零容量的 SynchronousQueue（直接交接，生产消费节奏对齐）、关闭用"毒丸"（第 6 篇）。

**串行线程封闭**：对象由生产者"安全发布"进队列，消费者拿到后**独占**——期间生产者不得再碰。对象池、缓冲区复用都用这个模式把"不共享"的效率用到了极致。

> 双端队列 Deque（ArrayDeque/LinkedBlockingDeque）：**工作密取（work stealing）**——每个消费者有自己的双端队列，自己从一端取，偷别人的任务从另一端取，减少竞争（ForkJoin 的调度基础；ForkJoinPool 在 Java 7 引入，正是这一思想的标准化）。

### 阻塞方法与中断方法

阻塞方法（take/put/sleep/join）可能抛 **InterruptedException**——这是**可中断阻塞**的信号。调用阻塞方法的两种选择：传递异常（方法声明 throws）或恢复中断状态（`Thread.currentThread().interrupt()`）。**绝不要捕获后忽略**（吞掉中断剥夺了调用者取消的能力，详见第 6 篇）。

### 同步工具类

**1. 闭锁 CountDownLatch（一次性倒计数）**

`await()` 阻塞直到计数为 0；countDown() 减一。用途：等待 N 个并行任务都完成。书中 TestHarness——用两把闭锁实现"同时发令 + 全员计时"：

```java
// 测试 N 个线程并发执行某任务的总耗时
public long timeTasks(int nThreads, final Runnable task) throws InterruptedException {
    final CountDownLatch startGate = new CountDownLatch(1);
    final CountDownLatch endGate = new CountDownLatch(nThreads);

    for (int i = 0; i < nThreads; i++) {
        Thread t = new Thread(() -> {
            try {
                startGate.await();          // 等待同时发令（避免先启动的线程"抢跑"，制造真实竞争）
                task.run();
            } catch (InterruptedException ignored) {
            } finally {
                endGate.countDown();        // 完成
            }
        });
        t.start();
    }
    long start = System.nanoTime();
    startGate.countDown();                  // 发令
    endGate.await();                        // 等全部完成
    return System.nanoTime() - start;
}
```

没有 startGate 会怎样：线程逐个 start，先启动的开始干活——测的是"启动梯次"而非并发竞争。

**2. FutureTask（可携带结果的任务）**

FutureTask.get() 阻塞取结果（可带超时），任务只执行一次。用做**异步计算的句柄**，也可以做"昂贵结果只算一次"的加载器（闭锁的升级版：不光"完成了"，还"有结果"）：

```java
// 预加载：构造时开始计算，get 时大概率已经算完——用等待换取延迟确定性
public class Preloader {
    private final FutureTask<ProductInfo> future = new FutureTask<>(() -> loadProductInfo());
    private final Thread thread = new Thread(future);
    public void start() { thread.start(); }

    public ProductInfo get() throws DataLoadException, InterruptedException {
        try {
            return future.get();               // 若计算抛异常，get 会把它包装为 ExecutionException 重抛
        } catch (ExecutionException e) {
            Throwable cause = e.getCause();
            if (cause instanceof DataLoadException) throw (DataLoadException) cause;
            else throw launderThrowable(cause); // launderThrowable：受检/运行时异常分别处理（见第 6 篇）
        }
    }
}
```

注意异常语义：Callable 抛出的异常被 FutureTask 捕获，通过 get() 的 ExecutionException 重抛——**不调用 get，异常会被吞掉**（这也是第 6 篇"必须处理 Future 结果"的原因）。

**3. 信号量 Semaphore（许可计数）**

acquire 获取许可（无则阻塞）、release 归还。用途：**限制并发访问资源数**——有界阻塞容器：

```java
// 用信号量把普通容器变成"有界阻塞"容器
class BoundedHashSet<T> {
    private final Set<T> set;
    private final Semaphore sem;
    public BoundedHashSet(int bound) {
        set = Collections.synchronizedSet(new HashSet<>());
        sem = new Semaphore(bound);
    }
    public boolean add(T o) throws InterruptedException {
        sem.acquire();                       // 先拿许可
        boolean wasAdded = false;
        try {
            wasAdded = set.add(o);
            return wasAdded;
        } finally {
            if (!wasAdded) sem.release();    // 没加成功要还许可
        }
    }
    public boolean remove(Object o) {
        boolean wasRemoved = set.remove(o);
        if (wasRemoved) sem.release();       // 移除后还许可
        return wasRemoved;
    }
}
```

信号量不表示"哪个许可被谁持有"，只维护计数——与锁最大的区别是**释放者可以不是获取者**（生产者-消费者式的资源移交）。

**4. 栅栏 CyclicBarrier（可重用的汇合点）**

所有线程到达 await() 才一起继续（可携带 barrierAction 回调，在"全员到齐、一起放行前"由最后一个到达的线程执行）；**可重复使用**（区别于闭锁——闭锁是一次性倒计时，栅栏按轮次循环），适合**多轮迭代**的并行算法。细胞自动机的并行模拟：

```java
// N 个工作线程各算一块；每轮结束在栅栏汇合，由 barrierAction 统一提交新值
public class CellularAutomata {
    private final Board mainBoard;
    private final CyclicBarrier barrier;
    private final Worker[] workers;

    public CellularAutomata(Board board) {
        this.mainBoard = board;
        int count = Runtime.getRuntime().availableProcessors();
        this.barrier = new CyclicBarrier(count, () -> mainBoard.commitNewValues());  // 栅栏动作
        this.workers = new Worker[count];
        for (int i = 0; i < count; i++)
            workers[i] = new Worker(mainBoard.getSubBoard(count, i));
    }

    private class Worker implements Runnable {
        private final Board board;
        Worker(Board board) { this.board = board; }
        public void run() {
            while (!board.isConverged()) {
                for (int x = 0; x < board.getMaxX(); x++)
                    for (int y = 0; y < board.getMaxY(); y++)
                        board.setNewValue(x, y, computeValue(x, y));
                try {
                    barrier.await();         // 等所有线程算完这一轮（await 抛 InterruptedException/ BrokenBarrierException）
                } catch (InterruptedException ex) { return; }
                  catch (BrokenBarrierException ex) { return; }   // 栅栏被打破（有线程退出/超时）——本轮作废
            }
        }
    }
    public void start() {
        for (int i = 0; i < workers.length; i++) new Thread(workers[i]).start();
        mainBoard.waitForConvergence();
    }
}
```

**闭锁 vs 栅栏**：闭锁等"事件"（计数归零），参与者各自走各自的路；栅栏等"彼此"（全员到齐一起走），可循环使用。

> 【演进】java.util.concurrent 的后续补充：Java 7 的 **Phaser**（多阶段、可动态增减参与方，比 CyclicBarrier 灵活）、**TransferQueue/LinkedTransferQueue**（融合 put 与 take 的交接语义）、Java 8 的 **CompletableFuture**（替代手工 Future 编排，见第 5 篇）、**StampedLock**（乐观读，见第 10 篇）。

### 案例研究：高效可伸缩的结果缓存

书 §5.6 用"计算缓存"把前几章的知识串起来——从"能跑"演进到"正确且高效"：

**版本一：HashMap + 粗粒度锁（Memoizer1）**——安全但并发差（整个 compute 串行化，第一个线程算时其他线程全在等，即使算的是不同的 key）：

```java
public class Memoizer1<A, V> implements Computable<A, V> {
    @GuardedBy("this") private final Map<A, V> cache = new HashMap<>();
    private final Computable<A, V> c;

    public synchronized V compute(A arg) throws InterruptedException {
        V result = cache.get(arg);
        if (result == null) {
            result = c.compute(arg);      // 耗时计算在锁内——不同 key 的计算也无法并行
            cache.put(arg, result);
        }
        return result;
    }
}
```

**版本二：ConcurrentHashMap（Memoizer2）**——锁没了，但引入竞态：**check-then-act 不原子**，两个线程可能同时发现 miss 并各自计算——"缓存"退化成"有时重复计算的缓存"（对可幂等的计算只是浪费，对非幂等计算就是错误）：

```java
public class Memoizer2<A, V> implements Computable<A, V> {
    private final ConcurrentHashMap<A, V> cache = new ConcurrentHashMap<>();
    private final Computable<A, V> c;

    public V compute(A arg) throws InterruptedException {
        V result = cache.get(arg);
        if (result == null) {                       // 检查
            result = c.compute(arg);
            cache.put(arg, result);                 // 写入——期间别的线程可能也在算同一个 key
        }
        return result;
    }
}
```

**关键洞察：缓存的值应该是 Future 而不是值本身**——第一个线程创建"计算中的票据"，后来者等这张票据，而不是各自重算。

**版本三：putIfAbsent + FutureTask（Memoizer3）**——"几乎正确"：重复计算的窗口从"整个计算期间"缩小到"创建 FutureTask 与 putIfAbsent 之间的间隙"：

```java
public class Memoizer3<A, V> implements Computable<A, V> {
    private final ConcurrentMap<A, Future<V>> cache = new ConcurrentHashMap<>();
    private final Computable<A, V> c;

    public V compute(final A arg) throws InterruptedException {
        Future<V> f = cache.get(arg);
        if (f == null) {                                       // 竞态窗口：两个线程都走到这里
            Callable<V> eval = () -> c.compute(arg);
            FutureTask<V> ft = new FutureTask<>(eval);
            f = cache.putIfAbsent(arg, ft);                    // 原子地"没有才放入"
            if (f == null) { f = ft; ft.run(); }               // 放入成功者负责执行
        }
        try {
            return f.get();                                    // 后来者：等第一个线程的结果
        } catch (ExecutionException e) {
            throw launderThrowable(e.getCause());
        }
    }
}
```

**最终版（Memoizer）**：在 Memoizer3 上补两处——**因取消而失败的 Future 要从缓存清除**（否则后来者永远 get 到 cancelled），get 前循环重查：

```java
public class Memoizer<A, V> implements Computable<A, V> {
    private final ConcurrentMap<A, Future<V>> cache = new ConcurrentHashMap<>();
    private final Computable<A, V> c;

    public Memoizer(Computable<A, V> c) { this.c = c; }

    public V compute(final A arg) throws InterruptedException {
        while (true) {
            Future<V> f = cache.get(arg);
            if (f == null) {
                Callable<V> eval = () -> c.compute(arg);
                FutureTask<V> ft = new FutureTask<>(eval);
                f = cache.putIfAbsent(arg, ft);
                if (f == null) { f = ft; ft.run(); }
            }
            try {
                return f.get();
            } catch (CancellationException e) {
                cache.remove(arg, f);        // 被取消的 future 必须清除——否则该 key 永远"缓存着失败"
            } catch (ExecutionException e) {
                throw launderThrowable(e.getCause());
            }
        }
    }
}
```

这个案例的**层次感**正是本书的方法论：每一步只解决一个问题（安全 → 竞态 → 原子复合 → 取消污染），每一步都指出新引入的缺陷。**组合三种工具（并发容器 + FutureTask + 原子复合操作）不需要任何显式锁**——这是"善用高层结构"的示范。

> 【演进】今天的标准答案是 `cache.computeIfAbsent(arg, c::compute)`——一行搞定上述全部语义（Java 8 起，映射函数在桶级锁下执行"没有才计算"）。但理解 Memoizer 的演进依然重要：computeIfAbsent 里不宜放超长计算（长时间占桶），高竞争下的精细方案仍会回到 FutureTask 组合。
