### 在线程中执行任务

**任务的抽象**：大多数并发程序围绕"任务（task）"组织——抽象而离散的工作单元。任务（Runnable）与执行（怎么跑、在哪个线程、几个并发）应当**分离**——这是 java.util.concurrent 的核心设计思想（Executor 框架）。

书用 Web 服务器展示三种执行策略：

**1. 串行执行**——一个线程处理所有请求：简单、理论上有"单线程的好处"（无竞态），但吞吐极差（一个慢请求阻塞所有后续请求），CPU 在 IO 等待时白白空转：

```java
// 串行 Web 服务器：线程在 handleRequest 的 IO 上阻塞时，其他连接全部排队
class SingleThreadWebServer {
    public static void main(String[] args) throws IOException {
        ServerSocket socket = new ServerSocket(80);
        while (true) {
            Socket connection = socket.accept();
            handleRequest(connection);      // 处理完一个才 accept 下一个
        }
    }
}
```

**2. 每任务一线程（thread-per-task）**——结构上最直观（"一个连接一个任务"），任务之间互不阻塞：

```java
// 每连接一线程：快速响应，但线程数不受控
class ThreadPerTaskWebServer {
    public static void main(String[] args) throws IOException {
        ServerSocket socket = new ServerSocket(80);
        while (true) {
            final Socket connection = socket.accept();
            Runnable task = () -> handleRequest(connection);
            new Thread(task).start();       // 无上限地创建线程！
        }
    }
}
```

问题：

- **线程生命周期开销**：创建/销毁有真实成本（系统调用、栈分配），请求频繁时开销可观；
- **资源消耗**：空闲线程占内存（默认栈约 1MB，可 -Xss 调整）；线程多到一定程度，GC 压力、调度开销陡增；
- **稳定性**：无界创建线程的终点是 OutOfMemoryError——**这是最容易触发的"崩溃边界"，收到多少连接就建多少线程的系统必然垮在高流量下**。

**3. 线程池（thread pool）**——固定数量的工作线程从队列取任务执行，兼得响应性与稳定性（第 7 篇详述配置）。

### Executor 框架

```java
Executor executor = anExecutor;
executor.execute(runnable);   // 提交任务，怎么执行由执行策略决定
```

Executor 虽只有一个方法，但它是**执行策略的载体**——把"任务的提交"与"任务的执行"解耦。生产者-消费者模式在 Executor 上的体现：execute 的调用者是生产者，工作线程是消费者。

**执行策略要回答的问题**（设计任何异步服务前先回答这六个）：

1. 任务在**什么线程**中执行（新建？池？调用者线程？）；
2. 任务按**什么顺序**执行（FIFO/LIFO/优先级）；
3. 可以有多少任务**并发**执行；
4. 可以有多少任务**排队**等候（有界/无界）；
5. 系统过载时需要**放弃**哪些任务（拒绝策略：抛异常？丢弃？调用者执行？）；
6. 任务开始/结束时应该执行**哪些动作（钩子：记录、统计、清理）**。

```java
// 把"每连接一线程"服务器换成 Executor：一行改动，执行策略随手可换
class TaskExecutionWebServer {
    private static final Executor exec = Executors.newCachedThreadPool();

    public static void main(String[] args) throws IOException {
        ServerSocket socket = new ServerSocket(80);
        while (true) {
            final Socket connection = socket.accept();
            Runnable task = () -> handleRequest(connection);
            exec.execute(task);             // 替代 new Thread(task).start()
        }
    }
}
```

**线程池**——执行策略的标准实现：

| 工厂方法 | 配置 | 适用 |
| --- | --- | --- |
| newFixedThreadPool(n) | 固定 n 线程，无界队列 | 负载稳定的场景 |
| newCachedThreadPool | 0 核心、上限 ∞、SynchronousQueue | 大量短命小任务 |
| newSingleThreadExecutor | 单线程 + 无界队列 | 任务需要严格串行 |
| newScheduledThreadPool(n) | 定时/周期 | 替代 Timer |

线程池的优势：复用（省创建销毁）、**限流**（活动线程有上限——过载时排队而不是垮掉）、解耦（执行策略与任务代码独立演化）。

**生命周期**：ExecutorService 的状态机——运行 → 关闭（shutdown：不再接新任务，存量跑完）/ 立即关闭（shutdownNow：中断运行中的任务，返回未执行任务列表）→ 终止（awaitTermination 等待）。支持生命周期的 Web 服务器：

```java
// 支持优雅关闭：shutdown 后 accept 的调用者负责处理 RejectedExecutionException
class LifecycleWebServer {
    private final ExecutorService exec = Executors.newCachedThreadPool();

    public void start() throws IOException {
        ServerSocket socket = new ServerSocket(80);
        while (!exec.isShutdown()) {
            try {
                final Socket connection = socket.accept();
                exec.execute(() -> handleRequest(connection));
            } catch (RejectedExecutionException e) {
                if (!exec.isShutdown()) log("task submission rejected", e);  // 关闭后的提交被拒——正常
            }
        }
    }
    public void stop() { exec.shutdown(); }    // 关闭由服务的拥有者发起（第 6 篇）
    ...
}
```

### 延迟任务与周期任务

**ScheduledThreadPoolExecutor 优于 Timer**：

```java
// Timer 的两个坑都在这段代码里
Timer timer = new Timer();
timer.schedule(new LongRunningTask(), 10);              // 慢任务会推迟后面的所有任务
timer.schedule(new ComplicatedTask(), 1000);            // 它若抛异常，TimerThread 整个挂掉
```

- Timer 只有**一个线程**执行所有定时任务——一个慢任务会推迟所有任务；一个任务抛出未捕获异常，**Timer 认为整个调度器坏了**，后续任务全部不再执行（ScheduledThreadPoolExecutor 的任务异常只影响自己）；
- Timer 对**系统时钟敏感**（用绝对时间），NTP 调整会出问题；ScheduledThreadPoolExecutor 用相对时间（nanoTime）。

结论：**新代码一律用 ScheduledThreadPoolExecutor**（或其工厂 newScheduledThreadPool / newSingleThreadScheduledExecutor）。

### 携带结果的任务：Callable 与 Future

Runnable 没有返回值、不能抛受检异常——Executor 要支撑"异步计算"，需要更强的任务抽象。**Callable\<V\>** 的 call 有返回值可抛异常；**Future** 是结果的句柄：

```java
Callable<V> task = () -> { ...; return result; };
Future<V> future = exec.submit(task);   // 提交后立刻返回 Future
V result = future.get();                // 阻塞直到完成（可带超时 get(timeout, unit)）
// future.cancel(true)：尝试取消（中断正在运行的任务）
// future.isDone() / isCancelled()
```

Future 的语义：任务的生命周期只能前进不能后退（一旦终态——完成/取消/失败——永久停留）；get 的异常路径——计算抛出的异常包装为 ExecutionException 重抛（`getCause()` 取原始异常）、任务被取消则抛 CancellationException、get(timeout) 超时抛 TimeoutException。

**ExecutorCompletionService**：把"完成"与"结果获取"解耦——完成的任务进入结果队列，take() 按完成顺序取（页面渲染的完整例子见第 7 篇）：

```java
// = Executor + 完成队列。submit 时任务包装为 QueueingFuture，完成时自动入队
ExecutorCompletionService<ImageData> completionService = new ExecutorCompletionService<>(executor);
completionService.submit(() -> downloadImage(info));
Future<ImageData> f = completionService.take();   // 谁先完成取谁（而不是按提交顺序 get）
```

### 为任务设置时限

**给异步任务一个预算**：get(timeout) / invokeAll(timeout) 超时的任务取消掉，避免无限等待把调用方拖死。页面渲染总预算（先取已完成的结果、超时的图片放弃渲染）之外，另一个经典例子——"在限定时间内检查所有邮箱"：

```java
// 有限时间内做完所有任务：并发执行 + 总预算
boolean checkMail(Set<String> hosts, long timeout, TimeUnit unit) throws InterruptedException {
    ExecutorService exec = Executors.newCachedThreadPool();
    final AtomicBoolean hasNewMail = new AtomicBoolean(false);   // 多线程安全的结果汇聚
    try {
        for (final String host : hosts)
            exec.execute(() -> { if (checkMail(host)) hasNewMail.set(true); });
    } finally {
        exec.shutdown();                          // 不再接受新任务
        exec.awaitTermination(timeout, unit);     // 最多等 timeout：到点还没完的不管了
    }
    return hasNewMail.get();
}
```

invokeAll 是它的批量版：提交一批任务，等全部完成或超时，返回各自的 Future（超时未完成的处于取消状态）：

```java
List<Callable<T>> tasks = ...;
List<Future<T>> futures = exec.invokeAll(tasks, timeout, unit);   // 返回时：要么完成，要么被取消
for (Future<T> f : futures) {
    try { process(f.get()); }                     // 被取消的 get 抛 CancellationException——按业务处理
    catch (ExecutionException e) { ... } catch (CancellationException e) { /* 超时的部分 */ }
}
```

### 任务与负载：为任务选择合适的执行策略

- 任务有类型：**短小独立**（好调度）/ **长任务**（占死线程）/ **依赖任务**（可能死锁，见第 8 篇）/ **要求独占资源**；
- 有界队列 + 拒绝策略：数据库连接、内存都有限，**无界队列会积累成灾**——用有界队列让过载"尽早失败"（caller-runs 或抛异常），好过慢慢 OOM（第 7 篇的饱和策略）。

> 【演进】书中写作时（Java 5/6）Executor 是新鲜事物；今天它已是基础。现代选择：Java 8 **CompletableFuture** 声明式编排异步任务（thenApply/thenCombine/allOf/anyOf，回调式流水线，替代手管 Future 列表）；Java 21 **虚拟线程**（`Executors.newVirtualThreadPerTaskExecutor()`）让"每任务一线程"的模式复活——阻塞式写法 + 虚拟线程的低成本阻塞，特别适合 IO 密集服务。注意虚拟线程场景**不要池化**（每任务一个虚拟线程即可），且慎用 ThreadLocal（数量巨大时内存放大）。结构化并发（Java 21+ 预览）进一步把"父任务等子任务、超时统一取消"变成语言级结构。
