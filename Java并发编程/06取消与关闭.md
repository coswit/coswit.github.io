### 取消的难题

没有"抢占式安全停止线程"的方法（stop 已废弃——直接释放锁会破坏数据一致性）。取消的本质是**协作式**的：请求方发出"请停下来"，任务在合适的时机**自愿配合**。

**取消标志位的问题**：

```java
private volatile boolean cancelled;
public void run() {
    while (!cancelled) { ... }
}
```

对可轮询的任务够用；但**任务一旦阻塞**（take/sleep/等 IO），永远检查不到标志——需要**中断**来打断阻塞。

### 中断（Interruption）

中断**不意味着停止**，只是"通知"——被中断线程自己决定怎么响应：

- `interrupt()`：发出中断（置位中断状态；若阻塞在 sleep/wait/join 会立刻抛 InterruptedException）；
- `isInterrupted()`：查询中断状态；
- `Thread.interrupted()`：查询**并清除**（静态方法，唯一清除途径）。

**处理 InterruptedException 的准则**（最重要的一节）：

1. **传递异常**：方法自己也声明 throws InterruptedException，让调用者决定；
2. **恢复中断状态**：不能抛时（Runnable 的 run 签名限制），捕获后重新置位：

```java
public void run() {
    try {
        ...阻塞调用...
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // 恢复中断状态，让上层逻辑感知
        // 收尾后退出循环
    }
}
```

3. **绝不吞掉**：捕获后什么都不做 = 剥夺调用者的取消能力，是最常见的并发 bug 之一。

### 中断策略

- 任务应该有**明确的中断策略**：收到中断是尽快退出？做完当前单元再退出？吞掉（既然这是不可取消的阶段）？
- **区分"任务的中断"与"线程的中断"**：线程池的工作线程属于池，任务不该决定"恢复中断吞掉"——那会影响池里排队的下一个任务。Executor 的标准做法：shutdownNow 对池内任务统一中断，工作线程收到中断时把中断传递给当前任务，任务自己决定行为；
- **不可中断的阻塞**（Socket IO、锁等待）：要用特定手段（关闭 socket、Future.cancel 底层机制）。

### 用 Future 取消

```java
Future<?> task = exec.submit(runnable);
// mayInterruptIfRunning=true：已在运行也中断；false 只取消还没开始的
task.cancel(true);
```

cancel 之后 get 必然抛 CancellationException。**不要在不拥有任务的地方中断线程池的工作线程**——只有任务的拥有者（创建者）才知道中断策略。

### 停止基于线程的服务

**服务的生命周期由创建它的所有者管理**（所有权原则：线程池拥有工作线程，要由池的拥有者关闭它）。

**两阶段终止模式（日志服务例子）**：

```java
// 错误：直接关闭消费者线程——队列里未写盘的日志丢失
public void stop() { ... }

// 正确：两阶段终止——先停止接收，再清空队列
public class LogService {
    private final BlockingQueue<String> queue;
    private final LoggerThread loggerThread;
    private volatile boolean shutdownRequested;   // ① 关闭请求标志
    private final PrintWriter writer;

    public synchronized void stop() {
        try {
            shutdownRequested = true;
            loggerThread.interrupt();             // ② 中断消费者（唤醒阻塞的 take）
        } finally { writer.close(); }
    }
    public void log(String msg) throws InterruptedException {
        if (!shutdownRequested)
            queue.put(msg);                       // 关闭后不再接收新日志
        else
            throw new IllegalStateException("logger is shut down");
    }
    private class LoggerThread extends Thread {
        public void run() {
            try {
                for (String msg = queue.take(); msg != null; msg = queue.take()) // 需配合毒丸
                    writer.println(msg);
            } finally { writer.close(); }
        }
    }
}
```

**毒丸（poison pill）**：往队列放一个"公认的终结对象"，消费者收到后知道该退出了——可靠的优雅关闭手段（只对无界队列/生产者数量已知时好用）。

**关闭 ExecutorService** 的标准姿势：

```java
void shutdownAndAwaitTermination(ExecutorService pool) {
    pool.shutdown();                                // 第一阶段：拒绝新任务
    try {
        if (!pool.awaitTermination(60, TimeUnit.SECONDS))
            pool.shutdownNow();                     // 第二阶段：取消剩余任务
        if (!pool.awaitTermination(60, TimeUnit.SECONDS))
            System.err.println("Pool did not terminate");
    } catch (InterruptedException ie) {
        pool.shutdownNow();
        Thread.currentThread().interrupt();         // 恢复中断
    }
}
```

### JVM 关闭

- **关闭钩子（shutdown hook）**：`Runtime.addShutdownHook(thread)`——JVM 正常关闭时执行（做资源清理）。钩子里要保证快、线程安全（并发关闭时其他线程还在跑）；
- **守护线程（daemon thread）**：JVM 退出时不等守护线程——**只应用于可随时被砍死的工作**（心跳、日志 flush 这类需要收尾的不能用守护线程）；
- 非正常终止（kill -9、Runtime.halt）不执行钩子。

### 要点小结

| 场景 | 手段 |
| --- | --- |
| 轮询型任务 | volatile 标志 / 中断状态检查 |
| 阻塞型任务 | interrupt + 正确处理 InterruptedException |
| 异步任务 | Future.cancel(true) |
| 服务优雅关闭 | 两阶段终止 / 毒丸 / shutdownNow + awaitTermination |
| 绝不做 | 吞中断、stop()、在不确定拥有权时中断线程 |
