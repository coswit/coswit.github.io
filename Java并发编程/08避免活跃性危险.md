### 死锁（Deadlock）

**死锁：两个（或更多）线程互相持有对方需要的锁，永久等待。**经典的哲学家用餐问题就是死锁的原型：每位哲学家拿起左手筷子后等右手筷子——人人都拿着一根、等另一根，永远吃不上饭。死锁的四个必要条件（操作系统课的 Coffman 条件，破坏任一即可解）：

1. **互斥**：资源一次只能被一个线程持有；
2. **持有并等待**：持着已有资源再去等新资源；
3. **不可剥夺**：已获得的资源不能被强行抢走；
4. **循环等待**：等待关系成环。

本章给出的两条主流“破坏路径”，正好对应其中两个条件（Coffman 框架是笔者借用的组织方式，原书本章并未以此展开）：

```mermaid
flowchart LR
    c2[条件：持有并等待] -- 定时 tryLock --> s1[拿不到就全部放弃重来]
    c4[条件：循环等待] -- 全局固定加锁顺序 --> s2[所有线程按同一顺序加锁]
```

（互斥一般是锁存在的意义所在，不在可破坏之列；开放调用不是针对某个条件的破坏手段，而是全程通用的最佳实践，见下文。）

**锁顺序死锁**：两个线程以不同顺序获取相同的两把锁：

```java
// 经典的左右手锁
class LeftRight {
    private final Object left = new Object();
    private final Object right = new Object();

    public void leftRight() {
        synchronized (left)  { synchronized (right) { doSomething(); } }
    }
    public void rightLeft() {                    // 顺序相反
        synchronized (right) { synchronized (left)  { doSomethingElse(); } }
    }
    // 线程A调 leftRight（拿了 left 等 right），线程B调 rightLeft（拿了 right 等 left）
    // —— 互相持有对方需要的锁，永远等待
}
```

这种“程序结构里写死的顺序”就是隐患本身；死锁要同时满足两个线程、相反顺序、时机交错才会发生——**又一次：测试通过不代表安全**。别低估概率性风险：

> A production application may perform billions of lock acquire-release cycles per day. Only one of those needs to be timed just wrong to bring the application to deadlock.
>
> 生产应用一天可能执行几十亿次加锁-解锁循环，其中只要有一次时机不对，就足以让应用死锁。

原书的驱动程序 DemonstrateDeadlock（Listing 10.4）只有 20 个线程、5 个账户、每线程 100 万次随机转账——就能在大多数系统上**很快**死锁。脚注还点出反直觉之处：持锁时间越短（这本是降争用的正确做法），测试越难暴露潜在死锁，低负载测试更是几乎无效。

**动态的锁顺序死锁**：转账时“先锁 from 再锁 to”，A→B 与 B→A 并发即死锁。看似代码里锁顺序一致（from→to），但**参数的传入顺序**使实际锁序相反：

```java
// 危险：transferMoney(myAccount, yourAccount) 与 transferMoney(yourAccount, myAccount) 并发
public void transferMoney(Account from, Account to, DollarAmount amount) {
    synchronized (from) { synchronized (to) { ... } }
}
```

**修复：定义全序**——按唯一可比的键（账户 id）排序加锁，任何调用路径下锁序都一致：

```java
// 身份哈希做全序比较 + tieLock 兜底哈希碰撞，保证任意两账户间的加锁顺序全局一致
private static final Object tieLock = new Object();
public void transferMoney(final Account fromAcct, final Account toAcct, final DollarAmount amount) {
    class Helper {
        public void transfer() {
            if (fromAcct.getBalance().compareTo(amount) < 0)
                throw new IllegalStateException();
            else {
                fromAcct.debit(amount);
                toAcct.credit(amount);
            }
        }
    }
    int fromHash = System.identityHashCode(fromAcct);   // 身份哈希：全序的可比键
    int toHash = System.identityHashCode(toAcct);
    if (fromHash < toHash) {
        synchronized (fromAcct) { synchronized (toAcct) { new Helper().transfer(); } }
    } else if (fromHash > toHash) {
        synchronized (toAcct) { synchronized (fromAcct) { new Helper().transfer(); } }
    } else {   // 哈希碰撞：先拿全局 tieLock 串行化，避免碰撞时两个线程以相反顺序加锁
        synchronized (tieLock) {
            synchronized (fromAcct) { synchronized (toAcct) { new Helper().transfer(); } }
        }
    }
}
```

（也可以拿账号这类唯一业务键做全序；全序 + tie-breaker 是通用解。“锁分解/锁分段”属于下一篇性能话题的争用优化手段——笔者引申：降低锁竞争也能减少死锁概率，但那不是本章给出的死锁解法。）

**协作对象间的死锁**

持锁期间调用**外来方法（alien method）**——外部回调可能又去获取别的锁，形成环。书中 Taxi/Dispatcher 的互相“礼貌通知”：

```java
// Taxi 与 Dispatcher 互相调用对方的方法（各自方法都同步）：
// 线程1：taxi.setLocation 锁 taxi → 调 dispatcher.notifyAvailable（锁 dispatcher）
// 线程2：dispatcher.getImage 锁 dispatcher → 调 taxi.getLocation（锁 taxi）
// 交叉进行即死锁——每个对象都“持着自己的锁伸手要对方的锁”
class Taxi {
    @GuardedBy("this") private Point location, destination;
    private final Dispatcher dispatcher;
    public synchronized void setLocation(Point location) {
        this.location = location;
        if (location.equals(destination))
            dispatcher.notifyAvailable(this);   // 持 taxi 锁调外部方法！
    }
    public synchronized Point getLocation() { return location; }
}
class Dispatcher {
    @GuardedBy("this") private final Set<Taxi> taxis;
    @GuardedBy("this") private final Set<Taxi> availableTaxis;
    public synchronized void notifyAvailable(Taxi taxi) { availableTaxis.add(taxi); }
    public synchronized Image getImage() {
        Image image = new Image();
        for (Taxi t : taxis)
            image.drawMarker(t.getLocation());  // 持 dispatcher 锁调 taxi 的同步方法！
        return image;
    }
}
```

**开放调用（open call）**：**在同步代码块之外调用外来方法**——把“构造参数、状态快照”在锁内准备好，回调/通知放到锁外：

> Calling a method with no locks held is called an open call.
>
> 调用时不持有任何锁的方法调用，就叫开放调用。——原书 §10.1.4

```java
// Taxi 的改进：锁内只更新自己的状态，通知动作放到锁外（开放调用）
// （与原书 Listing 10.6 略有出入：原书保留 synchronized 方法修饰符并嵌套同步块，
//   此处直接去掉方法级同步，语义相同且更清晰）
class Taxi {
    private Point location, destination;              // 不再在方法级同步，改为内部同步块
    private final Dispatcher dispatcher;
    ...
    void setLocation(Point location) {
        boolean reachedDestination;
        synchronized (this) {                          // 锁内：只碰自己的状态
            this.location = location;
            reachedDestination = location.equals(destination);
        }
        if (reachedDestination)                       // 锁外：调用外来方法（不会持锁进入别人的同步区）
            dispatcher.notifyAvailable(this);
    }
}

// Dispatcher 的改进：getImage 同样改为“锁内快照、锁外取值”
class Dispatcher {
    ...
    public Image getImage() {
        Set<Taxi> copy;
        synchronized (this) {                          // 锁内：拷一份引用快照
            copy = new HashSet<>(taxis);
        }
        Image image = new Image();
        for (Taxi t : copy)
            image.drawMarker(t.getLocation());         // 锁外：开放调用
        return image;
    }
}
```

开放调用既避免死锁，又缩小了锁范围——**在持锁时调用未知代码，活跃性与性能双重风险**。

> Strive to use open calls throughout your program. Programs that rely on open calls are far easier to analyze for deadlock-freedom than those that allow calls to alien methods with locks held.
>
> 尽量在整个程序中坚持使用开放调用。依赖开放调用的程序，比允许持锁调用外来方法的程序好分析得多（无死锁的论证简单得多）。

**开放调用的代价是原子性**：重构把原本原子的操作变成非原子。上面的例子可以接受——更新位置与通知 Dispatcher 本不必原子；但 getImage 从“某一时刻的完整快照”变成了“分时刻逐个取值”，语义有变化。原子性丢失不可接受时，用**协议替代锁**保护开放调用后的路径——典型场景是服务关停：锁内把状态改为“shutting down”，让想启动新操作的其他线程（包括再次发起关停的）看到服务不可用、根本不进来；然后**锁外**等待进行中的操作完成——靠协议让别的线程“不来”，而不是靠锁“进不来”。

### 死锁的避免与恢复

- **固定锁顺序**（全局排序）：适用于能明确排序的场景——把“哪些锁、按什么序获取”写进设计文档并全程遵守；
- **开放调用**：缩小锁范围，外来调用一律出锁后执行；
- **定时/可中断的锁**：tryLock(timeout) 拿不到就放弃、释放已持有的锁、退避一会儿再重试，可能恰好解开死锁条件让程序自愈（不要求全程序统一使用，局部替换也有效）。三条关键限定：①超时了**未必知道原因**——可能死锁，可能有人持锁进了死循环，也可能只是某段活动异常地慢；但至少能记录失败信息、比杀掉整个进程更体面地重启计算；②只适用于**两把锁在同一处一起获取**的场景——若锁是经方法调用逐层嵌套获取的，外层锁无法单独释放；③与数据库的死锁恢复机制不同——数据库搜索 is-waiting-for 图找环后**选定牺牲者回滚事务**（检测 + 回滚），tryLock 超时是“概率性避免”（超时 + 退避重试），独占锁换 tryLock 本身也是有代价的保险；
- **JVM 无法自动恢复死锁**（数据库可以）——死锁发生后线程永久卡住，只能重启进程；

**诊断**：

- **jstack**（或 kill -3 / jcmd Thread.print）直接输出死锁检测——JVM 的死锁探测器能识别**内置锁**的循环等待（显式 Lock 的死锁 Java 6 起也能识别，但精度有差：内置锁与获取它的**栈帧**关联，显式 Lock 只与获取它的**线程**关联；Java 5 的转储里显式锁干脆完全不显示）：

```text
Found one Java-level deadlock:
=============================
"Thread-1":
  waiting to lock monitor 0x... (object 0x..., a java.lang.Object),
  which is held by "Thread-0"
"Thread-0":
  waiting to lock monitor 0x... (object 0x..., a java.lang.Object),
  which is held by "Thread-1"
```

- **程序化检测**：ThreadMXBean.findDeadlockedThreads()（返回死锁线程 id 数组；能同时查监视器锁与 ownable synchronizer）——可以定期巡检、发现后告警：

```java
ThreadMXBean mbean = ManagementFactory.getThreadMXBean();
long[] deadlockedIds = mbean.findDeadlockedThreads();   // 非空即发现死锁循环
if (deadlockedIds != null) alert(...);
```

- **预防优于检测**：评审时先找出“会获取多把锁的位置”（尽量让这个集合小），再全局分析所有实例的锁序一致——全程开放调用能让这一分析大幅简化；平时也可以周期性抓线程转储，观察程序的锁行为（原书脚注的建议）。

**比例问题**：死锁是概率性事件——低负载测不出来，高负载 + 时机凑巧才爆发；一次死锁丢失的请求往往还伴随超时雪崩。这也是“原生锁顺序设计”要在代码评审期完成的原因。

### 资源死锁

锁之外的资源也可以死锁：两个任务各持有一个数据库连接，都等待对方的连接；线程池耗尽时互相等待对方释放线程（线程饥饿死锁，见第 7 篇——单线程池中的依赖任务是最典型形态）。资源死锁没有 jstack 式的自动检测（除非发生在锁层面），防御手段同样是：统一资源申请顺序、限制资源数、超时回退。

### 饥饿与活锁

- **饥饿（starvation）**：线程长期拿不到资源（锁被高频占用、优先级低的线程被压制）。要避免滥用线程优先级——**优先级是平台相关、无保证的提示**（不同 OS 策略不同），依赖优先级做正确性等于依赖运气；不要试图用改优先级来“调性能”，往往是把饥饿从一处搬到另一处；
- **糟糕的响应性**：两种独立成因——①后台计算任务与前台事件线程抢 CPU（对真正的后台计算**降优先级**是少数正当使用优先级的场景）；②线程长时间持锁（迭代大集合、锁内 IO），把别的线程挡在门外——把耗时逻辑移出热点锁。别用散落各处的 Thread.yield / sleep(0) 来“让一让”：其语义未定义（JLS 17.9），JVM 可以实现为 no-op；代码里到处是 yield/sleep，正是程序在抢救响应性问题的信号；
- **活锁（livelock）**：线程没阻塞却在“反复尝试-失败-重试”——消息处理失败被事务回滚并放回**队列头部**，下次取出来的还是它，永远处理不完（原书称之为**毒消息问题， poison message problem**）；或是两个互相让路的礼貌线程彼此同步退让，谁也过不去。线程在做有用功吗？没有——只是活着。这类活锁常源于**过度积极的错误恢复**：把不可恢复的错误当成可恢复的反复重试。修复：引入**随机退避**打破对称性——这正是以太网 CSMA/CD（Carrier Sense Multiple Access with Collision Detection，载波侦听多路访问/冲突检测）的经典解法，且连续冲突后还要**指数退避**；不可恢复的失败则**有限重试 + 死信队列/人工介入**；
- 原书与饥饿、活锁并列点到的还有**错过信号（missed signal）**：通知先于等待发生时会丢失——通知不“粘”（not sticky），先 notify 后 wait 的线程不会因此立即醒来。坚持“等待与通知都在持有同一把锁时进行”的规范结构即可规避。

### 小结

| 危险 | 成因 | 药方 |
| --- | --- | --- |
| 锁顺序死锁 | 相反顺序获取相同的锁 | 全序加锁（id/哈希排序 + tie-breaker） |
| 协作死锁 | 锁内调外来方法 | 开放调用（锁内备料、锁外调用） |
| 线程饥饿死锁 | 池中任务等待池的任务 | 任务与执行策略解耦、分池 |
| 资源死锁 | 连接/线程互相等待 | 统一资源获取顺序、超时 |
| 饥饿 | 优先级滥用/锁被垄断 | 避免滥用优先级（后台任务降优先级除外）；缩短持锁时间 |
| 活锁 | 互相重试/退让 | 随机退避、有限重试 |

> 【演进】死锁检测/诊断工具链比成书时完善得多：jcmd Thread.print、JFR（Java Flight Recorder）+ JDK Mission Control 可以回放分析；异步框架（Netty/CompletableFuture/协程）用“不持锁跨越异步边界”的结构天然规避了大量锁顺序问题——代价是把活跃性风险换成了“回调饿死/线程池打满”的新形态，应对思路仍是第 7 篇的任务隔离与背压。
