### 死锁（Deadlock）

**锁顺序死锁**：两个线程以不同顺序获取相同的两把锁：

```java
// 经典的左右手锁
class LeftRight {
    private final Object left = new Object();
    private final Object right = new Object();

    public void leftRight() {
        synchronized (left)  { synchronized (right) { doSomething(); } }
    }
    public void rightLeft() {                    // 顺序相反
        synchronized (right) { synchronized (left)  { doSomething(); } }
    }
    // 线程A调 leftRight（拿了 left 等 right），线程B调 rightLeft（拿了 right 等 left）
    // —— 互相持有对方需要的锁，永远等待
}
```

**动态的锁顺序死锁**：转账时"先锁 from 再锁 to"，A→B 与 B→A 并发即死锁。看似代码里锁顺序一致（from→to），但**参数的传入顺序**使实际锁序相反：

```java
// 危险：transferMoney(myAccount, yourAccount) 与 transferMoney(yourAccount, myAccount) 并发
public void transferMoney(Account from, Account to, DollarAmount amount) {
    synchronized (from) { synchronized (to) { ... } }
}
```

**修复：定义全序**——按唯一可比的键（账户 id）排序加锁：

```java
// 通过锁排序（含 tie-breaker 哈希冲突时的"第三把锁"）保证任何两个账户间的加锁顺序全局一致
private static final Object tieLock = new Object();
public void transferMoney(final Account fromAcct, final Account toAcct, final DollarAmount amount) {
    class Helper {
        public void transfer() {
            if (fromAcct.getBalance().compareTo(amount) < 0)
                throw new IllegalStateException();
            else {
                fromAcct.debit(amount);
                toAcct.credit(amount);
            }
        }
    }
    int fromHash = System.identityHashCode(fromAcct);
    int toHash = System.identityHashCode(toAcct);
    if (fromHash < toHash) {
        synchronized (fromAcct) { synchronized (toAcct) { new Helper().transfer(); } }
    } else if (fromHash > toHash) {
        synchronized (toAcct) { synchronized (fromAcct) { new Helper().transfer(); } }
    } else {   // 哈希碰撞：加锁占位锁，保证同一时刻只有一个线程在碰撞性转账中决定顺序
        synchronized (tieLock) {
            synchronized (fromAcct) { synchronized (toAcct) { new Helper().transfer(); } }
        }
    }
}
```

### 协作对象间的死锁

锁的持有期间调用**外来方法（alien method）**——外部回调可能又去获取别的锁，形成环：

```java
// Taxi 与 Dispatcher 互相"礼貌地"通知对方（各自方法都同步）：
// taxi.setLocation 锁 taxi → 调 dispatcher.notifyAvailable（锁 dispatcher）
// dispatcher.markAvailable 锁 dispatcher → 调 taxi.getLocation（锁 taxi）
// 两个线程交叉调用即死锁
```

**开放调用（open call）**：**在同步代码块之外调用外来方法**——把"构造参数、状态快照"在锁内准备好，回调/通知放到锁外：

```java
// Dispatcher 的改进：锁内只更新自己的状态，通知动作放到锁外（开放调用）
public void vehicleMoved(Taxi taxi) {
    boolean notify = false;
    synchronized (this) {                 // 锁内：只碰自己的状态
        if (taxis.contains(taxi)) {
            availableTaxis.add(taxi);
            notify = true;
        }
    }
    if (notify)                           // 锁外：调用外来方法（不会持有锁进入别人的同步区）
        listener.onAvailable(taxi);
}
```

### 死锁的避免与恢复

- **固定锁顺序**（全局排序）：适用能明确排序的场景；
- **开放调用**：缩小锁范围（本来就该"快进快出"），外来调用一律出锁后执行；
- **定时/可中断的锁**：tryLock(timeout) 拿不到就放弃、回退并释放已持有的锁，稍后重试——破坏"持有并等待"条件；
- **JVM 无法自动恢复死锁**（数据库可以），定位手段：**jstack** 直接输出 deadlock 检测（"Found one Java-level deadlock"）、ThreadMXBean.findDeadlockedThreads()。

### 资源死锁

锁之外的资源也可以死锁：两个任务各持有一个数据库连接，都等待对方的连接；线程池耗尽时互相等待对方释放线程（线程饥饿死锁，见第 7 篇）。

### 饥饿与活锁

- **饥饿（starvation）**：线程长期拿不到资源（锁被高频占用、优先级低的线程被压制）。要避免滥用线程优先级（平台相关、无保证）；
- **糟糕的响应性**：如 GUI 后台任务占用锁太久——把耗时逻辑移出热点锁；
- **活锁（livelock）**：线程没阻塞却在"反复尝试-失败-重试"（消息处理失败反复放回队列重发；两个互相让路的礼貌线程彼此同步退让）。修复：引入**随机退避**打破对称性。

### 小结

| 危险 | 成因 | 药方 |
| --- | --- | --- |
| 锁顺序死锁 | 相反顺序获取相同的锁 | 全序加锁（id/哈希排序） |
| 协作死锁 | 锁内调外来方法 | 开放调用 |
| 线程饥饿死锁 | 池中任务等待池的任务 | 任务与执行策略解耦、加池 |
| 资源死锁 | 连接/线程互相等待 | 统一资源获取顺序、超时 |
| 活锁 | 互相重试/退让 | 随机退避、有限重试 |
