### 性能与可伸缩性

**性能**与**可伸缩性（scalability）**是两个目标：

- 性能：单任务/单请求的快慢（服务时间、延迟）；
- 可伸缩性：**增加资源时吞吐量的增长能力**（加 CPU 能不能成比例地处理更多工作）。

并发程序通常在两者间权衡：为并发付出的结构开销（锁、协调、上下文切换）换取多核扩展能力。

### Amdahl 定律

**加速比受串行部分的限制**：

```
Speedup ≤ 1 / (F + (1 - F) / N)
F：串行（不可并行）比例；N：处理器数
```

- 串行 10%（F=0.1）时，无论多少核，加速比上限 10 倍；
- **结论：消除热点串行段比增加处理器有效得多**——锁的竞争、全局队列、共享计数器都是串行点。

### 线程引入的开销

- **上下文切换**：保存/恢复现场（内核态切换、缓存污染），μs 级；
- **内存同步**：锁的获取/释放（无竞争时也有指令开销，volatile 内存屏障禁止重排优化）；
- **阻塞**：挂起线程由 OS 调度（内核锁），抢不到锁的自旋 vs 挂起的权衡（自适应自旋）。

### 减少锁的竞争

**可伸缩性杀手是锁竞争（串行化）**，减少竞争的手段按效果排列：

**1. 缩小锁的范围（快进快出）**

```java
// 锁住整个方法 vs 只锁状态更新——后者串行段更短
synchronized (this) { count++; }          // 好
// 不变式允许时，把耗时 IO、计算移出锁外
```

**2. 减小锁的粒度**

- **锁分解（lock splitting）**：一把锁保护多个独立状态 → 拆成多把锁各保护一个（如一个类的读写计数与状态标志分开锁）；
- **锁分段（lock striping）**：一组独立对象数组，按哈希选锁——ConcurrentHashMap 的经典实现（默认 16 段，理论并发度 ×16）：

```java
// 锁分段的示意
private final Object[] locks = new Object[N_BUCKETS];
Object lock = locks[hash(key) % N_BUCKETS];
synchronized (lock) { ... 操作对应桶 ... }
```

**3. 避免热点域**

热点域（hot field）= 所有操作都要访问的共享点（如集中维护的计数器 size）——它把并行操作重新串行化。ConcurrentHashMap 的 size 是**估计值**（各段计数相加/无锁计数），就是主动避免热点域（牺牲精确性换伸缩性）。

**4. 替代方案**

- **读多写少 → 读写锁 ReentrantReadWriteLock**：读并行、写互斥（见第 10 篇）；
- **简单计数 → 原子变量**：CAS 无锁（见第 11 篇），竞争下的伸缩性优于锁。

### 减少上下文切换

- 任务数与线程数匹配（过多线程在等锁/等 IO 时频繁切换）；
- 无锁结构、非阻塞算法减少挂起/唤醒；
- I/O 密集与 CPU 密集任务分池隔离。

### 并发程序的测试（第 12 章精要）

- **正确性测试**：在并发压力下验证不变式与后置条件（多线程读写后校验总量/键值一致性）；
- 使用库工具：**CountDownLatch 同步开始**（所有线程就绪后同时起跑，制造真实竞争窗口）；
- **JMH/Junit 并发**：现代用 jcstress 或 JMH 的多线程模式替代书中的自制框架；
- **性能测试**：区分吞吐量（任务/秒）、延迟（分位数 p99 比平均值重要）、可伸缩性（增加核数的曲线）；
- 用 **profiler / jstack / jfr** 找竞争热点与切换热点；测试要覆盖真实负载（缓存命中/未命中、GC 影响）。

### 小结

优化顺序（先正确后性能）：

1. 正确的同步策略（不可变、封闭、并发容器）；
2. 测量（profiler、吞吐/延迟分位数）找**真正的**串行热点；
3. 缩小锁范围 → 分解/分段 → 读写锁/原子变量 → 更高级结构（异步、消息化）。
