### 显式锁 Lock

Java 5 的 java.util.concurrent.locks 提供了 synchronized 之外的锁：

```java
Lock lock = new ReentrantLock();
lock.lock();
try {
    // 临界区
} finally {
    lock.unlock();   // 必须在 finally —— 锁的释放不再自动！
}
```

**与内置锁对比的优势**：

- **获取与释放分离**（跨方法/作用域持锁）；
- **可中断的锁获取**：lockInterruptibly()——等待锁时响应中断（解决"无限等待死锁"）；
- **定时获取**：tryLock(timeout) 拿不到就放弃——死锁恢复手段；
- **非阻塞获取**：tryLock() 立刻返回；
- **公平锁**：`new ReentrantLock(true)` 按 FIFO 授予（默认非公平）。

```java
// 定时锁 + 可中断：拿不到就回退（避免死锁的关键手段）
if (lock.tryLock(1, TimeUnit.SECONDS)) {
    try { ... } finally { lock.unlock(); }
} else { /* 走备选路径 */ }
```

**公平性的代价**：公平锁要挂起/唤醒（排队），吞吐低于非公平锁（非公平允许"插队"，刚释放的锁被正好到来的线程直接拿走，省上下文切换）。只有需要避免饥饿时才用公平锁。

**选型**：**优先 synchronized**——不会忘记释放、JVM 优化好；需要 tryLock/超时/可中断/非块结构时才用 Lock。混用要小心（同一状态一半 synchronized 一半 Lock 保护 = 两种锁互不相干）。

### 读写锁 ReentrantReadWriteLock

读-读兼容、读-写/写-写互斥。适合**读多写少且持锁时间长**（缓存、配置表）：

```java
public class ReadWriteMap<K, V> {        // 读写锁包装的线程安全 Map
    private final Map<K, V> map;
    private final ReadWriteLock lock = new ReentrantReadWriteLock();
    private final Lock r = lock.readLock();
    private final Lock w = lock.writeLock();

    public V get(K key) { r.lock(); try { return map.get(key); } finally { r.unlock(); } }
    public V put(K key, V value) { w.lock(); try { return map.put(key, value); } finally { w.unlock(); } }
}
```

- **锁降级**：写锁内可以获取读锁再释放写锁（写 → 读的平滑过渡）；反之（升级）不允许——读锁中请求写锁会死锁；
- 注意：读锁"批量释放"策略（写线程等待时，新读者是否插队）影响写饥饿；竞争激烈写多时读写锁可能比独占锁更慢（维护两把锁状态的成本）。

> 【演进】Java 8 的 **StampedLock** 提供乐观读：`tryOptimisticRead()` 拿版本戳 → 读数据 → `validate(stamp)` 校验期间无写入才使用，否则升级读锁重读——读路径完全无锁，比 ReentrantReadWriteLock 更快（注意不可重入、API 更易错）。

### 构建自定义同步工具（第 14 章精要）

**条件队列（condition queue）**：让线程"等待某个条件成立"——Object.wait/notify/notifyAll 就是内置的条件队列：

```java
// 标准形式：条件谓词放在 while 中循环检查
synchronized (lock) {
    while (!conditionPredicate())   // ① 用 while 而非 if：虚假唤醒 + 条件可能再次失效
        lock.wait();                // ② 释放锁并阻塞；醒来后重新竞争锁
    doAction();                     // ③ 条件成立才执行
}

// 通知方
synchronized (lock) {
    setConditionTrue();
    lock.notifyAll();               // ④ notifyAll 优先于 notify：notify 只唤醒一个，
}                                   //    而被唤醒的可能不是等"这个条件"的线程
```

**wait/notify 的规则**：

- 条件等待必须持有锁（否则 IllegalMonitorStateException）；
- **wait 前检查条件（while）**，wait 返回后**重新检查**；
- 有状态变化就 notifyAll（唤醒错了无害，漏了致命）；
- **不要用 notify 的场合**：多个条件谓词共用一个条件队列——notify 可能唤醒错误条件的等待者；
- 单次通知 vs 通知所有 vs 信号（二值锁存、信号量等）由语义决定。

**Condition**：Lock 的条件队列——一个 Lock 可以有**多个 Condition**（每个条件谓词一个等待集），信号更精准：

```java
private final Lock lock = new ReentrantLock();
private final Condition notFull  = lock.newCondition();
private final Condition notEmpty = lock.newCondition();

public void put(E x) throws InterruptedException {
    lock.lock();
    try {
        while (count == items.length) notFull.await();   // 等"非满"
        items[putPtr] = x;
        if (++putPtr == items.length) putPtr = 0;
        ++count;
        notEmpty.signal();                               // 通知"非空"的等待者
    } finally { lock.unlock(); }
}
```

**AQS（AbstractQueuedSynchronizer）**：juc 的同步器骨架——**状态（int）+ FIFO 等待队列**，子类只需实现 tryAcquire/tryRelease 等模板方法。ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 全部基于 AQS。**Java 9 后新增 VarHandle 支持的更轻量结构**，但 AQS 依然是理解 juc 锁家族的钥匙。

### 小结

| 需求 | 工具 |
| --- | --- |
| 普通互斥 | synchronized（优先） |
| 超时/可中断/非块结构 | ReentrantLock |
| 读多写少 | ReentrantReadWriteLock / StampedLock |
| 等待条件 | wait/notifyAll（while 循环）或 Condition |
| 自定义同步器 | AQS |
