## 1. 概述

> 本篇按《深入理解Java虚拟机(第3版)》第4章结构整理。给问题定位用的工具分两层:**JDK 自带的命令行与可视化工具**(本章),以及更重的分析仪(perfetto/async-profiler 等,见 Android 目录相关笔记)。

命令行工具速查表:

| 工具 | 作用 | 一句话记忆 |
| --- | --- | --- |
| jps | 列出 JVM 进程(Java Process Status) | 类似 ps,但只看 Java |
| jstat | 收集 GC/类加载/JIT 统计(Statistics) | 最常用的 GC 观测工具 |
| jinfo | 查看/修改虚拟机参数(Configuration Info) | 运行时改 flag |
| jmap | 生成堆转储快照、对象统计(Memory Map) | OOM 排查第一站 |
| jcmd | 万能命令(virtual machine command) | JDK8+ 推荐逐步替代以上多个 |
| jstack | 线程快照(Thread Stack) | 死锁/CPU 飙高排查 |

## 2. 基础故障处理工具

### 2.1 jps:虚拟机进程状况工具

```bash
jps -l
# 2660 com.example.Main        输出主类全名
# 2661 jar                      只写 jar 说明主类在 MANIFEST 中
jps -m    # 显示传给 main 的参数
jps -v    # 显示 JVM 参数
```

### 2.2 jstat:虚拟机统计信息监视工具

```bash
jstat -gcutil 2660 1000 10
# 每 1000ms 输出一次,共 10 次,输出各区域占用百分比
```

```text
  S0     S1     E      O      M     CCS    YGC    YGCT    FGC    FGCT     GCT
  0.00 100.00  55.35  80.12  95.30  90.11   127   1.234     8    0.876    2.110
```

关键列:

| 列 | 含义 |
| --- | --- |
| S0/S1/E | 两个 Survivor 与 Eden,占各自容量的百分比 |
| O | 老年代(Old)占用百分比 |
| M/CCS | 元空间(Metaspace)与压缩类空间(Compressed Class Space) |
| YGC/YGCT | Young GC 次数 / 累计耗时(秒) |
| FGC/FGCT | Full GC 次数 / 累计耗时——**频繁增长是最危险的信号** |

### 2.3 jinfo:虚拟机配置信息工具

```bash
jinfo -flag MaxHeapSize 2660           # 查看某个 flag
jinfo -flag +PrintGCDetails 2660       # 运行时打开(仅对可写 flag 生效)
jinfo -sysprops 2660                   # 查看 System.getProperties()
```

JDK 9 后 jinfo 的部分能力(尤其修改 flag)被移到 jcmd 中。

### 2.4 jmap:内存映像工具

```bash
jmap -dump:live,format=b,file=heap.hprof 2660
# 生成堆转储快照(heap dump);live 表示先做一次 Full GC 只保留存活对象
jmap -histo 2660 | head -20
# 按类统计实例数与占用,快速找大对象
jmap -finalizerinfo 2660               # 等待 Finalizer 的对象(Finalizer 机制见第3章)
```

> 生产环境注意:`-dump` 与 `-histo`(live 版)都会触发 Stop-The-World 或 Full GC,大堆上停顿明显,谨慎在高峰期执行。

### 2.5 jstack:堆栈跟踪工具

```bash
jstack -l 2660    # -l 额外输出锁信息
```

输出中值得关注的行:

- `Found one Java-level deadlock`:jstack 会自动做**死锁检测**(dead lock detection)
- `BLOCKED (on object monitor)`:等监视器锁
- `WAITING (parking)`:LockSupport.park,线程池空闲线程的常态
- `at ...`:线程当前调用栈,CPU 飙高时多次抓栈对比找热点

### 2.6 jcmd:多功能命令行工具

JDK 8 引入的"瑞士军刀",逐步统一替代 jps/jinfo/jmap/jstack:

```bash
jcmd -l                                  # 列进程(同 jps)
jcmd 2660 VM.flags                       # 同 jinfo -flags
jcmd 2660 GC.class_histogram             # 同 jmap -histo
jcmd 2660 Thread.print                   # 同 jstack
jcmd 2660 GC.heap_dump /tmp/heap.hprof   # 同 jmap -dump
jcmd 2660 help                           # 查看全部可用命令
```

## 3. 可视化故障处理工具

- **JConsole**(Java 监视和管理控制台):基于 JMX(JMX 见 `java.lang.management`),看内存各区域曲线、线程状态、类加载、MBean;有"检测死锁"(Detect Deadlock)按钮。
- **VisualVM**:多合一故障排查工具——程序快照(概览/环境/JVM 参数)、监视(CPU/堆/类/线程曲线)、线程 dump 与死锁检测、堆 dump 分析(类实例直方图)、以及**插件体系**(Visual GC 插件可看 GC 过程动画)。
- **JHSDB**(JDK 9+):基于**服务性代理**(Serviceability Agent,SA)的调试工具,可以从进程或 core dump 中查看对象、内部数据结构,原书用它演示了手工查找 `java.lang.String` 在哪里被引用。

## 4. 排查思路串起来

一次典型的"服务变慢"排查流程:

```bash
# 1. 找到进程,确认基本情况
jps -l && jcmd 2660 VM.flags

# 2. 观察曲线:是不是 GC 问题?
jstat -gcutil 2660 1000
# → FGC 次数持续增长:老年代下不去,进入下一步

# 3. 找大对象
jcmd 2660 GC.class_histogram | head -20
# → 某业务类实例数百万:代码层泄漏(缓存未清理/监听器未注销)

# 4. 需要细节时抓快照离线分析
jcmd 2660 GC.heap_dump /tmp/heap.hprof   # 用 MAT/VisualVM 分析支配树
```

| 现象 | 首选工具 |
| --- | --- |
| 服务变慢、超时 | jstat 先看 GC,再 jstack 看线程 |
| OOM(内存溢出) | jmap/jcmd 导堆快照 + MAT 分析支配树(dominator tree) |
| CPU 100% | top -Hp 找线程 → 换算 16 进制 → jstack 对号 |
| 死锁/挂起 | jstack -l(自动死锁检测) |
| 运行时想改 flag | jcmd 2660 VM.set_flag ... |
