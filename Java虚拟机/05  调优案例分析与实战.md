## 1. 概述

> 本篇按《深入理解Java虚拟机(第3版)》第5章结构整理。本章全部是真实案例,每个案例按"**现象 → 定位 → 根因 → 措施**"展开。

调优的前提认知:

- 多数系统**不需要"调优"**,默认参数 + 合理内存布局已足够;先怀疑代码,再怀疑虚拟机
- 调优要有**量化目标**(延迟? 吞吐?),没有指标的"优化"是玄学
- 调优手段优先级:**业务代码 > JVM 参数 > 换收集器/换硬件**

## 2. 案例分析

| 案例 | 现象 | 根因 | 措施 |
| --- | --- | --- | --- |
| 高性能硬件上的部署 | 升级机器反而卡顿 | 单 JVM 堆太大,GC 停顿与周转变差 | 拆小堆做集群,或用 G1/ZGC 处理大堆 |
| 集群间同步 | 内存溢出 | 全量数据在节点间同步缓存 | 数据压缩、按需同步、放宽一致性 |
| 堆外内存溢出 | 堆没满却 OOM | NIO 的 DirectMemory 超限 | 控制直接内存上限,注意它由 Full GC 顺带清理 |
| 外部命令执行 | 系统缓慢 | Runtime.exec 每次调用 fork 新进程 | 改用 Java API 或池化控制并发 |
| JVM 进程崩溃 | 进程消失,留下 hs_err 日志 | 崩溃原因三看:hs_err、系统日志、内核日志 | 见下文崩溃排查流程 |
| 数据结构不当 | 内存占用虚高 | 包装类型装箱(HashMap&lt;Integer,Integer&gt;) | 改用原始类型数组/集合 |
| 虚拟内存交换 | GC 后长停顿 | 堆被操作系统换出(swap)到磁盘 | 关闭 swap/锁内存 |
| 安全点停顿 | 其他线程 STW 过久 | 长可数循环不进入安全点(safepoint) | 见下文,长循环用 long 计数是诱因 |

### 2.1 高性能硬件上的程序部署

32GB 内存的服务器给 JVM 分 20GB+ 大堆,通常不如"部署多个 4~8GB 的小 JVM 实例组成集群":大堆一次回收的停顿与整理成本高,且一个进程故障影响全部流量。大堆场景应选择**低延迟收集器**(G1、ZGC、Shenandoah)而不是默认的 Parallel。

### 2.2 堆外内存溢出(直接内存)

`java.lang.OutOfMemoryError: Direct buffer memory`:NIO 的 `DirectByteBuffer` 分配在堆外,不受 `-Xmx` 约束,由 `-XX:MaxDirectMemorySize` 控制;它的释放依赖 Cleaner 在 **Full GC** 时顺带清理——所以堆设得小、Full GC 不发生,堆外反而先爆。

```java
// 典型触发方式:NIO 读写
ByteBuffer buf = ByteBuffer.allocateDirect(1024 * 1024); // 堆外分配
```

### 2.3 外部命令导致系统缓慢

```java
Runtime.getRuntime().exec("some_command"); // 每次 fork 一个子进程,开销远大于普通方法调用
```

原书案例:一个"获取 Mac 地址"的功能每次都 exec 系统命令,高并发下 fork 把 CPU 耗尽。措施:能 Java 实现的(NetworkInterface.getHardwareAddress())不用外部命令;必须要用时用进程池控制并发。

### 2.4 不恰当的数据结构导致内存占用过大

`HashMap<Integer, Integer>` 存几百万个键值对,内存占用是直觉的三四倍:

```text
HashMap.Entry     32B
Integer key       16B(对象头12B + int 4B,对齐后16B)
Integer value     16B
─────────────────────────────
约 64B/条,其中真正的数据只有 8B
```

措施:改用平行数组(`int[]`),或第三方原始类型集合(如 HPPC、Eclipse Collections 的 IntIntMap)。

### 2.5 由安全点导致长时间停顿

**安全点**(safepoint):JVM 要 STW 时,必须等所有线程跑到"安全点"才能停下。可数循环(counted loop,如 `for (int i=0; i<n; i++)`)默认在循环内**不设**安全点——一个线程跑一个超长的 int 循环,其他所有线程都得等它。

现象:Minor GC 本身很短,但日志里 `stop the world` 耗时秒级;`-XX:+PrintSafepointStatistics`(旧版本)能看出是 `spin` 时间长。措施:大循环用 `long` 计数(会产生安全点检查),或 JDK 11+ 的 Loop Strip Mining。Android 上对应的坑见 `Android` 目录的 ART 相关键。

## 3. 崩溃排查与调优实战

### 3.1 JVM 进程崩溃排查流程

1. 拿到崩溃日志 `hs_err_pid<pid>.log`:看**帧栈**与**当前线程**、崩溃时正在执行的指令
2. 对照**当前线程**在做什么:是 JIT 编译、GC 还是业务代码
3. 查系统日志(`dmesg`、`/var/log/messages`):是否被 OOM Killer 杀掉(那是操作系统内存不够,不是 JVM 的 OOM)
4. 疑似虚拟机 bug 时,降级/升级 JDK 版本验证

### 3.2 实战:Eclipse 运行速度调优(方法演示)

原书用 Eclipse 自身演示了一套"测量 → 修改 → 再测量"的方法论,比结论更有价值:

| 步骤 | 手段 | 发现 |
| --- | --- | --- |
| 建立基线 | 全量启动计时、-verbose:class 统计类加载 | 启动加载类 1.5 万+ |
| 看 JIT 消耗 | -XX:+CITime | 编译时间占比可观 |
| 调整内存布局 | 增大新生代,减少 Minor GC 次数 | 停顿次数下降 |
| 换收集器 | 换成低停顿收集器 | 交互卡顿改善 |

> 方法论:**先测量、一次只改一个变量、每一步留数据**。这套流程对任何系统(包括 Android 应用)通用。
