## 1. 概述

> 本篇按《深入理解Java虚拟机(第3版)》第8章结构整理。执行引擎是虚拟机的核心部件之一:物理机的执行引擎直接建立在 CPU 指令集上,虚拟机的执行引擎则由软件实现,可以自行定制指令集与执行引擎的结构,还能执行其他语言编译后的字节码。

## 2. 运行时栈帧结构

**栈帧**(stack frame)是方法执行的基本单元:每个方法从调用到结束,对应一个栈帧在虚拟机栈中入栈出栈。栈帧里存:

| 组成 | 作用 |
| --- | --- |
| 局部变量表(Local Variable Table) | 存方法参数与局部变量 |
| 操作数栈(Operand Stack) | 字节码指令的工作区 |
| 动态连接(Dynamic Linking) | 指向运行时常量池中该方法的符号引用 |
| 方法返回地址(Return Address) | 正常/异常结束后回到哪 |
| 附加信息 | 实现相关(调试信息等) |

一个栈帧需要的内存在编译期就完全确定(写入 Code 属性的 max_locals、max_stack),运行期不再变化。

### 2.1 局部变量表

以 **变量槽 slot** 为最小单位(可以设计为 32 位/64 位)。`long`、`double` 占两个 slot,其余占一个。

**slot 复用对 GC 的影响**(原书经典实验):

```java
public static void main(String[] args) {
    byte[] placeholder = new byte[64 * 1024 * 1024];
    System.gc();   // ① placeholder 还在作用域内,但此后的代码没有再读写它——依然会被回收?
                    // 局部变量表无 slot 被复用时,placeholder 的槽位在方法结束前视为"存活"
}
```

若把代码放入 `{ byte[] placeholder = ...; }` 块中,**部分编译器实现**(如 javac 的 -gc 模式差异)会在块结束后让后续变量复用 slot,从而允许 GC;显式 `placeholder = null` 也能达到同样效果——但**不鼓励到处写 =null**,作用域粒度控制好才是正道(`System.gc()` 是否回收还取决于收集器配置)。

### 2.2 操作数栈

Java 字节码是**基于栈的指令集**:指令不操作具名寄存器,而是压栈/出栈。`iadd` 的执行过程:

```text
iload_0     // 局部变量0压栈
iload_1     // 局部变量1压栈
iadd        // 弹出两个int,相加,结果压回
istore_2    // 弹出存入局部变量2
```

### 2.3 动态连接

栈帧中持有运行时常量池中该方法的**符号引用**——一部分在类加载解析阶段就变成直接引用(**静态分派**用),另一部分每次运行时才解析(**动态分派**用),见下文方法调用。

### 2.4 方法返回地址

- 正常完成:按方法描述符把返回值压入调用者的操作数栈,PC 恢复到调用指令的下一条
- 异常完成:不产生返回值,通过**异常处理表**决定去向(方法内没有 handler 则继续出栈)

## 3. 方法调用

方法调用不是方法执行——**只确定调用哪一个方法**。

### 3.1 解析(Resolution)

编译期就完全确定、运行期不变的方法,类加载时解析成直接引用:

- `invokestatic`:静态方法
- `invokespecial`:私有方法、实例构造器、父类方法
- 加上 final 方法(`invokevirtual` 的特例),共四类"非虚方法"(non-virtual method)

### 3.2 静态分派(Static Dispatch)——重载的原理

```java
public class Overload {
    static abstract class Human {}
    static class Man extends Human {}
    static class Woman extends Human {}

    public void sayHello(Human guy) { System.out.println("hello, human"); }
    public void sayHello(Man guy)   { System.out.println("hello, man"); }
    public void sayHello(Woman guy) { System.out.println("hello, woman"); }

    public static void main(String[] args) {
        Human man = new Man();      // 静态类型 Human,实际类型 Man
        new Overload().sayHello(man);   // 输出: hello, human
    }
}
```

javac 重载决策依据**静态类型**(static type,引用的类型)而非**实际类型**(actual type,对象的类型)。经典面试题的重载优先级:char → int → long → float/double → Character → Object → 可变参数 `sayHello(char...)`,逐级放宽找最贴切的方法。

### 3.3 动态分派(Dynamic Dispatch)——重写的原理

```java
Human man = new Man();
man.sayHello();   // 调用的是 Man 的实现
```

字节码角度 `invokevirtual` 的解析过程:

1. 找到操作数栈**栈顶元素的实际类型** C
2. 在 C 中找同名同描述符的方法,找到则访问校验通过后返回直接引用
3. 没找到则**自下而上**按继承关系在父类中找
4. 都没找到抛 `AbstractMethodError`

`invokevirtual` 每次执行都要在接收者实际类型的方法表中搜索,这就是"运行时绑定"在指令层面的实现;方法表(vtable)类加载期建立,子类同签名方法覆盖同索引项,查找近似 O(1)。

### 3.4 单分派与多分派

按**一个还是多个宗量**决定方法选择:

- Java 的**编译期静态分派是多分派**:依据静态类型 + 方法参数(两个宗量)
- Java 的**运行期动态分派是单分派**:只依据接收者的实际类型(一个宗量)

即 Java 是**静态多分派、动态单分派**的语言。

### 3.5 动态类型语言支持

JDK 7 引入 `invokedynamic` 指令与 `java.lang.invoke` 包(MethodHandle),为 Groovy/JRuby/Lambda 等动态分派场景提供支持——调用点( CallSite )由引导方法(Bootstrap Method)在**第一次执行时**决定目标方法,而非像 invokevirtual 那样固定在接收者类型体系里。Lambda 表达式的底层实现即基于 invokedynamic(见第10章语法糖)。

## 4. 基于栈的解释执行引擎

**基于栈 vs 基于寄存器的指令集**(JVM 是前者,Android 的 Dalvik/ART 是后者):

| | 基于栈 | 基于寄存器 |
| --- | --- | --- |
| 可移植性 | 高(不依赖具体寄存器架构) | 低(需映射物理/虚拟寄存器) |
| 指令长度 | 短,零地址指令多 | 长,操作数带在指令里 |
| 性能 | 解释执行慢,但利于编译优化 | 指令数少,解释执行快 |

HotSpot 实际是**解释器 + 即时编译器混合**(mixed mode):解释器先跑保证启动速度,热点代码交编译器生成本地代码——这部分的展开见第11章。
