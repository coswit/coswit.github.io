## 1. 概述

> 本篇按《深入理解Java虚拟机(第3版)》第11章结构整理。后端编译器把字节码(或前端 AST)变成**本地机器码**,核心矛盾是:**编译要花时间/空间,换运行速度**。

三条路线:

| 路线 | 代表 | 特点 |
| --- | --- | --- |
| 即时编译(JIT, Just In Time) | HotSpot C1/C2、Graal | 运行时按"热点"编译,有 profile 依据,优化激进 |
| 提前编译(AOT, Ahead Of Time) | jaotc、GraalVM Native Image | 运行前编好,启动快、峰值稳,但缺运行时信息 |
| 混合模式(mixed) | HotSpot 默认 | 解释器起步 + 热点 JIT,两者互补 |

## 2. 即时编译器

### 2.1 解释器与编译器

HotSpot 内置两个(组)即时编译器:

- **C1(Client Compiler)**:编译快、优化浅——局部优化为主,追求快速见效
- **C2(Server Compiler)**:编译慢、优化深——激进优化,依赖运行 profile

**分层编译**(Tiered Compilation,JDK 8 起默认)五层:

| 层 | 状态 |
| --- | --- |
| 0 | 解释执行,采集 profile |
| 1/2/3 | C1 编译,带不同粒度的 profile 采集 |
| 4 | C2 编译,全力优化 |

热点代码先用 C1 顶着,攒够 profile 后交给 C2 出"完全体"。

### 2.2 编译对象与触发:热点探测

**热点代码**(hot spot code)两种:被多次调用的方法、被执行多次的循环体(后者以"方法回边"计数)。探测手段:

- 基于采样的(Sampling Based):周期性查线程栈顶,简单但受线程状态干扰
- **基于计数器的**(Counter Based):HotSpot 采用。每个方法两个计数器——
  - **方法调用计数器**(Invocation Counter):默认阈值 C2 约 10000 次(`-XX:CompileThreshold`)
  - **回边计数器**(Back Edge Counter):循环体回边次数,触发**栈上替换**(OSR, On Stack Replacement)——方法还在执行中就把解释执行的循环替换成编译后的代码

热度会**衰减**(decay):一段时间不达标的计数器减半(`-XX:-UseCounterDecay` 可关),避免冷方法长期占着编译产物。

### 2.3 编译过程

- **C1**:字节码 → HIR(高级中间表示,平台无关)→ LIR(低级中间表示,平台相关)→ 机器码;线性扫描寄存器分配
- **C2**:字节码 → **理想图**(Ideal Graph,sea-of-nodes)→ 全局优化 → 机器码;图着色寄存器分配。C2 的很多激进优化(下一节的逃逸分析等)都在理想图上做

编译在**后台线程**异步进行,期间方法继续解释执行,编好后整体替换。

## 3. 提前编译器(AOT)

JDK 9~10 交付了 jaotc;真正成气候的是 **GraalVM Native Image**。AOT 的优劣都来自"提前":

| 优势 | 代价 |
| --- | --- |
| 启动即峰值,无预热(serverless/CLI 场景香) | 没有运行 profile,激进优化(内联/去虚化)只能保守 |
| 不用带 JIT,运行内存更低 | 反射/动态代理/字节码生成需要**提前配置**告知(reachability metadata) |
| 编译产物封闭,攻击面小 | 类加载器玩法受限(见第9章的动态加载案例) |

> 原书(第3版)成稿时 AOT 尚在演进,评判基调是"JIT 与 AOT 长期共存、按场景分工"——至今仍然成立。

## 4. 编译优化技术

经典优化几十种,最有分量的几个:

| 技术 | 一句话 |
| --- | --- |
| 方法内联(inlining) | 优化之母:把被调方法体复制进调用点 |
| 逃逸分析(escape analysis) | 判断对象是否"逃出"方法/线程,派生三种优化 |
| 公共子表达式消除(CSE) | 相同表达式只算一次 |
| 数组边界检查消除 | 证明不越界就删掉检查 |

### 4.1 方法内联(Method Inlining)

最重要的优化——内联之后,方法体里的代码才能享受调用点的上下文信息(常量传播、去虚化):

```java
// 内联前
int add(int a, int b) { return a + b; }
int r = add(1, 2) * 3;

// 内联后(常量随之折叠)
int r = 9;
```

内联的敌人是**虚方法调用**(invokevirtual 运行期才知道目标,见第8章)。JIT 的对策:类型继承关系分析CHA + **去虚化**(devirtualization)——运行 profile 显示调用点实际只有一个实现,就按它内联,同时留一个"类型不对就退回"的守卫。

### 4.2 逃逸分析(Escape Analysis)

分析对象动态作用域:方法内不逃逸(不传出方法)/ 线程内不逃逸 / 完全不逃逸。基于此做三种优化:

```java
// 对象不逃逸 → 没必要在堆上分配
public int sum() {
    Point p = new Point(1, 2);   // 逃逸分析:未逃出方法
    return p.x + p.y;
}
```

| 派生优化 | 做法 |
| --- | --- |
| 栈上分配(stack allocation) | 标量替换的"理论目标"(HotSpot 实际未直接实现栈上分配) |
| **标量替换**(scalar replacement) | 把不逃逸对象拆成基本类型局部变量——GC 压力直接消失(实际采用的方式) |
| 锁消除(lock elision) | 不逃出线程的对象,其同步锁直接删(`-XX:+EliminateLocks`) |

```java
// 锁消除示例:stringBuffer 只在本方法使用,append 的锁被删
public String concat(String a, String b) {
    StringBuffer sb = new StringBuffer();  // 局部对象,未逃逸
    sb.append(a).append(b);                // 两次锁开销被消除
    return sb.toString();
}
```

### 4.3 公共子表达式消除(Common Subexpression Elimination)

```java
int d = (c * b) * 12 + a + (a + b * c);   // b*c 是公共子表达式
// → int t = b * c; d = t * 12 + a + (a + t);
```

### 4.4 数组边界检查消除(Array Bounds Check Elimination)

Java 每次数组访问都隐含一次越界检查(安全但费)。JIT 在能**证明**不越界时删掉它——典型如循环内以 `i < arr.length` 为条件访问 `arr[i]`;证明不了的场景用隐式异常优化:先不检查,越界了靠 CPU 陷阱信号走到异常处理。

> 观察手段:`-XX:+PrintCompilation` 看编译事件;`-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining` 看内联决策;JITWatch 可视化分析编译日志。
