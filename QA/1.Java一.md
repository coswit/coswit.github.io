## Java中 == 和 equals 和 hashCode 的区别

Java 中的数据类型可分为两类：基本数据类型和引用类型。基本数据类型包括 byte、short、char、int、long、float、double、boolean，它们之间的比较用双等号（==），比较的是**值**。引用类型包括类、接口、数组，用 == 比较时，比较的是它们在**内存中的存放地址**。对象存放在堆中，栈中存放的是对象的引用（地址），因此**== 比较的是栈中的值**（基本类型比较的就是值本身，引用类型比较的就是地址）。如果要比较堆中对象的内容是否相同，就需要重写 equals 方法了。

默认情况下（没有覆盖 equals 方法），equals 调用的是 Object 类的 equals 方法，而 Object 的 equals 方法判断的是**两个对象的内存地址是否是同一个地址**（是不是同一个对象），即与 == 等效：

```java
public boolean equals(Object obj) {  
    return (this == obj);  
} 
```

**但是**，如果类中覆盖了 equals 方法，就要根据具体代码来确定其作用了。**覆盖后一般是通过对象的内容是否相等来判断对象是否相等。**下面是 String 类重写的 equals 方法（JDK 8 实现）：

```java
public boolean equals(Object anObject) {  
    if (this == anObject) {  
        return true;  
    }  
    if (anObject instanceof String) {  
        String anotherString = (String) anObject;  
        int n = value.length;  
        if (n == anotherString.value.length) {  
            char v1[] = value;  
            char v2[] = anotherString.value;  
            int i = 0;  
            while (n-- != 0) {  
                if (v1[i] != v2[i])  
                    return false;  
                i++;  
            }  
            return true;  
        }  
    }  
    return false;  
}
```

Object#equals 方法的注释上给出了重写 equals 要遵守的规则：自反性、对称性、传递性和一致性，并且要求**重写 equals 方法时也必须重写 hashCode 方法**，以维持 hashCode 的语义：如果两个对象相等，那么它们的哈希值必须相同；反过来哈希值相同，对象却不一定相等（可能是哈希冲突）。

hashCode() 方法返回一个数值，从方法名上来看，其目的就是生成一个 hash 码，hash 码的主要用途是在**对对象进行散列的时候作为 key 输入**（如 HashMap、HashSet）。如果只重写 equals 而不重写 hashCode，相等的两个对象会得到不同的哈希值，在 HashMap / HashSet 中就会出现"重复"元素等异常行为。

在 HashMap 中定位一个元素时，先用 hashCode 定位到桶，再用 equals 在桶内精确比对，所以两者的契约必须保持一致。实际开发中推荐用 Objects.equals(a, b) 来判等，它是 null 安全的，源码就是 (a == b) || (a != null && a.equals(b))。

## int 和 Integer 的区别

Java 为每一个基本数据类型都引入了对应的包装类，并从 Java 5 开始引入了自动装箱 / 拆箱机制，使得两者可以相互转换。**所以最基本的一点区别就是**：Integer 是 int 的包装类，int 的默认值是 0，而 Integer 的默认值是 null。

两者用 == 比较时：如果一方是基本类型 int，会把 Integer 自动拆箱为 int 后再比较**值**；如果两边都是 Integer，则不会拆箱，比较的是**引用**。另外，Integer 的 IntegerCache 缓存了 -128~127 的对象，该范围内自动装箱得到的是同一个对象：

```java
Integer a = 127, b = 127;
System.out.println(a == b);      // true，缓存范围内返回同一对象
Integer c = 128, d = 128;
System.out.println(c == d);      // false，超出缓存范围，是两个不同对象
System.out.println(c.equals(d)); // true，equals 比较的是内容
```

自动装箱调用的是 Integer.valueOf(int)（缓存就发生在这一步），自动拆箱调用的是 intValue()。拆箱时要留意空指针：包装类型为 null 时参与 == 比较、算术运算，或在三目运算符中与基本类型混用（如 cond ? 1 : integerValue，会触发自动拆箱），都会抛出 NullPointerException。

因此比较 Integer 的值时，推荐使用 equals 而不是 ==。

## Java多态的理解

多态（Polymorphic）：同一个父类引用，在运行时可以指向不同的子类对象，并表现出不同的行为。

多态的存在有三个前提：

1. 要有继承关系；
2. 子类重写（Override）父类方法；
3. 父类数据类型的引用指向子类对象。

弊端：父类引用不能直接使用子类特有的成员属性和成员方法。如果非要用到，可以通过强制类型转换（向下转型）。

## String、StringBuffer、StringBuilder的区别

- **String**：字符串常量，不可变，每次拼接（如 +=）都会创建新的对象；
- **StringBuffer**：字符串变量，线程安全，拼接直接在字符串后追加；
- **StringBuilder**：字符串变量，非线程安全，拼接直接在字符串后追加。

执行效率：StringBuilder 高于 StringBuffer 高于 String。String 是不可变的，每次 += 赋值都会创建一个新对象；StringBuilder 和 StringBuffer 都是可变的，拼接时通过 append 方法在原来的基础上追加，性能比 String 高；而 StringBuffer 因为是线程安全的（方法加了 synchronized），效率低于 StringBuilder。

对于大数据量的字符串拼接，采用 StringBuffer、StringBuilder。编译器会把用 + 进行的拼接优化掉：JDK 5~8 优化为 StringBuilder.append，所以简单场景下 + 和后两者性能基本没区别（JDK 9 起进一步改为 invokedynamic 调用 StringConcatFactory）；但**在循环中拼接时，每次循环都会创建一个新的 StringBuilder**，这种场景仍需显式使用 StringBuilder。

为什么把 String 设计成不可变：String 内部用 final 修饰的数组存储（JDK 8 是 private final char[] value，JDK 9 起改为 byte[] value 以节省内存），并且 String 类本身是 final 的，无法被继承和修改。好处是：

- 可以在字符串常量池中安全地复用：String a = "abc"; String b = "abc"; a == b 为 true，两个字面量指向常量池中同一个对象，而 new String("abc") 会在堆中创建新对象；
- 天然线程安全，可以在多线程间放心共享；
- hashCode 可以缓存：String 会把第一次计算的 hash 缓存下来，作为 HashMap 的 key 时不必重复计算；
- 作为类名、文件路径、URL 等参数使用时不可被篡改，更安全。

## 内部类

Java 常见的内部类有四种：成员内部类（Member Inner Class）、静态内部类（Static Nested Class）、方法内部类/局部内部类（ Local Inner Class）和匿名内部类（Anonymous Inner Class）。

- 成员内部类（Member Inner Class）：定义在类内部，方法外，隐式持有外部类的 `this` 引用，可以随意访问外部类的所有成员（包括私有属性），必须先有外部类实例：`Outer.Inner inner = new Outer().new Inner();。

  ```java
  class Outer {
      private String msg = "Hello";
      class Inner {
          void print() {
              System.out.println(msg); // 直接拿到外部类的私有变量
              System.out.println(Outer.this.msg); // 显式写法，当变量名冲突时使用
          }
      }
  }
  ```

- 静态内部类（Static Nested Class）：使用 `static` 修饰的类，不持有外部类的引用。只能访问外部类的静态成员（变量和方法），不能直接访问外部类的非静态成员。

  静态内部类的设计意图，只是为了方便管理类结构而定义。

  ```java
  class Outer {
      private static String staticMsg = "静态";
      private String instanceMsg = "实例";
      static class StaticInner {
          void show() {
              System.out.println(staticMsg); // ✅ 可以访问
              // System.out.println(instanceMsg); // ❌ 编译报错
          }
      }
  }
  ```

- 方法内部类/局部内部类（ Local Inner Class）：定义在方法体内。**作用域仅限于该方法内**。方法执行完，该类就失效了。

  ```java
  class Outer {
      void method(final String param) { // 或 String param 且不修改
          String local = "局部变量";
          class LocalInner {
              void show() {
                  System.out.println(local); // ✅ 可以访问（JDK8后自动加final语义）
                  // local = "修改"; // ❌ 如果在这里修改，编译报错（失去 effectively final）
              }
          }
          new LocalInner().show();
      }
  }
  ```

- 匿名内部类（Anonymous Inner Class）：没有显式类名的局部内部类，通常在定义的同时直接实例化，用于一次性继承抽象类或实现接口。同局部内部类，能访问外部类成员和方法内的 `effectively final` 变量。

  ```java
  // 经典用法：代替繁琐的实现类
  Runnable task = new Runnable() {
      @Override
      public void run() {
          System.out.println("匿名内部类执行");
      }
  };
  
  // Java 8后，函数式接口多被 Lambda 替代，但匿名类在需要继承普通类时依然无可替代
  ArrayList<String> list = new ArrayList<String>() { // 创建 ArrayList 的匿名子类
      {
          add("初始化块"); // 实例初始化块
      }
  };
  ```

问题：

1. **内存泄漏（最严重风险）**：
   - **非静态内部类**隐式持有外部类引用。如果内部类中启动了耗时线程（或注册了监听器）且未及时销毁，**外部类无法被GC回收**，导致内存泄漏。
   - **解决方法**：如果内部类不需要访问外部类实例属性，**务必将其声明为 `static`**（静态嵌套类）。
2. **序列化问题**：
   - 非静态内部类默认持有外部引用，**强烈不建议序列化**，否则会导致序列化异常或难以调试的错误。如果需要序列化，使用静态嵌套类。
3. **为什么局部变量要加 `final`？**
   - 因为内部类的生命周期可能比方法长（比如线程），方法执行完栈帧销毁了，但内部类对象还在堆里。为了能让内部类访问到变量的值，Java 底层会**拷贝一份变量值**存到内部类中。为了防止拷贝值和原始值不一致导致逻辑混乱，强制要求该变量不可变（`final`/`effectively final`）。
4. **字节码视角**：
   - 每个内部类编译后都会生成独立的 `.class` 文件，如 `Outer$Inner.class`。非静态内部类的构造函数会被编译器偷偷添加一个外部类对象的入参。

##  抽象类和接口

| 对比维度       | 抽象类 (Abstract Class)             | 接口 (Interface)                                             |
| :------------- | :---------------------------------- | :----------------------------------------------------------- |
| **关键字**     | `extends`（单继承）                 | `implements`（多实现）                                       |
| **构造方法**   | 可以有                              | 不能有                                                       |
| **成员变量**   | 支持各种访问修饰符的变量（非final） | 默认且只能是 `public static final`（常量）                   |
| **普通方法**   | 可以有具体实现                      | Java 8 后允许 `default`/`static` 方法有实现；Java 9 允许私有方法 |
| **访问修饰符** | 任意（private/protected/public）    | 方法默认且强制为 `public`（Java 9 私有方法除外）             |

**设计层面：**

- **抽象类（Is-A 关系）**：强调 **“是什么”**。它用于定义一类事物的**共同本质**。负责**抽象出状态和通用逻辑**，用于代码复用。
- **接口（Can-Do 关系）**：强调 **“能做什么”**。负责**抽象出行为**，是面向接口编程的核心。


##  Serializable 和 Parcelable 的区别

| **特性**         | **Serializable**                                 | **Parcelable**                                               |
| ---------------- | ------------------------------------------------ | ------------------------------------------------------------ |
| **出身与标准**   | Java 原生接口（`java.io.Serializable`）          | Android 特有接口（`android.os.Parcelable`）                  |
| **核心机制**     | 依赖 **反射 (Reflection)** 和大量的 **I/O 操作** | 直接写入 **内存缓冲区 (Parcel)**，使用高效的 Native/IPC 优化 |
| **性能/速度**    | 较慢，频繁创建临时对象，易引发 GC                | **非常快**（通常比 `Serializable` 快 10 倍以上）             |
| **内存开销**     | 较高（会产生较多垃圾对象）                       | 极低                                                         |
| **实现难度**     | 极其简单（只需 `implements Serializable`）       | 需编写样板代码（模板/模板生成，或使用 `@Parcelize` 注解）    |
| **主要应用场景** | **磁盘存储**（文件、数据库）或 **网络传输**      | **进程间通信 (IPC)**、`Activity`/`Fragment` 传递参数         |

**最大的区别就是存储媒介的不同：**Serializable 使用 IO 读写存储在硬盘上，Parcelable 是直接在内存中读写。内存读写速度远大于 IO 读写，所以 Parcelable 更加高效。另外 Serializable 在序列化过程中会产生大量的临时变量，会引起频繁的 GC，效率低下。

补充：实现 Serializable 时建议显式声明 private static final long serialVersionUID。反序列化时会比对该值与本地类的版本号，不一致就抛 InvalidClassException；如果不显式声明，编译器会根据类结构自动生成，一旦类发生改动，旧数据的反序列化就会失败。


## 闭包和局部内部类的区别

**闭包（Closure）** 是一个概念：函数（代码块）连同它所捕获的外部变量（词法环境）构成的整体。被捕获变量的生命周期会随闭包延长——即使定义它的方法已经返回，闭包中仍能访问这些变量。

**局部内部类** 是 Java 的一种语言结构：定义在方法或作用域内部的类。Java 中没有独立的函数类型，局部内部类 / 匿名内部类（JDK 8 后还有 lambda）访问方法的局部变量，实际就是靠"捕获"实现的，可以看作 Java 对闭包的一种受限模拟。

两者的区别：

- 局部内部类捕获的局部变量必须是 final（JDK 8 起要求 effectively final，即事实上不再修改），只能读取值，不能修改变量本身；而真正的闭包（如 Kotlin、JavaScript 中）捕获的是变量本身，可以在闭包内修改它的值；
- 捕获引用类型变量时，局部内部类捕获的是引用的拷贝，不能改变引用的指向，但仍可以修改对象内部的内容；
- Kotlin 的 lambda / 匿名函数是真正的闭包，可以直接读写外层局部变量，这也是它比 Java lambda（要求 effectively final）更灵活的地方。

一句话总结：闭包是"函数 + 捕获的环境"的概念，局部内部类是 Java 中实现类似闭包效果的语言结构；由于 final 的限制，它只能实现"值捕获"的受限闭包。

##  String转换成Integer的方式以及原理

String 转 int：

```java
int i = Integer.parseInt(s);
int i = Integer.valueOf(s).intValue(); // valueOf 内部就是调用 parseInt，并对 -128~127 启用缓存
```

int 转 String：

```java
String s = String.valueOf(i); // 内部调用 Integer.toString(i)
String s = Integer.toString(i);
String s = i + "";            // JDK 8 及之前优化为 StringBuilder 拼接，JDK 9 起改为 invokedynamic
```

parseInt 的核心原理是：从高位到低位逐位取字符，`result = result * radix + digit`。为了统一处理正数和负数的溢出判断，内部全程用负数累加（int 的负数范围比正数大 1），最后再取反返回。

下面是 `Integer.parseInt(String s, int radix)` 的源码（注释解释了溢出判断的技巧）：

```java
public static int parseInt(String s, int radix) throws NumberFormatException {
    // 前置校验：s 不能为 null；表示进制的 radix 要在（2~36）范围内
    if (s == null) {
        throw new NumberFormatException("null");
    }
    if (radix < Character.MIN_RADIX) {
        throw new NumberFormatException("radix " + radix +
                                        " less than Character.MIN_RADIX");
    }
    if (radix > Character.MAX_RADIX) {
        throw new NumberFormatException("radix " + radix +
                                        " greater than Character.MAX_RADIX");
    }

    int result = 0; // 结果，在下面的计算中一直是负数：
                    // 假如字符串是正数 "7"，那么返回之前 result 保存的是 -7，
                    // 这样是为了保持正数和负数在计算上的一致性
    boolean negative = false;
    int i = 0, len = s.length();

    // limit 默认初始化为最大正整数的负数。
    // 假如字符串表示的是正数，那么 result（返回之前一直是负数形式）
    // 就要和这个值比较，判断是否溢出
    int limit = -Integer.MAX_VALUE;
    int multmin;
    int digit;

    if (len > 0) {
        // 首先判断第一个位置是否含有正负号
        char firstChar = s.charAt(0);
        if (firstChar < '0') { // Possible leading "+" or "-"
            if (firstChar == '-') {
                negative = true;
                // 负号的情况下，判断溢出的边界就变成了整数的最小值
                limit = Integer.MIN_VALUE;
            } else if (firstChar != '+') {
                throw NumberFormatException.forInputString(s);
            }
            if (len == 1) // Cannot have lone "+" or "-"
                throw NumberFormatException.forInputString(s);
            i++;
        }

        multmin = limit / radix;
        // multmin 用来判断 result 接收下一个数字后会不会溢出。
        // 拿正数举例（result、multmin 在计算中都是负数）：假设上限是 21，
        // 那么 multmin = 21 / 10 = 2；如果此时 result 是 3，下一个数字来了，
        // result 即将变成 result * 10 + digit，肯定大于 21，即溢出。
        // 溢出的值在 int 里是保存不下来的，不可能先计算出溢出后的 result
        // 再去与最大值比较，所以要先比较 result < multmin
        // （说明 result * radix 后必然超出 limit）
        while (i < len) {
            // Accumulating negatively avoids surprises near MAX_VALUE
            digit = Character.digit(s.charAt(i++), radix);
            if (digit < 0) {
                throw NumberFormatException.forInputString(s);
            }
            // 溢出判断一：result 统一用负数计算，所以用小于号。
            // 从正数的角度看就是：result > multmin 时，result * radix 肯定溢出
            if (result < multmin) {
                throw NumberFormatException.forInputString(s);
            }
            result *= radix;
            // 溢出判断二：相当于正数角度的 result + digit > limit。
            // 但不能先加再比较，否则结果本身已经溢出、判断不出溢出了，
            // 所以写成 result < limit + digit，很巧妙
            if (result < limit + digit) {
                throw NumberFormatException.forInputString(s);
            }
            result -= digit; // result 是负数，减去 digit 相当于绝对值相加
        }
    } else {
        throw NumberFormatException.forInputString(s);
    }
    return negative ? result : -result; // 正数就返回 -result（取反回来）
}
```

## 设计原则 S.O.L.I.D

| 简写 | 原则         |
| ---- | ------------ |
| SRP  | 单一职责原则 |
| OCP  | 开放封闭原则 |
| LSP  | 里氏替换原则 |
| ISP  | 接口分离原则 |
| DIP  | 依赖倒置原则 |

**单一职责原则**

> 修改一个类的原因应该只有一个

换句话说就是让一个类只负责一件事，当这个类需要做过多的事情的时候，就需要分解这个类。

如果一个类承担的职责过多，就等于把这些职责耦合在了一起，一个职责的变化可能会削弱这个类完成其它职责的能力。

**开放封闭原则**

> 类应该对扩展开放，对修改关闭

扩展就是添加新功能的意思，因此该原则要求在添加新功能时不需要修改代码。

符合开闭原则最典型的设计模式是装饰者模式，它可以动态地将职责附加到对象上，而不用去修改类的代码。

**里氏替换原则**

> 子类对象必须能够替换掉所有父类对象

继承是一种 IS - A 关系，子类需要能够当成父类来使用，并且需要比父类更特殊。

如果不满足这个原则，那么各个子类的行为上就会有很大差异，增加继承体系的复杂度。

**接口分离原则**

> 不应该强迫客户依赖于它们不用的方法

因此使用多个专门的接口比使用单一的总接口更好。

**依赖倒置原则**

> 高层模块不应该依赖于低层模块，两者都应该依赖于抽象。
>
> 抽象不应该依赖于细节，细节应该依赖于抽象。

高层模块包含一个应用程序中重要的策略选择和业务模块，如果高层模块依赖于低层模块，那么低层模块的改动就会直接影响到高层模块，从而迫使高层模块也需要改动。

依赖于抽象意味着：

* 任何变量都不应该持有一个指向具体类的指针或者引用
* 任何类都不应该从具体类派生
* 任何方法都不应该覆写它的任何基类中的已经实现的方法

除了 S.O.L.I.D 之外，还有两个常见的设计原则：

* **迪米特法则（Law of Demeter，最少知识原则）**：一个对象应该对其他对象有最少的了解，只与"直接的朋友"（自己的成员变量、方法的参数和返回值等）通信，不依赖陌生对象，以降低耦合；
* **合成复用原则（Composite Reuse Principle）**：优先使用对象的组合 / 聚合关系来达到复用，而不是继承。

#### 三大特性

**封装**

利用抽象数据类型将数据和基于数据的操作封装在一起，使其构成一个不可分离的独立实体。数据被保护在抽象数据类型的内部，尽可能的隐藏内部细节，只保留一些对外接口使之与外部发生联系。用户无需知道对象内部的细节，但可以通过对象对外提供的接口来访问该对象。

优点：

* 降低耦合：可以独立开发、测试、优化和修改等
* 减轻维护的负担：可以更容易的被程序猿理解，并且在调试的时候可以不影响其他模块
* 有效地调节性能：可以通过剖析确定哪些模块影响了系统的性能
* 提高软件的可重用性
* 降低了构建大型系统的风险：即使整个系统不可用，但是这些独立的模块却有可能是可用的

**继承**

继承实现了 IS - A 关系，继承应该遵循里氏替换原则，子类对象必须能够替换掉所有父类对象。

**多态**

多态分为编译时多态和运行时多态。编译时多态主要指方法的重载，运行时多态指程序中定义的对象引用所指向的具体类型在运行期间才确定。

运行时多态有三个条件：

* 继承
* 覆盖
* 向上转型

重载和重写的对比：

|          | 重载（Overload）             | 重写（Override）                        |
| -------- | ---------------------------- | --------------------------------------- |
| 范围     | 同一个类中                   | 父子类之间                              |
| 参数列表 | 必须不同                     | 必须相同                                |
| 返回类型 | 可以不同（不能仅靠它区分）   | 相同或返回其子类型（协变返回，JDK 5 起）|
| 访问权限 | 无限制                       | 不能比父类更严格                        |
| 异常     | 无限制                       | 不能抛出更宽的受检异常                  |
| 绑定时机 | 编译期（静态分派）           | 运行期（动态绑定）                      |

##  对象拷贝理解？深拷贝、浅拷贝的区别？

首先要明白为什么需要使用克隆？

克隆的对象可能包含一些已经修改过的属性，而 new 出来的对象的属性都还是初始化时候的值，所以当需要一个新的对象来保存当前对象的"状态"时，就需要克隆了。

那如何实现对象克隆呢？有两种方式：

1. 实现 Cloneable 接口并重写 Object 类中的 clone() 方法；
2. 实现 Serializable 接口，通过对象的序列化和反序列化实现克隆，可以实现真正的深度克隆。

深拷贝和浅拷贝的区别是什么？

- **浅拷贝**：当对象被复制的时候只复制它本身和其中包含的值类型的成员变量，而引用类型的成员变量只是复制了引用，并没有复制引用指向的对象。
- **深拷贝**：除了对象本身被复制外，对象所包含的所有引用类型的成员变量也将被复制。

浅拷贝的效果可以用代码直观地看到：

```java
Person copy = (Person) person.clone();
copy.address == person.address; // true——两个对象共享同一个 address 引用
```

Object 提供的 clone() 方法默认是浅拷贝。如果想实现深拷贝，就需要对象所包含的引用类型的成员变量也实现 Cloneable 接口并重写 clone() 方法，或者实现 Serializable 接口通过序列化来实现。

##  Enumeration 和 Iterator 的区别？

- 接口不同

  Enumeration 只能读取集合数据，而不能对数据进行修改；Iterator 除了读取集合的数据之外，也能对数据进行删除操作。Enumeration 已经被 Iterator 取代了，之所以没有被标记为 Deprecated，是因为在一些遗留类（Vector、Hashtable）中还在使用。

  ```java
  public interface Enumeration<E> {
      boolean hasMoreElements();
      E nextElement();
      default Iterator<E> asIterator() {
          return new Iterator<>() {
              @Override public boolean hasNext() {
                  return hasMoreElements();
              }
              @Override public E next() {
                  return nextElement();
              }
          };
      }
  }
  ```

  ```java
  public interface Iterator<E> {
      boolean hasNext();
      E next();
      default void remove() {
          throw new UnsupportedOperationException("remove");
      }
      default void forEachRemaining(Consumer<? super E> action) {
          Objects.requireNonNull(action);
          while (hasNext())
              action.accept(next());
      }
  }
  ```

- Iterator 支持 fail-fast 机制，而 Enumeration 不支持

  Enumeration 是 JDK 1.0 添加的接口。使用到它的类包括 Vector、Hashtable 等，Enumeration 存在的目的就是为它们提供遍历接口。

  Iterator 是 JDK 1.2 才添加的接口，它是为 HashMap、ArrayList 等集合提供的遍历接口。Iterator 是支持 fail-fast 机制的。

  Fail-fast 机制是指 Java 集合（Collection）中的一种错误机制。当多个线程对同一个集合的内容进行操作时，就可能会产生 fail-fast 事件。例如：当某个线程 A 通过 Iterator 去遍历某集合的过程中，若该集合的内容被其他线程所改变了，那么线程 A 访问集合时，就会抛出 ConcurrentModificationException 异常，产生 fail-fast 事件。

fail-fast 的实现原理：集合内部用 modCount 字段记录结构性修改的次数，Iterator 创建时把它记录到 expectedModCount，每次调用 next() / remove() 前都会检查两者是否一致，不一致就立即抛出 ConcurrentModificationException。

注意：for-each 循环作用在集合上时，底层就是通过 Iterator 实现的（数组则是按下标遍历），所以在 for-each 中直接 add / remove 集合元素同样会触发 fail-fast。正确的删除方式是使用 iterator.remove()（它会在删除后同步 expectedModCount），并发场景则使用 CopyOnWriteArrayList、ConcurrentHashMap 这类并发容器。
