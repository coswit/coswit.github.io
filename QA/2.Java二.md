### 1. 哪些情况下的对象会被垃圾回收机制处理掉？

**判定可回收**：现代 JVM 用**可达性分析**——从 GC Roots（栈上的局部变量、静态字段、常量引用、JNI 引用等）出发向下搜索，不可达的对象即为可回收对象（早期引用计数法无法处理循环引用，已不采用）。

**引用强度影响回收时机**：软引用（内存不足时回收，适合缓存）、弱引用（下次 GC 必回收，ThreadLocal 的 key）、虚引用（唯一作用是回收时收到通知）。

**分代收集**：对象分代存放，不同代用不同算法：

- 新生代（Eden + 两个 Survivor）：朝生夕死，**复制算法**，Minor GC；
- 老年代：存活久，**标记-清除 / 标记-整理**，Full GC；
- 方法区：JDK 8 起永久代被移除，改为**元空间（Metaspace，本地内存）**，类元数据基本不再被 GC 管辖（类卸载条件苛刻）。

对象晋升老年代的途径：年龄达到阈值（默认 15）、大对象直接进老年代、动态年龄判断。

常见收集器：CMS（并发标记清除，低停顿，JDK 14 移除）、G1（Region 化、可预测停顿，JDK 9+ 默认）、ZGC/Shenandoah（亚毫秒停顿）。

Android 的 ART：并发复制（CC）、并发标记清除（Concurrent Mark Sweep），配合后台线程做 compaction。

### 2. 讲一下常见的编码方式？

编码的原因：计算机存储的最小单元是字节（8 bit，0-255），而要表示的字符远超 256 个，必须规定 char 到 byte 的转换规则。

- **ASCII**：128 个字符，一个字节的低 7 位。0-31 是控制字符（回车、换行），32-126 是可打印字符；
- **ISO-8859-1**（Latin-1）：在 ASCII 基础上扩展西欧字符，单字节，覆盖 256 个，应用广泛；
- **GB2312 / GBK**：双字节编码表示汉字（GBK 是 GB2312 的超集）；
- **UTF-16**：Unicode 的一种存取形式。基本多文种平面（BMP）内的字符用 2 字节，**增补平面字符用代理对（4 字节）**，所以它并不是严格定长；
- **UTF-8**：变长编码，按字符的 Unicode 码点分为 1~4 字节（ASCII 兼容 1 字节、常用中文 3 字节、emoji 4 字节），是网络传输与文件存储的事实标准。

参考自：[几种常见的编码格式](https://www.cnblogs.com/mlan/p/7823375.html)

### 3. UTF-8编码中中文占几个字节，int型几个字节？

UTF-8 中文：**常用汉字 3 字节**（Unicode BMP 的 CJK 区）；Emoji、生僻字等增补平面字符 4 字节。UTF-8 单字符最多 4 字节（RFC 3629）。作为对比：GBK 中文 2 字节、UTF-16 中文 2 字节（代理对 4 字节）。int：**4 字节（32 位）**。

### 4. 静态代理和动态代理的区别，什么场景使用？

**静态代理**：代理类在编译期就写死，目标接口的每个方法都要在代理类中显式转发。简单直接，但接口方法多时样板代码爆炸，一个代理只能服务一个接口。

**动态代理**：运行时动态生成代理类。JDK 动态代理基于**接口**——`Proxy.newProxyInstance` 生成实现了一组接口的 `$Proxy0` 类，方法调用统一转发到 `InvocationHandler.invoke`：

```java
public interface IUserService { void save(String name); }

IUserService target = new UserServiceImpl();
IUserService proxy = (IUserService) Proxy.newProxyInstance(
        target.getClass().getClassLoader(),
        target.getClass().getInterfaces(),
        (p, method, args) -> {
            System.out.println("before: " + method.getName());  // 增强逻辑
            Object result = method.invoke(target, args);        // 反射调用目标
            System.out.println("after");
            return result;
        });
proxy.save("test");
```

**CGLIB 动态代理**：基于**继承**——生成目标类的子类并重写非 final 方法（FastClass 机制避免反射），不要求接口；Spring 默认对有接口的类用 JDK 代理、无接口用 CGLIB。

**使用场景**：AOP（Spring 事务、日志、权限）、Retrofit（接口方法 → HTTP 请求的动态代理是核心原理）、ARouter/路由框架、懒加载 ORM、Hook 系统服务（Android 动态代理替换 AMS/INotificationManager）。

### 5. Java的异常体系

异常简介：异常是阻止当前方法继续执行的问题，如文件找不到、网络连接失败、非法参数等。发现异常的理想时期是编译阶段，但编译阶段不能找出所有异常，余下的问题必须在运行期间处理。

Java 中的异常分为可查异常和不可查异常。

**可查异常（编译时异常）**：编译器在编译时即可发现，程序运行时很容易出现的状况，必须 try-catch 捕获或 throws 声明抛出，否则编译无法通过，如 IOException、SQLException 及自定义 Exception。

**不可查异常**：包括**运行时异常**和**错误**。异常能被程序本身处理，错误无法处理。运行时异常是程序运行时才暴露的问题（空指针、类转换、数组越界等），由程序员决定是否捕获。错误表示 JVM 层面的严重问题（虚拟机错误、动态连接失败等），与代码编写者的操作基本无关。

**层次结构**：Throwable → Error / Exception；Exception → RuntimeException（非受检）与其他受检异常。异常都是对象，是 Throwable 子类的实例。

**异常处理机制**：异常发生时，在堆上 new 一个异常对象，然后要么 throw 抛出（终止当前执行路径，沿调用栈寻找 catch），要么 try-catch 就地捕获。

**throws 与 throw**：throws 声明方法可能产生的异常；throw 抛出异常对象并退出当前方法。

**finally 清理**：finally 不是为了释放内存（有 GC），而是释放文件、网络连接等资源；无论是否捕获异常都会执行。更好的资源关闭方式是 try-with-resources（Effective Java 条目 9）。

参考自：[https://www.jianshu.com/p/ffca876ce719](https://www.jianshu.com/p/ffca876ce719)

### 6. 谈谈你对解析与分派的认识

**解析（Resolution）**：编译期/类加载期就能确定的符号引用替换，适合静态方法、私有方法、final 方法、构造器——它们的调用目标唯一，`invokestatic / invokespecial` 直接绑定。

**静态分派（Static Dispatch）**：**方法重载**的选择。按变量的**静态类型（编译期类型）**在编译期确定调用哪个重载版本：

```java
Human man = new Man();
// 静态类型 Human，实际类型 Man
sayHello(man);          // 调用 sayHello(Human) —— 重载看静态类型
```

**动态分派（Dynamic Dispatch）**：**方法重写**的选择。`invokevirtual` 在运行期按**实际类型**查找虚方法表（vtable）确定执行版本——多态的底层实现（见第 8 题）。子类覆写的方法在 vtable 中替换父类槽位，因此实际类型优先。

一句话：**重载是静态分派（编译期、看静态类型），重写是动态分派（运行期、看实际类型）**。

参考：[静态分派与动态分派](https://www.jianshu.com/p/1976b01c07d2)

### 7. 修改对象A的equals方法的签名，那么使用HashMap存放这个对象实例的时候，会调用哪个equals方法？

HashMap 内部（putVal/getNode）调用的是 `key.equals(k)`，编译期静态绑定到 **`equals(Object)` 这个签名**。如果只是把 equals 的参数改成别的类型（如 `equals(MyType)`），那不是重写而是重载——Object 的 `equals(Object)` 并没有被覆盖，HashMap 调用的就是 Object 的默认实现（引用比较）。结果是两个"内容相等"的对象会被当成不同的 key。教训：覆写 equals 必须保持 `equals(Object)` 签名，并加 @Override 让编译器兜底。

### 8. Java中实现多态的机制是什么？

靠**运行期动态绑定**：编译期编译器按引用的静态类型校验方法存在，生成 `invokevirtual` 指令；运行期 JVM 根据对象的**实际类型**在虚方法表（vtable）中确定执行哪个版本。三个前提：继承、覆写、向上转型。注意：字段没有多态（按编译期类型访问）；static / private / final 方法在编译期绑定，不参与多态。详见 1.Java一 第 4 题。

### 9. 如何将一个Java对象序列化到文件里？

让类实现 Serializable 并用 ObjectOutputStream / ObjectInputStream：

```java
public class User implements Serializable {
    private static final long serialVersionUID = 1L;
    public String name;
}

// 写入文件
try (ObjectOutputStream oos = new ObjectOutputStream(
        new FileOutputStream("user.txt"))) {
    oos.writeObject(new User());
}

// 从文件读回
try (ObjectInputStream ois = new ObjectInputStream(
        new FileInputStream("user.txt"))) {
    User user = (User) ois.readObject();
}
```

要点：显式声明 serialVersionUID（版本对齐）；静态与 transient 字段不参与序列化；反序列化**不调用构造器**，因此 readObject 需要防御性校验（Effective Java 条目 85-90 详述了序列化的安全陷阱）。

### 10. 说说你对Java反射的理解

反射：在运行状态中，对任意一个类都能知道其所有属性和方法；对任意对象都能调用其任意方法和属性。这种动态获取信息与动态调用对象方法的能力称为反射机制。

**原理**：每个类编译为 .class 文件，被 ClassLoader 加载后 JVM 在内存中生成唯一的 Class 对象，承载类的全部信息（父类、接口、构造器、方法、字段）。拿到 Class 引用即拿到 Method / Field / Constructor 的一切。

**典型场景**：

- 访问隐藏 API / 修改系统未开放的逻辑（Android 中常见，注意非 SDK 接口限制）；
- 自定义注解在运行时的提取（APT 之外的处理方式）；
- 动态加载与插件化、模块化（DexClassLoader、65k 时代的 multidex 方案）；
- 框架基石：Spring 依赖注入、Retrofit、Gson（注解 + 反射）。

**代价**：编译期类型检查丧失、代码冗长、性能低于直接调用（现代 JVM 对反射已有一定优化）。原则：能不用就不用，必须用时"反射只创建、接口来访问"（Effective Java 条目 65）。

参考自：[Java反射以及在Android中的特殊应用](https://www.jianshu.com/p/8f394d90a85c)

### 11. 说说你对Java注解的理解

注解（Annotation）是 JDK 5 引入的元数据机制：以 `@interface` 定义的接口（编译后继承 java.lang.annotation.Annotation），为程序元素（包、类、方法、字段、参数）附加"名=值"形式的元数据。**注解本身不影响代码执行**，需要由工具（编译器、APT、运行时反射代码）读取并处理。

**定义与使用**

```java
@Retention(RetentionPolicy.RUNTIME)   // 运行时可读取
@Target(ElementType.METHOD)           // 只能标注方法
public @interface MyTag {
    String name() default "默认";      // 成员以"无形参方法"声明，可给默认值
    int age() default 0;
}

@MyTag(name = "test", age = 1)
public void m() { }
```

无成员的注解叫标记注解（@Override）；有成员的提供更多元数据。

**四个元注解**

| 元注解 | 作用 |
| --- | --- |
| @Retention | 保留阶段：SOURCE（仅源码，编译丢弃）、CLASS（默认，进 class 文件运行时不可见）、RUNTIME（运行时反射可读） |
| @Target | 可修饰的程序元素：TYPE / FIELD / METHOD / PARAMETER / CONSTRUCTOR / LOCAL_VARIABLE / ANNOTATION_TYPE / PACKAGE |
| @Documented | javavadoc 时包含注解说明 |
| @Inherited | 子类可继承父类的注解 |

**常用内置注解**：@Override（校验重写）、@Deprecated（过时警告）、@SuppressWarnings（抑制警告）、@SafeVarargs（泛型可变参数安全）、@FunctionalInterface（函数式接口校验）。

**运行时提取（反射）**：AnnotatedElement（Class/Method/Field 的父接口）提供 isAnnotationPresent / getAnnotation / getAnnotations；注意必须 RUNTIME 保留：

```java
for (Method method : clazz.getMethods()) {
    MyTag tag = method.getAnnotation(MyTag.class);
    if (tag != null)
        System.out.println(method.getName() + ": " + tag.name() + "," + tag.age());
}
```

**注解的意义**：编译器辅助检查（@Override）、编译期生成代码（APT，如 ButterKnife/Room）、运行时处理（反射/动态代理）。一句话：注解是元数据，起"描述、配置"作用，是现代框架（Retrofit、Room、Hilt）声明式编程的基础。

### 12. 说说你对依赖注入的理解

依赖注入（DI）是**控制反转（IoC）**的一种实现方式：对象不自己创建所依赖的资源，而是由外部（框架或调用方）提供——把"我依赖谁"从硬编码变成外部装配。对比：

```java
// 硬编码依赖：无法替换、难以测试
class SpellChecker {
    private final Lexicon dict = new EnglishLexicon();
}

// 构造器注入：依赖从外部传入（Effective Java 条目 5）
class SpellChecker {
    private final Lexicon dict;
    SpellChecker(Lexicon dict) { this.dict = Objects.requireNonNull(dict); }
}
```

**好处**：解耦（实现可替换）、可测试（注入 mock）、生命周期统一管理、资源按需共享。

**Android 的 DI 演进**：手写构造器注入 → **Dagger2**（编译期注解生成依赖图，反射零开销但学习曲线陡）→ **Hilt**（Dagger 的 Android 封装，标准组件开箱即用，官方推荐）→ Koin（Kotlin，运行时 ServiceLocator 风格，简单无代码生成）。

参考：[反射、注解与依赖注入总结](https://www.jianshu.com/p/24820bf3df5c)

### 13. 说一下泛型原理，并举例说明

泛型的原理是**类型擦除**：泛型只存在于编译期，编译器利用它做类型检查并自动插入强制转换，字节码里的泛型信息会被擦成原始类型（无边界擦成 Object，有边界擦成第一个边界）。所以 `new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()` 为 true，也不能对 `List<String>` 做 instanceof；由此带来不能 `new T()`、静态成员不能用类的类型参数等限制。举例：`List<String> list = new ArrayList<>(); list.add(123);` 编译不通过，但用原始类型 `List` 绕过检查后能存进去，取出时抛 ClassCastException（堆污染）。

详细的泛型总结（用法、类型擦除、通配符 PECS、不变性）见 [Java泛型总结](/QA/Java泛型总结.md)。

### 14. Java中String的了解

- **不可变**：final 类 + 私有 final 数组（JDK 8 是 `char[] value`，JDK 9 起改为 `byte[] value` 压缩存储），好处是常量池复用、线程安全、hashCode 缓存；
- **常量池**：字面量 `"abc"` 进字符串常量池，相同字面量复用同一对象；`new String("abc")` 在堆中创建新对象（== 的经典陷阱）；
- **拼接**：少量 + 编译器会优化（JDK 5~8 为 StringBuilder，JDK 9 起 invokedynamic），**循环中拼接必须显式用 StringBuilder**（1.Java一 第 5 题）；
- String / StringBuilder / StringBuffer：不可变 / 可变非线程安全 / 可变线程安全（synchronized）；
- String 重写了 equals/hashCode（按内容），并缓存第一次计算的 hash。

### 15. String为什么要设计成不可变的？

**字符串常量池**：JVM 维护字符串常量池实现复用。字面量 `"abcd"` 直接查池返回引用，两个相同字面量指向同一对象；`new String("abcd")` 无视常量池直接在堆上建新对象。**如果字符串可变，两个引用指向同一字符串时，改一个就会影响另一个**——常量池的复用就无从谈起。`intern()` 可把堆中对象登记/映射到常量池。

注意赋值的本质：`str = "456"` 只是让 str 指向新实例，原对象内容从未被修改——"改 String"其实是换引用。

**缓存 hashCode**：String 的 hash 字段只在第一次计算时求值并缓存；不可变保证 hash 永不失效，作为 HashMap 的 key 时不必重复计算。

**安全性**：String 广泛用作参数（类名、文件路径、网络地址、反射的类名），可变的字符串会被中途篡改引发安全问题。

**线程安全**：不可变对象可自由在多线程间共享，无需同步。

代价是修改操作产生新对象（ substring/concat 等都如此）——高频拼接用 StringBuilder。

参考：[为什么 String 是不可变的](https://www.jianshu.com/p/b1d62928552d)

### 16. Object类的equal和hashCode方法重写，为什么？

Object 的 equals 默认就是 `==`（引用比较），hashCode 是与内存地址相关的 identity hash。**值类**（有"逻辑相等"概念）必须重写：不重写 equals，两个内容相等的对象业务上不相等；而**重写 equals 就必须同时重写 hashCode**——否则相等的对象散列值不同，HashMap/HashSet 里就互相找不到（定位桶靠 hashCode、桶内比对靠 equals，见 HashMap原理）。约定：equals 相等 ⇒ hashCode 必须相等；反之不要求（哈希冲突）。详见 1.Java一 第 1 题。

### 17. 为什么Java里的匿名内部类只能访问final修饰的外部变量？

匿名内部类会被编译成独立的外部类（Outer$1），捕获的局部变量**以拷贝形式**（构造器参数/合成字段）传进去。局部变量在栈上、方法结束就销毁，而内部类对象的生命周期可能更长——它持有的是副本。若允许修改，就会出现"内部类改的是副本、外部改的是本体"的不一致。因此 Java 要求捕获的变量为 final（保证副本与本体一致）。

JDK 8 起放宽为 **effectively final**（事实上不再修改即可，不必显式写 final）；lambda 捕获外层变量遵循同样的规则。想要"在 lambda 里改外部变量"的标准做法是用数组/AtomicInteger 包装，或改用成员变量。

### 18. Synchronized

synchronized 是 Java 中解决并发数据同步访问的关键字，保证同一时刻共享资源只被一个线程访问。

**两种用法与底层指令**：同步方法通过常量池的 ACC_SYNCHRONIZED 标志实现（执行前获取监视器锁，异常抛出前自动释放）；同步代码块通过 monitorenter / monitorexit 指令实现（可重入：锁计数器自增/自减，为 0 时释放）。

**synchronized 与三性**

- **原子性**：monitorenter 加锁后，即使时间片耗时切换，锁未释放其他线程也无法进入，可重入特性保证同一线程下次时间片继续执行——临界区内操作不可分割；
- **可见性**：JMM 规定"解锁前必须把变量同步回主内存"，后续加锁线程读到的一定是最新值；
- **有序性**：无法禁止指令重排，但临界区内单线程执行 + as-if-serial 语义（单线程执行结果不受重排影响），观察者角度是有序的。

**锁优化（JDK 6）**：synchronized 直接走 ObjectMonitor（C++ 实现）需要用户态/内核态切换，开销大（重量级锁）。JDK 6 引入锁升级：**无锁 → 偏向锁（只 CAS 记录线程 ID）→ 轻量级锁（CAS 自旋）→ 重量级锁（内核挂起）**，以及锁消除（逃逸分析证明无竞争则去掉锁）与自适应自旋。注意：**偏向锁在 JDK 15 起被废弃移除**（维护成本高、现代收益小），默认直接从轻量级锁开始。

### 19. volatile

**用法**：轻量级的同步手段，只能修饰变量（不能修饰方法/代码块），声明可能被多线程访问的变量时使用。

**原理**：写 volatile 变量时 JVM 向处理器发送 Lock 前缀指令，把缓存行强制刷回主内存；多处理器间通过**缓存一致性协议（MESI）**——各处理器嗅探总线上的数据，发现本地缓存行对应内存被修改就置为无效，使用时强制从主内存重读。由此保证可见性。

**三性**：

- 可见性 ✔（如上）；
- 有序性 ✔（禁止指令重排优化，内存屏障）；
- **原子性 ✘**——`count++` 是读改写三步，volatile 挡不住并发丢失更新。

**适用场景**（可以替代 synchronized 的条件）：运算结果不依赖变量当前值（纯赋值/状态标志），或能确保只有单一线程写；变量不需要与其他状态变量组成不变约束。其他场景用 synchronized 或原子类。

一句话对比：synchronized 保证原子/可见/有序，volatile 只保证可见与有序。

### 20. 类加载流程双亲委托机制

**类加载流程**：装载（Loading）→ 链接（验证 Verification / 准备 Preparation / 解析 Resolution）→ 初始化（Initialization）。准备阶段为静态变量分配内存并设零值（`static int a = 1` 此刻 a=0，赋值在初始化），final 常量在此阶段直接赋予指定值。

**双亲委托机制**：类加载器收到加载请求先委托父加载器，逐级递归到 Bootstrap；父加载器能完成就成功返回，不能完成才自己加载。三层加载器：Bootstrap（rt.jar）→ Ext/Platform → Application；Android 中是 BootClassLoader → PathClassLoader（应用）/ DexClassLoader（动态 dex）。

**执行细节**：

1. 先查自己的加载缓存，命中直接返回；
2. 未命中委托父加载器（同样策略，直到 Bootstrap）；
3. 所有父加载器都加载不了才自己加载并放入缓存。

**为什么需要**：

- **安全**：核心类库（如 java.lang.Object）永远由 Bootstrap 加载，全程序唯一。用户自己写同名 Object 可以编译但永远无法被加载，防止核心 API 被篡改；
- **命名空间**：类的唯一性由"全限定名 + 类加载器"共同确定。委托模型让所有加载器共享 JDK 核心类，避免同名类混乱、ClassCastException。

**破坏双亲委派的场景**（加餐）：SPI（JDBC 驱动等，核心库要加载应用 classpath 的实现——线程上下文类加载器）、OSGi/插件化（网状委托）、热修复（替换 dex 加载顺序）、Tomcat 的 WebappClassLoader（应用间隔离优先自己加载）。
