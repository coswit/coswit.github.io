### 1. 开启线程的三种方式？

**① 继承 Thread 类**：重写 run 方法（线程执行体），new 子类实例后 start()。

```java
public class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println(Thread.currentThread().getName());
    }
}
new MyThread().start();
```

**② 实现 Runnable 接口**：实现 run 方法，作为 Thread 的 target。**推荐**：不占用继承名额、多个线程可共享同一个 target（同一份资源）。

```java
Runnable task = () -> System.out.println(Thread.currentThread().getName());
new Thread(task, "线程1").start();
new Thread(task, "线程2").start();   // 共享同一 task
```

**③ Callable + FutureTask**：call 方法**有返回值、可抛异常**；FutureTask 包装后交给 Thread，get() 阻塞取结果。

```java
FutureTask<Integer> ft = new FutureTask<>(() -> { /* 耗时计算 */ return 42; });
new Thread(ft).start();
Integer result = ft.get();   // 阻塞直到完成
```

**对比**：

| 方式 | 返回值 | 继承限制 | 资源共享 |
| --- | --- | --- | --- |
| 继承 Thread | 无 | 占用单继承名额 | 多实例各自独立 |
| 实现 Runnable | 无 | 无 | 多线程共享同一 target |
| Callable + Future | 有，可抛异常 | 无 | 搭配线程池/Executor 使用最佳 |

> 【演进】实践中的第四种：**线程池 submit**（返回 Future，见第 15 题）与 **CompletableFuture**（编排异步流水线）；JDK 21 正式发布**虚拟线程（Virtual Thread / Loom）**——`Thread.ofVirtual().start(task)`，由 JVM 调度到少量平台线程上，阻塞成本极低，百万级并发线程成为可能，是"每个请求一个线程"编程模型的回归。Kotlin 侧用协程（结构化并发）。

### 2. run() 和 start() 方法的区别？

- **start()**：由 JVM 创建一个新线程，run 中的代码在**新线程**执行，并触发线程就绪；一个 Thread 对象只能 start 一次，重复调用抛 **IllegalStateException**；
- **run()**：只是普通方法调用，**不创建新线程**，代码在当前调用者线程执行，重复调用没有问题。

### 3. 如何控制某个方法允许并发访问线程的个数？

信号量 Semaphore：

```java
Semaphore semaphore = new Semaphore(5);  // 最多 5 个线程并发
semaphore.acquire();    // 申请许可（无许可则阻塞）
try { ... } finally {
    semaphore.release(); // 归还许可
}
```

同理的还有固定线程数的线程池（天然限制并发）与 RateLimiter（Guava，限速率而非并发数）。

### 4. 在 Java 中 wait() 和 sleep() 方法的区别

- **归属**：wait() 是 Object 的方法，必须在 synchronized 块内调用（要持有该对象的监视器锁）；sleep() 是 Thread 的静态方法，任何地方都能调；
- **锁**：wait() 会**释放锁**并进入该对象的等待集，被 notify/notifyAll（或中断）唤醒后要**重新竞争锁**才能继续；sleep() **不释放锁**，睡够时间自动继续；
- **用途**：wait/notify 是线程间协作机制（生产者-消费者）；sleep 只是让当前线程定时暂停；
- 两者都响应中断（InterruptedException）。

### 5. 谈谈 wait/notify 关键字的理解

- 两者都是 Object 的本地 final 方法，**调用前必须持有该对象的监视器锁**（否则抛 IllegalMonitorStateException）；
- wait()：线程进入该对象的等待集并释放锁（还可带超时参数）；
- notify()：唤醒等待集中**一个**线程（选择由虚拟机决定，无法指定）；notifyAll() 唤醒全部，被唤醒者重新竞争锁；
- **为什么定义在 Object 而不是 Thread**：锁是加在对象上的，等待与唤醒以对象（监视器）为单位，任何对象都可能成为锁；
- **标准姿势：循环中 wait**（防止虚假唤醒与条件被抢先）：

```java
synchronized (obj) {
    while (条件不成立)      // 用 while 而不是 if！
        obj.wait();
    ... // 执行对应逻辑
}
```

### 6. 什么导致线程阻塞？

典型阻塞场景与线程状态的对应：

- **BLOCKED**：竞争 synchronized 锁失败，等待进入监视器；
- **WAITING**：wait() / join() / LockSupport.park()（Lock.await 也在其上）；
- **TIMED_WAITING**：sleep(ms) / wait(ms) / join(ms) / parkNanos；
- **IO 阻塞**：网络、磁盘读写（操作系统层面挂起，Java 线程状态仍为 RUNNABLE——状态上看不出 IO 等待）。

排查手段：jstack 抓线程快照，看大量线程停留在哪一类状态。

### 7. 线程如何关闭？

标准方式是 **interrupt + 可中断逻辑**：

- 目标线程在循环条件里检查 `Thread.currentThread().isInterrupted()`，阻塞方法（sleep/wait/join）被中断时捕获 InterruptedException 并**恢复中断标志**（再次 interrupt）后退出；
- volatile 布尔标志位也常用（对非阻塞的轮询循环有效，但唤不醒阻塞中的线程）；
- **不要用** stop()（已废弃，直接释放锁会破坏数据一致性）和 suspend/resume（易死锁）；
- 线程池：shutdown() 平缓停止（不再接新任务，存量跑完），shutdownNow() 中断运行中的任务；
- 守护线程随 JVM 退出而终止（不要用它做需要收尾的工作）。

### 8. 讲一下 Java 中的同步的方法

- **synchronized**：同步方法 / 同步块（对象锁或类锁），基于 monitor，保证互斥 + 可见性；
- **volatile**：保证可见性与有序性（禁止重排），不保证原子性，适合状态标志；
- **Lock**：ReentrantLock 支持可中断抢锁、超时 tryLock、公平锁、多条件变量 Condition；
- **原子类**：AtomicInteger 等基于 CAS 的无锁原子更新（LongAdder 高并发计数更快）；
- **ThreadLocal**：以隔离代替同步，每线程一份副本；
- 并发容器与工具类（ConcurrentHashMap、CountDownLatch 等）与不可变对象是更高层的手段。

### 9. 数据一致性如何保证？

从 Java 内存模型（JMM）的三个性质入手：

- **原子性**：synchronized / Lock 互斥；CAS 与原子类（单一变量的无锁原子操作）；
- **可见性**：volatile（新值立即刷主存、读强制读主存）、synchronized（解锁前刷写）、final（正确构造后不可变）；
- **有序性**：volatile 禁止指令重排、synchronized 的临界区串行化，happens-before 规则是判断依据；

实践优先级：能不共享就不共享（栈封闭/ThreadLocal）→ 共享则不可变（final）→ 必须共享可变就用锁/原子类/并发容器。

### 10. 如何保证线程安全？

按代价从低到高选择：

1. **不共享**：变量栈封闭、ThreadLocal；
2. **不可变**：final 类/字段（String）、正确发布（final 字段或锁保护发布）；
3. **限制共享**：锁（synchronized / ReentrantLock）、原子类 CAS、并发容器（ConcurrentHashMap、CopyOnWriteArrayList）；
4. 注意**复合操作**仍需额外同步：check-then-act（如先 contains 再 put）不是原子的，要用 putIfAbsent 等原子方法或外部锁；
5. 结构上：优先用线程池 + 任务化（Runnable 无共享）、消息/队列解耦（BlockingQueue），Kotlin 用协程 + 不可变数据。

### 11. 如何实现线程同步？

- **synchronized**：同步方法/代码块；配合 wait/notify/notifyAll 做等待-通知协作；
- **显式锁**：ReentrantLock + Condition（await/signal），支持多个条件队列、超时与可中断；
- **轻量同步**：volatile 标志位、Atomic 原子类、LongAdder；
- **同步工具类**：CountDownLatch（一次性倒计数）、CyclicBarrier（周期汇合）、Semaphore（许可限流）、Exchanger（两线程交换数据）；
- **队列同步**：BlockingQueue 天然的生产者-消费者同步（put/take 阻塞）。

### 12. 两个进程同时要求读写，能不能实现？如何防止进程同步？

能实现并发读写，但进程间内存隔离，必须借助操作系统机制协调：

- **文件锁**：FileChannel.lock / lock（共享读、独占写）；
- **共享内存 + 信号量**：System V / POSIX 的 shm + sem 做经典 PV 互斥；
- **数据库**：SQLite 事务 / 行锁天然串行化；
- **消息化**：Socket / 消息队列 / Binder（Android）把并发访问收敛到一个服务端串行处理；
- 经典模型即"读者-写者问题"：读写锁（读共享、写独占）思想；Android SP 跨进程不可靠就是缺少这层协调的反例。

### 13. 线程间操作 List

- ArrayList 非线程安全：并发写会数据错乱，迭代中修改抛 ConcurrentModificationException（fail-fast 尽力检测）；
- **Collections.synchronizedList(new ArrayList<>())**：全方法加同一把锁，读写都互斥（迭代仍需手动 synchronized）；
- **CopyOnWriteArrayList**：读完全无锁，写时复制底层数组——适合**读多写少**（监听器列表）；迭代器是快照，不抛 CME；
- 迭代中删除：用 Iterator.remove() 或 removeIf，不要 for-each 里直接 list.remove；
- Vector（全同步）已过时，不推荐新代码使用。

### 14. Java 中对象的生命周期

创建 → 使用 → 不可达 → （finalize）→ 空间回收：

1. **创建**：类加载检查 → 分配内存（指针碰撞/空闲列表，TLAB）→ 零值初始化 → 设置对象头 → init 构造；
2. **使用**：强/软/弱/虚四种引用影响回收时机（软引用内存不足回收、弱引用下次 GC 必回收）；
3. **判定死亡**：可达性分析（从 GC Roots：栈变量、静态字段、常量、JNI 引用等出发），不可达即垃圾；finalize() 最多执行一次且不推荐依赖（见 Effective Java 条目 8）；
4. **回收**：分代收集——新生代 Minor GC（Eden + 两个 Survivor，复制算法），老年代 Full GC（标记-清除/整理）；
- **内存泄漏 = 无用但可达**：静态集合、未注销的监听器、ThreadLocal 不 remove（见 Effective Java 条目 7）。

### 15. 说说线程池

**线程池的好处**：

1. **重用线程**：创建与销毁开销巨大，重用减少开销；
2. **控制并发数**：避免大量线程互相争夺 CPU 造成阻塞；
3. **统一管理**：提供定时、定期、单线程、并发数控制等能力。

**ThreadPoolExecutor 七参数**：

```java
public ThreadPoolExecutor(int corePoolSize,      // 核心线程数
                           int maximumPoolSize,  // 最大线程数
                           long keepAliveTime,   // 非核心线程空闲存活时长
                           TimeUnit unit,        // 时长单位
                           BlockingQueue<Runnable> workQueue, // 任务队列
                           ThreadFactory threadFactory,        // 线程工厂
                           RejectedExecutionHandler handler)   // 拒绝策略
```

**执行流程（顺序很重要）**：

1. 当前线程数 < corePoolSize：直接新建**核心线程**执行任务；
2. 核心线程满：任务进入 workQueue 排队；
3. 队列满 且 线程数 < maximumPoolSize：新建**非核心线程**执行任务；
4. 队列满 且 线程数已达 maximumPoolSize：执行**拒绝策略**（默认 AbortPolicy 抛 RejectedExecutionException；还有 CallerRuns 调用者执行、Discard 丢弃、DiscardOldest 丢最老）。

**常见工厂线程池**：FixedThreadPool（定长，core=max）、SingleThreadExecutor（单线程串行）、CachedThreadPool（core=0，max=∞，SynchronousQueue 即来即建）、ScheduledThreadPool（定时/周期）。

> 【注意】阿里巴巴规范**不推荐直接用 Executors 工厂**：FixedThreadPool / SingleThreadExecutor 用无界队列（LinkedBlockingQueue 默认 Integer.MAX_VALUE），任务堆积会 OOM；CachedThreadPool 最大线程数无上限，可能创建海量线程。推荐手写 `new ThreadPoolExecutor(...)` 明确参数。
>
> 线程数经验：CPU 密集型 ≈ 核数 + 1；IO 密集型 ≈ 2 × 核数（或 核数 × (1 + 等待时间/计算时间)）。Android 中主线程 StrictMode 会拦截网络操作，子线程更新 UI 需要 Handler/协程切回。

### 16. 并发编程面临的挑战

1. **上下文切换**：CPU 时间片轮转，线程切换要保存/恢复现场（寄存器、程序计数器、栈帧），切换成本 μs 级。减少切换：无锁化（CAS）、协程/虚拟线程（用户态调度）、锁粒度缩小、`-XX:+UseSpinning` 类自旋；进程切换比线程切换更重（还要切地址空间）；
2. **死锁**：互斥、持有并等待、不可剥夺、循环等待四条件齐备即发生。避免：按固定顺序加锁、tryLock 带超时、一次性申请所有资源。排查：`jstack <pid>` 直接输出 deadlock 信息、MAT 分析锁持有；
3. **资源限制**：硬件（带宽、磁盘 IO）与软件（数据库连接池、线程池）的上限。受限时增加线程数只会加剧竞争——先定位瓶颈（profiler），资源受限场景串行化反而更快。

### 17. Java 中并发问题，从底层看是怎么发生的？

**总述**：并发的发生需要两个前提——**多个执行流 + 访问同一份共享数据**。Java 线程映射到操作系统线程（1:1；虚拟线程也跑在载体平台线程上），会被调度到不同 CPU 核心**并行**执行；每个核心有私有的寄存器和多级缓存，JIT 与 CPU 又会做各种性能优化。这些行为在单线程下无害——重排被 as-if-serial 语义兜底、中间状态无人观察；多线程下则暴露为三类问题：**可见性 ← 多核私有缓存、有序性 ← 指令重排、原子性 ← 任务切换**。

**JMM 的定位与抽象**：JMM（Java Memory Model）不是问题来源，而是把"硬件真实行为 vs 程序员直觉的顺序一致性"之间的差距规范化、以 happens-before 与程序员立契约的模型。它把硬件结构抽象为两块：

- **主内存（main memory）**：共享变量所在地，对应 JVM 的**堆 + 方法区**（对象实例、数组、静态字段、运行时常量池）；
- **工作内存（working memory）**：每线程一份，涵盖线程栈、寄存器、store buffer、CPU 缓存——即"线程访问共享变量的私有路径"。

由此得到 JVM 内存区域的并发边界：

- 只有堆/方法区里的**共享数据**适用 JMM 规则、才有并发问题；线程栈中的局部变量天然线程隔离——**栈封闭（stack confinement）**是并发第一选择；
- 但栈里存的是**引用**，对象本体在堆中：两个线程的局部引用指向同一堆对象，"私有"就变"共享"（对象逃逸，escape）；
- long/double 非原子（JLS 17.7）针对堆中共享字段，局部变量无此问题；ThreadLocal 的 ThreadLocalMap 物理上也在堆里，但逻辑上线程独享，无竞争。

**① 可见性 ← CPU 多核私有缓存 + Store Buffer / Invalidate Queue**

硬件结构与一致性协议：

- L1/L2 cache 每核心私有，L3 与主内存（DRAM）共享；
- 多核缓存同一变量时，靠**缓存一致性协议（MESI）**维护一致——Modified（已修改，与主存不一致）/ Exclusive（独占，一致）/ Shared（共享，一致）/ Invalid（失效）；
- 写共享变量前要先让其他核心的缓存行失效，但等待确认太慢，CPU 为此引入两个**异步结构**：
  - **Store Buffer**：写操作先进入本核心的 Store Buffer 便继续执行，之后才刷入缓存、对其他核心可见；
  - **Invalidate Queue**：收到失效消息的核心先入队并立刻回 ACK，之后再异步真正置本地缓存行为无效。

即使 MESI 保证最终一致，这两个队列造成的"短暂不一致"在并发程序里就是可见性问题：

```java
boolean flag = false;
// 线程 A：flag = true;    —— 可能还停留在 Store Buffer 里
// 线程 B：while (!flag) {} —— 读到的一直是本核心缓存的旧值，死循环
```

注意：x86 属于强内存模型（TSO），Store Buffer 迟早会刷出，但 **JIT 还可能把未标 volatile 的 `!flag` 读取提升（hoisting）到循环外**——死循环依旧发生。可见性问题是"硬件延迟可见 + 编译器优化"的合力，两者都归 JMM 管。

**② 原子性 ← 线程切换发生在"指令之间"，而高级语言的一步 = 多条指令**

- 时间片耗尽或阻塞时任务被切换，切换点在**任何两条机器指令之间**都合法——单核同样有原子性问题（调度交叉），多核是真正的并行执行，问题更严重；
- `count++` 是读改写（read-modify-write）三步，字节码为 getfield → iconst_1 → iadd → putfield：两线程都读到 0、各加 1、先后写回 1，期望 2 实得 1——**丢失更新（lost update）**；
- 这类"结果依赖线程执行相对时序"的错误即**竞态条件（race condition）**，涉及共享变量的区域即**临界区（critical section）**；
- 极端例子：32 位 JVM 上 64 位 long/double 的一次赋值都不是原子的（JLS 允许拆成两次 32 位读写）。

CPU 层的原子支持：

- x86：**LOCK 前缀**（早期锁总线，现代锁缓存行 cache locking），如 `lock inc`、`lock cmpxchg`——AtomicInteger 的 CAS 底层就是 lock cmpxchg；
- ARM：LDREX/STREX 独占访问，或 ARMv8.1 的 LSE 原子指令（Android 设备即 ARM）；
- Java 层：synchronized / Lock 靠互斥把临界区整体串行化。

**③ 有序性 ← 编译器 / CPU / 内存系统重排（Reordering）**

重排的三层来源：

- **编译器重排**：JIT 指令调度；
- **CPU 乱序执行**（out-of-order execution，指令级并行 ILP）；
- **内存系统重排**：Store Buffer 异步刷入，使写操作对其他核心的可见顺序 ≠ 程序顺序。

单线程下 as-if-serial 语义兜底（结果不受影响）；多线程交错时暴露。经典案例 DCL：`new Singleton()` 分三步——分配内存 → 初始化 → 赋值引用，后两步可能重排为"先赋值、后初始化"，线程 B 第一次判空时拿到**未初始化完成的引用**——所以实例字段必须 volatile。

禁止重排靠**内存屏障（Memory Barrier / Fence）**，按拦截的读写组合分四类：

| 屏障 | 拦截的重排 |
| --- | --- |
| LoadLoad | 读-读 |
| LoadStore | 读-写 |
| StoreStore | 写-写 |
| StoreLoad | 写-读（最强也最贵，volatile 写之后必插） |

落地细节：

- x86 对应 lfence / sfence / mfence；实际 JVM 的 volatile 写多用 `lock addl $0,(rsp)`，借 LOCK 前缀达成全屏障效果；
- 插入策略（JSR-133 Cookbook）：**volatile 写前 StoreStore、写后 StoreLoad；volatile 读后 LoadLoad + LoadStore**；
- 各屏障职责：写前的 StoreStore 保证先前的普通写随 volatile 写一起可见，写后的 StoreLoad 排空 Store Buffer，读后屏障（ARM 等弱内存模型上）强制先处理 Invalidate Queue——这正是 volatile 同时保证可见性与有序性的底层动作。

**④ JMM：用 happens-before 在"性能"与"正确性"之间画线**

JMM 是规范，落地由 JVM 按具体平台插入屏障；面向程序员暴露的是 **happens-before（hb）** 规则：

- **程序顺序**：单线程内，前操作 hb 后操作；
- **volatile 规则**：对 volatile 变量的写 hb 后续对它的读；
- **锁规则**：解锁 hb 后续对同一把锁的加锁；
- **线程协作**：Thread.start() hb 线程内任意操作；线程内任意操作 hb join() 返回；
- **传递性**：A hb B 且 B hb C ⇒ A hb C。

**三性 → 底层根源 → 解决手段**：

| 问题 | 底层根源 | Java 层面的手段 |
| --- | --- | --- |
| 可见性 | 私有缓存 + Store Buffer / Invalidate Queue | volatile、synchronized、final |
| 有序性 | 编译器 / CPU / 内存系统重排 | volatile（内存屏障）、synchronized、happens-before |
| 原子性 | 指令中间的线程切换 | synchronized / Lock 互斥、CAS 原子类（lock cmpxchg） |

按 happens-before 写代码，缓存、重排、切换对程序就是透明的。
