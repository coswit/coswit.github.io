### 1. 简述HTTP

HTTP（超文本传输协议）是基于 TCP 的应用层协议，用于从 Web 服务器传输超文本到本地浏览器。工作于客户端-服务端架构：浏览器作为 HTTP 客户端通过 URL 向 Web 服务器发送请求，服务器返回响应。

特点：

- **简单快速灵活**：只需传送请求方法和路径；可传输任意类型数据，由 Content-Type 标记；
- **媒体独立**：客户端与服务器约定 MIME-type 即可传任何内容；
- **无状态**：协议对事务处理没有记忆能力，后续处理需要先前信息时必须重传——由此诞生了 Cookie/Session 等补充机制（见第 11 题）；
- 连接性随版本演进：HTTP/1.0 默认短连接（每次请求都建 TCP 连接），**HTTP/1.1 起默认持久连接（长连接）**，旧资料说"HTTP 是无连接的"指的是 1.0 时代的行为，注意别在面试里说错。

### 2. HTTP请求报文和响应报文

HTTP/1.x 报文是面向文本的（HTTP/2 起为二进制帧），分为请求报文与响应报文两类。

**请求报文** = 请求行 + 请求头 + 空行 + 请求数据：

- 请求行：`方法 URL 协议版本`，如 `GET /index.html HTTP/1.1`；
- 请求头：关键字/值对，典型的有 User-Agent（浏览器类型）、Accept（可识别内容类型）、Host（主机名，支持一个 IP 多个域名的虚拟主机）；
- 空行：通知服务器请求头结束；
- 请求数据：POST 等方法携带的 body（GET 不用），配套 Content-Type / Content-Length。

**响应报文** = 状态行 + 响应头 + 空行 + 响应正文：

```
HTTP/1.1 200 OK
Date: Sat, 31 Dec 2025 23:59:59 GMT
Content-Type: text/html; charset=UTF-8
Content-Length: 122

<html>...</html>
```

**状态码**（首位数字表示类别）：

| 类别 | 含义 |
| --- | --- |
| 1xx | 指示信息，请求已接收继续处理（100 Continue、101 协议切换） |
| 2xx | 成功（200 OK、**206 Partial Content** 部分内容/断点续传） |
| 3xx | 重定向（**301 永久**、**302 临时**、304 缓存有效 Not Modified） |
| 4xx | 客户端错误（**400 请求语法错、401 未授权、403 禁止、404 未找到**、429 请求过多） |
| 5xx | 服务器错误（500 内部错误、502 网关错误、**503 服务不可用**、**504 网关超时**） |

### 3. GET 和 POST 的区别

- **语义**：GET 获取资源（幂等、可缓存、可收藏为书签）；POST 提交数据（非幂等、默认不缓存）；
- **参数位置**：GET 参数在 URL 中（长度受浏览器/服务器限制、明文暴露在历史记录与日志里）；POST 参数在 body（理论无限制，Content-Type 决定编码）；
- **安全**：两者都不加密（明文走 TCP）， HTTPS 才是真正的传输加密；"POST 比 GET 安全"只是相对不显式暴露参数；
- **本质**：底层都是 TCP 上的 HTTP 报文，浏览器/服务器实现上的差异（如 GET 产生一个 TCP 包、POST 部分实现先发头部再发 body 产生两个包）不是协议规定。

补充：PUT（幂等替换）、DELETE（删除）、HEAD（只要响应头）、OPTIONS（询问支持的方法，CORS 预检用）。

### 4. Http1.1和Http1.0及2.0的区别

**HTTP/1.0 → 1.1**

- **长连接**：1.0 默认短连接（一个 TCP 连接只传一个对象，要用 keep-alive 参数请求保持）；1.1 **默认持久连接**，一个连接上传多个请求响应，省去反复三次握手的开销；
- **管线化（pipelining）**：1.1 允许不等上次响应就发下一个请求，但服务器必须**按序响应**——前面的响应慢会阻塞后面（队头阻塞），且浏览器支持差，实践中基本被弃用；
- **Host 头**：1.1 强制要求 Host 字段，支持虚拟主机（一个 IP 部署多个域名）；
- **缓存控制**：引入更多缓存头（Cache-Control、ETag、If-None-Match 等，替代 1.0 的 Expires/If-Modified-Since）；
- **节约带宽**：引入 Range 请求（断点续传），只取资源的部分内容，响应 206 + Content-Range；错误响应不再强制关闭连接；
- **错误提示**：新增 24 个状态码（206/409/410 等）。

**HTTP/1.1 → 2.0**

- **二进制分帧**：报文拆成二进制 Frame 传输，是其余特性的基础；
- **多路复用**：**同一个 TCP 连接上并行收发多个请求/响应**（帧交错传输、按流重组），彻底解决 1.1 的 HTTP 层队头阻塞，不用再靠开多个连接（域名分片）提并发。注意：TCP 层的队头阻塞仍在（丢包会阻塞所有流），这由 HTTP/3 解决；
- **头部压缩（HPACK）**：1.x 的头部是纯文本重复传输（每次都带 User-Agent、Cookie 等）；2.0 用静态表 + 动态表 + 哈夫曼编码压缩头部；
- **服务器推送**：服务器可以在浏览器请求 HTML 之前主动推送 CSS/JS 等资源。

> 【演进】**HTTP/3（QUIC）**：把传输层从 TCP 换成基于 UDP 的 QUIC——继承 TLS 1.3 加密、0/1-RTT 握手（连接建立更快）、传输层无队头阻塞（流之间独立）、连接迁移（网络切换不断线）。Android 的 Cronet / OkHttp（需启用 HTTP/3）已支持。

### 5. HTTPS 与 TLS 握手

HTTPS = HTTP + TLS：在 TCP 之上、HTTP 之下加一层加密，解决明文传输的**窃听、篡改、冒充**三大风险（机密性、完整性、身份认证）。

**TLS 1.2 握手（RSA 简化版）**：

1. Client Hello：客户端发送支持的 TLS 版本、加密套件、**随机数 C**；
2. Server Hello + 证书：服务器返回选定的套件、**随机数 S**、**数字证书**（含服务器公钥，由 CA 签发）；
3. 客户端验证证书（CA 链、域名、有效期），生成**预主密钥**，用服务器公钥加密发给服务器；
4. 双方用（C + S + 预主密钥）按相同算法生成**会话密钥**；
5. 之后的应用数据全部用会话密钥**对称加密**传输（握手用非对称，通信用对称——兼顾安全与性能）。

**TLS 1.3**（更快的现状标准）：握手从 2-RTT 缩短为 **1-RTT**，会话恢复可 **0-RTT**；废除了不安全套件，密钥交换只用 ECDHE（提供前向安全——私钥泄露不影响历史会话）。

证书体系：CA 用自己的私钥给服务器证书签名，浏览器内置根证书逐级验证。抓包工具（Charles）能解密 HTTPS 的原理是让自己当 CA，客户端装了它的根证书。

### 6. DNS解析过程

DNS（域名系统）把域名解析为 IP。查找顺序：

1. **浏览器缓存**（有 TTL 过期时间）；
2. **系统缓存**：hosts 文件（Windows 的 `C:\Windows\System32\drivers\etc\hosts`、Linux 的 `/etc/hosts`）与系统 DNS 缓存；
3. 以上是本机完成。未命中则问**本地 DNS 服务器（LDNS）**——操作系统配置的 DNS（校园网/运营商提供），约 80% 的解析在它的缓存中完成；
4. LDNS 未命中：LDNS 向**根域名服务器**请求 → 返回负责该顶级域（com/cn/org）的 **gTLD 服务器**地址；
5. LDNS 问 gTLD → 返回域名注册商的 **Name Server（权威 DNS）** 地址；
6. Name Server 返回域名对应的 IP 与 TTL；
7. LDNS 按 TTL 缓存结果并返回给客户端，解析结束。

客户端 → LDNS 是**递归查询**（你要给我最终答案）；LDNS → 根/gTLD/权威是**迭代查询**（层层问路）。

> 【演进与补充】DoT/DoH（DNS over TLS/HTTPS）加密 DNS 查询防劫持；Android 9 起支持 Private DNS（DoT）。HTTPDNS（HTTP 协议直连取解析）是国内防运营商劫持的常用方案。

### 7. TCP 和 UDP 的区别

|  | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠：确认重传、有序、不丢不重 | 尽力交付：可能丢包、错序 |
| 传输单位 | 面向**字节流**（无边界，按窗口/拥塞切分） | 面向**报文**（应用给多长发多长） |
| 拥塞控制 | 有（慢启动等） | 无（网络拥塞也不降速） |
| 首部 | 至少 20 字节 | 8 字节 |
| 通信模式 | 一对一 | 一对一/一对多/多对多（支持广播） |
| 场景 | 文件传输、网页、邮件 | 实时音视频、DNS、游戏、广播 |

TCP 为可靠付出的代价：连接建立/释放、确认、流量控制、拥塞控制都增加开销。UDP 简单高效，可靠性需要应用层自己保证（如 QUIC 在 UDP 上实现了可靠传输、WebRTC）。

### 8. 三次握手与四次挥手

**三次握手（建立连接）**：

1. 客户端 → 服务器：**SYN=1，seq=x**（客户端进入 SYN_SENT）；
2. 服务器 → 客户端：**SYN=1，ACK=1，seq=y，ack=x+1**（服务器进入 SYN_RCVD）；
3. 客户端 → 服务器：**ACK=1，seq=x+1，ack=y+1**（双方 ESTABLISHED）。

- **为什么是三次不是两次**：核心是**双方都确认自己的发送与接收能力正常**，并同步初始序列号。两次的话，服务器无法确认客户端能收到自己的包；且历史重复的 SYN（网络中滞留的旧连接请求）会让服务器白白建立连接浪费资源；
- 第三次握手可以携带数据（前两次不行）；SYN 洪水攻击就是只发 SYN 不回 ACK，打满服务器的半连接队列（SYN cookie 缓解）。

**四次挥手（释放连接）**：

1. 客户端 → 服务器：**FIN=1，seq=u**（客户端 FIN_WAIT_1：我没有数据要发了）；
2. 服务器 → 客户端：**ACK=1，ack=u+1**（服务器 CLOSE_WAIT：我知道了，但我可能还有数据没发完）；
3. 服务器 → 客户端：**FIN=1，seq=w**（服务器 LAST_ACK：我也发完了）；
4. 客户端 → 服务器：**ACK=1，ack=w+1**（客户端 TIME_WAIT，等 2MSL 后 CLOSED）。

- **为什么挥手要四次**：TCP 全双工，两个方向独立关闭。收到 FIN 只代表对方不再发送，自己可能还有数据要发——所以 ACK 与 FIN 分开发（对比握手时服务器把 SYN+ACK 合并成一次）；
- **TIME_WAIT 等 2MSL 的原因**：保证最后一个 ACK 能重传到达（丢了对方会重发 FIN）；让本连接的旧报文在网络中消亡，避免污染新连接；
- 服务器大量 CLOSE_WAIT：应用层没有及时调用 close（代码泄漏连接的信号）。

### 9. TCP 如何保证可靠传输

- **序列号 + 确认应答（ACK）**：每个字节有序号，接收方确认；数据不丢、不重、有序；
- **超时重传**：发出后超过 RTO 未收到 ACK 就重传；快速重传：连续收到 3 个重复 ACK 立即重传（不等超时）；
- **滑动窗口（流量控制）**：接收方通过窗口大小（rwnd）告知发送方自己的缓冲余量，防止发送方淹没接收方；窗口内可连续发送不必逐个等 ACK；
- **拥塞控制**：防止网络过载——**慢启动**（拥塞窗口 cwnd 从 1 指数增长）、**拥塞避免**（到达阈值后线性增长）、**快重传 + 快恢复**（3 个重复 ACK，cwnd 减半继续）。发送速率取 min(rwnd, cwnd)；
- 校验和：检测报文段损坏。

### 10. 从输入URL到页面展示的过程

1. **URL 解析**与合法性检查，补全协议；
2. **DNS 解析**：浏览器缓存 → hosts → LDNS → 根/gTLD/权威（见第 6 题），拿到服务器 IP；
3. **建立 TCP 连接**：三次握手（HTTPS 再加 TLS 握手，见第 5、8 题）；
4. **发送 HTTP 请求**：构建请求报文（方法、头、body）；
5. **服务器处理**：负载均衡 → Web 服务器/网关 → 应用逻辑（可能查缓存、数据库）→ 返回响应报文；
6. **浏览器解析渲染**：HTML 构建 DOM 树、CSS 构建 CSSOM，合并成渲染树 → 布局 layout（计算几何位置）→ 绘制 paint → 合成；遇到 js/script 会阻塞 DOM 构建（async/defer 优化），图片等子资源按需再次发起请求；
7. **连接处理**：长连接复用或关闭（四次挥手）。

这题是网络知识的"串讲题"，把 DNS/TCP/TLS/HTTP/渲染的考点全部串起来。

### 11. Cookie、Session 与 Token

HTTP 无状态，会话保持方案：

- **Cookie**：服务器通过 Set-Cookie 写到浏览器的小段数据，后续请求自动携带。可设过期时间、域、HttpOnly（禁 JS 读取防 XSS 窃取）、Secure（仅 HTTPS）、SameSite（防 CSRF）；
- **Session**：状态存**服务器**（内存/Redis），浏览器只拿 SessionID（通常放在 Cookie）。分布式下需要 Session 共享（Redis 集中存）或粘性路由；
- **Token（JWT）**：状态存**客户端**——服务器签发的自包含令牌（头.负载.签名），请求时放 Authorization 头。服务器无需存会话（天然适合分布式/移动端），通过签名验证不可篡改；缺点是签发后**无法主动吊销**（需配合黑名单/短有效期 + refresh token）。

演进逻辑：Cookie+Session（有状态、服务端压力大）→ Token（无状态、水平扩展友好，移动端友好）。
