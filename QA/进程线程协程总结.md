# 进程、线程、协程总结（含 Android 跨进程）

## 一、进程（Process）

**资源分配的基本单位**。每个进程拥有独立的虚拟地址空间、页表、文件描述符等资源，相互隔离。

- 隔离性好：一个进程崩溃不会影响其他进程，一个进程的指针无法直接访问另一个进程的内存；
- 代价是重：创建 / 销毁开销大，进程间切换要换地址空间（页表、TLB 失效），进程间通信必须借助内核提供的 IPC 机制；
- 典型用途：应用隔离、沙箱（Android 中每个 app 默认运行在独立进程，每个进程一个独立虚拟机）。

## 二、线程（Thread）

**CPU 调度的基本单位**。线程属于进程，同一进程内的线程共享堆、方法区和打开的文件，但各自拥有独立的栈和寄存器上下文。

- 比进程轻：创建和切换不需要切换地址空间，只保存 / 恢复寄存器、栈指针、程序计数器，但仍要陷入内核态；
- 共享带来便利也带来风险：数据竞争需要用 synchronized / volatile、wait / notify 等机制协调；
- 一个线程的未捕获异常可能让整个进程退出；
- 数量有限：每个线程默认栈在 MB 级（Linux 默认 8MB、JVM 默认约 1MB），创建几千个线程系统就很吃紧；
- Android 中主线程（UI 线程）负责界面绘制和事件分发，耗时操作放工作线程，主线程阻塞过久会 ANR（线程相关面试题见 [3.Java三](./QA/3.Java三.md)）。

## 三、协程（Coroutine）

**运行在线程之上、由程序（运行时库）在用户态调度的轻量级任务**。协程的切换发生在用户态，由代码在挂起点主动让出（协作式调度），不需要内核参与。

为什么协程轻量：

- 切换不陷入内核，只保存 / 恢复少量寄存器，成本接近一次函数调用；
- 栈开销小：Go 的 goroutine 是有栈协程，初始栈仅几 KB 按需增长；Kotlin 协程是无栈协程（stackless），通过编译器对 `suspend` 函数做状态机变换实现挂起，挂起时根本不占用线程；
- 因此单机可以轻松创建数十万甚至百万级协程，适合高并发 IO 场景。

几个容易混淆的点：

- 协程不是线程：一个线程可以轮流执行成千上万个协程；
- 协程"挂起"不等于"阻塞线程"：`suspend` 函数挂起时线程被释放去跑别的协程；
- 协程本身不能提升单线程的计算能力，需要并行还是要靠多线程调度器（如 Kotlin 的 `Dispatchers.Default`，大小为 CPU 核数）；
- 协程内部共享可变状态依然需要同步（Kotlin 用 `Mutex`、`Channel` 等，比线程的锁更轻）。

## 四、三者对比总表

| 维度 | 进程 | 线程 | 协程 |
| --- | --- | --- | --- |
| 定位 | 资源分配的基本单位 | CPU 调度的基本单位 | 用户态调度的轻量任务 |
| 地址空间 | 独立 | 共享所属进程 | 共享所属线程 |
| 谁来调度 | 内核（抢占式） | 内核（抢占式） | 程序 / 运行时（协作式，挂起点让出） |
| 切换成本 | 高：切页表、TLB 失效、内核态 | 中：寄存器上下文、内核态 | 低：用户态保存少量寄存器 |
| 栈开销 | 独立地址空间，MB 级 | 每线程独立栈，MB 级 | KB 级（有栈）或无栈（Kotlin） |
| 可创建数量级 | 几十~几百 | 数百~数千 | 数万~数百万 |
| 通信方式 | IPC（管道、共享内存、Socket、Binder…） | 共享内存 + 锁 / wait-notify | Channel、挂起恢复，同调度器内天然串行 |
| 崩溃影响 | 隔离，不影响其他进程 | 可能拖垮整个进程 | 一般只影响自身（异常向外抛给协程作用域） |
| 典型场景 | 应用隔离、多进程模块 | 并行计算、阻塞型任务 | 高并发 IO、异步流程编排 |

一句话：**进程隔离资源，线程抢占调度，协程协作让出**；粒度从重到轻，切换成本从高到低。

## 五、通信方式对比

- **进程间（IPC）**：内存不互通，必须走内核机制——管道、消息队列、共享内存、信号量、Socket；Linux/Android 上还有 Binder。
- **线程间**：共享进程内存，直接读写共享变量，配合同步原语（synchronized / volatile、wait / notify、Lock、原子类）保证可见性与原子性。
- **协程间**：同一线程内的协程天然串行无竞争；跨协程通信用 Channel / Flow，保护共享状态用 Mutex——不需要系统级同步原语，但也同样存在"共享可变状态"的问题。

## 六、Android 中的跨进程（IPC）

Android 基于 Linux 内核，但**没有使用传统的管道 / 共享内存，而是自己实现了 Binder** 作为主要 IPC 方式。

### 为什么是 Binder

- 性能：传统 IPC 需要 2 次拷贝（发送方→内核→接收方），Binder 通过内核 `mmap` 让接收方与内核共享内存，只需 **1 次拷贝**，仅次于共享内存，且易用性好于它；
- 稳定：C / S 架构，客户端通过系统唯一的句柄（Binder 驱动分配）访问服务端；
- 安全：内核在事务中附带发送方的 UID / PID，一次校验身份，比传统 IPC 应用层自己验签更可靠（传统的 Socket 地址可以伪造）。

AMS、PMS 等几乎所有系统服务都构建在 Binder 之上。Binder 的原理、AIDL 生成代码分析、手写 Binder 见 [Android_Binder](./Android/Android_Binder.md)。

### 各种 IPC 方式对比

| 方式 | 特点 | 适用场景 |
| --- | --- | --- |
| Bundle / Intent | 最简单，基于 Binder，只能传可序列化数据；受 Binder 事务缓冲区（进程共享约 1MB）限制，过大会 TransactionTooLargeException | 四大组件间传递小数据 |
| 文件共享 | 简单，但并发读写不可靠 | 简单的数据交换，对同步要求低 |
| Messenger | 底层是 Binder + 消息（AIDL 封装），串行处理，不需要写 AIDL 接口，只能传消息不能调方法 | 低频、单向或一问一答的跨进程通信 |
| AIDL | 功能最强：自定义接口、支持并发调用、能拿到返回值和回调 | 复杂的跨进程 RPC，客户端需要主动调用服务的场景 |
| ContentProvider | 底层 Binder，面向数据的 CRUD，支持批量、权限控制 | 跨进程共享数据（通讯录、媒体库） |
| Socket（LocalSocket） | 走网络协议栈，开销大 | 网络通信，或不在意性能的本地跨进程 |
| 广播 | 单向、异步、低频 | 跨进程事件通知，不适合高频或请求-响应 |

选型：**传消息用 Messenger，调接口用 AIDL，共享数据用 ContentProvider，传小组件参数用 Bundle，网络用 Socket**。

### 开启多进程的代价

通过 `android:process` 开启多进程后要注意（详见 [Android_Binder](./Android/Android_Binder.md#android中的多进程模式)）：

- 同一 Application 会在每个进程里各创建一次，`onCreate` 会执行多次；
- 静态变量、单例在不同进程间是不同的对象， SharedPreferences 跨进程不再可靠；
- 进程间内存不共享，组件间传递对象必须序列化（Parcelable / Serializable）。
