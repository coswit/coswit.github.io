## 6. 擦除的神秘之处(The mystery of erasure)

看一个反直觉的事实:

```java
class Frobler {
    public static void main(String[] args) {
        Class c1 = new ArrayList<String>().getClass();
        Class c2 = new ArrayList<Integer>().getClass();
        System.out.println(c1 == c2);   // true!
    }
}
```

`ArrayList<String>` 与 `ArrayList<Integer>` 的 Class 是**同一个**——泛型类型在运行时被"擦除"了。

### C++ 的做法(The C++ approach)

对比 C++ 模板:编译器看到 `Holder<int>` 使用时,会**按类型实例化**出一份专属代码,类型信息完整保留,`new T()`、`T` 的成员访问都合法。Java 的泛型不是这样的实现:

```java
public class Manipulator<T> {
    private T obj;

    public Manipulator(T x) { obj = x; }

    public void manipulate() {
        // obj.f();   // 编译错误:T 在运行时是什么类型,编译器无从知晓
    }
}
```

当你想在泛型代码里调用 `T` 的方法时,擦除的掣肘立刻显现——**编译器只认识 Object 的方法**。给 `T` 加边界 `T extends HasF` 后才能调用 `HasF` 的方法(见第 8 节)。

### 迁移兼容性(Migration compatibility)

Java 选择擦除的核心原因是**迁移兼容性(migration compatibility)**:Java 5 的泛型必须能让泛型代码与非泛型的旧代码**互相操作**——泛型容器擦除后就是原始类型(raw type)的容器,新旧二进制可以混用。代价是:你无法在运行时知道泛型参数的类型。

> 泛型是"语言后期补装"的:容器类在 Java 1.0 就定型为持有 Object,擦除式泛型是在不动旧代码的前提下加上编译期检查的折中。C++ 的模板则是语言设计之初的机制,因此没有这个包袱。

### 擦除的问题(The problem with erasure)

擦除式泛型做不到的事:

```java
class Erased<T> {
    private final int SIZE = 100;

    public void f(Object arg) {
        // if (arg instanceof T) {}            // 编译错误
        // T var = new T();                    // 编译错误
        // T[] array = new T[SIZE];            // 编译错误
        // T[] array = (T) new Object[SIZE];   // 未检查警告:运行时不是真正的 T[]
    }
}
```

运行时,"T 是什么"这个信息不存在了。泛型参数在方法体内部**不可用**——它只在"边界"处起作用。

### 边界处的动作(The action at the boundaries)

泛型所有的动作发生在**编译期与编译器插入转型的边界处**:

```java
// 你写的代码:
SimpleHolder holder = new SimpleHolder();   // 假设 set/get 操作 T
holder.set("Item");
String s = (String) holder.get();           // 手写转型(前泛型风格)

// 泛型版:Holder<String> holder = ...
holder.set("Item");
String s = holder.get();   // 无转型——转型由编译器在边界处插入
```

即:值**进入**泛型容器时编译器检查类型、**离开**时编译器自动插入强转。方法内部的泛型类型 T 则是完全擦除的。

## 7. 补偿擦除(Compensating for erasure)

既然擦除带走了类型信息,就要用别的方式把信息**重新传进**泛型代码。

### 创建类型的实例(Creating instances of types)

方案一:传入 `Class<T>`,用反射创建(这正是 15-1 中 `BasicGenerator<T>` 的做法):

```java
class ClassAsFactory<T> {
    T x;

    public ClassAsFactory(Class<T> kind) {
        try {
            x = kind.getDeclaredConstructor().newInstance();
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    }
}
```

方案二(更推荐):显式的**工厂对象**。当类的构造器有参数、或类没有无参构造器时,`Class<T>` 方案失效,工厂都能胜任:

```java
interface FactoryI<T> {
    T create();
}

class Foo2<T> {
    private T x;

    public <F extends FactoryI<T>> Foo2(F factory) {  // 工厂自身也是泛型
        x = factory.create();
    }
}

class IntegerFactory implements FactoryI<Integer> {
    public Integer create() { return 47; }
}
```

> Java 8 之后,`java.util.function.Supplier<T>` 就是标准工厂接口:`new Foo2<>(() -> 47)` 或方法引用 `SomeClass::new`,语义与上面的 FactoryI 完全一致。

### 泛型数组(Arrays of generics)

`new T[]` 非法,通常的变通是`(T[]) new Object[容量]`——能工作但有未检查警告,且数组在运行时**实际是 Object[]**,`ArrayStoreException` 检查失效:

```java
class GenericArray<T> {
    private T[] array;

    @SuppressWarnings("unchecked")
    public GenericArray(int size) {
        array = (T[]) new Object[size];   // 运行时实为 Object[]
    }

    public T get(int index) { return array[index]; }
    public void put(int index, T item) { array[index] = item; }

    public T[] rep() { return array; }    // 若对外暴露会出问题
}
```

如果确实需要**运行时类型正确的泛型数组**,用 `Array.newInstance()` 反射创建,类型信息由调用方传入:

```java
class GenericArrayWithTypeToken<T> {
    private T[] array;

    @SuppressWarnings("unchecked")
    public GenericArrayWithTypeToken(Class<T> type, int size) {
        array = (T[]) Array.newInstance(type, size);   // 真正的 T[] 数组
    }
}
```

这正是标准库 `ArrayList<T>` 内部的做法(内部持有 `Object[]`,取出时转型)——**宁可内部用 Object[],也不暴露泛型数组**。

## 8. 边界(Bounds)

边界(bounds)给类型参数加约束:`<T extends Bound>`,声明"T 必须是 Bound 或其子类"。这有两个作用:

1. **补偿擦除**:只有声明了边界,编译器才知道 T 能调用哪些方法;
2. **约束调用方**:只接受满足条件的类型。

```java
interface HasColor {
    Color getColor();
}

class Colored<T extends HasColor> {       // T 必须实现 HasColor
    T item;

    Colored(T item) { this.item = item; }
    Color color() { return item.getColor(); }  // 有边界,才能调 HasColor 的方法
}
```

边界还能**同时约束多个类型**(类似多重继承):

```java
class Solid<T extends Dimension & HasColor & Weight> {
    // T 必须同时是 Dimension 的子类,并实现 HasColor 和 Weight
    T item;

    Solid(T item) { this.item = item; }
    Color color() { return item.getColor(); }       // 来自 HasColor
    double weight() { return item.weight(); }       // 来自 Weight
}
```

注意:`extends` 后第一个可以是类,其后必须全是接口;顺序错了编译报错。边界与继承可以叠加:`class Foo<T extends Animal>` 里再用 `Colored<T>` 时,T 还要满足 Colored 的边界。

## 9. 通配符(Wildcards)

通配符解决的核心问题是**协变(covariance)**。

### 数组协变 vs 泛型不变

数组是协变的:`Apple[]` 可以赋给 `Fruit[]`(Apple 是 Fruit 的子类)。但这是运行时错误的温床:

```java
Fruit[] fruits = new Apple[10];        // 编译通过(协变)
try {
    fruits[0] = new Strawberry();      // 编译也通过!
} catch (Exception e) {
    System.out.println(e);             // 运行时 ArrayStoreException
}
```

泛型**不协变**:`List<Apple>` 不是 `List<Fruit>` 的子类型——否则你就能往"其实是 apple 列表"的容器里放草莓。编译期拒绝,比运行时爆炸好得多。通配符就是在"绝对不变"与"受控协变"之间的折中:

```java
List<Apple> apples = new ArrayList<>();
// List<Fruit> fruits = apples;        // 编译错误:泛型不协变
List<? extends Fruit> fruits = apples; // 合法:"某种 Fruit 的列表"
```

### 编译器有多聪明?(How smart is the compiler?)

`List<? extends Fruit>` 的语义是"**某种**具体但未知的 Fruit 子类的列表"。编译器唯一能确定的是:取出的一定是 Fruit;但**放进去任何东西都不安全**:

```java
static void writeExact(List<Apple> apples, Apple apple) {
    apples.add(apple);                  // OK:类型精确
}

static void writeWithWildcard(List<? extends Fruit> apples, Apple apple) {
    // apples.add(apple);               // 编译错误!
    // 编译器不知道这个列表的确切元素类型,
    // 它可能是 List<Strawberry>,放 Apple 就错了
}
```

反过来读永远是安全的:

```java
static void readExact(List<Apple> apples) {
    Apple apple = apples.get(0);        // 精确类型,直取
}

static void readWithWildcard(List<? extends Fruit> fruits) {
    Fruit f = fruits.get(0);            // 取出只能当 Fruit 用
}
```

> 总结:`? extends T` 是**生产者(producer)**——只读不写;"get"。

### 逆变(Contravariance)

`? super Apple` 是反向的——"Apple 或其某个**父类**的列表"。写入安全、读取只能按 Object:

```java
static void writeTo(List<? super Apple> apples) {
    apples.add(new Apple());     // OK:无论列表是 List<Apple> 还是 List<Fruit>,装 Apple 都合法
    apples.add(new Jonathan());  // OK:Jonathan 是 Apple 的子类
    // Apple a = apples.get(0);  // 编译错误:元素类型只保证是 Object
    Object o = apples.get(0);
}
```

> `? super T` 是**消费者(consumer)**——只写不读;"put"。
>
> 合起来就是经典口诀:PECS——Producer Extends, Consumer Super。

三种引用的能力对照:

| 引用类型               | 放入元素        | 取出元素 | 语义                     |
| ---------------------- | --------------- | -------- | ------------------------ |
| `List<Apple>`          | 仅 Apple 及子类 | Apple    | 精确类型,读写皆可       |
| `List<? extends Fruit>`| 不可放入        | Fruit    | 某种未知 Fruit 子类:只读 |
| `List<? super Apple>`  | Apple 及子类    | Object   | 某个未知父类:只写       |
| `List<?>`              | 不可放入        | Object   | 任意未知类型:几乎只读   |

### 无界通配符(Unbounded wildcards)

`List<?>` 表示"持有某种特定类型的列表,但我不关心是什么"。它和原始类型(raw type)`List` 的区别:**`List<?>` 有类型检查,`List` 没有**。

典型用途是"对任何类型的列表都成立的操作":

```java
static void rawArgs(List holder, Object arg) {
    // holder.add(arg);        // 原始类型:编译器放弃检查(仅警告)
}

static void unboundedArg(List<?> holder, Object arg) {
    // holder.add(arg);        // 编译错误:? 的列表拒绝写入任何对象
    Object o = holder.get(0);  // 读出只能当 Object
}
```

判断意图的口诀:**用 `List<?>` 表达"我能处理任何类型";用 `List` 通常是把检查关掉,基本总是可疑的**。

一个微妙的场景:持有**混合类型**对象的列表必须写成 `List<?>`(如 `Arrays.asList(1, 2.0, "three")` 的返回)。

### 捕获转换(Capture conversion)

`List<?>` 无法直接写入,但**把它传给一个泛型方法**,编译器能"捕获"那个未知的类型参数:

```java
static <T> void f1(Holder<T> holder) {
    T t = holder.get();    // 在方法内部,T 是被捕获的具体类型
    // ... 可以安全地对 holder 做精确类型的操作
}

static void f2(Holder<?> holder) {
    f1(holder);            // 捕获转换:? 的类型被捕获为 f1 的 T
}
```

即:无法对 `?` 直接做的事,转交给泛型方法后反而能做——因为编译器在调用点捕获到了确切类型。这是通配符机制的自洽闭环。
