本篇是泛型笔记（三）,覆盖第 15 章小节 10–17（各种泛型议题、自限定类型、混入、潜在类型）,并补充 On Java 8 的 Java 8 视角。小节编号接前两篇。

## 10. 问题（Issues）

### 基本类型不能做类型参数（No primitives as type parameters）

擦除式泛型无法持有基本类型:`List<int>` 非法,只能 `List<Integer>` 并依赖自动装箱。装箱有可测的性能代价,容器类因此为基本类型提供专门的类（如 `IntStream`、第三方 fastutil 等）。C++ 模板没有这个限制。

### 实现参数化接口（Implementing parameterized interfaces）

一个类不能实现同一个泛型接口的**两种参数化**,否则擦除后接口重复:

```java
interface Payable<T> { }

class Employee implements Payable<Employee> { }
// class Hourly extends Employee implements Payable<Hourly> {}
// 编译错误:Hourly 会同时带来 Payable<Employee> 和 Payable<Hourly>,
// 擦除后都是 Payable,无法区分
```

### 转型与警告（Casting and warnings）

向泛型类型强转会得到"未检查（unchecked）"警告——因为运行时类型信息不存在,编译器无法保证转型正确:

```java
@SuppressWarnings("unchecked")
void f(Object obj) {
    List<String> list = (List<String>) obj;   // unchecked warning
}
```

有时必须与警告共存,但**每处 @SuppressWarnings 都应该有明确理由**。

### 重载（Overloading）

擦除会让两个"看起来不同"的重载撞车:

```java
void f(List<String> strList) { }
void f(List<Integer> intList) { }
// 编译错误:擦除后二者签名都是 f(List),无法共存
```

### 基类劫持了接口（Base class hijacks an interface）

```java
class Pet implements Comparable<Pet> { }

class Cat extends Pet { }
// 想让 Cat implements Comparable<Cat>?做不到:
// Cat 已经继承了 Comparable<Pet>,不能再实现 Comparable<Cat>
// ——基类"劫持"了接口的参数化
```

## 11. 自限定类型（Self-bounded types）

### 古怪的循环泛型（Curiously recurring generics）

下面这个形式叫 CRG（curiously recurring generics,古怪循环泛型）,初看费解:

```java
class GenericType<T> { }

class CuriouslyRecurringGeneric extends GenericType<CuriouslyRecurringGeneric> {
    // "我继承自『以我自己为参数』的泛型类"
}
```

它的实际用途:`基类`能用**导出类的类型**代替自己,模拟"自类型（self-type）"。

### 自限定（Self-bounding）

给参数加上循环边界,强制用户必须循环继承:

```java
class SelfBounded<T extends SelfBounded<T>> {
    T element;

    SelfBounded<T> set(T arg) {
        element = arg;
        return this;
    }

    T get() { return element; }
}

// 正确用法:参数就是自己
class A extends SelfBounded<A> { }
// class B extends SelfBounded<A> {}   // 编译错误:必须循环
```

### 参数协变（Argument covariance）

自限定的真正回报是**参数协变**。普通继承中,覆盖方法的参数必须精确相同（不协变）;自限定的 setter 却随子类改变参数类型:

```java
class GenericSetter<T> {
    void set(T arg) { }
}

// 不用自限定:
class BaseGS extends GenericSetter<Base> { }
class DerivedGS extends BaseGS {
    // void set(Derived d) {}   // 这不是覆盖,而是重载!
}

// 用自限定:
class SelfBoundedSetter<T extends SelfBoundedSetter<T>> {
    void set(T arg) { }
}

class StringSetter extends SelfBoundedSetter<StringSetter> {
    // set(StringSetter) 沿继承链精确匹配,类型一路跟随子类
}
```

标准库中的应用:`enum<E extends Enum<E>>` 正是这个模式。

## 12. 动态类型安全（Dynamic type safety）

Java 5 引入泛型后,新旧代码混用时旧代码可能把错误类型塞进你的泛型容器（它看到的是原始类型）,污染在运行时才爆炸。`Collections` 提供动态类型检查的包装器:

```java
List<String> list = new ArrayList<>();
List<String> checkedList = Collections.checkedList(list, String.class);

// 旧式代码拿到 checkedList 后:
// checkedList.add(42);   // 运行时立即抛 ClassCastException,而不是等到读取时
```

类似的还有 `checkedCollection()`、`checkedMap()`、`checkedSet()`。它们把"污染的暴露时机"从**远端的读取处**提前到**写入的当场**。

## 13. 异常（Exceptions）

泛型与异常的配合受到严格限制:

- **不能抛出/捕获泛型类型的异常对象**:`catch(T e)` 非法（擦除后 catch 无法区分）;
- **泛型类不能直接或间接继承 Throwable**:`class Problem<T> extends Exception` 非法;
- 类型参数可以出现在 **throws 子句**里——"方法可能抛出调用方指定的异常类型":

```java
interface Processor<T, E extends Exception> {
    void process(List<T> resultCollector) throws E;
}

class StringProcessor implements Processor<String, FailureException> {
    // E 被具体化为 FailureException,process 可抛出它
    public void process(List<String> resultCollector) throws FailureException { }
}
```

这带来一种有限的"检查型异常传播抽象":处理器接口不必绑定具体异常,实现类各自决定。

## 14. 混入（Mixins）

**混入（mixin）**:把多个类的行为"混合"进一个类。例如,混合 `Restaurant` 与 `Greeting` 得到一个"会打招呼的餐馆",还能继续混出"会打招呼、带摄影师的约会餐馆"。代码复用的理想是"像搭积木一样组合能力"。

### C++ 中的混入

C++ 可以"继承多个类、每个类有自己的实现与状态",配合模板按需实例化,是天然的多继承混入。

### 与接口混入（Mixing with interfaces）

Java 的"多继承"只有接口。接口能定义**能力组合**（`interface Mixin extends Interface1, Interface2`）,但每个实现类要自己写全部实现,能力无法复用:

```java
interface Timestamped { long getStamp(); void setStamp(long stamp); }
interface SerialNumbered { long getSerialNumber(); }

class Mixin implements Timestamped, SerialNumbered {
    private long stamp;
    private long serialNumber;

    // 两套实现都要手写,无法从别处复用
    public long getStamp() { return stamp; }
    public void setStamp(long stamp) { this.stamp = stamp; }
    public long getSerialNumber() { return serialNumber; }
}
```

### 用 Decorator 模式（Using the Decorator pattern）

装饰器:层层包裹,每层持有一个内层对象并"附加"一种能力。相比典型 Decorator,mixin 版本的关键差别:**包装层会暴露内层的全部接口**,而不是固定接口:

```java
class TimestampedImp implements Timestamped { /* 实现细节 */ }
class SerialNumberedImp implements SerialNumbered { /* 实现细节 */ }

class Mixin extends TimestampedImp implements SerialNumbered {
    private SerialNumberedImp s = new SerialNumberedImp();
    // 时间戳能力来自继承,序号能力来自组合 + 手工转发
    public long getSerialNumber() { return s.getSerialNumber(); }
}
```

### 用动态代理混入（Mixins with dynamic proxies）

动态代理可以工厂化地生成"混合体"——两个接口的两个实现,合成一个同时实现两接口的代理对象,调用按接口分发给对应实现:

```java
class MixinProxy implements InvocationHandler {
    // 每个接口绑定一个实现对象
    Map<String, Object> delegatesByMethod;

    @Override
    public Object invoke(Object proxy, Method method, Object[] args)
            throws Throwable {
        String methodName = method.getName();
        Object delegate = delegatesByMethod.get(methodName);
        return method.invoke(delegate, args);   // 分发给持有该方法的实现
    }

    @SuppressWarnings("unchecked")
    public static Object newInstance(Object... delegates) {
        // 收集所有接口,生成实现它们的代理
        Class[] interfaces = ...;
        return Proxy.newProxyInstance(
                ClassLoader.getSystemClassLoader(), interfaces,
                new MixinProxy(delegates));
    }
}

// 使用:一行得到混合体
Object mixin = MixinProxy.newInstance(
        new TimestampedImp(), new SerialNumberedImp());
Timestamped t = (Timestamped) mixin;
SerialNumbered s = (SerialNumbered) mixin;
```

局限性:代理对象只能调用接口方法,**无法访问任何状态字段**;方法命名冲突时策略简陋。

## 15. 潜在类型（Latent typing）

泛型的最高理想:写出**不依赖具体类型或接口**的通用代码。看这段伪代码:

```java
// 假想语言:只要对象"会 speak 和 sit"就能表演,不需要公共接口
def perform(performer):
    performer.speak()
    performer.sit()
```

这叫**潜在类型（latent typing,也叫结构化类型 structural typing）**或"鸭子类型（duck typing）":代码对类型的要求是"有这个签名的方法"而非"声明了这个接口"。C++ 模板天然如此（`perform` 接受任何有 speak/sit 的类型）,Python/Ruby 运行时如此。

Java 的泛型由于擦除 + 静态类型,**没有任何机制支持潜在类型**——泛型代码只能调用 Object 的方法或边界声明的方法。结果:同样的通用逻辑,Java 必须为每种类型层次写一遍,或把类型"上转型"到某个接口。

## 16. 补偿潜在类型的缺失（Compensating for the lack of latent typing）

既无语言支持,只能在"保持编译期类型安全"与"绕过类型系统"之间取舍。

### 反射（Reflection）

反射是 Java 里最接近潜在类型的机制——完全无视接口,按名字调用方法:

```java
class Mime {
    public void walkAgainstTheWind() { }
    public void pushInvisibleWalls() { }
    public String toString() { return "Mime"; }
}

// 潜在类型风格的调用:只要求"有这个方法"
static void perform(Object performer) {
    try {
        Method method = performer.getClass()
                .getMethod("walkAgainstTheWind");
        method.invoke(performer);
    } catch (Exception e) {
        throw new RuntimeException(performer.getClass().getSimpleName(), e);
    }
}
```

代价:方法名是字符串（拼错只有运行时才知道）、参数与返回值全靠 Object、性能差。

### 对序列应用方法（Applying a method to a sequence）

"给容器里每个对象调用某个方法"——潜在类型语言一行搞定,Java 用反射 + 边界接口折中:

```java
interface Performs {
    void speak();
    void sit();
}

// 有公共接口时,泛型 + 边界即可:
static <T extends Performs> void performAll(Collection<T> collection) {
    for (T performer : collection) {
        performer.speak();
        performer.sit();
    }
}
```

### 没有合适的接口时（When you don't happen to have the right interface）

当类型来自**无法修改的第三方库**（没有公共接口）时,只剩两条路:反射,或……

### 用适配器模拟（Simulating latent typing with adapters）

适配器模式:为不相关类型各写一个"翻译器",把潜在类型的调用翻译成各自的方法:

```java
interface Performer { void perform(); }

// 适配器把 Mime 的方法"翻译"成 perform
class MimePerformerAdapter implements Performer {
    private Mime mime;
    public MimePerformerAdapter(Mime m) { mime = m; }
    public void perform() { mime.walkAgainstTheWind(); }
}

class DogPerformerAdapter implements Performer {
    private Dog dog;
    public DogPerformerAdapter(Dog d) { dog = d; }
    public void perform() { dog.speak(); dog.sit(); }
}
```

编译期安全换来了样板的膨胀。

## 17. 函数对象作为策略（Using function objects as strategies）

策略模式在 Java 里通常用接口表达"一个可替换的操作"。泛型 + 接口的组合:

```java
interface Combiner<T> {
    T combine(T x, T y);
}

class Functional {
    // 用策略对象折叠一个集合:
    public static <T> T reduce(Iterable<T> seq, Combiner<T> combiner) {
        Iterator<T> it = seq.iterator();
        if (it.hasNext()) {
            T result = it.next();
            while (it.hasNext())
                result = combiner.combine(result, it.next());
            return result;
        }
        return null;
    }
}

// 使用:求和策略
Combiner<Integer> sum = (x, y) -> x + y;   // Java 8 之前的匿名类写法同理
```

> On Java 8 中这一节已被整个 **Functional Programming** 章取代:`Combiner<T>` 就是 `BinaryOperator<T>`,reduce 直接用 Stream 完成。函数式接口 + lambda 才是现代写法。

## 18. Java 8 的受助潜在类型（On Java 8: Assisted Latent Typing in Java 8）

"Java 不支持潜在类型"在 Java 8 之后需要修正——**非绑定方法引用（unbound method references）**提供了变通:把方法本身作为参数传入,泛型方法就能对**毫无公共接口的类型**执行操作。Eckel 称之为"受助潜在类型（assisted latent typing）"——"受助"是因为方法必须显式传递,不能只按名字调用:

```java
import java.util.function.*;

class PerformingDogA {
    public void speak() { System.out.println("Woof!"); }
    public void sit() { System.out.println("Sitting"); }
}

class RobotA {    // 与 PerformingDogA 没有任何公共接口
    public void speak() { System.out.println("Click!"); }
    public void sit() { System.out.println("Clank!"); }
}

class CommunicateA {
    // P 没有任何边界!操作完全由传入的两个 Consumer 决定
    public static <P> void perform(P performer,
                                   Consumer<P> action1,
                                   Consumer<P> action2) {
        action1.accept(performer);   // 把方法引用绑定到 performer 并调用
        action2.accept(performer);
    }
}

public class DogsAndRobotMethodReferences {
    public static void main(String[] args) {
        CommunicateA.perform(new PerformingDogA(),
                PerformingDogA::speak, PerformingDogA::sit);
        CommunicateA.perform(new RobotA(),
                RobotA::speak, RobotA::sit);
    }
}
```

`perform()` 是一段单一代码,却工作在不相关的类型上——潜在类型的目标达成了。而且与 Python 等语言的潜在类型相比,这里只要求**签名一致**,连方法名都可以不同（传什么方法引用就调什么）,泛化程度反而更高。

### 配合 Supplier 的泛型工具（On Java 8: Generic Methods to Use with Suppliers）

受助潜在类型的实战应用——`Suppliers` 工具:用生成器填充任意容器:

```java
public class Suppliers {
    // 创建并填充一个 Collection:
    public static <T, C extends Collection<T>> C
    create(Supplier<C> factory, Supplier<T> gen, int n) {
        return Stream.generate(gen)
                .limit(n)
                .collect(factory, C::add, C::addAll);
    }

    // 填充已有容器:
    public static <T, C extends Collection<T>>
    C fill(C coll, Supplier<T> gen, int n) {
        Stream.generate(gen).limit(n).forEach(coll::add);
        return coll;
    }

    // 受助潜在类型版:填充"任何有添加方法的对象",不限于 Collection
    public static <H, A> H fill(H holder,
                               BiConsumer<H, A> adder,
                               Supplier<A> gen, int n) {
        Stream.generate(gen).limit(n)
              .forEach(a -> adder.accept(holder, a));
        return holder;
    }
}

// 使用:
RandomList<Teller> tellers = Suppliers.create(RandomList::new, Teller::new, 4);
List<Customer> customers = Suppliers.fill(new ArrayList<>(), Customer::new, 12);
// Bank 不是 Collection,但有 put 方法——非绑定方法引用 Bank::put 完成适配:
Bank bank = Suppliers.fill(new Bank(), Bank::put, BankTeller::new, 3);
```

第三个 `fill` 的妙处:holder 不必实现任何接口,`BiConsumer<H, A>` 传入的"添加方法"就是对潜在类型的补偿——这正是第 16 节"适配器模拟"的函数式进化版。

## 19. 小结:转型真有那么糟吗?（On Java 8: Is Casting Really So Bad?）

Eckel 在 On Java 8 的章末反思了"狗进猫列表"这个泛型最常用的论证:前泛型时代把 Dog 塞进猫列表,取出转型时会抛 ClassCastException——听起来是泛型的最强理由。但他坦承:**这种 bug 在实践中极为罕见**,他几乎没见过谁真的被它困扰过。

他的结论:

> 泛型这个通用语言特性的意图是**表达力（expressiveness）**,而不只是类型安全的集合。类型安全的集合只是"能写出更通用代码"的副作用。

同时,由于泛型是后期补装进 Java 的,一些容器无法做到应有的健壮——例如 `Map.containsKey(Object key)`、`get(Object key)` 的参数是 Object 而非参数化类型（编译器不检查键类型）,而 C++ 的 map 键类型始终编译期检查。这是擦除式泛型的历史代价,也是理解本章所有"怪异"行为的钥匙。
