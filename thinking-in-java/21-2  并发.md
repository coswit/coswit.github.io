## 3. 共享资源(Sharing resources)

### 不恰当地访问资源(Improperly accessing resources)

多线程读写同一份数据时,可能"叠着写"互相覆盖——**竞态条件(race condition)**。经典反例 EvenGenerator:

```java
// 本意:下一个偶数
public abstract class IntGenerator {
    private volatile boolean canceled = false;
    public abstract int next();
    public void cancel() { canceled = true; }
    protected boolean isCanceled() { return canceled; }
}

public class EvenGenerator extends IntGenerator {
    private int currentEvenValue = 0;

    @Override
    public int next() {
        ++currentEvenValue;   // 危险区第一步
        ++currentEvenValue;   // 危险区第二步:两步之间可能被切走
        return currentEvenValue;
    }
}
```

`++` 是"读-改-写"三步,不是原子的。一个线程执行完第一个 `++` 后被切走,另一个线程读到的就是奇数。多线程按不同节奏访问同一个 EvenGenerator,用偶数检查器抓住错误:

```java
public class EvenChecker implements Runnable {
    private IntGenerator generator;

    @Override
    public void run() {
        while (!generator.isCanceled()) {
            int val = generator.next();
            if (val % 2 != 0) {
                System.out.println(val + " not even!");
                generator.cancel();   // 一旦抓到,通知所有检查器退出
            }
        }
    }
}
```

要点:错误**不一定出现**(时序依赖),这是并发 bug 难缠的根源;测试通过不等于没有竞态。

### 解决共享资源竞争(Resolving shared resource contention)

防止多个任务同时踩进"危险区"的手段是**加锁(lock)**:第一个到达的任务锁住资源,其余任务挂起等待。Java 的内建机制是 **synchronized** 关键字:

```java
public synchronized int next() {   // 方法级锁:对象内置锁(monitor)
    ++currentEvenValue;
    ++currentEvenValue;
    return currentEvenValue;
}
```

- 锁是**对象级**的(静态方法则是类级):一个线程拿到某对象的锁,其他想进入该对象任何 synchronized 方法的线程都得等;
- **每个对象都自带一把锁**;锁在任务离开 synchronized 方法/块时释放(异常也释放);
- synchronized 开销:进入/退出有成本,被锁住的代码串行——**只锁真正需要的部分**。

何时需要同步?**读取与写入共享可变数据的所有路径**都要同步;读方不同步同样危险(可见性问题,见下文)。

> Brian Goetz 的建议:在多线程与单线程混杂的场景中,共享可变数据的访问要么全部同步,要么全部不碰;单独同步写方是不够的。

### 显式 Lock 对象(Using explicit Lock objects)

Java 5 的 `java.util.concurrent.locks` 提供显式锁,比 synchronized 灵活:可尝试获取、可限时、可中断、可以不成对(方法论上更危险):

```java
public class MutexEvenGenerator extends IntGenerator {
    private int currentEvenValue = 0;
    private Lock lock = new ReentrantLock();   // 可重入锁

    @Override
    public int next() {
        lock.lock();                    // 显式加锁
        try {
            ++currentEvenValue;
            ++currentEvenValue;
            return currentEvenValue;
        } finally {
            lock.unlock();              // 必须在 finally 里解锁!
        }
    }
}
```

**try-finally 是显式锁的铁律**——忘了 unlock 就是死锁。ReentrantLock 的进阶能力:

```java
if (lock.tryLock()) {            // 尝试获取,拿不到立即返回 false
    try { /* ... */ } finally { lock.unlock(); }
} else {
    // 拿不到就干别的,不必挂起
}

lock.tryLock(2, TimeUnit.SECONDS);       // 限时等待
lock.lockInterruptibly();                // 等待中可被中断
```

选择:**能用 synchronized 就用 synchronized**(自动释放、不会忘记),需要 tryLock/限时/可中断时才用显式锁。

### 原子性与易变性(Atomicity and volatility)

**原子性(atomicity)**:操作不可分割。看似一步的 `++` 实际是三个动作,可能被线程间的任务切换打断。引入锁使 ++ 序列变成"原子"。

更深的问题是**可见性(visibility)**:不 synchronized 时,一个线程改了字段,另一个线程**可能永远看不到**——每个线程可以缓存变量的私有副本(JIT 与 CPU 优化的自由度)。

**volatile** 关键字:保证字段的读写直接发生在主内存,写 volatile 变量会刷回主存并使其他核的缓存失效——解决了可见性与指令重排序。

> volatile 的局限:它不保证原子性!`volatile int i; i++` 依然是三步操作。volatile 适合"一写多读"的标志位(如 canceled);任何复合操作仍需加锁。

对 long/double,JVM 允许 64 位读写拆成两次 32 位(除非 volatile/锁),多线程裸读写甚至能读到"半新半旧"的值——又一个必须同步的理由。

### 原子类(Atomic classes)

`java.util.concurrent.atomic` 提供"免锁、线程安全"的基本类型操作,靠 **CAS(Compare-And-Swap,比较并交换)** 的 CPU 原语实现:

```java
import java.util.concurrent.atomic.*;

AtomicInteger i = new AtomicInteger(0);
i.incrementAndGet();   // 原子的 ++i
i.getAndIncrement();   // 原子的 i++
i.compareAndSet(expect, update);  // CAS:当前值等于 expect 才改成 update

AtomicLong, AtomicLongArray,
AtomicBoolean, AtomicReference ... // 家族成员
```

原子类比锁**更轻**(无挂起/唤醒),竞争激烈时仍有优势;但它们只覆盖单变量——多变量的不变式还是得加锁。正常工程里,优先用高层工具(并发容器、Executor),原子类留给特殊的热点。

### 临界区(Critical sections)

只同步方法内部的一小段——**同步控制块(synchronized block)**,指定以哪个对象为锁:

```java
class Pair {                    // 非线程安全的值对
    private int x, y;
}

abstract class PairManager {
    protected Pair p = new Pair();
    private List<Pair> storage = new ArrayList<>();

    public Pair getPair() {
        // 临界区:复制一个快照返回(锁 this)
        synchronized (this) {
            return new Pair(p.getX(), p.getY());
        }
    }
}

class ExplicitPairManager extends PairManager {
    private Lock lock = new ReentrantLock();

    public void increment() {
        lock.lock();
        try {
            p.incrementX();
            p.incrementY();
            store(getPair());
        } finally {
            lock.unlock();
        }
    }
}
```

同步控制块让**读方与写方用同一把锁**,但锁的范围缩到最小——比把整个方法标 synchronized 更细。临界区的目标:**同一时刻只有一个任务在危险区**。

### 在其他对象上同步(Synchronizing on other objects)

synchronized 块的锁对象**不必是 this**——可以拿任意对象当锁,于是同一类里可以存在**两把互不相干的锁**:

```java
class DualSync {
    private Object syncObject = new Object();

    public synchronized void f() {          // 锁:this
        for (int i = 0; i < 5; i++)
            System.out.println("f()");
    }

    public void g() {
        synchronized (syncObject) {         // 锁:syncObject,与 f 互不阻塞
            for (int i = 0; i < 5; i++)
                System.out.println("g()");
        }
    }
}
```

这解锁了"多把锁保护多个独立资源"的设计;风险是读者必须追踪"哪个锁保护哪个资源",**每个共享对象一把锁、命名清晰**是维护性的底线。

### 线程本地存储(Thread local storage)

让每个线程拥有变量的**独立副本**,从根上消除共享——`ThreadLocal<T>`:

```java
public class ThreadLocalVariableHolder {
    private static ThreadLocal<Integer> value =
            new ThreadLocal<Integer>() {          // 或 ThreadLocal.withInitial(...)
                private Random rand = new Random(47);

                @Override
                protected synchronized Integer initialValue() {
                    return rand.nextInt(10000);
                }
            };

    public static void increment() {
        value.set(value.get() + 1);
    }

    public static int get() { return value.get(); }
}
```

每个线程 get 到的都是自己 set 的值,天然隔离。典型用途:数据库连接/会话上下文按线程绑定(SimpleDateFormat 的线程安全用法)。

## 4. 终止任务(Terminating tasks)

### 装饰性花园(The ornamental garden)

用一个模拟理解竞态:公园有多个入口(多个线程)同时 `count++` 一个总计数器——不保护则最终计数**偏小**(丢失更新):

```java
class Count {
    private int count = 0;
    private Random rand = new Random(47);

    // 去掉 synchronized 后,结果随机变小:
    public synchronized int increment() {
        int temp = count;
        if (rand.nextBoolean())   // 一半概率让出,放大竞争窗口
            Thread.yield();
        return (count = ++temp);
    }
    public synchronized int value() { return count; }
}
```

### 在阻塞时终止(Terminating when blocked)

线程的三种阻塞,终止难度不同:

| 阻塞原因                 | 可否被 interrupt() 打断           |
| ------------------------ | ---------------------------------- |
| sleep() / wait() / join()| 可以,抛 InterruptedException     |
| 等 synchronized 锁       | **不可以**                         |
| 等 ReentrantLock         | 可以(用 lockInterruptibly())     |
| 传统 I/O(如 InputStream.read) | **不可以**                   |
| NIO(Channel 上的阻塞)   | 可以,抛 ClosedByInterruptException |

### 中断(Interruption)

`t.interrupt()` 设置线程的**中断状态**,若线程正阻塞在可中断处则抛异常。任务的 run() 被要求处理 InterruptedException——这是"被通知去死"的标准信号:

```java
class Blocked implements Runnable {
    @Override
    public void run() {
        try {
            while (!Thread.currentThread().isInterrupted()) {
                System.out.println("working");
                TimeUnit.MILLISECONDS.sleep(100);   // 阻塞点:可被中断唤醒
            }
        } catch (InterruptedException e) {
            System.out.println("Exiting via interrupt");
        }
    }
}
```

对**不可中断的阻塞**,专用解法:

- I/O 流:`close()` 底层流(如 Socket),read() 立刻抛 SocketException;
- 显式锁:`lockInterruptibly()` 让等锁可被中断。

`shutdownNow()`(Executor 的"强停")就是对所有任务线程发 interrupt——所以任务要能优雅响应中断才算可终止。

### 被互斥量阻塞(Blocked by a mutex)

等 synchronized 锁无法被中断;演示:三个任务竞争同一把锁,一个任务陷入永久等待,interrupt 无法挽救——改用 ReentrantLock.lockInterruptibly() 则可以被中断脱身。

### 检查中断(Checking for an interrupt)

不依赖异常的轮询式检查:

```java
class NeedsCleanup {
    void cleanup() { System.out.println("Cleaning up"); }
}

class Blocked3 implements Runnable {
    private volatile double d = 47.0;

    @Override
    public void run() {
        try {
            while (!Thread.interrupted()) {     // 静态方法:检查并清除中断状态
                NeedsCleanup n1 = new NeedsCleanup();
                try {
                    System.out.println("sleeping");
                    TimeUnit.MILLISECONDS.sleep(1000);   // 阻塞点 1
                    NeedsCleanup n2 = new NeedsCleanup();
                    try {
                        System.out.println("calculating");
                        for (int i = 1; i < 2500000; i++)
                            d = d + (Math.PI + Math.E) / d;   // 长计算(阻塞点 2:不可中断)
                        System.out.println("Finished time-consuming operation");
                    } finally {
                        n2.cleanup();     // 内层资源在内层 finally 清理
                    }
                } finally {
                    n1.cleanup();         // 外层资源在外层 finally 清理
                }
            }
            System.out.println("Exiting via while() test");
        } catch (InterruptedException e) {
            System.out.println("Exiting via InterruptedException");
        }
    }
}
```

两个要点:

- `interrupted()`(静态)**检查并清除**状态;`isInterrupted()`(实例)**只查不清**;
- 在长计算内部周期性查中断,能让任务在**不可中断的计算**中也可被叫停——"检查中断"是响应性的最后一道保险。
