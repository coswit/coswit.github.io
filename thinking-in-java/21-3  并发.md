## 5. 任务间协作（Cooperation between tasks）

互斥（锁）解决"不能同时踩";协作解决"你干完我才能干"——任务间握手。

### wait() 与 notifyAll()

`wait()` 让任务**挂起并释放锁**,进入该对象的等待集;`notifyAll()` 唤醒该对象上所有等待的任务,它们醒来后**重新竞争锁**。经典示例——抛光-打蜡协作:

```java
class Car {
    private boolean waxOn = false;      // 条件标志:是否已打蜡

    public synchronized void waxed() {
        waxOn = true;                   // 改变条件
        notifyAll();                    // 通知所有等待者
    }

    public synchronized void buffed() {
        waxOn = false;                  // 改变条件
        notifyAll();
    }

    public synchronized void waitForWaxing() throws InterruptedException {
        // while 而非 if:醒来后必须重新检查条件
        while (waxOn == false)
            wait();
    }

    public synchronized void waitForBuffing() throws InterruptedException {
        while (waxOn == true)
            wait();
    }
}
```

```java
class WaxOn implements Runnable {          // 打蜡任务
    private Car car;
    public WaxOn(Car c) { car = c; }

    public void run() {
        try {
            while (!Thread.interrupted()) {
                System.out.println("Wax On! ");
                TimeUnit.MILLISECONDS.sleep(200);   // 模拟干活
                car.waxed();                        // 条件成立,通知
                car.waitForBuffing();               // 等待对方完成
            }
        } catch (InterruptedException e) {
            System.out.println("Exiting via interrupt");
        }
    }
}
// WaxOff 对称:buffed() + waitForWaxing()
```

**wait vs sleep**:

|          | sleep()          | wait()                |
| -------- | ---------------- | --------------------- |
| 所属     | Thread 静态方法  | Object 的方法         |
| 释放锁   | **不释放**       | **释放**              |
| 唤醒     | 时间到           | notify/notifyAll/超时 |
| 前提     | 无               | 必须持有该对象的锁    |

wait/notify 的调用位置约束:必须在 synchronized 上下文里（锁住 wait 的那个对象）,否则 IllegalMonitorStateException。

> 等待条件的标准范式永远是 `while (条件不满足) wait();`——醒来后条件未必成立（别的任务可能又改了它,或被"虚假唤醒"）,必须复查。

### 错过的信号（Missed Signals）

notify 发生在对方 wait **之前**时,通知丢失——对方永远等下去。防御法就是上面的 while 复查:任务醒来发现条件已满足就直接干活,不依赖"通知恰好到达"。用显式 Condition 时对应 `await()`/`signalAll()`。

### notify() vs. notifyAll()

`notify()` 只唤醒**一个**等待任务,且不保证唤醒"正确的那个"（按对象监视器队列,与条件无关）。多个任务等待不同条件时,notify 可能唤醒不相关任务,它检查条件后继续 wait,而真正该醒的任务被漏掉——**死等**。因此规则:**永远用 notifyAll(),它只是让所有等待者醒来复查一遍条件**。

### 生产者与消费者（Producers and consumers）

饭店模型:厨师（生产者）做菜放窗口,服务员（消费者）取菜;窗口空则服务员等,窗口满则厨师等——同一个锁上的两个条件:

```java
class Restaurant {
    private Meal meal;                  // "窗口":null 表示没菜
    private final WaitPerson waitPerson = new WaitPerson(this);
    private final Chef chef = new Chef(this);
    private ExecutorService exec;
    private final Random rand = new Random(47);

    class WaitPerson implements Runnable {      // 消费者
        public void run() {
            try {
                while (!Thread.interrupted()) {
                    synchronized (this) {
                        while (meal == null)
                            wait();             // 没菜,等
                    }
                    System.out.println("Waitperson got " + meal);
                    synchronized (chef) {
                        meal = null;
                        chef.notifyAll();       // 通知厨师:窗口空了
                    }
                }
            } catch (InterruptedException e) { /* 退出 */ }
        }
    }

    class Chef implements Runnable {            // 生产者
        public void run() {
            try {
                while (!Thread.interrupted()) {
                    synchronized (this) {
                        while (meal != null)
                            wait();             // 有菜没被取走,等
                    }
                    System.out.print("Order up! ");
                    synchronized (waitPerson) {
                        meal = new Meal(rand.nextInt(30));
                        waitPerson.notifyAll(); // 通知服务员:菜好了
                    }
                }
            } catch (InterruptedException e) { /* 退出 */ }
        }
    }
}
```

注意锁的**交叉**:每个任务"持自己的锁改共享条件,再持对方的锁发通知"——这种手动握手的复杂度,正是后来"队列模型"要消灭的。

### 使用显式 Lock 与 Condition 对象（Using explicit Lock and Condition objects）

Java 5 起,wait/notify 有了更细粒度的替代:一个 Lock 可以派生**多个 Condition**,每个条件独立等待/唤醒——饭店模型里"有菜""窗口空"两个条件分开,唤醒更精准（也仍建议 signalAll）:

```java
class ChefAndWaitPerson {
    private Lock lock = new ReentrantLock();
    private Condition orderAvailable = lock.newCondition();   // 条件 1
    private Condition orderSubmitted = lock.newCondition();  // 条件 2

    void produce() throws InterruptedException {
        lock.lock();
        try {
            while (meal != null)
                orderSubmitted.await();       // 对应 wait()
            meal = new Meal();
            orderAvailable.signalAll();       // 对应 notifyAll()
        } finally {
            lock.unlock();
        }
    }
}
```

### 生产者-消费者与队列（Producer-consumers and queues）

wait/notify 手动握手的**现代替代**:**阻塞队列（BlockingQueue）**——队满则 put 阻塞,队空则 take 阻塞,同步全部内置:

```java
// 用 BlockingQueue 跑任务:
class LiftOffRunner implements Runnable {
    private BlockingQueue<LiftOff> rockets;

    public LiftOffRunner(BlockingQueue<LiftOff> queue) { rockets = queue; }

    public void add(LiftOff lo) throws InterruptedException {
        rockets.put(lo);
    }

    public void run() {
        try {
            while (!Thread.interrupted()) {
                LiftOff rocket = rockets.take();   // 队列空则阻塞
                rocket.run();
            }
        } catch (InterruptedException e) { /* 退出 */ }
    }
}

// LinkedBlockingQueue(可选容量)/ ArrayBlockingQueue(固定容量)
// SynchronousQueue:零容量,put 直接交接给 take——"手递手"
```

吐司流水线展示了多级队列组装任务:洗涤→涂黄油→涂果酱,每级一个队列、一个任务,天然并发:

```java
class Toast {
    enum Status { DRY, BUTTERED, JAMMED }
    private Status status = Status.DRY;
    // 逐级加工:先 butter 队列,再 jammer 队列,最后由 eater 消费
}
```

### 用管道在线程间通信（Using pipes for I/O between tasks）

`PipedWriter/PipedReader` 提供线程间的字符流通道（生产-消费的字节流版）。如今较少直接使用（阻塞队列更常用）,理解"IO 管道本质是阻塞通道"即可:

```java
PipedWriter writer = new PipedWriter();
PipedReader reader = new PipedReader();
writer.connect(reader);   // 连接后,一端写,另一端阻塞读
```

## 6. 死锁（Deadlock）

任务各自持有一把锁、又都想拿对方的锁,永远互等——**死锁（deadlock）**。原书哲学家就餐:每位哲学家先拿左筷再拿右筷,围成一圈时可能人人手握左筷等右筷:

```java
class Chopstick {                        // 筷子就是锁
    private boolean taken = false;

    public synchronized void take() throws InterruptedException {
        while (taken)
            wait();
        taken = true;
    }

    public synchronized void drop() {
        taken = false;
        notifyAll();
    }
}

class Philosopher implements Runnable {
    private Chopstick left, right;

    public void run() {
        try {
            while (!Thread.interrupted()) {
                // 思考后就餐:先拿左,再拿右
                left.take();
                right.take();   // 若右筷被邻座拿走,握着左筷干等 → 死锁温床
                // 吃饭...
                right.drop();
                left.drop();
            }
        } catch (InterruptedException e) { /* 退出 */ }
    }
}
```

死锁的阴险之处:**不一定发生**——取决于时序,开发机上可能永远不复现,部署到多核才爆发。

死锁成立的**四个必要条件**（同时满足才死锁）:

1. **互斥（mutual exclusion）**:资源一次只能被一个任务使用（筷子一次一人拿）;
2. **请求与保持（hold and wait）**:任务持有资源的同时请求新资源（握左筷等右筷）;
3. **不可剥夺（no preemption）**:资源不能被强行夺走,只能持有者自愿释放;
4. **循环等待（circular wait）**:等待链首尾相接成环（围圈就餐）。

**破坏任意一条即可防死锁**。最容易的是破坏第 4 条:给资源**全局排序**,所有任务按同一顺序申请——让其中一位哲学家先拿右筷,环就不存在了:

```java
// 示意改写:原书的修复方式是"把某一位哲学家的左右筷引用对调"(实现见注释),这里改写为按座位号反向拿筷,原理相同
if (seat == 4) {          // 5 号位:先右后左
    right.take();
    left.take();
} else {
    left.take();
    right.take();
}
```

> On Java 8 用容量为 1 的 BlockingQueue（StickHolder）实现同样的哲学家示例:pickUp() 时 take() 阻塞、putDown() 时 put()——锁语义由队列提供,死锁条件与解法完全相同。Java 没有"防死锁"的语言级支持,只能靠设计纪律。

## 7. 新的库组件（New library components）

`java.util.concurrent` 的同步工具,比 wait/notify 高一级。

### CountDownLatch（倒数闸门）

一次性"等 N 件事发生"的闸门:`countDown()` 计数减一,`await()` 阻塞到计数归零:

```java
public class CountDownLatchDemo {
    static final int SIZE = 100;

    public static void main(String[] args) throws Exception {
        ExecutorService exec = Executors.newCachedThreadPool();
        CountDownLatch latch = new CountDownLatch(SIZE);   // 计数 100

        for (int i = 0; i < 10; i++)
            exec.execute(new WaitingTask(latch));          // 等待者:await()

        for (int i = 0; i < SIZE; i++)
            exec.execute(new TaskPortion(latch));          // 干活者:干完 countDown()

        System.out.println("Launched all tasks");
        exec.shutdown();
    }
}

class TaskPortion implements Runnable {
    private static int counter = 0;
    private final int id = counter++;
    private final CountDownLatch latch;

    public void run() {
        try {
            TimeUnit.MILLISECONDS.sleep(1000);   // 干活
        } catch (InterruptedException e) { /* ... */ }
        latch.countDown();                        // 完成一件
    }
}
```

典型用途:主线程等"全部子任务就绪"再继续（并行计算的汇合点）。计数无法重置,一次性。

### CyclicBarrier（循环栅栏）

N 个任务**互相等齐**再一起继续,可循环使用（`reset()`）——适合"多阶段全员同步"的并行迭代算法:

```java
CyclicBarrier barrier = new CyclicBarrier(parties, () -> {
    // 全部到达后执行的栅栏动作(如合并结果)
});

// 每个任务在阶段末:
barrier.await();   // 等其他所有任务也到达,然后全体继续
```

与 CountDownLatch 的区别:Latch 是"N 个完成事件唤醒等待者",Barrier 是"N 个参与者互相等";Barrier 可重复触发。

### DelayQueue（延迟队列）

**无界的 BlockingQueue,元素到期才能被取走**:元素实现 `Delayed` 接口,`getDelay()` 归零后 take() 才能拿到。到期时间最早的排在队头:

```java
class DelayedTask implements Delayed {
    private final long triggerTime;         // 到期时刻(System.nanoTime() + delayNs)

    @Override
    public long getDelay(TimeUnit unit) {
        return unit.convert(
                triggerTime - System.nanoTime(), TimeUnit.NANOSECONDS);
    }

    @Override
    public int compareTo(Delayed other) {   // 按"最先到期"排序
        return Long.compare(getDelay(TimeUnit.NANOSECONDS),
                other.getDelay(TimeUnit.NANOSECONDS));
    }
}
```

天然适合**定时任务队列**:所有任务按到期时间排序,take() 只在最早任务到期时返回。

### PriorityBlockingQueue（优先级阻塞队列）

BlockingQueue + 优先级:按 Comparator 排序出队（而非 FIFO）,队空则 take 阻塞。读取迭代器不保证顺序,但 take() 总给最高优先级元素:

```java
PriorityBlockingQueue<PriorityTask> queue =
        new PriorityBlockingQueue<>(11, Comparator.comparingInt(p -> p.priority));
```

适合"按紧急度调度"的任务队列（与 DelayQueue 组合 = 定时 + 优先）。

### ScheduledExecutor（周期调度）

`ScheduledThreadPoolExecutor` 支持**固定频率/固定间隔**调度,替代老 Timer（Timer 是单线程的,一个任务异常会杀死整个 Timer）:

```java
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(10);
scheduler.schedule(task, 5, TimeUnit.SECONDS);                     // 一次性延迟
scheduler.scheduleAtFixedRate(task, 0, 1, TimeUnit.SECONDS);       // 固定频率
scheduler.scheduleWithFixedDelay(task, 0, 1, TimeUnit.SECONDS);    // 固定间隔(上次结束起算)
```

### Semaphore（信号量）

**N 个许可**的计数信号量:`acquire()` 取许可（无则阻塞）,`release()` 归还——控制"同时访问某资源的任务数":

```java
public class Pool<T> {                       // 对象池:容量受限
    private int size;
    private List<T> items = new ArrayList<>();
    private volatile boolean[] checkedOut;
    private Semaphore available;             // 剩余许可

    public synchronized T getItem() throws InterruptedException {
        available.acquire();                 // 占一个坑位(满了则等)
        return getNextAvailableItem();
    }

    public synchronized void putItem(T x) {
        if (markAsUnused(x))
            available.release();             // 归还坑位
    }
}
```

经典模型:有限连接池、停车场。`acquire(n)` 一次拿多个。

### Exchanger（交换器）

**两个任务在汇合点交换对象**:一方 `exchange(obj)` 阻塞,另一方也 exchange 时各自拿到对方的东西——天然的生产-消费缓冲对:

```java
class ExchangerProducer<T> implements Runnable {      // 生产者:装满缓冲后交换
    private Exchanger<List<T>> exchanger;

    public void run() {
        List<T> holder = new ArrayList<>();
        while (!Thread.interrupted()) {
            // 填充 holder...
            holder = exchanger.exchange(holder);      // 交出满的,换回空的
        }
    }
}
class ExchangerConsumer<T> implements Runnable {      // 消费者:对称
    public void run() {
        List<T> holder = new ArrayList<>();
        while (!Thread.interrupted()) {
            holder = exchanger.exchange(holder);      // 交出空的,换回满的
            // 消费 holder...
        }
    }
}
```

适用于"两个任务轮流使用两个缓冲区"的场景（双缓冲）。
