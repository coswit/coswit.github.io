本篇是并发笔记(四),内容来自 On Java 8 的 Concurrent Programming 章——Bruce Eckel 用 Java 8 的 parallel Stream 与 CompletableFuture 重写的并发章,取代了 TIJ4 时代的低层细节路线,主线是:**能用高层工具就别碰底层**。

## 1. 术语问题(The Terminology Problem)

并发(concurrency)、并行(parallelism)、多任务(multitasking)、多处理(multiprocessing)、多线程(multithreading)、分布式系统——文献里混用严重。Brian Goetz 在 2016 年的演讲里给出干净的二分:

> Concurrency is about correctly and efficiently controlling access to shared resources.
> Parallelism uses additional resources to produce an answer faster.
>
> 并发关注的是正确且高效地控制共享资源的访问;并行是用额外的资源更快地算出结果。

按"慢在哪里"来定义更实用:

- **并发(Concurrency)**:同时推进多个任务,一个任务不必等另一个完成才开始。解决**有阻塞**的问题——最典型是 I/O,任务等外部输入时被称为阻塞,这类问题叫 I/O 密集(I/O bound);
- **并行(Parallelism)**:在多个处理器上同时执行。解决**计算密集(compute-bound)**的问题——拆开分头算才更快。

二者常被混为一谈的重要原因是:**Java 用同一种机制——线程——同时实现这两者**。更细的分法(非标准术语):纯并发(单 CPU 上跑)、并发-并行、并行-并发(如 Java 8 Stream,单核也能跑)、纯并行(离开多核跑不了)。

并发/并行的库支持是典型的**泄漏抽象(Leaky Abstraction)**:本想"抽象掉"的底层细节(CPU 缓存、处理器数量)总在不断穿透回来,最终还是得全部理解。

## 2. 并发的新定义(A New Definition of Concurrency)

Eckel 给出他认为终于抓住本质的定义:

> Concurrency is a collection of performance techniques focused on the reduction of waiting.
>
> 并发是一组以减少等待为核心的性能技术。

拆开看:

- **一组技术**:手段五花八门(线程、队列、Stream、Actor……),这是并发难以定义的原因;
- **性能技术**:并发的唯一正当理由是"程序不够快"。并发极易失控,除非有明确的性能问题,否则别用;用了,也选最简单的够用方案;
- **减少等待**:关键且微妙——**只有某处在等待,才有优化空间**。I/O 秒回、各核满载互不等待,并发无从发力;反之,等待的形式多样,才催生了多样的并发技术。

## 3. 并发的超能力(Concurrency Superpowers)

一个科幻隐喻:在一栋千万房间的楼里找一件东西,你拥有"分身术"——每遇岔路就一分为二。理想模型里分身与处理器一一对应,但现实会泄漏:

- 处理器只有几个,分身却可以有几千个——需要**任务切换**机制;
- 分身敲门等待时,对应的处理器不该闲着——把处理器派给能干活的分身;
- 单处理器时,切换成本由唯一的 CPU 承担,并发可能**更慢**;但若任务大多在阻塞(敲门等待),单处理器上的并发依然受益——切换到"不等待的任务"上;
- 计算密集型(如破解密码)最好"每个工人独占一个处理器";客服模型(有限的人接打不完的电话)则必须排队;而"鞋匠与精灵"模型提醒:工序中**最慢的一环**限制整体速率,决定方案设计。

两个任务"同时"执行还会互相干扰——**共享内存(shared memory)**问题:两个工人抢同一个蛋糕盒,蛋糕挤烂。这就是**竞态条件(race condition)**:结果取决于谁先抢到。它发生得如此偶然,以至于并发"理论上确定,实际上不确定"——细心的检查也许能写出正确的并发程序,但实践里更常见的是"看起来对,条件凑齐才崩"的程序,而触发条件可能根本无法用测试复现。这是学习并发最强的理由:**不懂它,迟早被咬**。

## 4. 并发是为了速度(Concurrency is for Speed)

除非程序不够快,否则不值得跳进并发这口"悲伤之井"。先考虑:更快的机器(往往比程序员的时间便宜)、profiler 找瓶颈换算法。都不行,才**在最孤立的局部**引入并发。

速度问题第一眼很简单:拆开分头跑。时钟频率提升停滞后,提速以多核形式出现,并发正是利用多核的手段。但**单处理器**上并发也常能提速——反直觉却在理:单处理器上并发本有上下文切换的额外开销,若所有任务永远不阻塞,并发纯属亏本;**阻塞**改变了账本**——一个任务等 I/O 时,没有并发整个程序就停摆,有并发其他任务还能推进。事件驱动 UI 是单处理器受益的典型:耗时计算放后台线程,界面才能保持响应。

实现层面的两条路:**进程**(独立地址空间,OS 隔离好、编程容易,但数量与开销受限)与**线程**(共享内存与 I/O,经济但必须协调共享资源)。Java 选择了后者:在顺序语言之上加线程。

## 5. Java 并发的四大格言(The Four Maxims of Java Concurrency)

Eckel 多年与 Java 并发搏斗的总结。这些格言针对 Java 的设计问题(有些语言天生免疫)。

### 格言一:别做(1. Don't do it)

(也别自己做。)避开并发深坑最简单的办法就是不用它。看似简单的尝试也暗坑无数。唯一正当理由是速度——"希望它更快"不算,`profiler` 证明不够快才算。被迫入坑时,选**最简单、最安全**的路径:用久经考验的库,自己写的代码越少越好。并发领域没有"太简单"一说,**机灵是你的敌人**。

### 格言二:没有什么是真的,一切都有影响(2. Nothing is true and everything matters)

无并发的世界里,变量赋值天经地义地生效;并发世界里,必须**假设一切皆不可靠、怀疑一切**:连给变量赋值都可能不按预期工作。平时可以无视的东西——处理器缓存与主内存的一致性、对象构造的深水区(构造器会不会把数据泄露给其他线程)——统统变成必须理解的问题。

### 格言三:能跑不等于没坏(3. Just because it works doesn't mean it's not broken)

> You can't prove a concurrent program is correct, you can only (sometimes) prove it is incorrect.
>
> 你无法证明一个并发程序是对的,只能(有时)证明它是错的。

多数时候连"证伪"都做不到:坏了也检测不出来。测试通常无能为力,只能靠代码审视 + 深厚功力。即使"能跑",也只是在设计参数内能跑;超出参数照样崩。这个领域要对抗"达克效应(Dunning-Kruger Effect,知道得越少越自信)":无论你多确信代码线程安全,它多半仍有洞。**最危险的状态是"自信"**。

### 格言四:你仍然必须理解它(4. You must still understand it)

被前三条吓退、"继续绕着走"是理性反应——甚至可以考虑 Clojure/Scala 这些为并发而生的 JVM 语言。但逃不掉:

- 即使你从不显式开线程,你用的框架会(Swing、Timer、Web 服务器……);
- 你写的组件终将被别人放进多线程环境——哪怕你的选择是宣布"非线程安全",你也得懂这句话意味着什么;
- Java 本质是多线程语言,Web 系统这类最常见的 Java 应用天生并发。**你没得选线程什么时候出现。**

## 6. 残酷真相(The Brutal Truth)

Java 在自信、热情与紧迫中诞生。语言的早期像气体一样可塑,似乎怎么改都行;一旦被广泛使用就凝固,任何决策都被永久固化——Java 的版图上因此散落着糟糕的决定(Thread 类里一堆 Deprecated 方法就是证据)。

线程被塞进了 Java 1.0。当时并不清楚并发对高级语言意味着什么:C 这类原始语言把线程当外挂库没问题,但把原始线程模型贴进一门复杂语言,根本的不匹配就暴露了——**要把并发做对,语言的一切特性都会被牵连**,包括"标识符是否代表可变的值"这种最底层的决定。不变性与无副作用(纯函数式语言的基石)能极大简化并发,但当年对主流语言的设计者来说太激进。结果:

> Java 永远不会是一门"为并发而设计"的语言,只是一门"允许并发"的语言。
>
> Java threads can never be simple or safe.

了不起的是,尽管带着无法修复的根本缺陷,后续版本仍把抽象层一点点垫高——Java 8 的 **parallel Stream 与 CompletableFuture 是史诗级的魔法**,大幅简化了并发的思维与代码。但根本问题仍在:语言的每个角落依然脆弱,你仍然必须理解那些复杂微妙的问题。

## 7. 并行流(Parallel Streams)

Stream 采用**内部迭代**(库控制迭代器,用易分割的 Spliterator),换来一个神奇能力:**在表达式里加一个 `parallel()`,整个流就变成并行任务集**:

```java
import java.util.stream.*;

public class ParallelPrime {
    static final int COUNT = 100_000;

    public static boolean isPrime(long n) {
        return rangeClosed(2, (long) Math.sqrt(n))
                .noneMatch(i -> n % i == 0);
    }

    public static void main(String[] args) throws IOException {
        Timer timer = new Timer();
        List<String> primes =
                iterate(2, i -> i + 1)
                        .parallel()                       // [1] 一词并行化
                        .filter(ParallelPrime::isPrime)
                        .limit(COUNT)
                        .mapToObj(Long::toString)
                        .collect(Collectors.toList());
        System.out.println(timer.duration());
        Files.write(Paths.get("primes.txt"), primes,
                StandardOpenOption.CREATE);  // 写盘防死代码消除
    }
}
```

注释掉 [1] 的 `parallel()` 后耗时约为 3 倍。看起来是白捡的午餐——但"残酷真相"警告过:不可能这么简单。

### parallel() 不是万灵药(parallel() is not a Panacea)

对"求 1..N 的和"做基准对比(全程序计时,非微基准;结果随机器而异):

```java
public class Summing {
    static final int SZ = 100_000_000;
    static final long CHECK = (long) SZ * ((long) SZ + 1) / 2; // 高斯求和

    static void timeTest(String id, long checkValue,
                         LongSupplier operation) { /* 计时并校验 */ }

    public static void main(String[] args) {
        timeTest("Sum Stream", CHECK, () ->
                LongStream.rangeClosed(0, SZ).sum());
        timeTest("Sum Stream Parallel", CHECK, () ->
                LongStream.rangeClosed(0, SZ).parallel().sum());
        timeTest("Sum Iterated", CHECK, () ->
                LongStream.iterate(0, i -> i + 1)
                        .limit(SZ + 1).sum());
        // "Sum Iterated Parallel" 更慢且 SZ 上百万时内存溢出,注释掉
    }
}
/* Output(示例):
Sum Stream: 167ms
Sum Stream Parallel: 46ms
Sum Iterated: 284ms
*/
```

结论一:`rangeClosed().parallel()` 快很多;但 `iterate().parallel()` **更慢还会 OOM**。为什么?流并行算法先把数据**切分**再分头算,数据源的可分割性决定一切:

| 数据源           | 可分割性                                     |
| ---------------- | -------------------------------------------- |
| 数组             | 便宜、均匀、长度已知——**理想**               |
| 链表             | 只能"第一个 + 其余",几乎不可分割——**糟糕** |
| 无状态生成器     | 类似数组(range 就是)——好                  |
| 迭代式生成器     | 类似链表(iterate 就是)——差               |

结论二:装箱毁掉一切。`long[]` 换成 `Long[]` 后,基准全线爆炸:

```text
同一台机器、SZ=1000 万的对比:
Basic Sum(循环 long[]):        16ms
parallel()(long[] 并行求和):    14ms
Long Basic Sum(循环 Long[]):    21ms
Long Array Stream Reduce:     1046ms   ← 装箱 + 流
Long Parallel:                1008ms   ← 并行救不回装箱的损失
Long parallelPrefix:          3287ms
```

原因在**处理器缓存**:long[] 是连续内存,CPU 能预取、缓存命中率高;Long[] 是"引用的数组",对象本体散落堆中、几乎每次访问都出缓存。parallelPrefix 更惨:每步读两个元素写回一个,三次出缓存。

> 教训:parallel() 不是"加个词就变快"。**先看数据结构可否高效分割,再警惕装箱**;否则可能显著变慢。

### Stream 与 Collection 的纠葛

流为"无限流"模型设计,集合为有限规模优化——Java 8 把两者捏在一起:集合没有 map/reduce,必须先变 Stream。集合转 Stream 加 parallel() 的组合有坑(如 limit() 与 parallel() 的交互语义反直觉),但大方向是好的:**先用 Stream 表达问题,再评估要不要 parallel()**。

## 8. 创建与运行任务(Creating and Running Tasks)

Stream 搞不定的场合,要自己创建任务。历史上那些原始机制(裸 Thread、中断等)归入低层附录;这里只给"最简单且最好"的规范形式。

### 任务与 Executor(Tasks and Executors)

早期 Java 直接 new Thread(开销大,现已不鼓励)。Java 5 起的标准做法:**任务是 Runnable,执行交给 ExecutorService 线程池**(线程复用):

```java
// 一个"打盹任务":睡 0.1 秒后报出自己的线程名
public class NapTask implements Runnable {
    final int id;
    public NapTask(int id) { this.id = id; }
    @Override
    public void run() {
        new Nap(0.1);
        System.out.println(this + " " + Thread.currentThread().getName());
    }
    @Override public String toString() { return "NapTask[" + id + "]"; }
}

public class SingleThreadExecutor {
    public static void main(String[] args) {
        ExecutorService exec = Executors.newSingleThreadExecutor();
        IntStream.range(0, 10)
                 .mapToObj(NapTask::new)
                 .forEach(exec::execute);   // 提交 10 个任务
        System.out.println("All tasks submitted");   // 立即打印:提交不阻塞
        exec.shutdown();                    // 关门:不收新任务,已有的跑完
        while (!exec.isTerminated())        // 等全部完成(main 与任务并发)
            new Nap(0.1);
    }
}
```

- `shutdown()` 后再提交任务抛 `RejectedExecutionException`;
- `shutdownNow()` 还会试图中断正在运行的任务——中断是反模式,能不用就不用(见第 9 节);
- 单线程执行器的输出里只有 `main` 和 `pool-1-thread-1` 两个线程交错——并发的直接证据。

### 多线程与线程封闭(Using More Threads)

`newCachedThreadPool()` 给每个任务分线程,并行执行明显更快。但线程一多,**共享可变状态**立刻出事:

```java
public class InterferingTask implements Runnable {
    final int id;
    private static Integer val = 0;      // 静态可变共享状态

    @Override
    public void run() {
        for (int i = 0; i < 100; i++)
            val++;                        // 非原子的读改写
        System.out.println(id + " "
                + Thread.currentThread().getName() + " " + val);
    }
}
// CachedThreadPool 跑 10 个:输出 200/300/... 乱序且每次不同
// SingleThreadExecutor 跑:稳定输出 100/200/.../1000
```

多线程版本每次结果都不同——val 是**可变共享状态(mutable shared state)**,并发修改产生竞态。单线程执行器却次次正确:**SingleThreadExecutor 的本质价值是线程封闭(thread confinement)**——任务在同一根线程上串行,线程安全被"强制"施加,牺牲提速换取免于调试地狱。

### 产生结果(Producing Results)

Runnable 靠副作用交结果,副作用正是万恶之源。消除法:**用 Callable 返回结果,消灭共享状态**——"自私小孩原则:什么都不分享(Share nothing)":

```java
public class CountingTask implements Callable<Integer> {
    final int id;
    public CountingTask(int id) { this.id = id; }
    @Override
    public Integer call() {
        Integer val = 0;
        for (int i = 0; i < 100; i++)
            val++;                        // 局部变量,无共享
        return val;                       // 结果用返回值交付
    }
}

// invokeAll:全部完成后返回 Future 列表
List<Future<Integer>> futures = exec.invokeAll(tasks);
Integer sum = futures.stream()
        .map(f -> { try { return f.get(); }
                    catch (Exception e) { throw new RuntimeException(e); } })
        .reduce(0, Integer::sum);
```

**Future** 是 Java 5 的"凭据"机制:提交任务不等待,回头凭 Future 取结果。但 `get()` 会**阻塞**,`invokeAll()` 又要等全部完成——Future 其实只推迟了等待,并没有消灭等待;提取结果的异常处理也很啰嗦。Future 已被判定为低效方案、不再推荐(老代码里还会遇到)。

同样的事用并行流干净得多:

```java
System.out.println(
        IntStream.range(0, 10)
                 .parallel()                       // 就这一个词
                 .mapToObj(CountingTask::new)
                 .map(ct -> ct.call())
                 .reduce(0, Integer::sum));        // 1000
```

### Lambda 与方法引用做任务(Lambdas and Method References as Tasks)

Java 8 按**签名匹配**(结构一致)接受任务,不要求"是 Runnable/Callable 类型"——非绑定方法引用也能直接提交:

```java
exec.submit(() -> System.out.println("Lambda1"));   // lambda
exec.submit(new NotRunnable()::go);                 // 任意签名的非绑定方法引用
exec.submit(() -> { System.out.println("Lambda2"); return 1; });
exec.submit(new NotCallable()::get);
```

这正是"非绑定方法引用做潜在类型补偿"的并发应用:任务不实现任何接口,凭签名就能提交。

## 9. 终止长任务(Terminating Long-Running Tasks)

长任务需要被叫停。原始的中断机制(interrupt)混乱、易错、丢状态,是**反模式**;但 InterruptedException 作为历史残留还得继续 catch。

最佳实践:**标志位 + 任务自查**——不拔电源,而是请任务"走到合适的地方自己收尾":

```java
public class QuittableTask implements Runnable {
    final int id;
    public QuittableTask(int id) { this.id = id; }

    private AtomicBoolean running = new AtomicBoolean(true);

    public void quit() { running.set(false); }      // 外部请求退出

    @Override
    public void run() {
        while (running.get())                       // [1] 周期性自查标志
            new Nap(0.1);
        System.out.print(id + " ");                 // [2] 退出前打印
    }
}

public class QuittingTasks {
    public static final int COUNT = 150;
    public static void main(String[] args) {
        ExecutorService es = Executors.newCachedThreadPool();
        List<QuittableTask> tasks =
                IntStream.range(1, COUNT)
                         .mapToObj(QuittableTask::new)
                         .peek(qt -> es.execute(qt))   // 边建边提交
                         .collect(Collectors.toList());
        new Nap(1);                          // 跑一会儿
        tasks.forEach(QuittableTask::quit);  // 逐个请求退出
        es.shutdown();
    }
}
```

为什么是 **AtomicBoolean** 而不是 boolean?这正是并发最深的难点:换成普通 boolean,这个程序**大概率永远不出错**——但它依然不安全,而且几乎不可能写出能暴露问题的测试。你得不到"做错了"的任何即时反馈,**线程安全只能靠把所有坑记在脑子里**。

任务不会按创建顺序退出:独立运行的任务对信号的非确定性响应,再上一课。javac 会让 main 在任务全部结束后才退出;换成 CompletableFuture 的写法(下一节),连 ExecutorService 都不需要。

## 10. CompletableFuture

Java 8 的 CompletableFuture 是 Future 的彻底升级:**链式操作**——干洗店收据的比喻:Future 让你"凭票取衣",但取衣还是要你自己到场等;CompletableFuture 让"取衣→搭配→熨烫→收纳"整条流水线自动衔接。

```java
// 最简形式:runAsync 启动任务,join 等待收尾(无 ExecutorService、无 shutdown)
List<CompletableFuture<Void>> cfutures =
        tasks.stream()
             .map(CompletableFuture::runAsync)   // 每个任务异步启动
             .collect(Collectors.toList());
tasks.forEach(QuittableTask::quit);
cfutures.forEach(CompletableFuture::join);       // 等全部结束
```

### 基本用法(Basic Usage)

用一个状态机对象演示(Machina:每步 0.1 秒推进一步,START→ONE→TWO→THREE→END):

```java
public class Machina {
    public enum State { START, ONE, TWO, THREE, END;
        State step() {
            if (equals(END)) return END;
            return values()[ordinal() + 1];
        }
    }
    private State state = State.START;
    private final int id;

    public static Machina work(Machina m) {     // 每次推进一步
        if (!m.state.equals(State.END)) {
            new Nap(0.1);
            m.state = m.state.step();
        }
        System.out.println(m);
        return m;
    }
}
```

**completedFuture 包装 + thenApply 串操作**:

```java
CompletableFuture<Machina> cf =
        CompletableFuture.completedFuture(new Machina(0))
                .thenApply(Machina::work)     // 取出包装的对象→运算→重新包装
                .thenApply(Machina::work)
                .thenApply(Machina::work)
                .thenApply(Machina::work);
```

CompletableFuture 的本质便利:**自动拆包/重新包装**它携带的对象(像 Stream 的 map),你不用碰"容器"细节。`thenApply` 接 Function(有入参有返回),函数可以换类型——返回类型跟着变。

**加 Async 前缀 = 异步执行**:

```java
CompletableFuture<Machina> cf =
        CompletableFuture.completedFuture(new Machina(0))
                .thenApplyAsync(Machina::work)   // 立即返回,后台执行
                .thenApplyAsync(Machina::work)
                .thenApplyAsync(Machina::work)
                .thenApplyAsync(Machina::work);
System.out.println(cf.join());   // 没有 join,程序可能先退出!
```

同步调用 = "干完再返回";**Async 调用 = "立即返回,后台继续干"**。后台衔接靠库把操作链存成**回调(callback)**表——手工管理回调的灾难叫"回调地狱",CompletableFuture 替你管理。一般而言:**没有特殊理由就用 Async 版**。

### 操作一览(Other Operations)

| 操作                        | 入参行为           | 结果                        |
| --------------------------- | ------------------ | --------------------------- |
| `runAsync(runnable)`        | 无参任务           | CompletableFuture\<Void\>   |
| `supplyAsync(supplier)`     | 无参,产结果       | CompletableFuture\<T\>      |
| `thenApply(fn)`             | 拿到解包的值       | 运算结果(类型可变)        |
| `thenAccept(consumer)`      | 拿到解包的值       | 无结果(Void)               |
| `thenRun(runnable)`         | 不看值,只接在后面 | 无结果                      |
| `thenCompose(fn)`           | 拿到值             | 结果必须已是 CompletableFuture(扁平化)|
| `join()` / `get()`          | —                  | 阻塞取值;join 不抛受检异常 |
| `getNow(默认值)`            | —                  | 未完成给默认值              |
| `complete(v)` / `obtrudeValue(v)` | —           | 手动完成 / 强制覆盖结果     |
| `cancel(mayInterrupt)`      | —                  | 取消(变成"异常完成")      |

`getNumberOfDependents()` 显示一个阶段可以**分叉**出多个后续任务。

### 组合多个 CompletableFuture(Combining CompletableFutures)

两个 future 各自完成(像赛跑),组合方法决定怎么用双方结果:`thenCombine(other, fn)`(融合两值)、`applyToEither(other, fn)`(取先完成者)、`thenAcceptBoth`、`runAfterEither/Both` 等:

```java
CompletableFuture<A> cfa = CompletableFuture.supplyAsync(() -> makeA());
CompletableFuture<B> cfb = CompletableFuture.supplyAsync(() -> makeB());

CompletableFuture<C> cfc =
        cfa.thenCombine(cfb, (a, b) -> combine(a, b));   // 两者齐备才融合
cfc = cfa.applyToEither(cfb, x -> useFirst(x));          // 谁先好用谁
```

### 异常(Exceptions)

操作链中的异常不会沿调用栈传播(链是回调,不是调用栈),而是被**装进 future**:异常完成(exceptionally completed)后,链上后续操作跳过,`join()` 抛 CompletionException。处理:

```java
cf.exceptionally(ex -> fallback)   // 异常时给兜底值,链继续
  .whenComplete((v, ex) -> /* 正常/异常都执行 */);
```

原书演示:链中某步抛 RuntimeException,后续 thenApply 全部跳过,exceptionally 接住并给出替代值——**异步世界的 try-catch**。

## 11. 死锁(Deadlock)

等待链首尾相接,全体卡死。On Java 8 的哲学家实现用**容量为 1 的 BlockingQueue** 做筷子——pickUp() 时 take()(筷子被占则阻塞),putDown() 时 put(),线程安全全由队列承担:

```java
public class StickHolder {
    private static class Chopstick { }
    private Chopstick stick = new Chopstick();
    private BlockingQueue<Chopstick> holder = new ArrayBlockingQueue<>(1);

    public StickHolder() { putDown(); }

    public void pickUp() {
        try { holder.take(); }                 // 不可得则阻塞
        catch (InterruptedException e) { throw new RuntimeException(e); }
    }

    public void putDown() {
        try { holder.put(stick); }
        catch (InterruptedException e) { throw new RuntimeException(e); }
    }
}

public class Philosopher implements Runnable {
    private final int seat;
    private final StickHolder left, right;

    @Override
    public void run() {
        while (true) {
            right.pickUp();      // 先右后左
            left.pickUp();
            System.out.println(this + " eating");
            right.putDown();
            left.putDown();
        }
    }
}

public class DiningPhilosophers {
    public DiningPhilosophers(int n) {
        StickHolder[] sticks = new StickHolder[n];
        Arrays.setAll(sticks, i -> new StickHolder());
        Philosopher[] philosophers = new Philosopher[n];
        Arrays.setAll(philosophers, i ->
                new Philosopher(i, sticks[i], sticks[(i + 1) % n]));  // [1] 围成一圈
        // 修复:把某一位哲学家的左右顺序反过来,破坏循环等待
        // philosophers[1] = new Philosopher(1, sticks[0], sticks[1]);
        Arrays.stream(philosophers)
              .forEach(CompletableFuture::runAsync);   // 用 CF 启动全部
    }
}
```

程序"看起来在跑",直到某天输出戛然而止——死锁发生与否**取决于核数**(双核机器可能几乎不出现,多核一触即发)。这让它成为绝佳教材:你可能在双核机上确信程序正确,部署到别的机器才开始死锁。

死锁的四个必要条件:**互斥**(资源一次一个任务用)、**请求与保持**(拿着一个等另一个)、**不可剥夺**(资源不能被强抢)、**循环等待**(等待链成环)。四条同时满足才死锁,破坏任意一条即可解除;此处最省事的修复是破坏**循环等待**:让其中一位哲学家先拿左筷。

## 12. 构造器不是线程安全的(Constructors are not Thread-Safe)

直觉认为"对象构造完成前别人看不到它,何来竞争"——JLS(Java Language Specification,Java 语言规范)也这么宣称。但对象构造与共享内存的纠缠照样出事。最"无辜"的例子:用静态字段生成唯一 ID:

```java
public class StaticIDField implements HasID {
    private static int counter = 0;
    private int id = counter++;     // 看起来无懈可击
    public int getID() { return id; }
}
```

两个任务并发各建 10 万个对象,统计两边 ID 的交集:

```java
public class IDChecker {
    public static final int SIZE = 100_000;

    public static void test(Supplier<HasID> gen) {
        CompletableFuture<List<Integer>> groupA =
                CompletableFuture.supplyAsync(() -> make(gen));
        CompletableFuture<List<Integer>> groupB =
                CompletableFuture.supplyAsync(() -> make(gen));
        groupA.thenAcceptBoth(groupB, (a, b) ->
                System.out.println(dupCount(a, b))).join();
    }
    // make: Stream.generate(gen).limit(SIZE).map(getID).collect(toList())
}

// IDChecker.test(StaticIDField::new) → 输出 13287:重复 ID 上万个!
```

修复:普通 static int 换成 **AtomicInteger**:

```java
public class GuardedIDField implements HasID {
    private static AtomicInteger counter = new AtomicInteger();
    private int id = counter.getAndIncrement();   // 原子取增
    public int getID() { return id; }
}
// 重跑:重复数 0
```

同样的坑遍布构造器里的静态可变状态(静态集合等);修复思路同源:原子类、synchronized,或干脆消灭共享(每任务独立编号)。**构造器代码与普通代码在并发面前没有任何豁免权**。

## 13. 投入、复杂度与代价(Effort, Complexity, Cost)

做披萨的仿真:DOUGH(和面 0.4s)→ROLLED→SAUCED→CHEESED→TOPPED(0.5s)→BAKED→SLICED→BOXED,每步一个耗时状态。三种实现对比,衡量"为提速该投入多少":

**串行**(一人一饼):

```java
Pizza za = new Pizza(0);
while (!za.complete())
    za.next();      // 总耗时 = 各步 effort 之和 ≈ 1.6s/张
```

**并行流**(加一个词):

```java
IntStream.range(0, 5)          // 5 张饼
         .mapToObj(Pizza::new)
         .parallel()           // [1]
         .forEach(za -> { while (!za.complete()) za.next(); });
// 5 张饼约等于 1 张的时间(每张一个工人)
```

**CompletableFuture 流水线**(工序级并行——五张饼在流水线上交错推进):

```java
CompletableFuture[] futures = Arrays.stream(pizzas)
        .map(Pizza::roll)
        .map(pcf -> pcf.thenCompose(Pizza::sauce))
        .map(pcf -> pcf.thenCompose(Pizza::cheese))
        // ... toppings / bake / slice / box
        .toArray(CompletableFuture[]::new);
CompletableFuture.allOf(futures).join();
```

对比的启示不是"哪个更快",而是:**先实现串行版,确认不够快,再逐级引入并行**。每升一级,复杂度与出错面都在扩大;parallel() 是一行,流水线已经需要理解 thenCompose/异常传播。

## 14. 小结与告诫(Summary)

> The only justification for concurrency is "too much waiting."
>
> 并发的唯一正当理由是"等得太多了"。

并发很难,所以要先问:值不值得?换更快的机器(比程序员时间便宜)、拆到多台机器、先 profile——都试过再说。**奥卡姆剃刀**的编程版:先试最简单可行的方案,不够再升级(Eckel 自述:他无数次"确信最简单的方案不可能够快",一试却绰绰有余)。

并发的主要代价:

- 线程等共享资源时反而变慢;
- 线程管理的 CPU 开销;
- 糟糕设计带来的无回报复杂度;
- 饥饿、竞态、死锁、活锁(livelock)等病态;
- **跨平台不一致**:同样的竞态,有的机器立刻出现、有的从不出现——在后者上开发,分发后才炸。

**共享内存是万恶之源**:永远不要相信"共享内存并发程序能正确工作"——你只能发现它错,不能证明它对。单 CPU 上正确的程序,多 CPU 上照样可能崩("write once, run everywhere" 在并发面前不成立)。

Java 并发的众多历史方案有些已被证明无效(看 Thread 的 Deprecated 列表);Java 8 的 parallel Stream 与 CompletableFuture 是真正有价值的进步,但它们**假设你不共享内存**。若并发需求超出这些高层工具的表达力,考虑为并发而生的语言(Clojure、Frege),并发部分用它们写、其余仍是 Java——JVM 让这条路完全可行。

> 无论某个语言/库把并发包装得多简单,把它当作一门黑魔法:**总有什么东西会在你最想不到的时候咬你一口。**

深入必读:《Java Concurrency in Practice》(Brian Goetz 等)与 Doug Lea 的《Concurrent Programming in Java》——前者是必知清单,后者是 java.util.concurrent 的思想源头。
