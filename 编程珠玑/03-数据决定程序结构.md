多数程序员都见过这样的程序：它们本应是短小、干净、漂亮的程序，实际却是庞大、杂乱、丑陋的程序。核心往往就是这样的代码：

```c
if (k ==   1) c001++
if (k ==   2) c002++
   ...
if (k == 500) c500++
```

（统计文件中 1~500 每个整数出现的次数。）每个这样的程序都超过一千行；而今天多数程序员一眼就看出：用一个 500 元素的**数组**替换 500 个独立变量，代码就只剩一个零头。这正是本篇标题的含义——**数据的恰当视角确实能"结构"出程序**。

## 3.1 一个调查程序

某学院要汇总约两万份学生问卷，输出形如：

```text
                  Total    US   Perm  Temp  Male Female
                           Citi  Visa  Visa

African American  1289   1239    17     2   684   593
Mexican American   675    577    80    11   448   219
...
Caucasian        16272  15663   355    33  9367  6836
   Totals        19589  18319   839   129 11231  8253
```

真实问题比这复杂：25 个列（8 个类别）、3 页输出（两个校区各一页加合计）、还有若干相关表格。每份问卷是一条记录：entry[0] 是族群（0~7，含"拒答"）、entry[1] 是校区（0~2）、entry[2] 是公民身份……共 9 项。

程序员照系统分析师的高层设计编码：围绕 **350 个独立变量**（25 列 × 7 行 × 2 页）组织程序，干了两个月、写出一千行后估计自己完成了一半——变量声明之后，就是一团决定"读入每条记录时递增哪些变量"的乱麻。

关键的决策：**数字应该存成数组**。下一个决策更难：数组按输出结构摆（校区×族群×25 列三维），还是按输入结构摆（校区×族群×类别×类别内取值四维）？两种都能工作；三维版读数据略烦、写输出略省。最终程序 150 行：80 行建表、30 行产出上述输出、40 行产出其他表格。

更进一步：作者自己的输入循环有 40 行（8 个五语句块），把变化的下标偏移 `0, 0, 1, 4, 6, ...` 抽成 `offset[]` 数组后，6 行搞定——

```c
for i = [2, 8]
    if entry[i] == refused
        declined[ethnicgroup, i]++
    else
        j = offset[i] + entry[i]
        count[campus, ethnicgroup, j]++
```

他刚为一个数量级的缩减沾沾自喜，就错过了眼前第二个数量级。

为什么程序员会写大程序？一是缺 2.5 节说的那种"重要的懒惰"，抓着第一个念头就冲；二是更深层的原因——他们对问题的思维停留在"数组只是程序开头初始化后不再改动的固定表"的语言里，用 Adams 的话说，他们对"动态计数数组"有**概念块（conceptual blocks）**。

## 3.2 格式信函编程

登录电商网站后看到的定制页面，背后是数据库里 `Public|Jane|Q|Ms.|600|Maple Street|Your Town|Iowa|12345` 这样的记录。匆忙的程序员会写一堆 `print` 语句把字段嵌进文案。更优雅的做法是**格式信函模式（form letter schema）+ 生成器**：

```text
Welcome back, $1!
We hope that you and all the members
of the $0 family are constantly
reminding your neighbors there
on $5 to shop with us.
As usual, we will ship your order to
    $3 $1 $2. $0
    $4 $5
    $6, $7 $8
```

`$i` 指记录的第 i 个字段，字面 `$` 写作 `$$`。解释器的伪代码：

```c
read fields from database
loop from start to end of schema
    c = next character in schema
    if c != '$'
        printchar c
    else
        c = next character in schema
        case c of
            '$':       printchar '$'
            '0' - '9': printstring field[c]
            default:   error("bad schema")
```

**数据与控制分离**收益巨大：信函改版只需用文本编辑器改 schema。作者维护过一个 5300 行的 Cobol 程序（家庭财务状况小册子）：300 行清洗输入、800 行计算、**4200 行写输出**——后者本可用几十行解释器加 400 行 schema 替代，整个程序至多缩到三分之一。

## 3.3 数组示例集

**菜单**。八个菜单项的互斥选中，每项一个函数、共约 100 行。先抽出公共函数 `uncheckall` 降到 25 行；再利用 Visual Basic 的菜单项**数组**，8 个函数合成 1 个 4 行的：

```c
sub menuitem_click(int choice)
    for i = [0, numchoices)
        menuitem[i].checked = 0
    menuitem[choice].checked = 1
```

**错误消息**。脏系统把几百条错误消息散落在代码各处、与其他输出混在一起；干净系统通过单一函数访问它们。试试在两种组织下完成：列出所有可能的错误消息、给"严重"级别的消息加警报声、把消息翻译成法语或德语。

**日期函数**。给定年份与年内第几天，返回月与日（2004 年第 61 天 = 3 月 1 日）。Kernighan 与 Plauger 在《The Elements of Programming Style》里展示了某编程教材的 55 行程序，然后给出用一个 26 整数数组的 **5 行**版本。

**词分析**。拼写检查器用"后缀剥离"精简词典（只存 `laugh`，不存 `-ing/-s/-ed` 各形态，见 13.8 节）。McIlroy 1973 年造第一台实时语音合成器时就明白：这类语言学规则不该装在代码里——他用 1000 行代码加 400 行表实现；后来有人不加表、只改代码来完成 20% 的扩展，多花了 2500 行。McIlroy 认为若加更多表，连扩展后的任务 1000 行以内也能拿下。

## 3.4 构造数据

什么是结构良好的数据？标准一直在提高：

- 早年：选好变量名
- 之后：并行数组、寄存器偏移 → 语言内建**记录/结构体**与指向它们的指针
- 再后：把数据操作代码换成 `insert`、`search` 这样的具名函数，表示变了也不伤程序其余部分；Parnas 由此提出"系统要处理的数据深刻提示了好的模块结构"
- **面向对象编程（Object-Oriented Programming）**走完下一步：识别设计中的基本对象，对外公布抽象与其上的基本操作，隐藏实现细节。Smalltalk 与 C++ 这样的语言把对象封装进类——Column 13 研究集合抽象时会细看。

## 3.5 面向专用数据的强大工具

从零造每个应用的时代过去了。每个工具都利用数据的一种视角解决一类常见问题，Visual Basic、Tcl 与各种 shell 提供"胶水"：

| 工具 | 数据视角 | 例子 |
| --- | --- | --- |
| 超文本（Hypertext） | 统一接口的链接数据 | 早期 CD-ROM 百科/词典各有怪异界面，如今都收敛到浏览器 |
| 名字-值对（Name-Value Pairs） | 属性表 | `%title The C++ Programming Language`；VB 控件属性 `txtSample.Width = 400` |
| 电子表格（Spreadsheets） | 单元格数组 + 公式 | 组织预算：对会计用户界面最自然；调查程序今天或许就该进电子表格 |
| 数据库（Databases） | 记录与查询 | 跳伞日志：几分钟定义好录入界面，而不再是几天 |
| 领域专用语言（Domain-Specific Languages） | 直接写表达式/查询 | `47 * n * log(n)/log(2)`、`(design or architecture) and not building`；窗口从几百行代码变成几十行 HTML |

## 3.6 原则

> The programmer at wit's end for lack of space can often do best by disentangling himself from his code, rearing back, and contemplating his data. Representation is the essence of programming.
>
> 因空间不足而束手无策的程序员，最好的办法往往是从代码中抽身出来，往后一靠，凝视他的数据。**表示是编程的本质。**
>
> —— Fred Brooks《人月神话》第 9 章

本篇的故事跨越几十年、十几种语言，寓意相同：**能写小程序时就别写大程序**。多数结构印证了 Polya 在《How to Solve It》里说的**发明家悖论（Inventor's Paradox）**："更一般的问题可能更容易解"——直接解 23 种情形的问题，可能比写一个处理 n 种情形的通用程序再代入 n=23 更难。

- **Rework repeated code into arrays（把重复代码重做成数组）**。一长段相似代码，最简单的数据结构——数组——往往就是最佳表达。
- **Encapsulate complex structures（封装复杂结构）**。需要复杂数据结构时，用抽象术语定义它，把操作表达成类。
- **Use advanced tools when possible（尽量用高级工具）**。超文本、名字-值对、电子表格、数据库、语言，都是各自领域内的利器。
- **Let the data structure the program（让数据结构程序）**。动手写代码前，先透彻理解程序的输入、输出与围绕它们的中间数据结构。

## 3.7 习题选

**1.某编程教材用 25 个 if 语句计算 1978 年美国联邦所得税（税率 .14, .15, .16, ... 逐段递增），有何评论？** 每段一条记录（下界、基础税额、超出下界部分的税率），加一条下界为"无穷大"的哨兵记录——查表顺序查找即可，还顺带更快（见 9.2 节）。适用于一切分段线性函数。

**3.写一个"横幅"函数：输入大写字母，输出描绘该字母的字符数组。** 块字母 I 可编码为紧凑的行程格式：`3 9 X` / `6 3 b 3 X 3 b` / `3 9 X`（3 行全 X、6 行中间 X、再 3 行全 X）——又是数据表示问题。

**8.[S. C. Johnson] 七段数码管显示 16 位正整数，输出 5 个字节，第 j 字节的第 i 位为 1 当且仅当第 j 位数字的第 i 段应点亮。** 经典的查表题：10 个数字的段模式先做成常量表。

## 3.8 深入阅读

Steve McConnell《Code Complete》(Microsoft Press, 1993)：860 页的软件构建实用手册，与本篇最相关的是第 8~12 章"Data"（从声明数据、命名讲到表驱动程序与抽象数据类型），第 4~7 章"Design"是本篇主题的展开。配合其《Rapid Development》(1996) 与《Software Project Survival Guide》(1998)，从小函数的雅致构造到大项目的管理都有覆盖。
