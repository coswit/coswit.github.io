1960 年代末，人们就在谈论"用程序验证其他程序正确性"的前景。几十年过去，自动验证系统仍基本停留在纸面上——但程序验证的研究给了我们比"吞进程序、闪出好坏"的黑箱**有价值得多的东西：对计算机编程的根本理解**。多数程序员成长的路数是一位读者概括的"写完代码扔过墙，让 QA（Quality Assurance，质量保证）或测试部门去对付 bug"；本篇讲另一条路。先摆正位置：**编码只是写正确程序的一小部分，大头在前三篇——问题定义、算法设计、数据结构选择**。这些做对了，写正确代码通常不难。

## 4.1 二分查找的挑战

设计再好，程序员偶尔也得写精细的代码。2.2 节的问题：判断有序数组 `x[0..n-1]` 是否包含目标元素 t。精确地说：已知 n≥0 且 $x[0] \le x[1] \le \cdots \le x[n-1]$；n=0 时数组为空。答案存入整数 p：p 为 −1 表示 t 不在数组中，否则 $0 \le p \le n-1$ 且 $t = x[p]$。

算法描述人人都会：维护可能包含 t 的区间，取中点比较，丢掉一半，直到找到或区间为空。n 个元素约用 $\log_2 n$ 次比较。

多数程序员觉得"这还不容易"——**他们错了**。作者在专业程序员的课程上布置过这道题：几小时把上述描述转成任意语言的程序（伪代码也行），到期几乎人人都自称写对了；随后用测试用例检查三十分钟——**在几个班、一百多名程序员中，结果大同小异：九成的人在自己的程序里发现了 bug**（剩下那部分没发现 bug 的代码，作者也未必信其正确）。

这不算丢人：Knuth 在《Sorting and Searching》6.2.1 节的历史部分指出，**第一个二分查找发表于 1946 年，第一个发表了无 bug 二分查找的版本直到 1962 年才出现**。

## 4.2 编写程序

二分查找的关键思想：我们始终知道"若 t 在数组中，则它必在某个范围内"。引入记号 **mustbe(l, u)**：若 t 在数组中，则它必在闭区间 x[l..u] 内。程序骨架：

```c
initialize range to 0..n-1
loop
    { invariant: mustbe(range) }
    if range is empty,
        break and report that t is not in the array
    compute m, the middle of the range
    use m as a probe to shrink the range
        if t is found during the shrinking process,
        break and report its position
```

花括号里的断言就是**循环不变量（loop invariant）**——它在每次迭代开始与结束时都为真，把直觉形式化。接下来逐步求精，每一步都确保不破坏不变量：

区间用下标 l 与 u（lower/upper）表示；初始化 `l = 0; u = n-1` 使 mustbe(0, n-1) 成立——这正是程序开始时我们知道的。区间为空即 l > u，置 p = −1 并跳出。中点 `m = (l + u) / 2`（整除）。三种情况：

- `x[m] < t`：由有序性，$x[0] \le \cdots \le x[m] < t$，t 不可能在 x[0..m]，于是 mustbe(m+1, u)，令 `l = m+1`
- `x[m] == t`：找到，`p = m; break`
- `x[m] > t`：对称地，`u = m-1`

```c
l = 0; u = n-1
loop
    { mustbe(l, u) }
    if l > u
        p = -1; break
    m = (l + u) / 2
    case
        x[m] <  t:  l = m+1
        x[m] == t:  p = m; break
        x[m] >  t:  u = m-1
```

十来行代码加一条不变量断言——**精确陈述不变量、写每行代码时盯着"如何维持它"**，这套验证基本功把算法草图变成了可信的伪代码。

## 4.3 理解程序

写代码是自顶向下（从大致想法精化到每行），正确性分析则自底向上。下面是带完整断言标注的版本（原书此处自嘲：枯燥预警，犯困请直接跳到 4.4 节）：

```c
 1.  { mustbe(0, n-1) }
 2.  l = 0; u = n-1
 3.  { mustbe(l, u) }
 4.  loop
 5.      { mustbe(l, u) }
 6.      if l > u
 7.          { l > u && mustbe(l, u) }
 8.          { t is not in the array }
 9.          p = -1; break
10.      { mustbe(l, u) && l <= u }
11.      m = (l + u) / 2
12.      { mustbe(l, u) && l <= m <= u }
13.      case
14.          x[m] <  t:
15.                   { mustbe(l, u) && cantbe(0, m) }
16.                   { mustbe(m+1, u) }
17.                   l = m+1
18.                   { mustbe(l, u) }
19.          x[m] == t:
20.                   { x[m] == t }
21.                   p = m; break
22.          x[m] >  t:
23.                   { mustbe(l, u) && cantbe(m, n-1) }
24.                   { mustbe(l, m-1) }
25.                   u = m-1
26.                   { mustbe(l, u) }
27.      { mustbe(l, u) }
```

对循环的论证分三部分，每部分都扣着不变量：

| 性质 | 内容 | 二分查找中的论证 |
| --- | --- | --- |
| **初始化（Initialization）** | 首次进入循环时不变量为真 | 第 2 行赋值后第 3 行即 mustbe(l, u) |
| **保持（Preservation）** | 迭代开始时不变量为真，执行完循环体仍为真 | 三个分支：两个缩小区间后回到第 27 行的 mustbe(l, u)，一个直接正确终止 |
| **终止（Termination）** | 循环终止且结果正确 | 两处 break 都带着正确结论；关键还要证**不无限循环** |

停止性证明：第 12 行说明 m 总在当前区间内；case 的两个会继续循环的分支（`l = m+1`、`u = m-1`）都把 m 挡在新区间之外，**区间每次至少缩小 1**，而初始大小是有限的 n——程序必停。当年的专业程序员们最常犯的错误恰是死循环。

## 4.4 原则

- **Assertions（断言）**。输入、程序变量与输出之间的关系描述程序的"状态"，断言让程序员精确说出这些关系。
- **顺序控制结构**。理解"做完这句再做那句"的办法：语句之间放断言，逐段分析。
- **选择控制结构**。if/case 的正确性论证：**对每个分支分别考虑**；"某分支被选中"这一事实本身就能进入证明（执行了 `if i > j` 后面的语句，即可断言 i > j）。
- **迭代控制结构**。证明循环正确，先证初始化、再证保持（两步合起来是数学归纳法：不变量在每次迭代前后都真），最后证终止时结论成立；**"若停则对"与"必停"要分开证**。
- **Functions（函数）**。用两条断言陈述函数的目的——**前置条件（precondition）**：调用前必须为真的状态；**后置条件（postcondition）**：函数结束时保证的结果：

```c
int bsearch(int t, int x[], int n)
  /* precondition: x[0] <= x[1] <= ... <= x[n-1]
    postcondition:
        result == -1    =>   t not present in x
        0 <= result < n =>   x[result] == t
  */
```

  这两条与其说是事实陈述，不如说是**契约（contract）**：以前置条件满足为前提调用，函数执行将确立后置条件。证明一次函数体有此性质后，以后只看契约、不再看实现——这就是"契约式编程（programming by contract）"。

## 4.5 程序验证的地位

程序员互相说服"这段代码是对的"，第一工具是测试用例——好用、易懂、擅长抓 bug。但程序员显然对程序有更深的理解，否则根本写不出来；**程序验证的一大功劳，是给了程序员一门表达这种理解的语言**。

这门语言的用武之地远不止第一次写代码：代码走查用它讲解每一行（给每个循环勾一条不变量尤其有用）；测试期 assert 违例直指 bug，违例的形态还能帮你"修一个 bug 不引入另一个"；**调试时同时修代码与错误断言，任何时候都要理解代码，抵制"改到能跑为止"的恶习**；维护时，断言是接手陌生代码的珍贵线索。

最后两点清醒剂：这些技巧只是写正确程序的一小部分，**代码简单通常才是正确性的关键**；而熟悉验证技术的程序员有个太普遍的体验——"难"的部分一次就对，bug 全出在"容易"的部分：写难的部分时如临大敌用足形式化手段，写容易的部分时旧习复发、旧果重现。这种尴尬正是勤用这些技巧的最好动机。

## 4.6 习题选

**2.变体：返回 t 第一次出现的位置（原算法返回任意一个）。** 需要 $\log_2 n$ 次比较，见 9.3 节。

**5.证明下面程序在输入正整数 x 时终止：**

```c
while x != 1 do
    if even(x)
        x = x/2
    else
        x = 3*x+1
```

这正是著名的 **3x+1 问题（Collatz 猜想 / 冰雹数）**——截至目前无人证明终止性，是数学上的开放问题。

**6.[C. Scholten] 咖啡罐问题（Gries《The Science of Programming》）**：罐中有若干黑豆与白豆，另有一大堆"备用"黑豆。重复以下过程直到只剩一粒：随机取两粒，同色则都扔掉、放入一粒备用黑豆；异色则白豆放回、黑豆扔掉。证明过程终止；最后那粒豆的颜色由什么决定？——每步豆数减一，必终止；每步取走零或两粒白豆，**白豆数的奇偶性不变**：最后剩白豆，当且仅当初始白豆数是奇数。

**7.位图显示器上画线**：n 条直线 $y_i = a_i x + b_i$ 在 x∈[0,1] 内严格有序（不交叉），给定点 (x, y) 快速找出夹住它的两条线？——"梯子档"随 y 有序，**对线段做二分**，基本比较是判断点在给定线段的下方、上面还是上方。

**8.二分查找还能更快吗？** 比较次数 $\log_2 n$ 压不下去，但代码可以更快——见 9.3 节。
