到目前为止你什么都做对了：挖出了正确的问题定义，算法与数据结构选得仔细，还用验证技术写出了相当有把握的伪代码。怎么把这块宝石装进大系统？剩下的不过是——编程小事。

程序员是乐观主义者，容易被引上轻松的路：把函数编出来、塞进系统、虔诚地祈祷它能跑。偶尔真能跑。但另外 999/1000 次都是灾难：你得在庞大的系统里摸索着摆弄这个小函数。**聪明的程序员为函数搭建脚手架（scaffolding），给自己便捷的访问途径**。本篇把上一篇的二分查找伪代码落成可信的 C 函数：先编码，再用脚手架探测，然后彻底测试，最后做运行时间实验。函数虽小，路很长；结果是**一个我们信得过的程序**。

## 5.1 从伪代码到 C

数组与目标元素都用 `DataType`（`typedef int DataType;`），数组用两个全局变量实现（反映 C++ 类中访问数据的方式，全局变量也让脚手架更小）：

```c
int n;
DataType x[MAXN];
```

目标函数与契约：

```c
int binarysearch(DataType t)
 /* precondition: x[0] <= x[1] <= ... <= x[n-1]
    postcondition:
        result == -1     =>  t not present in x
        0 <= result < n  =>  x[result] == t
  */
```

4.2 节的伪代码几乎逐行翻译成 C：伪代码往 p 存值之处改为 return，伪代码循环换成 C 的死循环 `for (;;)` 再反转为 while：

```c
int binarysearch(DataType t)
    /* return (any) position if t in sorted x[0..n-1] or
        -1 if t is not present */
{   int l, u, m;
    l = 0;
    u = n-1;
    while (l <= u) {
        m = (l + u) / 2;
        if (x[m] < t)
            l = m+1;
        else if (x[m] == t)
            return m;
        else /* x[m] > t */
            u = m-1;
    }
    return -1;
}
```

## 5.2 测试脚手架

第一步永远是手工过几个测试用例；**微型用例（0、1、2 个元素的数组）常足以熏出 bug**。数组一大手工就乏味了，下一步是写驱动程序，五行 C 脚手架即可：

```c
while (scanf("%d %d", &n, &t) != EOF) {
    for (i = 0; i < n; i++)
        x[i] = 10*i;
    printf(" %d\n", binarysearch(t));
}
```

输入 `2 0` 生成元素为 {0, 10} 的两元素数组，输出 0（在位置 0 找到）；`2 -5`、`2 5`、`2 15` 输出 −1（不在数组中）——两元素数组的所有可能搜索全部覆盖。

测试并非总这么顺。几位专业程序员提出的这个版本：

```c
int badsearch(DataType t)
{   int l, u, m;
    l = 0;
    u = n-1;
    while (l <= u) {
        m = (l + u) / 2;
/* printf("  %d %d %d\n", l, m, u); */
        if (x[m] < t)
            l = m;          // bug: 区间没有缩小
        else if (x[m] > t)
            u = m;          // bug: 同上
        else
            return m;
    }
    return -1;
}
```

前两个小测试都过了（5 元数组找 20、30 都对）；找 40 却**死循环**。把注释里的 printf 打开（缩到最左以示这是脚手架），打印每轮的 l、m、u：

```text
5 40
  0 2 4
  2 3 4
  3 3 4
  3 3 4
  3 3 4
  ...
```

第三轮起 `3 3 4` 原地打转——`l = m`、`u = m` 没把 m 排除出区间，违反了 4.3 节终止证明里"区间每轮至少缩小 1"的关键性质。**在旧代码里塞进一条打印语句，往往比单步调试器这类复杂工具更快更有效**。

## 5.3 断言的艺术

Column 4 里断言引导了开发、支撑了正确性论证；现在把它们插进代码，确保运行时行为与理解一致。`assert(n > 0)` 在 n 非负时无事发生，为假时报错。

断言有弱有强。最弱的重述 if 条件本身；稍强一点，报告找到之前断言返回值在合法范围：

```c
assert(0 <= m && m < n && x[m] == t);
```

未找到而返回 −1 时，我们已知 l、u 交叉，于是想断言"找到了夹住 t 的相邻元素对"——在有序表里看见相邻的 1 和 3，就能断定 2 不在。但这条断言**对正确的程序也会偶发失败**，为什么？——n 为 0 时 u 初始化为 −1，`x[u+1]` 越界。需要**弱化**以处理边界：

```c
assert((u < 0 || x[u] < t) && (u+1 >= n || x[u+1] > t));
```

终止性（区间必缩小）也能在运行时检查：

```c
oldsize = size;
size = u - l + 1;
assert(size < oldsize);
```

作者自曝：多少次徒劳地调试"坏了的"二分查找，最后发现**要搜的数组根本没排序**。于是定义 `sorted()` 并 `assert(sorted())`——但这个 O(n) 的昂贵检查只能在全部搜索之前做一次；放进主循环，二分查找会退化成 $O(n \log n)$。

> Tony Hoare 的观察：测试时用断言、产品期关掉断言的程序员，就像在岸上演练（drilling）时穿救生衣、出海时反而脱掉的水手。

## 5.4 自动化测试

手工喂用例喂烦了，就让机器来。主循环让 n 从最小可能值（0）跑到最大合理值：

```c
for n = [0, maxn]
    print "n=", n
    /* test value n */
```

（print 报进度：有人嫌它刷屏无信息量，有人靠它安心——**看到第一个 bug 时，知道哪些测试已经通过是有用的**。）

第一部分测所有元素互异的数组（末尾多放一个"备胎"确认搜索不会越界找到它）：

```c
/* test distinct elements (plus one at the end) */
for i = [0, n]
    x[i] = 10*i
for i = [0, n)
    assert(s(10*i)     ==  i)
    assert(s(10*i - 5) == -1)
assert(s(10*n - 5) == -1)
assert(s(10*n)     == -1)
```

其中 `#define s binarysearch`，一改宏就能测不同变体。第二部分测全部元素相等的数组（找在的、找比它小和比它大的）。n 取 0~100 覆盖了空数组、bug 高发尺寸（0、1、2）、若干 2 的幂以及比 2 的幂大 1 小 1 的数；手做会无聊到出错，机器只花几秒。

## 5.5 计时

测试支撑了正确性信念，怎么支撑"约 $\log_2 n$ 次比较"的性能信念？计时脚手架主循环：

```c
while read(algnum, n, numtests)
    for i = [0, n)
        x[i] = i
    starttime = clock()
    for testnum = [0, numtests)
        for i = [0, n)
            switch (algnum)
                case 1: assert(binarysearch1(i) == i)
                case 2: assert(binarysearch2(i) == i)
    clicks = clock() - starttime
    print algnum, n, numtests, clicks,
        clicks/(1e9 * CLOCKS_PER_SEC * n  * numtests)
```

switch 选择被测算法——**脚手架永远该准备好同时测多个变体**；输出原始时钟数（务必检查原始数）与换算成纳秒的平均值。400MHz Pentium II 上实测：

```text
1  1000  10000      →  3445 ticks, 344.5 ns/次
1  10000 1000       →  4436 ticks, 443.6 ns/次
1  100000 100       →  5658 ticks, 565.8 ns/次
1  1000000 10       →  6619 ticks, 661.9 ns/次
```

每次 n 涨 10 倍、测试数降 10 倍，搜索耗时拟合为约 $50 + 30\log_2 n$ 纳秒——对数增长得到实验确认。（习题 7 指出此脚手架的潜在计时 bug：按顺序搜每个元素带来格外友好的缓存行为；若应用是随机探测，应先洗牌一个置换向量再按随机序搜索。）

## 5.6 完整程序

我相信这个 C 实现是正确的，因为：伪代码在方便的语言里小心推导，验证技术分析过；逐行翻译成 C；喂输入看输出；代码里撒了断言，理论分析与实际行为互相对账；机器轰炸了测试用例；简单实验证明运行时间如理论所料。

但**逻辑 bug 之外还有很多种 bug**：调用者记得先排序吗？找不到时返回 −1 是调用方想要的约定吗？目标多次出现时返回任意一个下标，用户是不是其实想要第一个或最后一个？完整程序的主函数用注释切换玩法：

```c
int main(void)
{   /* probe1(); */
    /* test(25); */
    timedriver();
    return 0;
}
```

## 5.7 原则

- **Scaffolding（脚手架）**：最好的脚手架通常是最容易搭的那种。有些任务用 VB/Java/Tcl 的图形界面半小时就能搭出点击式程序；但对多数算法任务，本篇的命令行技巧更简单、更可移植。
- **Coding（编码）**：先用顺手的高层伪代码勾出难函数，再翻译到实现语言。
- **Testing（测试）**：组件在脚手架里测试，比在大系统里容易得多也彻底得多。
- **Debugging（调试）**：程序在脚手架里调试已属不易，嵌进真实环境后更难（5.10 节讲大系统调试的故事）。
- **Timing（计时）**：如果运行时间无所谓，线性搜索比二分查找简单得多、多数人一次就能写对；既然复杂度是为性能引入的，就该做实验确认性能符合预期。

## 5.8 习题选

**5.[R. S. Cox] 对未排序数组套二分查找是常见 bug，每次搜索前完全检查有序要花 n−1 次比较，太贵；如何花小代价做部分检查？**（例如断言检查区间内少数采样点的有序性。）

**7.计时脚手架的 bug**：按序搜索每个元素使缓存行为格外友好；若预期搜索是随机探测的，先初始化并洗牌置换向量 p，再 `assert(binarysearch1(p[i]) == p[i])`，实测两版有无差别。

## 5.10 边栏：调试

每个程序员都知道调试难，而调试高手能让它看起来容易：憔悴的程序员描述追了几个小时的 bug，大师问几个问题，几分钟后大家就盯着出错代码了。**专家调试者从不忘记：无论系统行为初看多神秘，必然存在一个逻辑解释。**

- **坐着能登录、站着不能登录**（IBM Yorktown，100% 可复现）：不是地毯下的松线、不是静电——同事问对了问题："你坐着和站着分别是怎么登录的？"答案是**两个键帽被装反了**：坐着是盲打不受影响，站着 hunts and pecks（看键盘找键）就中招。一把螺丝刀解决问题。
- **银行系统首次处理国际数据就退出**：输入厄瓜多尔（Ecuador）数据时程序退出——用户输入其首都基多（**Quito**）时，程序理解成了 quit（退出运行）请求。
- **"work once twice（一次管一次）"**：第一笔交易正确、后续全错，重启又复现——开发人员一听这个刻画立刻知道：找一个**加载时初始化正确、首笔交易后未正确复位**的变量。
- 正确的问题引导聪明的程序员迅速逼近恶心的 bug："坐着和站着你各做什么不同的事？能各登录一次给我看吗？""程序退出前你到底敲了什么？""出问题之前它正确过吗？正确了几次？"
- Rick Lemons 说他最好的调试课是看魔术表演：每看一个"不可能"的戏法，他提醒自己**不可能的事就是不可能的**，从物理定律这块基石出发给每个戏法找到简单解释。

关于调试最好的书：Berton Roueché《The Medical Detectives》——书中的英雄们调试从轻症病人到重病小镇的复杂系统，其解题方法直接适用于计算机系统，真实故事比小说还抓人。
