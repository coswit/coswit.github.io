有的程序员对效率过度关注：过早担忧小小的"优化"，写出刻薄聪明、暗藏维护灾难的程序；有的又关注太少：程序结构漂亮但效率低得没用。**好的程序员把效率放进语境：它只是软件的众多问题之一，但有时非常重要。**

前几篇讲的是高层途径（问题定义、系统结构、算法设计、数据结构选择），本篇讲低层途径。**代码调优（code tuning）**定位现有程序中昂贵的部分，做小改动提升速度——不总是对的途径，也不光鲜，但有时能大幅改变程序性能。

## 9.1 一个典型的故事

某天下午 Chris Van Wyk 和作者聊完代码调优，转身去改一个三千行的 C 图形程序——几小时后运行时间减半。

该程序处理复杂图片要十分钟。第一步是**剖析（profiling）**：跑十张典型测试图，约 **70% 的时间花在内存分配函数 malloc 里**。第二步研究分配器：程序经由一个带错误检查的封装函数访问 malloc，改动无需触碰 malloc 源码；插入几行统计代码后发现，**最常见的那类记录的分配频率是第二名的三十倍**。

Van Wyk 的解法是**缓存（caching）原则：访问最频繁的数据应当最便宜地被访问**——把最常见类型的空闲记录缓存成链表，常见请求直接取链表而不再走通用分配器。运行时间降到原来的 45%，碎片减少还顺带提高了内存利用率。花几小时测量、给三千行程序加约二十行代码，速度翻倍，既不改用户视角也不增加维护难度。

典型小程序的剖析输出（形式与内容都与 Van Wyk 的相似）：

```text
    Func      Func+Child          Hit
    Time   %       Time      %    Count  Function
--------------------------------------------------
1413.406 52.8   1413.406  52.8   200002  malloc
 474.441 17.7   2109.506  78.8   200180  insert
```

一半时间在 malloc——剖析表总是长这样：**大部分时间流向少数热点，其余代码很少执行**。

## 9.2 急救小案例集

**案例一：整数取余**。2.3 节杂耍旋转算法内层循环里的 `k = (j + rotdist) % n;`。附录 3 的成本模型显示 `%` 接近 100 纳秒，是一般算术运算（约 10 纳秒）的十倍。替换成：

```c
k = j + rotdist;
if (k >= n)
    k -= n;
```

rotdist=1 时，运行时间从 119n 纳秒降到 57n，几乎快一倍，降幅与成本模型吻合。但 rotdist=10 时**两个版本完全一样（都是 206n）**——因为此时代码每隔 10 个字访问一次内存，把数据从 RAM（Random-Access Memory，随机存取存储器）取进缓存的代价成了主导。**在大量周期花在访存的程序里压缩计算时间，和在 I/O 密集程序里提速计算一样徒劳。**

**案例二：函数、宏与内联代码**。8.4 节用 `max` 函数算两值最大，程序约 89n 纳秒。老 C 程序员的膝跳反射是换成宏：

```c
#define max(a, b) ((a) > (b) ? (a) : (b))
```

作者的机器上算法 4 从 89n 降到 47n，提速近两倍（很多优化编译器会自动内联小函数，则无差别）。但把算法 3 的 max 换成宏后，n=10,000 的运行时间从 10 毫秒暴涨到 **100 秒——慢了一万倍**：宏的**传名调用（call-by-name）语义**让递归的 maxsum3 自调用超过两次，渐近时间从 $O(n\log n)$ 退化到接近 $O(n^2)$。C++ 的 `inline` 函数则两全其美：函数的干净语义加宏的低开销。手写成 if 语句？时间基本不变。

**案例三：顺序查找**。朴素版每次循环两个测试（到头了吗？是它吗？），平均 4.06n 纳秒。在数组尾部放**哨兵（sentinel）**值 t，把第一个测试合并进第二个：

```c
int ssearch2(t)
    hold = x[n]
    x[n] = t
    for (i = 0; ; i++)
        if x[i] == t
            break
    x[n] = hold
    if i == n
        return -1
    else
        return i
```

降到 3.87n，约 5%。再把循环**展开（unrolling）**八倍去掉增量：

```c
int ssearch3(t)
    x[n] = t
    for (i = 0; ; i += 8)
        if (x[i  ] == t) {         break }
        if (x[i+1] == t) { i += 1; break }
        if (x[i+2] == t) { i += 2; break }
        if (x[i+3] == t) { i += 3; break }
        if (x[i+4] == t) { i += 4; break }
        if (x[i+5] == t) { i += 5; break }
        if (x[i+6] == t) { i += 6; break }
        if (x[i+7] == t) { i += 7; break }
    if i == n
        return -1
    else
        return i
```

降到 1.70n，再省 56%。旧机器上减少开销能提速一两成就不错了；**现代体系结构上，循环展开还能避免流水线停顿、减少分支、提高指令级并行**。

**案例四：球面距离**。S 是球面上五千个点（经纬度），对后续两万个输入点各找 S 中角度距离最近的点。Margaret Wright 在斯坦福的原始程序：数组存经纬度，对每个输入点用含十个 sin/cos 的三角公式算到全部 S 点的距离——大图要几小时主机时间。作者一个周末设计了几个花哨的算法与数据结构，幸好都得上百行代码没敢写。Andrew Appel 的关键洞见：**不动数据结构层级，保持数组的简单结构，只调优距离计算的代码**——给每个点**增补 x、y、z 直角坐标**，输入点先算一次三角函数转坐标，然后与 S 点的距离用三维坐标差平方和（夹角随欧氏距离平方单调递增，答案不变）。复杂地图的耗时从几小时降到半分钟，代价只有两打行代码。

## 9.3 大手术——二分查找

作者所知最极端的代码调优例子：千元素整数表的二分查找（习题 4.8）。先声明：**二分查找通常不需要调优**——算法本身太高效，Column 4 里我们忽略微观效率、专注简单正确可维护。但有时调优后的搜索对系统影响巨大。4.2 节的代码（每轮循环对 x 元素最多做两次比较）有显而易见的浪费吗？以下四个程序逐步演化，最终版通常快两三倍。先把问题改成"**定位 t 的第一次出现**"（15.3 节正需要这样的搜索），用不变量 $x[l] < t \le x[u]$ 且 $l < u$：

```c
l = -1; u = n
while l+1 != u
    /* invariant: x[l] < t && x[u] >= t && l < u */
    m = (l + u) / 2
    if x[m] < t
        l = m
    else
        u = m
/* assert l+1 = u && x[l] < t && x[u] >= t */
p = u
if p >= n || x[p] != t
    p = -1
```

问题更难了，但每轮循环**只做一次比较**（上一版有时要测两种结果）。第二版利用 n=1000 的事实，把区间改用"下界 l 加增量 i（2 的幂）"表示，先保证初始增量为小于 1000 的最大 2 的幂 512：

```c
i = 512
l = -1
if x[511] < t
    l = 1000 - 512
while i != 1
    /* invariant: x[l] < t && x[l+i] >= t && i = 2^j */
    i = i / 2
    if x[l+i] < t
        l = l + i
/* assert i == 1 && x[l] < t && x[l+i] >= t */
p = l+1
if p >= n || x[p] != t
    p = -1
```

第一测失败、l 保持初值时，程序**从高位到低位逐位算出 p 的二进制位**。最终版不适宜心脏弱者：把循环整体展开，i 只有十个取值，全部写死在代码里：

```c
l = -1
if (x[511] < t) l = 1000 - 512
    /* assert x[l] < t && x[l+512] >= t */
if (x[l+256] < t) l += 256
    /* assert x[l] < t && x[l+256] >= t */
if (x[l+128] < t) l += 128
if (x[l+64 ] < t) l += 64
if (x[l+32 ] < t) l += 32
if (x[l+16 ] < t) l += 16
if (x[l+8  ] < t) l += 8
if (x[l+4  ] < t) l += 4
if (x[l+2  ] < t) l += 2
    /* assert x[l] < t && x[l+2] >= t */
if (x[l+1 ] < t) l += 1
    /* assert x[l] < t && x[l+1] >= t */
p = l+1
if p >= n || x[p] != t
    p = -1
```

作者在多种系统上对比过干净版与精调版：第一版书报告过四种机器、五种语言、数档优化下的加速——从 38% 到 5 倍。本版机器上（n=1000）一度测得每搜索从 350 纳秒降到 125 纳秒（降 64%），好得可疑——果然，计时脚手架**按顺序**搜 x[0]、x[1]……给了二分查找绝佳的访存模式与分支预测；改成按随机次序搜索后，干净版 418 纳秒、展开版 266 纳秒，提速 36%。

这个函数在计算地下世界自 1960 年代初就为人所知（Vyssotsky 1961 年在 Bell 实验室用它，每条 if 用三条 IBM 7090 指令实现；作者 1980 年代初从 Guy Steele 处学得，Steele 在 MIT 1960 年代末就知道）。**Column 4 的程序验证工具在推导中至关重要**——有它们，我们才敢相信最终程序正确；第一次见到既无推导又无验证的最终代码时，作者视之为魔法。

## 9.4 原则

关于代码调优最重要的原则是：**少做**。展开说：

- **The Role of Efficiency（效率的位置）**。正确性、功能、可维护性至少同样重要。Knuth 的名言：**过早的优化是编程万恶之源**；把对效率的关注留给它真正要紧的时刻。
- **Measurement Tools（测量工具）**。效率要紧时，第一步是剖析找出时间去向；热点之外遵循"没坏就别修"。附录 3 式的成本模型帮助理解哪些操作昂贵。
- **Design Levels（设计层级）**。调代码之前，先确认高层途径（Column 6）不能更有效地解决。
- **When Speedups Are Slowdowns（加速变减速时）**。`%` 换 if 有时快一倍有时毫无差别；函数换宏一次快两倍、一次慢一万倍。**"改进"之后必须在代表性输入上测量效果**。Jurg Nievergelt 对代码调优者的警告：*people who play with bits should expect to get bitten*（玩 bit 的人等着挨咬）。

决定调优之后怎么做？附录 4 的规则表（作者 1982 年《Writing Efficient Programs》的 27 条规则的修订版）解释了本篇所有案例：

| 类别 | 规则 | 本篇案例 |
| --- | --- | --- |
| **空间换时间** | Data Structure Augmentation（数据结构增补） | 球面点增补 x/y/z 坐标 |

| | Interpreters（解释器） | 3.2 节格式信函；10.4 节图形程序 |
| **循环** | Code Motion Out of Loops（代码外提） | 11.1 节把赋值移出主循环 |
| | Combining Tests（合并测试） | 哨兵：9.2 节顺序查找、Column 13 各结构、14.1 节堆 |

## 9.5 习题选

**4.递归求数组最大值，max 用宏时为何 n=27 要 6 秒、n=28 要 12 秒？** 宏按名展开使 `arrmax(n-1)` 被求值两次，运行时间满足 $T(n) = 2T(n-1) + O(1)$——指数级；递减数组即触发最坏行为。

**7.数十亿字节的序列里数 1 的个数？** 法一：逐单元（字节或字）计数再求和——逐位看、或用 `b &= (b-1)` 迭代置位位、或查 $2^{16}$ 元素的大表；法二：统计每种输入单元的出现次数，末尾乘以其 1 的位数求和。

**8.用哨兵求数组最大值（Dromey）**：把 `x[n]` 当哨兵放当前最大值，内层循环只剩一个比较。

**11.1960 年代 Sikorsky 飞机公司的仿真程序大部分时间在算三角函数，而函数只在 5 度的整数倍处求值——怎么提速？** 预计算换成查表：IBM 7090 上从半小时降到一分钟；直升机旋翼分析要跑约三百次，几百字内存把一周 CPU 时间缩成几小时。

**12.多项式求值 `y = aₙxⁿ + ... + a₀` 用 2n 次乘法，更快的函数？** **Horner 法则（Horner's method）**：

```c
y = a[n]
for (i = n-1; i >= 0; i--)
    y = x*y + a[i]
```

只要 n 次乘法，通常快一倍——**有时调优靠想数学而不是想代码**。
