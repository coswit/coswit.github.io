读到本篇标题，你的第一反应可能是"多古雅啊！"——内存以 GB 计的时代，压缩程序空间好像是史前话题。但认真思考紧凑程序偶尔非常有赚头：**省空间的思考常常带来让程序更简单的新洞见**；省空间对运行时间常有良性的副作用——程序更小加载更快、更容易装进缓存，数据更少处理时间通常也更少；网络传输时间通常正比于数据大小；玩具与家电里的小机器仍有小内存；**用大机器解大问题时，内存依然要小心**。

## 10.1 关键——简单性

简单性能换来功能、健壮性、速度与空间。Ritchie 与 Thompson 最初在 8192 个 18 位字的机器上开发 Unix，他们在系统论文里写道：

> There have always been fairly severe size constraints on the system and its software. Given the partially antagonistic desires for reasonable efficiency and expressive power, the size constraint has encouraged not only economy but a certain elegance of design.
>
> 系统及其软件一直处在相当严苛的尺寸约束下。在合理效率与表达力这对部分对立的愿望之间，尺寸约束促成的不仅是节省，还有某种设计上的优雅。

Fred Brooks 1950 年代中期写全国性公司的工资程序时，瓶颈是肯塔基州所得税的表示：税法用"收入 × 免税人数"的二维表规定，显式存储要几千字内存，超过机器容量。先试拟合数学函数——税表太锯齿，没有简单函数能逼近。Brooks 想到表出自立法者之手、不会偏爱疯狂函数，于是**去查州议会的会议记录**，发现肯塔基税是联邦税扣除后收入的简单函数：先按已有表格算联邦税，再用剩余收入和一张几十字的表得出州税。**研究问题发生的语境，把原问题替换成更简单的问题**——几千字的数据空间变成了可忽略不计。

## 10.2 一个示例问题

1980 年代初，作者咨询过一个地理数据库系统：2000 个街区各编号 0~1999，显示为地图上的点；用户触碰输入板选点，程序把物理位置转成 x、y∈[0,199] 的整数对，再查是哪个点。程序员的表示：**200×200 的点编号数组**（无点处为 −1），16 位整数共 80KB——系统长大后占了半 MB 内存的六分之一，怎么省？

这是**稀疏数组（sparse array）**的经典机会（绝大多数元素同值——这里是"空"）。通用表示：列指针数组 + 每列活跃元素的链表，查找：

```c
for (p = colhead[i]; p != NULL; p = p->next)
    if p->row == j
        return p->pointnum
return -1
```

最坏访问 200 个节点，平均约 10 个。空间：200 指针 + 2000 条记录（一整数两指针），按附录 3 模型约 24.8KB——但若用默认 malloc，每条记录实占 48 字节，总共 96.8KB，**反而比原来还大**。

程序员的 Fortran 不支持指针与结构，于是用**三个平行数组**：`firstincol[0..200]` 给出每列元素在 `row[]` 与 `pointnum[]` 中的起止：

```c
for k = [firstincol[i], firstincol[i+1])
    if row[k] == j
        return pointnum[k]
return -1
```

16 位整数实现，共 **8402 字节**；因模块结构良好，几小时改几个函数就换好了，运行时间无可察觉的退化，净赚 70KB。空间还能再压：

- `row` 元素都小于 200 → 用单字节 `unsigned char`，共 6400 字节
- 点本身已存 row → 干脆删掉 row 数组，共 **4400 字节**
- 运行时间不重要的话，顺序搜点数组本身，**空间为零**；或键索引：第 i 元素两个单字节字段存点 i 的 row/col，4000 字节

沿途用的省空间手法：不需要 lastincol 数组（本列最后一点紧邻下列第一点之前——**重算而非存储**的简单例子）；不需要 col 数组（经 firstincol 访问 row，当前列总是已知）；row 从 32 位压到 16 位再到 8 位；从记录退到数组。

## 10.3 数据空间技术

- **Don't Store, Recompute（不存储，重计算）**。素数表可换成素性测试函数；**生成器程序**只存程序与随机种子就能表示巨量随机测试对象；PC 软件"典型安装"占盘、"最小安装"留盘在盘上，以每次更慢的读取换磁盘空间。网络程序的对偶忠告："Store, don't retransmit"（本地缓存，别重传）。
- **Sparse Data Structures（稀疏结构）**。3.1 节把参差的二维表压进二维数组；**键索引**——键本身作下标就无须存键；共享大对象（长文本串）存指针；作者案头年历给 1821~2080 共 260 年的日历只印 **14 个规范日历**（元旦星期 7 种 × 闰平 2 种）加一张 260 年到日历号的映射表；电话系统把静音期当稀疏结构，用简洁表示传"沉默"，省出的带宽传别的通话。
- **Data Compression（数据压缩）**。信息论洞见：稀疏矩阵例把 row 从 32 压到 16 再到 8 位；早期个人机上作者把两个十进制数字 a、b 打包进一个字节（c = 10a+b，解码 `a = c/10; b = c%10`），I/O 时间减半、数字文件从两张软盘挤进一张。CD 音质立体声每秒 176,400 字节，MP3 能压到零头；13.8 节还有 75,000 个英语词挤进 52KB 的专用压缩。
- **Allocation Policies（分配策略）**。有时**怎么用空间比用多少更重要**：动态分配避免"10,001 个 x 记录耗尽内存而 20,000 个 y/z 记录闲置"；变长记录（换行符结尾）让 80 列穿孔卡时代过半是尾随空格的磁盘容量翻倍；作者曾用变长记录（最长 250、平均 80 字节）给 I/O 密集程序提速两倍；垃圾回收让旧 bit 与新 bit 一样好（14.4 节堆排序把两个不同时期使用的逻辑结构**叠加（overlay）**在同一物理空间）。Kernighan 1970 年代初的货郎担程序：两个 150×150 距离矩阵占大头，零对角且对称 → **两个三角矩阵共享一个方阵 c**，`a[i,j]` 用 `c[max(i,j), min(i,j)]` 访问，在 30,000 字的机器上省下 22,500 字很可观——若是 30,000×30,000 的矩阵，同样改动在今天的 GB 级机器上效果相同。**缓存敏感的内存布局**可能至关重要：多盘 CD 百科全书若布局不合访问模式，换盘换到人想退回单盘版（13.2 节将看到数组比链表摸的数据更多却更快，因为顺序访问与缓存配合得好）。

## 10.4 代码空间技术

瓶颈有时不在数据而在程序本身。图形程序整页的

```c
for i = [17, 43] set(i, 68)
for i = [18, 42] set(i, 69)
for j = [81, 91] set(30, j)
for j = [82, 92] set(31, j)
```

- **Function Definition（函数定义）**：抽成 `hor(17, 43, 68)`、`vert(81, 91, 30)`——用函数替换公共模式，自底向上设计的好原语与组件让系统易维护还省空间。微软砍掉少用功能把 Windows 缩成 Windows CE 适配小内存的移动平台，小 UI 与小 API（Application Programmer Interface，应用程序编程接口）各得其所。
- **Interpreters（解释器）**：再换成解释器读命令数组 `h 17 43 68`；还不够的话，每行打包进 32 位字（2 位命令 + 三个 10 位数）。Kernighan 与 Pike 的结论："虚拟机是个可爱的老想法，最近被 Java 与 JVM（Java Virtual Machine，Java 虚拟机）重新炒热；它给出了高级语言程序可移植高效表示的简便途径。"
- **Translation to Machine Language（到机器语言的翻译）**：编译器层面的小改动曾让早期 Unix 的代码空间缩 5%；最后手段是手写汇编——昂贵易错、通常收益甚微，但内存关键的系统（如 DSP）常用。1984 年的 Apple Macintosh 是惊人案例：128KB RAM（Random-Access Memory，随机存取存储器）的机器只有 64KB ROM（Read-Only Memory，只读存储器），设计团队靠精心泛化算子、合并函数、删除功能加整块 ROM 手写汇编（仔细的寄存器分配与指令选择），在方寸之地塞进了惊人的系统功能，估算只有高级语言编译代码的一半大小，而且飞快。

## 10.5 原则

- **The Cost of Space（空间的代价）**：多用 10% 内存会怎样？有的系统无代价；超小系统可能直接跑不起来；跨网络传输会慢 10%；缓存与分页系统上可能**剧增**（原本贴近 CPU 的数据开始在缓存间颠簸）。动手省空间前先弄清代价。
- **The "Hot Spots" of Space（空间的热点）**：与运行时间相反，**代码没有热点**——一条指令执行十亿次还是零次，占的存储一样；数据确有热点——稀疏矩阵例中单个结构占半 MB 机器的 15%，缩成十分之一影响巨大，把 1KB 结构缩百倍则无感。
- **Measuring Space（测量空间）**：性能监视器 + 附录 3 的空间模型；McIlroy 把链接器输出与源文件合并看每行耗多少字节（有的宏展开成几百行），据此裁剪目标代码；作者看过存储分配器返回内存块的"电影"（算法动画）而找到一个内存泄漏。
- **Tradeoffs（权衡）**：确实常要拿性能、功能或可维护性换内存——但本篇多个例子显示省空间可能对其他维度**正贡献**（1.4 节位图让数据进内存，时间从分钟到秒、代码从几百行到几十行）。原因只是原解远非最优——而还不完美的我们，代码常处在这个状态。**权衡掉任何 desirable 属性之前，先找能全面改善的技术。**
- **Work with the Environment（顺应环境）**：编译器与运行时系统的表示、分配策略、分页策略都影响空间效率，别与系统对着干。
- **Use the Right Tool for the Job（用对工具）**：数据空间四招（重算、稀疏结构、信息论、分配策略）、代码空间三招（函数定义、解释器、翻译）、外加总纲（简单性）——内存要紧时，把所有选项都考虑一遍。

## 10.6 习题选

**1.Feldman 的 Fortran 77 编译器挤在 64KB 代码空间里，把记录里的整数从 4 位字段放开成 8 位后，数据空间多几百字节、整个程序反而小了几千字节——为什么？** 访问紧缩字段的每条高级语言指令要编译成很多机器指令，不紧缩的访问指令更少：数据微增、代码大减。

**5.Brooks 的另一个早期问题：每格只存得起一位十进制数字，拟合函数离真值只差两三个单位但法律要求精确——怎么办？** **两种表示结合**：函数负责逼近，那一位数字存差值。（本版两位审稿人评论：他们最近也刚用"近似函数 + 差值表"解过问题。）

**8.日期 8 字节（MMDDYYYY）、社保号 9 字节、姓名 25 字节，空间要紧时能压到多少？** 世纪内的日朴可用世纪内天数 16 位（2 字节）表示；类似地按取值范围重新编码各字段。

## 10.8 边栏：一次大压缩

1980 年代初，Ken Thompson 造了一个解**国际象棋残局**的两阶段程序（如王双象对王马）。学习阶段从所有可能的将杀倒推，算出给定四五子的所有可能棋盘到将杀的距离——计算机科学家称之为动态规划，棋手称之为**回溯分析（retrograde analysis）**；由此数据库让程序对给定子力"全知"，对弈阶段下出完美残局，棋评家的形容是"复杂、流动、漫长而艰难"、"折磨人的缓慢与神秘"，颠覆了既定棋理。

显式存储所有棋盘贵得不可行。Thompson 把棋盘编码成键去索引磁盘文件，每条记录 12 位（含该局面的到将杀距离）。5 个固定子的位置用 5 个 0..63 的整数编码，30 位键意味着 $2^{30} \approx 10.7$ 亿条 12 位记录——超出当时磁盘容量。

关键洞见：**镜像对称的棋盘价值相同**。程序假定白王在 10 个标号方格之一（任意棋盘至多三次翻转即可规范化），磁盘文件降到 $10 \times 64^4$；再利用"黑王不能与白王相邻"（白王在这 10 格时两王只有 454 种合法相对位置），数据库缩到 $454 \times 64^3 \approx 1.21$ 亿条 12 位记录，舒舒服服装进一张（专用）磁盘。

利用数据结构中的对称性把磁盘空间压掉八倍，是整个系统成功的关键；压缩还顺带把学习阶段从好几个月缩到几周。程序只有一份，也必须挤进一张盘。
