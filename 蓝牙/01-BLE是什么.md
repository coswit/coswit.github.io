## 1. 从 Wibree 到 BLE

BLE 的前身是诺基亚 2006 年发布的 **Wibree** 项目:当时蓝牙(BR/EDR)已经在手机上普及,但它的功耗、成本与连接复杂度决定了它没法做"一节纽扣电池用几年"的传感器网络。Wibree 的目标非常克制——低功耗、低成本、低复杂度、小体积,不做万能无线标准。

2010 年,蓝牙 SIG 将 Wibree 收编,作为 **Bluetooth 4.0** 的低功耗部分发布。此后 BLE 的产业采纳速度远超同时期的其他低功耗无线技术(与它竞争的 Zigbee、ANT、6LoWPAN 专网方案最终都没能达到 BLE 的出货量),根本原因是:它**搭上了智能手机的便车**——每部手机都带一颗支持 BLE 的双模芯片,传感器只需要"被读",不需要网关。

> It's the right technology, with the right compromises, at the right time.
>
> 它是在正确的时间、以正确的折中出现的正确技术。

## 2. BLE 与经典蓝牙的关系

| 维度 | 经典蓝牙 BR/EDR | 低功耗蓝牙 BLE |
| ---- | --------------- | -------------- |
| 引入版本 | 1.0(1999) | 4.0(2010) |
| 空口速率 | 1 / 2 / 3 Mbps | 1M PHY 1 Mbps;2M PHY 2 Mbps;Coded PHY 125/500 kbps |
| 信道 | 79 个 1 MHz 信道 | 40 个 2 MHz 信道(3 广播 + 37 数据) |
| 调制 | GFSK / π4-DQPSK / 8DPSK | GFSK(2M PHY 仅速率不同) |
| 发现/连接速度 | 数秒(查询、寻呼) | 数毫秒(广播、CONNECT_IND) |
| 拓扑 | 微微网 piconet,主从时隙 | 星型连接 + 广播;Mesh(2017 起) |
| 典型场景 | 耳机、车载、文件传输 | 传感器、手环、标签、遥控器、LE Audio |
| 发射功率 | 1-100 mW(等级 1-3) | 典型 0 dBm,规范最高 10 dBm |
| 逻辑模型 | 服务发现协议 SDP + 多种专用 profile | 统一的属性数据库 ATT + GATT |

注意"双模(dual-mode)"与"单模(single-mode)"芯片:前者同时实现 BR/EDR 与 BLE(手机、笔记本),后者只有 BLE(传感器、手环,成本功耗更低)。经典蓝牙无"向下兼容 BLE"一说——BR/EDR 设备认不出 BLE 广播。

## 3. 设计目标

原书用一章篇幅讲 BLE 的设计目标,这些目标直接解释了后文协议栈里的每一个"奇怪"设计:

1. **低功耗(Low Power)**:纽扣电池(CR2032,约 220 mAh)供电数月到数年,而不是充电一次用一天。
2. **低成本(Low Cost)**:芯片要能和传感器做进同一颗 SoC,售价一两美元。
3. **小体积、全球可用**:2.4 GHz ISM 频段全球免许可。
4. **鲁棒性(robustness)**:在 Wi-Fi、微波炉、其他蓝牙共存的最恶劣 2.4 GHz 环境下仍能工作。
5. **易用**:配对、重连对用户透明,连接建立毫秒级。
6. **兼容既有蓝牙生态**:能复用手机端的天线、认证与品牌。

## 4. 核心设计理念

### 4.1 时间就是能量(Time Is Energy)

BLE 一切低功耗手段的本质就一句话:**让无线电尽可能快地关掉**。发射与接收是毫安级的电流,睡眠是微安级,所以:

- 空口数据速率定在 1 Mbps(而不是更低)——同样的数据,发得越快,射频开得越短;
- 广播、连接、加密全部走"事件"模型:平时深度睡眠,到点醒来收发几百微秒到几毫秒,再睡;
- 没有经典蓝牙那样的连续音频流时隙,没有周期性的寻呼扫描占空比。

### 4.2 非对称设计(Asymmetric Design)

连接的两个角色承担不对等的复杂度:**Central(中心,如手机)做绝大部分工作**——发起连接、管理信道跳频、决定连接参数;**Peripheral(外围,如传感器)** 只需要在约定时刻醒来应答。这样外围设备可以用最便宜的单片机实现协议栈,把内存和算力成本转嫁给手机。

### 4.3 无连接模型(Connectionless Model)

很多场景(温度计、iBeacon、胎压监测)根本不需要双向会话,BLE 把"广播/观察(Broadcast/Observe)"做成与"连接"并列的一等公民:广播者每几秒发一包,观察者听着就行,双方不建立任何状态,各自睡各自的。

### 4.4 客户端-服务器架构(Client-Server Architecture)

经典蓝牙的每个应用都自带一套专用协议(profile),BLE 反其道而行:**外围设备就是一个小小的数据服务器(Server)**,把所有数据组织成一张统一的属性表(Attribute Table);中心设备作为客户端(Client)用统一的 ATT/GATT 协议去读、写、订阅。一个通用的手机 App(如 nRF Connect)就能调试任何 BLE 外围设备——这是 BLE 生态爆发的关键。

> BLE 的应用层范式是**面向服务的架构(Service-Oriented Architecture)**:数据以服务(Service)和特征(Characteristic)的形式暴露,协议与规格(Specification)分离,客户端不需要预先知道对端是什么设备。

### 4.5 万物皆状态(Everything Has State)

BLE 把设备暴露的一切都视为**状态(State)**:电池电量、心率、开关状态。属性表就是一张"当前状态快照表",服务器在状态变化时主动通知(Notification)客户端。理解了这一点,ATT/GATT 的设计(读、写、订阅)就顺理成章。

### 4.6 十亿是个小数字(One Billion Is a Small Number)

经典蓝牙设备年出货量以十亿计,任何协议设计都要考虑**超大存量设备的互操作性**:16 位 UUID(而非 128 位)、极小的最小实现(MTU 23 字节)、一个连接最少只需要几 KB 内存——让最便宜的芯片也跑得起完整协议栈,同时老设备永远认识新设备的基本广播。

## 5. 一个典型工作日的功耗画像

以一个每秒上报一次的 BLE 温度传感器(CR2032,220 mAh)为例:

| 状态 | 单次时长 | 单次耗电占比 | 说明 |
| ---- | -------- | ------------ | ---- |
| 睡眠 | 24 h | < 10% | µA 级,RTC 定时醒来 |
| 广播/连接事件 | 1-3 ms | > 80% | mA 级射频电流 |
| 加密(重连时) | 数 ms | 视重连频率 | AES 硬件加速则可忽略 |

**优化方向永远是:减少醒来的次数、缩短每次醒来的时长**——后面链路层的连接间隔(Connection Interval)、从机延迟(Slave Latency)等参数都是围绕这个目标设计的。

## 6. 关键限制(设计折中的另一面)

- **吞吐**:1M/2M PHY 的空口速率并不低,但默认 27 字节载荷 + 连接间隔机制使实测吞吐通常在数百 kbps 量级(优化 DLE、MTU、间隔后 2M PHY 可到 1-2 Mbps)。
- **距离**:典型 10-30 m(0 dBm),Coded PHY 配高增益可达数百米,但那是牺牲速率换来的。
- **拓扑**:一个连接就是一条星型边,多角色并存(既做 Peripheral 又做 Central)从 4.1 起才放开;更大规模组网要靠 Mesh 的管理式泛洪。
- **时延与带宽不可兼得**:连接间隔越短时延越低、功耗越高——BLE 的所有参数都是这套权衡的旋钮。
