## 1. 三代经典平台与 SDK 形态

书里与配套资料覆盖的三类平台,恰好代表 BLE SoC 的三种软件形态:

| 平台 | 芯片形态 | SDK 形态 | 代表场景 |
| ---- | -------- | -------- | -------- |
| TI CC2540/41 | 8051 内核 + 2.4G 射频 SoC | **OSAL 任务调度 + BLE 协议栈库**(源码黑盒层)+ 应用 profile 例程 | 《4.0 BLE 开发完全手册》《BLE 权威教程》主线 |
| Dialog/Renesas DA1458x | Cortex-M0 SoC | RW 内核(`rwip`)消息驱动 + 架构层(`arch_`)电源管理 | 《DA1458x Software Platform Reference》 |
| Nordic nRF51/52 | Cortex-M0/M4 SoC | **SoftDevice**(协议栈独立二进制 + SVC 调用)+ 应用工程 | 《Getting Started with BLE》附录 |

共同范式:**协议栈是预编译库/固件,应用以事件驱动方式与之交互;主循环 = 事件泵 + 深度睡眠**。

## 2. TI CC254x:OSAL 世界观

- **OSAL(Operating System Abstraction Layer)**:极简协作式"操作系统"——任务注册、消息队列、定时器,没有抢占与线程。所有协议栈层(LL/L2CAP/GAP/GATT/HCI)与应用各自是一个 OSAL 任务,层间以事件与消息通信;
- **HAL 硬件抽象**:按键、LCD、UART、睡眠与电源(不同功耗模式 PM1-3);
- 应用层入口:`SimpleBLEPeripheral` 例程——初始化 GAP 角色任务(广播/连接参数由 `GAPRole_SetParameter` 配置)、注册 GATT 服务表、事件回调(状态变化、收写请求);
- **GATT 服务表**:以 C 数组静态声明属性表(`gattAttribute_t` 数组:类型/权限/值指针),栈按表应答 ATT 请求——正好印证"服务器就是一张属性表"的模型;
- **双芯片实验**:把 HostTestRelease 固件烧进 CC2540 USB dongle,它就变成纯 Controller/BT 网络处理器,PC 上用 BTool/BLE Device Monitor 经 HCI(HCI over USB)做主机——链路层与 HCI 的一切命令都能在 BTool 里逐条手动下发。

## 3. DA1458x:消息驱动 + 极致低功耗

- Dialog 的 RW 软件平台:内核 `rwip_schedule()` 主循环按消息驱动协议栈;`arch_` 层负责时钟与**睡眠策略**(sleep/wakeup,睡前保持 BLE 时基);
- 特点是功耗纪录级(宣称一节纽扣电池数年),外设与电源管理细节多;SDK 把 BLE 核心作为库(与 TI 类似),profile 与应用在用户区;
- 量产要点:OTP/Flash 引导、生产烧录配置、睡眠下 GPIO 与外设保持——嵌入式功耗调优的真实战场在这里,而不在协议层。

## 4. Nordic SoftDevice:协议栈"户口分离"

- **SoftDevice** 是独立预认证固件(MBR + 协议栈),应用通过 **SVC 超级调用**请求服务(S110 外设 / S120 中央 / S130 双角色,均基于 4.0/4.1——对应书籍年代;nRF52 时代演进为 S132/S140,支持 5.x);
- 应用与协议栈**中断优先级分区**,协议栈硬实时部分对应用透明;
- 好处:射频认证由 Nordic 打包,应用固件随便改不破坏认证;代价:必须遵守 SoftDevice 的内存布局与 API 规范;
- nRF52/54 至今仍是 BLE 开发与教学的事实标准,nRF Connect SDK(Zephyr)已是新项目首选——SoftDevice 概念演进为 Zephyr 蓝牙子系统。

## 5. 功耗设计实战(通用方法论)

1. **测**:功率分析仪(PPK2/OTII)抓电流波形,先看"醒来的次数与时长",不看平均电流;
2. **参数三旋钮**:广播间隔(被发现速度 ↔ 功耗)、连接间隔、Peripheral Latency——数值依据产品交互定(遥控器 7.5-15 ms;传感器 1-2 s);
3. **传输优化**:MTU/DLE 拉满 + 2M PHY,把"发射窗口"缩到最短;能批量就别碎包;
4. **睡眠质量**:确认广播/连接间隔外的空闲全部进入最深可用睡眠态,关掉不必要外设与调试引脚;
5. **重连策略**:定向广播 + 白名单直连,比"广撒网等连接"省一个数量级;
6. **避免反模式**:为了省电把广播间隔拉到 5 s 却要求"扫码即配网"(体验崩);为了吞吐把连接间隔 7.5 ms 却忘了 Latency(睡眠机会全丢)。

## 6. OTA/固件升级:一次 GATT 大传输的完整设计

OTA(Over-The-Air)升级是 BLE 产品必答题,也是"协议知识 → 工程能力"的综合应用。完整过程:

### 6.1 前置协商

1. App 连接后**先协商 MTU**(`requestMtu(247)`)与 DLE——分块越大,总耗时与功耗越低;
2. 读"升级控制"特征:设备返回**当前版本、镜像大小、上次断点的偏移量**——断点续传的基础;
3. (带鉴权的产品)校验权限:升级特征要求加密连接。

### 6.2 传输循环

```text
App 侧伪代码:
offset = device.resume_offset          # 续传起点
while offset < image_size:
    chunk = image[offset : offset + chunk_size]   # chunk_size = MTU - 3
    writeCommand(OTA_DATA, chunk)      # Write Command 无响应,高吞吐
    if (offset % 4096 == 0):           # 每页/每 N 块一次同步
        wait Notification(OTA_STATUS)  # 设备确认已落 flash 并回 CRC
        offset = acked_offset
```

要点:

- **数据走 Write Command(无响应写)**,靠设备周期性 Notification 回 ACK/偏移/CRC 做流量控制——完全对应 ATT 的 Command 与 Notification 语义,不能每块都用 Write Request(每块一来一回,吞吐减半);
- **flash 写入的特性**:擦写会阻塞 CPU(数十毫秒级),期间喂不上连接事件 → **监督超时断连**。解法:按 flash 页对齐分块、页擦除后集中写入、写 flash 期间放宽连接参数或通知 App 暂停几百毫秒;
- **通知与拥塞**:设备端 Notification 队列有深度限制(协议栈缓存),回 ACK 别追着发,注意协议栈的拥塞回调。

### 6.3 校验与切换

1. 传完后 App 发"校验"命令,设备对整镜像算 **CRC32(防错)与签名校验(防伪)**——CRC 只能发现传输损坏,防回滚/防篡改必须用非对称签名(如 ECDSA),密钥写在设备安全区;
2. 校验通过 → 设备标记新镜像有效并**重启进入 bootloader**:bootloader 校验、搬运/交换双区(double bank,可回退)或直接跳转(single bank,断电即变砖,便宜产品才用);
3. App 重连后读版本号确认升级成功。

### 6.4 常见翻车点

| 现象 | 根因 |
| ---- | ---- |
| 传到一半必断连 | 写 flash 阻塞导致监督超时(见 6.2) |
| 速率只有几 KB/s | MTU 还是 23、没用无响应写、连接间隔太长 |
| 断点续传后镜像损坏 | 偏移与 flash 页没对齐;ACK 的偏移语义两端理解不一致 |
| 升级后变砖 | 单区直写 + 校验缺失/中断电;bootloader 没有兜底回退 |
| 被"降级攻击" | 没做防回滚(版本单调性检查) |

## 7. 空口抓包

BLE 空口包不经 HCI,要看得懂"广播/连接"的真实飞行,需要专用 sniffer:

| 工具 | 硬件 | 说明 |
| ---- | ---- | ---- |
| TI Packet Sniffer / SmartRF | CC2540 USB dongle | 抓广播信道与指定连接,书配资料路线 |
| Nordic nRF Sniffer | nRF52 dongle + Wireshark 插件 | 跟随指定设备,自动解析广播与连接事件,当前最常用 |
| Ellisys / Frontline 专业仪 | 专用硬件 | 全信道并行、协议一致性测试,认证实验室级别 |

抓包要点:

- Sniffer 靠**访问地址**跟流:广播 AA 固定 0x8E89BED6;连接要抓到 CONNECT_IND 才能拿到连接 AA 与跳频参数继续跟;
- **Wireshark 直接解析 btsnoop**(HCI 日志)与空口捕获两种来源,过滤 `btatt`/`btle` 即可复用 Wireshark 技能;
- 加密连接里 sniffer 默认只见密文;给 sniffer 喂 LTK(调试构建导出)才能解密 ATT。

## 8. 排障速查表

| 症状 | 先查什么 |
| ---- | -------- |
| 广播谁也扫不到 | 广播开关/广播类型(ADV_NONCONN 扫不到 SCAN_RSP)/地址类型/频段占用 |
| 手机能连、App 连不上 | 权限(Android 12+)/白名单过滤策略/定向广播指向别人 |
| 连上立刻断(133) | HCI 日志看 Enhanced Connection Complete 后首个连接事件是否丢失;连接参数是否非法 |
| 发现不了服务 | 属性表句柄连续性;Service Changed 后未重新 discover |
| 收不到 Notify | CCCD 写了吗(0x2902 → 0x0001);写的是"本机开关"还是"对端 CCCD" |
| 配对失败/循环弹窗 | 双侧绑定记录不同步;IO 能力与期望的配对方法不符;LE Privacy 地址解析失败 |
| 吞吐低 | MTU(默认 23)/DLE 未开/1M PHY/连接间隔过长/写用了带响应方式 |
| 功耗高 | 功率波形看醒来频率;连接间隔与 Latency;广播数据是否过大 |
| OTA 升级断连 | 大流量把连接事件占满触发监督超时;MTU+DLE+批量化,必要时动态调参数 |

## 9. 从书本年代到今天

书配平台(CC254x/DA1458x/老 SoftDevice)停留在 4.0/4.1,但**协议骨架未变**:今天在 Zephyr 或 ESP-IDF 上写 BLE,广播参数、GATT 表、连接参数这些概念一字不差。新平台把 OSAL/RW 换成了 Zephyr/FreeRTOS,把静态 GATT 表换成了宏声明(`BT_GATT_SERVICE_DEFINE`),把 HCI 换成了更现代的 btmon 采集——**吃透广播参数、GATT 表、连接参数这套协议骨架,迁移成本只剩 API 拼写**。
