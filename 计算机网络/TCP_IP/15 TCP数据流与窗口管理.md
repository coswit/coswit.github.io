> 交互式流量（延迟 ACK、Nagle）、批量流量（滑动窗口）、零窗口探测、SWS、窗口回绕与自动调优。

## 1. 两种流量形态

- **交互式（interactive）**：小而频繁（ssh、游戏、聊天），关心**时延**。
- **批量（bulk）**：大块连续（文件传输、备份），关心**吞吐**。
TCP 的机制需要同时伺候好两类流量。

## 2. 交互式流量

### 延迟确认（Delayed ACK）

- 接收方收到数据不立即 ACK，**等待一小段时间（通常 ≤200 ms，Linux 动态约 40 ms）**：
  - 若期间有反向数据 → 捎带（piggyback）ACK；
  - 若等到第二个反向数据段 → 合并确认（每 2 个全尺寸段回一个 ACK，即 ACK 比例 2:1）；
  - 到时仍无 → 单独发 ACK。
- 意义：减少纯 ACK 小包数量；但**加剧交互时延**（等捎带）。

### Nagle 算法（RFC 896）

- 规则：连接上存在**未被确认的小段（< MSS，"tinygram"）**时，后续小数据先攒着不发，直到收到 ACK 或攒够一个 MSS。
- 动机：防止每敲一个键就发一个包的"小包泛滥"（浪费头部开销、加剧拥塞）。
- **Nagle × 延迟 ACK 的死锁**：发送方等 ACK 才放行下一个小段，接收方等可能到来的第二个小段才回 ACK → 引入意外的 ~40–200 ms 时延。交互应用（ssh 鼻祖 telnet 时代后的 X11、鼠标类）用 **`TCP_NODELAY`** 关闭 Nagle。
- 推荐组合：低时延服务 `TCP_NODELAY=1`；吞吐型保持默认。
- 相关：`TCP_QUICKACK`（Linux 临时关闭延迟 ACK）。

## 3. 批量流量与滑动窗口（Sliding Window）

### 窗口机制

接收方在每个 ACK 中用 **Window 字段** 通告"我还能收多少字节"（流量控制）：

```
发送方视角 (字节序号):
├─────已发已确认─────┼─────已发未确认─────┼───可用窗口(未发)───┼─────不允许发送─────┤
                      ◀───────── 发送窗口 (由接收方通告) ───────▶
可用窗口 = 通告窗口 − (snd.nxt − snd.una)      #Flight Size 在途量
```

- 左边界随 ACK 推进，右边界 = ACK号 + Window；窗口可增大/缩小。
- **吞吐上限 = min(带宽, 窗口 / RTT)**：窗口不足时链路喂不满——BDP（带宽×时延积）大的"长肥网络（LFN）"需要大窗口，正是 Window Scale 存在的原因（第 12 章）。
- 数量级感受（BDP）：155 Mb/s × 100 ms ≈ 1.9 MB；1 Gb/s × 10 ms ≈ 1.25 MB——都远超 64 KB 的原始窗口上限，故必须 Window Scale。

### 窗口自动调优

- 接收端：内核按需**动态增长接收缓冲**（Linux `tcp_moderate_rcvbuf`），通告窗口随之扩大，直至 BDP 满足或上限。
- 发送端：发送缓冲自动扩容（`tcp_wmem` 区间）。
- 手工固定 `SO_RCVBUF` 会封顶通告窗口，长 RTT 链路吞吐上不去的经典原因。

## 4. 零窗口与持续计时器（Persist Timer）

接收应用不读数据 → 接收缓冲满 → 通告 **Window = 0** → 发送方停发：

```
发送方 ──[数据]──▶ 接收方 (窗口逐渐减小... 最终 WIN=0)
发送方等待...   为防"窗口更新ACK丢失"造成死锁:
  零窗口探测(Zero Window Probe): 定期发送 1 字节 (persist timer 指数退避, 如5s→10s→...→60s)
  接收方回: WIN=0 (继续等) 或 WIN>0 (恢复发送)
```

- 若不探测而"窗口更新"ACK 丢失，双方互等死锁；接收方即使 WIN=0 也必须回应探测（探测字节可被缓冲/丢弃）。
- 探测持续到窗口打开或应用放弃（受 `tcp_retries2` 类似上限约束）。

## 5. 糊涂窗口综合症（Silly Window Syndrome, SWS）

- 现象：接收方一点点腾出空间就通告小窗口 / 发送方一点点塞小段 → 线路上净是小包（有效载荷/头部比极差）。
- **接收端避免**（Clark 方法）：空间不足 `min(MSS, 缓冲/2)` 时继续通告 **WIN=0**，攒够再开窗。
- **发送端避免**：应用写入的小数据只有满足以下才发送——能发满一个 MSS，或 ≥ 当前通告窗口的一半，且连接上无未确认数据（这条即 Nagle 的强化版）；否则等待/攒批。
- 结果：窗口永远只在"有意义的尺寸"间移动。

## 6. 紧急数据（带外数据，Out-of-Band / URG）

- URG 标志 + Urgent Pointer 指示"字节流中某处是紧急标记"，接收方可用 `SO_OOBINLINE`/`recv(MSG_OOB)` 优先取用。
- 实际是**带内信令**（数据仍在字节流里），且各实现语义不一，**现代应用避免使用**（Telnet 的中断指令是历史用例）；已成为安全与兼容性负担。

## 7. 大窗口与序号回绕（Wrapped Windows）

- 序号 32 bit，高速链路上很快回绕（10 Gb/s 下约 1.7 秒一轮）。
- **PAWS（Protection Against Wrapped Sequence numbers，RFC 1323）**：每段携带单调递增的时间戳，接收方丢弃时间戳"更老"的段，从而区分"新数据"与"回绕后的旧重复"。
- 回绕比较需用有符号减法（模 2³² 意义下的先后）。


## 9. 要点回顾

- 交互流量：延迟 ACK（≤200 ms）与 Nagle（攒小段等 ACK）互搏；低时延场景 `TCP_NODELAY`。
- 批量流量：滑动窗口 + 通告窗口控制；吞吐 ≤ 窗口/RTT；自动调优于 LFN 场景放大窗口。
- 零窗口靠 persist timer 的 1 字节探测防死锁；SWS 两端规则避免小包抖动。
- 32 bit 序号回绕用 PAWS（时间戳）防护；URG/带外数据基本弃用。
