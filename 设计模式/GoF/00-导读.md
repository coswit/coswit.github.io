# 《Design Patterns: Elements of Reusable Object-Oriented Software》导读笔记

> 作者：Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides，合称 **GoF（Gang of Four）**，1994 年出版。本书奠定了"设计模式"这一词汇的现代含义，收录 **23 个模式**，示例语言为 **C++ 与 Smalltalk**（成书早于 Java，但概念完全通用）。
>
> 本目录笔记按原书第 1、2 章的导读 + 第 3 章 catalog 的模板整理，每个模式附 mermaid 类图（Structure）与按原书 Motivation 场景改写的 Java 示例（原书为 C++/Smalltalk）；与上级目录的《设计模式之一/之二/之三》（java-design-patterns 风格的示例）互补对照。

## 什么是设计模式（What Is a Design Pattern）

> A design pattern names, abstracts, and identifies the key aspects of a common design structure that make it useful for creating a reusable object-oriented design.
>
> 设计模式命名、抽象并标识出一类常见设计结构中使其有利于复用面向对象设计的关键方面；它指出了参与其中的类与对象、各自的角色与协作方式、以及职责的分布。

一个模式有四个基本要素：

1. **模式名（Pattern name）**：一两个词描述设计问题、解法与效果，扩大设计词汇量。
2. **问题（Problem）**：何时使用该模式——问题所在的前因后果、使用条件。
3. **解决方案（Solution）**：设计的组成元素、它们的关系与协作方式。解决方案是抽象的——是问题的模板化解法，不是具体实现。
4. **效果（Consequences）**：应用该模式带来的代价与收益——空间/时间权衡、语言灵活性影响、对系统可扩展性的影响等。

模式的思想源自建筑学家 Christopher Alexander 的《A Pattern Language》：*"每个模式描述了一个在我们周围不断重复发生的问题，以及该问题解法的核心。这样你就能一次又一次地使用该方案，而不必重复劳动。"*

## 设计模式的起点：Smalltalk MVC

原书以 Smalltalk 的 **Model/View/Controller** 作为引子（1.2 节）：MVC 把交互式应用拆成三类对象——**Model**（应用数据与领域逻辑）、**View**（Model 的屏幕呈现）、**Controller**（定义对用户输入的反应）。它身上已经能看到多个模式的雏形：

* View 依附于 Model、随 Model 的变化而更新——**Observer** 的雏形
* View 把输入的解释交给 Controller，可替换不同的输入策略——**Strategy** 的雏形
* View/Controller 可嵌套组合成复合视图——**Composite** 的雏形

MVC 的启示：把对象拆小、各司其职，再用"观察、组合、策略"把它们接起来——这正是"模式"作为可复用微架构的样子。

## 原书的模式描述模板

第 3 章 catalog 中每个模式都按以下格式描述：

| 小节 | 内容 |
| --- | --- |
| Pattern name / Classification | 模式名与分类（目的 × 范围） |
| Intent | 意图：模式做什么、其基本原理 |
| Also known as | 别名 |
| Motivation | 动机：一个说明问题的场景 |
| Applicability | 适用性：什么场合使用 |
| Structure | 结构：OMT 类图的等价表示 |
| Participants | 参与者：组成设计的类/对象及其职责 |
| Collaborations | 协作：参与者如何协作满足职责 |
| Consequences | 效果：模式如何达成目标、代价与权衡 |
| Implementation | 实现要点、陷阱、技巧（与模式无关的部分不谈） |
| Sample Code | 示例代码 |
| Known Uses | 已知应用：真实系统中的例子 |
| Related Patterns | 相关模式：与哪些模式有密切的配合/对比 |

## 目录的组织方式：目的（Purpose）× 范围（Scope）

**目的（purpose）**：模式是用来干什么的——创建型（Creational，对象创建）、结构型（Structural，类与对象的组合）、行为型（Behavioral，类与对象的交互与职责分配）。

**范围（scope）**：模式作用于类还是对象——**class pattern** 处理类之间的（编译期、静态）继承关系；**object pattern** 处理对象之间的（运行期、动态）组合关系。

## 支撑全书的两大原则

1. **Program to an interface, not an implementation.（面向接口编程，而非面向实现编程）**
   声明变量、参数、返回值时只承诺抽象接口（abstract class / interface），不承诺具体类。这样客户端不受实现细节影响，实现了可替换。
2. **Favor object composition over class inheritance.（优先使用对象组合，而非类继承）**
   继承（"white-box reuse"）对父类内部白盒可见、耦合紧、编译期静态绑定；组合（"black-box reuse"）只依赖接口、封装好、运行期可变。继承只应表达泛化（is-a）关系，仅为复用实现而继承是误用；组合 + 委托（delegation）能获得继承的复用能力又不失灵活性。

这两条贯穿 23 个模式：多数 object-scope 模式可以理解为"把继承能做的事改用组合来做"的手段。

## 模式如何解决设计问题（第 1 章要点）

- **寻找合适的对象（Finding Appropriate Objects）**：难点在于把系统划分成一组"职责恰好"的对象——太细则碎、太粗则僵。模式提供经过验证的划分方式。
- **决定对象的粒度（Determining Object Granularity）**：Facade、Flyweight、Composite 等模式分别在不同方向上控制粒度。
- **指定对象接口（Specifying Object Interfaces）**：接口 = 一组操作的签名（signature）；类型 = 接口的名字。书中使用静态类型视角，但也讨论动态类型。
- **描述对象的实现（Describing Object Implementations）**：
  - **implementation inheritance**（实现继承，复用父类已有功能）与 **interface inheritance**（接口继承，只承诺能力）是两回事；子类化同时引入两者。
  - 抽象类（abstract class）可为部分实现定义公共接口；接口（interface/C++ 纯抽象类）只定义能力。
  - 不要为"复用实现"而继承，继承应表达 is-a。
- **复用机制（Putting Reuse Mechanisms to Work）**：三种复用手段——类继承、对象组合、参数化类型（parameterized types，即模板/泛型）。组合优先；委托（delegation）是组合的强化形式（把请求转发给受托对象，可按需替换，书中 ExtremeChess/ConstraintSolver 的例子）。
- **运行期结构与编译期结构（Run-Time and Compile-Time Structures）**：类图只描述编译期结构，远不足以刻画面向对象系统——大量对象在运行期才被创建并动态连接成对象网络，理解一个系统的关键是它的运行期对象图。object 模式的价值大半在于管理这种动态关系。
- **聚合与相识（Aggregation vs. Acquaintance）**：聚合（aggregation）表示"拥有"——整体与部分、常伴随生命期从属；相识（acquaintance）表示"仅仅认识"——持有引用但没有从属关系。二者在类图上往往无法区分，耦合程度却完全不同，需要靠语义约定来辨明。
- **三类软件**：**application programs**（不可复用的应用）、**toolkits**（可复用的类库，如 GUI 组件集）、**frameworks**（整个应用/子系统的可复用设计， dictates your application's structure）。设计模式比框架更小、更抽象；框架通常"内嵌"多个模式。

## 如何选择与使用模式（How to Select / Use）

**选择：**

1. 浏览目录的目的分类（创建型/结构型/行为性）圈定候选；
2. 逐条读 Intent，与你的问题对照；
3. 沿 Related Patterns 的关联网横向比较；
4. 审查 Applicability 是否匹配、Consequences 的代价能否接受。

**使用：**

1. 先通读一遍模式（含 Motivation、Structure）建立整体印象；
2. 研究 Participants 与 Collaborations，理解职责分布；
3. 看 Sample Code，落到具体语言；
4. 给你的模式使用起有意义的名字（如 `ScrollingComposer`），保持项目词汇一致；
5. 按需裁剪实现——模式是起点不是终点（"patterns are a starting point, not an endpoint"），不必逐字照抄。

## 第 2 章案例研究：文档编辑器 Lexi

Lexi 是一个 WYSIWYG 文档编辑器（类似早期 Word），原书用它把多个模式串成一个完整设计——这也是读通全书的主线：

| 设计问题 | 采用的模式 | 说明 |
| --- | --- | --- |
| 文档结构（文本、图形混排，递归嵌套） | **Composite** | 一切排版元素是 Glyph，字符/图形是叶，行/列/页是容器 |
| 格式化算法（断行等可替换） | **Strategy** | Compositor 族：SimpleCompositor / TeXCompositor，可按文档切换 |
| 给元素加边框、滚动条等修饰 | **Decorator** | MonoGlyph 派生 Border、Scroller，动态包装任意 Glyph |
| 支持多种 look-and-feel（Motif/PM/Mac） | **Abstract Factory** | WidgetFactory 一次换掉整族控件；还可用 Factory Method 或 Prototype 实现 |
| 支持多种窗口系统（X/PM/…） | **Bridge** | Window（抽象）与 WindowImp（实现）分离——与 look-and-feel 是两个独立维度 |
| 用户操作（菜单项触发动作） | **Command** | 每个 MenuItem 持有 Command 对象，可统一调度 |
| 撤销/重做（undo/redo） | **Command** + 历史列表 | execute/unexecute 成对入栈；需要状态快照时配合 Memento |
| 拼写检查与断字（旁挂分析服务） | **Observer** + **Iterator** | 分析服务订阅文档变化，用 Iterator 遍历内容 |
| 大量字符对象的内存开销 | **Flyweight** | 每种字符一份 Glyph，位置/样式作为外部状态传入 |

> Lexi 的启示：真实系统里模式从不孤立出现，而是互相配合——Composite 构成结构，Decorator 修饰它，Iterator/Visitor 遍历它，Flyweight 共享它的叶节点，Command 操作它，Observer 监视它。
