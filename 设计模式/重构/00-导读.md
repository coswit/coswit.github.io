## 重构的定义

> **Refactoring (noun)**: A change made to the internal structure of software to make it easier to understand and cheaper to modify without changing its observable behavior.
>
> **Refactoring (verb)**: To restructure software by applying a series of refactorings without changing its observable behavior.
>
> 名词：在**不改变软件可观察行为**的前提下，调整其内部结构，使其更易理解、修改成本更低的变更。动词：通过一系列这样的小变更重新构造软件。

关键词拆解：

* **不改变可观察行为（observable behavior）**：对使用者而言功能不变——这是重构与功能开发的边界，也是测试能守护的底线。
* **一系列小步（a series of refactorings）**：每个手法都微小、独立可验证、随时可停；一连串小步累积出结构性改善。
* **更易理解、更廉价（easier to understand and cheaper to modify）**：重构算的是经济账——不为美而美，为的是降低后续每一次变更的成本。

## 两顶帽子（The Two Hats）

开发中我们在两种活动之间切换：

* **添加功能（adding functionality）**：只添加新能力与对应测试，不碰既有结构；
* **重构（refactoring）**：只重组结构，不加任何新功能、不改任何行为。

规则：同一时刻只戴一顶帽子。可以频繁换帽子，但不能同时戴两顶——"加一点功能、顺手重构一点、再回来接着加"会让两件事都做不干净：commit 混杂两种意图、难以 review、出问题时难以定位和回滚。

## 重构不是什么

| 活动 | 与重构的区别 |
| --- | --- |
| 性能优化 | 也常保持行为不变，但目标是速度而非可理解性，手段常与重构相反（为速度牺牲清晰） |
| 重写（rewrite） | 推倒重来、另起炉灶；重构全程让系统处于可运行、可发布状态 |
| 大规模结构调整 | 架构级目标也由一连串小重构逐步逼近、保持可运行，而不是一次性"大爆炸"切换 |
| 代码风格化 | 重构改变的是结构（函数边界、模块划分、职责分布），不是缩进与格式 |

## 第 1 章走读：一个账单程序的重构

场景：一家剧团演出莎士比亚等剧目，客户（customer）下单后剧团出具账单（statement）。数据有两份：剧目表 `plays`（playID → name/type）与账单 `invoices`（customer + 若干场演出 performance{playID, audience}））。初始程序只有一个 `statement()` 函数（Java 改写）：

```java
public String statement(Invoice invoice, Map<String, Play> plays) {
    int totalAmount = 0;
    int volumeCredits = 0;
    StringBuilder result = new StringBuilder("Statement for " + invoice.customer + "\n");
    for (Performance perf : invoice.performances) {
        Play play = plays.get(perf.playId);
        int thisAmount = 0;
        switch (play.type) {
            case "tragedy": thisAmount = 40000;                       // 单位：美分
                if (perf.audience > 30) thisAmount += 1000 * (perf.audience - 30);
                break;
            case "comedy":  thisAmount = 30000 + 300 * perf.audience;
                if (perf.audience > 20) thisAmount += 10000 + 500 * (perf.audience - 20);
                break;
            default: throw new IllegalArgumentException("unknown type: " + play.type);
        }
        volumeCredits += Math.max(perf.audience - 30, 0);             // 积分
        if ("comedy".equals(play.type)) volumeCredits += perf.audience / 5;
        result.append(String.format("  %s: $%.2f (%d seats)\n",
                play.name, thisAmount / 100.0, perf.audience));       // 输出一行
        totalAmount += thisAmount;
    }
    result.append(String.format("Amount owed is $%.2f\n", totalAmount / 100.0));
    result.append(String.format("You earned %d credits\n", volumeCredits));
    return result.toString();
}
```

起点的问题（Comments on the Starting Program）：

* 程序"能跑"，但**结构与意图不匹配**：一个函数同时做计算、格式化、累加三种事；
* switch 按剧种分支，将来每加一个剧种都要钻进这团代码；
* 金额以美分为单位的裸整数在程序各处流动，"÷100 转美元"的格式化知识散落在每条输出语句里；
* 典型的"没有明显坏到要重写，但每次修改都在变难"——重构的标准对象。

重构主线（每一步都小到几分钟、做完即可提交，全程测试保持绿色）：

| 步骤 | 手法 | 动机 |
| --- | --- | --- |
| 1. 把 switch 计算块提炼为 `amountFor(perf, play)` | Extract Function | 让 `statement` 里只剩流程，计算细节有名字 |
| 2. 提炼 `playFor(perf)`，并从 `amountFor` 签名中删掉 `play` 参数 | Extract Function + Change Function Declaration | 函数自己能查到的数据不该出现在参数里 |
| 3. 提炼 `volumeCreditsFor(perf)`；把金额格式化提炼成 `usd()` | Extract Function | 同上；魔法数字与格式化知识各归其位 |
| 4. 把临时变量 `totalAmount`、`volumeCredits` 变成查询函数 | Replace Temp with Query | 临时变量只在函数内可见，挡住了进一步的提炼 |
| 5. 删掉不再被使用的旧代码 | Remove Dead Code | 死代码误导读者 |
| 6. 把"计算"与"渲染"两个阶段拆开 | Split Phase | 得到中间数据结构 `createStatementData`（每场演出补齐 play/amount/volumeCredits，及总额） |
| 7. 新增 `htmlStatement()` | ——（纯加功能） | 只需写 20 行 HTML 渲染，计算完全复用——重构红利兑现 |
| 8. 按剧种建立 `PerformanceCalculator` 层次（`TragedyCalculator`/`ComedyCalculator`），把 `amount`/`volumeCredits` 的 switch 移入子类 | Replace Type Code with Subclasses + Replace Conditional with Polymorphism | 类型分支的判断应消失在多态里 |

最终形态（示意）：

```java
// ---- 计算阶段：createStatementData ----
StatementData createStatementData(Invoice invoice, Map<String, Play> plays) {
    List<Performance> enriched = invoice.performances.stream()
            .map(p -> Performance.enrich(p, playFor(p, plays)))   // 挂上 play、calculator
            .collect(Collectors.toList());
    return new StatementData(invoice.customer, enriched,
            enriched.stream().mapToInt(Performance::amount).sum(),
            enriched.stream().mapToInt(Performance::volumeCredits).sum());
}

// ---- 渲染阶段：两种输出只写各自的渲染 ----
String statement(Invoice invoice)      { /* 文本渲染 StatementData */ }
String htmlStatement(Invoice invoice)  { /* HTML 渲染 StatementData */ }

// ---- 计算：按剧种多态 ----
abstract class PerformanceCalculator {
    abstract int amount(Performance perf);
    int volumeCredits(Performance perf) { return Math.max(perf.audience - 30, 0); }
}
class TragedyCalculator extends PerformanceCalculator { /* 40000 + 观众>30 加价 */ }
class ComedyCalculator  extends PerformanceCalculator { /* 30000+300*观众 … 并覆写积分 */ }
```

走读的启示（Final Thoughts）：

* 每一小步都微不足道，串起来却重写了整个程序的结构——重构的复利来自"步数多"而不是"步子大"；
* > Any fool can write code that a computer can understand. Good programmers write code that humans can understand.
  > 任何傻瓜都能写出计算机能理解的代码，优秀的程序员写的是**人**能理解的代码。
* 重构的红利延迟兑现：`htmlStatement` 看似顺手，但没有前面的结构铺垫，它绝不可能这么简单；
* 小步 + 测试 = 可以在任何一步停下来去干别的，系统始终处于可发布状态。

## 为什么要重构（Why Should We Refactor）

1. **改善软件设计（improves the design）**：不改的代码会腐烂——补丁式修改让重复滋生、职责发散。重构持续还债，让代码保持"该有的形状"（DRY、高内聚低耦合）。
2. **让软件更容易理解（makes it easier to understand）**：代码首先是写给人读的。"只可意会"的理解不可靠——把理解**写回代码**（提炼、改名）比记在脑子里或注释里更可靠，也让下一个人（包括下周的自己）免费获益。
3. **帮助找到 bug（helps me find bugs）**：结构清晰让隐含假设显式化；"对代码的理解加深"与"重构动作"互相推进，很多 bug 在重构途中自己浮出水面。
4. **让编程更快（helps me program faster）**：好设计是快速开发的前提——改动处处受阻时，速度的上限不是打字速度而是结构。卫生习惯的成本远低于"等有时间再大扫除"。

## 何时重构（When Should We Refactor）

* **预备性重构（preparatory refactoring）**：加功能前先把挡路的代码理顺。第一版前言中的名句：
  > When you have to add a feature to a program but the code is not structured in a convenient way, first refactor the program to make it easy to add the feature, then add the feature.
  > 要给程序加功能，却发现代码结构不顺手时：先重构到"容易加"，再加功能。（"让路"最省力的时刻就是现在。）
* **为理解而重构（refactoring to understand）**：读代码时随手提炼、改名，把刚获得的理解固化进代码——这比只在脑内缓存它更稳。
* **随手清理（campsite rule / 童子军军规）**：*"Leave the campground cleaner than you found it."*（让营地比你来时更干净。）每次经过都留一点改善；但要有判断力——改坏味道最大的那一处就收手，别把一次顺手变成一次远征。
* **三次法则（Rule of Three，Don Roberts）**：第一次直接做；第二次做类似的会有点烦，但还是做了；**第三次就该重构了**。
* **代码评审与结对**：评审发现的问题当场小步修掉，或记成待办——评审输出的应该是可执行的改动而不是一堆意见。
* **不设"重构周"**：重构是日常开发的一部分，不是阶段性运动。集中大扫除往往意味着日常欠账太多。

何时不重构：

* **重写更便宜**：代码极度难懂又没有测试、行为只能靠考古时，与其硬啃不如重写；大型遗留系统可用"绞杀者模式（Strangler Fig Application）"逐步用新系统包围替换旧系统；
* **不值得救**：一次性脚本、行将退役的模块——投入产出不成立就放过它。

## 重构的难题（Problems with Refactoring）

* **数据库**：schema 与线上数据绑死，不能像代码那样"改完就跑"。对策：小步迁移脚本；新旧结构并存过渡（先扩展出新结构、双写/回填、再收缩旧结构，即 expand–contract）；数据迁移与代码重构分开成小步交替进行。
* **修改已发布接口（changing published interfaces）**：对外 API 的调用方不受你控制。对策：**迁移式重构**——保留旧签名转调新实现、标记 `@Deprecated`、给下游一个迁移期，最后再删旧接口。（内部接口则一步到位，别留尸位素餐的兼容层。）
* **分支与团队协作**：重构重排"everyone's cheese"，长命分支合并时冲突惨烈。对策：持续集成（CI）、小步高频提交、短命分支/主干开发——重构与分支策略互相放大对方的收益。
* **遗留代码没有测试**：没有测试的重构是盲人走钢丝。先设法把代码置于测试之下再动手（Michael Feathers《Working Effectively with Legacy Code》整本都在讲这件事）。这也是下一节"测试是前提"的原因。

## 重构、架构与 Yagni

传统观点认为架构必须先行，因为后期改动太贵；于是前期拼命预留弹性。Fowler 的修正：**Yagni（You Aren't Gonna Need It，你不会需要它）**——只为今天的真实需要构建，把"未来的变化"留给重构去应对。这个立场的前提恰恰是**变更成本足够低**，而把变更成本压低的那只手就是重构 + 测试 + CI。好架构是**演化**出来的（evolutionary architecture），不是一次画完的。

## 重构与软件开发过程

**自测试代码（self-testing code）+ 持续集成（CI）+ 重构**三者互相成就：测试给重构兜底，重构让测试容易写（可测性是结构属性），CI 让小步可以随时合入。这个三角是 XP／敏捷／持续交付共同的技术底座。

## 重构与性能

重构可能让程序变慢一点，但换来的是**可调优性**：结构清晰后才容易定位和替换热点。Fowler 的做法：先把代码写到清晰，再做专门的性能优化；优化时靠 profiling 而不是猜——时间几乎总是集中在少数热点上，集中处理那一小块即可（必要时甚至可以为速度牺牲局部清晰，并把原因写成注释）。性能优化是又一项"戴另一顶帽子"的专门活动，不与重构混做。

## 重构的来历与自动化工具（第 2 章补记）

* **来历（Where Did Refactoring Come From?）**：这套技术发源于 **Smalltalk 社区**——那里的开发者习惯于在小步调整中保持系统可用；学术奠基是 Ralph Johnson 指导、**William Opdyke 1992 年的博士论文**（首次系统论证了重构操作的安全性），Brant 和 Roberts 的 **Refactoring Browser** 则把常用重构做成了菜单命令。1999 年第 1 版出版后，"refactoring"进入主流词汇表。
* **自动化重构（Automated Refactorings）**：改名、提炼函数、内联等手法语义明确，最适合由 IDE 全自动完成（IntelliJ、Eclipse 早已内置），又快又稳——**工具能做的交给工具**，人专注判断"改什么、往哪改"；跨模块搬移、拆分阶段这类工具难以覆盖的手法，仍靠小步手工 + 测试推进。

## 测试：重构的安全网（第 4 章）

* **自测试代码（self-testing code）**：一套跑起来就能自动发现错误的测试（术语来自 Kent Beck）。它是重构的前提——没有测试，每次重构都是赌博；有测试，小步才有意义（每步跑一次）。
* **红—绿—重构（red–green–refactor）**：TDD 的循环：先写一个失败的测试（红）→ 写最少的代码让它通过（绿）→ 在测试保护下重构消坏味道。测试与重构互为前后件。
* 实践要点（书中以账单程序为例用 mocha/chai 写测试）：
  * 一个测试只盯一个失败点——报告失败时能立刻知道哪里坏了；
  * 观察行为与验证行为分开（把期望值硬编码进断言，而不是把计算结果自证一遍）；
  * 探测边界（boundaries）：空列表、零观众、未知剧种等退路径往往藏 bug；
  * bug 修复前先写一个能复现它的失败测试；
  * 测试代码同样是代码，也要保持清晰、避免过度耦合实现细节（测行为而非实现）。
* 单元测试为主、少量集成测试兜外围即可——测试数量的标准是"**能自信地重构**"，不多不少。

## 与 GoF 设计模式的关系

* **模式是重构的目的地之一**：不少手法的终点正是一个模式——Replace Function with Command → **Command**；Introduce Special Case → **Null Object**；Replace Subclass with Delegate → **Strategy/State**；Change Value to Reference（注册表共享实例）→ **Flyweight** 的共享思路；Replace Constructor with Factory Function → **Factory Method**。
* GoF 的两大原则之一 *"Favor object composition over class inheritance"*（优先组合而非继承）在第 12 章的两个"以委托取代…"手法中得到最直接的落地：**继承轴只有一根，委托可以有很多根**。
* 反过来，GoF 模式笔记回答"该到达什么结构"，重构回答"怎么安全地走过去"。
* 参见 [../GoF/00-导读.md](../GoF/00-导读.md)。
