# 代码的坏味道（Bad Smells in Code，第 3 章）

> "If it stinks, change it."（有味道，就换掉它。）——奶奶的家训，也是 Kent Beck 借奶奶之口给这一章的开场。
>
> 判断"何时代码需要重构"无法精确量化，Fowler 用 **smells（坏味道）** 这个词承认这种模糊性：它不是可度量的规则，而是经验性的症状。重要的不是背清单，而是**训练出对味道的敏感**。
>
> 下面 24 个坏味道按原书顺序整理，每条给出：症状、为什么是问题、常用手法（指向本目录 02–08 的条目）。注意：**有味道不等于必须重构**——是否动手取决于成本、风险与代码的剩余寿命；有些味道（如注释、可变数据）甚至要权衡后再处理。

## Mysterious Name（神秘命名）

改名是重构里频率最高的动作。名字与所做之事不符（或干脆叫 `data`、`handle`、`temp2`），读者就必须钻进实现才能理解意图——**名字就是压缩的文档**。

→ Change Function Declaration（改函数名）、Rename Variable、Rename Field。

## Duplicated Code（重复代码）

> 一旦你有重复代码，就意味着：改一处逻辑时要记得同步改另外几处，漏改即 bug。

* 同类中重复的代码块 → **Extract Function**，双方调用之；
* 兄弟子类间重复 → **Pull Up Method** 提到超类（字段重复则 Pull Up Field）；
* 两个"相似而不相同"的函数 → 提炼出相同部分后 **Parameterize Function**；或以 **Substitute Algorithm** 换掉更糟的那份；
* 重复属于根本不相关的两个模块 → 提炼函数/类后放进共享的第三方模块，或 **Extract Class** 圈出公共部分。

## Long Function（长函数）

历史最悠久、最经典的坏味道。**程序越长越难理解**；但克服它的武器不是缩短，而是**更好的命名与提炼**：一堆短小、命名良好的函数构成的过程，读起来就像注释过的大纲。

* 短函数的真正代价是**好名字**——先把函数起名的功夫练出来；
* 经验法则：**感到需要写注释的地方，多半该提炼函数**，让函数名替代注释（几个以时间/数字划分的"段落"各提炼一个）；
* 前置障碍常是临时变量与参数 → **Replace Temp with Query** 清路，再 **Extract Function**；
* 参数太多不好提炼 → **Introduce Parameter Object**、**Preserve Whole Object** 收拢；
* 条件与循环本身占行数 → **Decompose Conditional**（条件表达式提炼）、以 **Replace Conditional with Polymorphism** 消除类型分支、以 **Guard Clauses** 砍嵌套。

## Long Parameter List（长参数列表）

参数列表越长，越难理解、越容易传错顺序。缓解路径：

* 参数能由对象自己算出 → **Replace Parameter with Query**；
* 调用方本就持有这些数据所在的完整对象 → **Preserve Whole Object**（传对象而非散字段）；
* 总是结伴出现的几个参数 → **Introduce Parameter Object**（数据泥团成对象）；
* 布尔开关参数 → **Remove Flag Argument**（拆成显式函数）；
* 多个函数共享同一批参数/数据 → **Combine Functions into Class**（变成共享字段的类）。

## Global Data（全局数据）

> 这是个特别恶劣的坏味道（classic damnable smell）——代码在任何角落都能改它，而你无法知道谁改的。

可变的全局数据把"谁在什么时候改了它"变成全程序范围的悬案。重灾区：可修改的公共字段、模块级可变状态、Singleton 里的可变字段。

→ **Encapsulate Variable**：把直接访问收窄到 getter/setter 之后，至少能设断点、加校验、控权限；只读的全局数据风险小得多——尽量把全局做成**不可变**。

## Mutable Data（可变数据）

可变状态是 bug 温床：一处修改、处处受影响，且时序上难以复现。对它的攻击面：

* 局部化可见性并收窄写点 → **Encapsulate Variable**；
* 一个变量承担两种用途 → **Split Variable**；
* 变量的值可以由源数据算出 → **Replace Derived Variable with Query**（可变"缓存"变只读计算）；
* 计算与渲染/副作用混在一处互相污染 → **Split Phase**；
* 值的副本满天飞、别名同步负担重 → **Change Reference to Value**（改成不可变值对象）。

## Divergent Change（发散式变化）

> 一个模块因为**不同的原因**、在**不同的方向**上被反复修改。

新加一个"财务规则"要改三个方法，新接一个"数据库"又要改另外五个方法——这个类至少身兼两职。内聚的反面。数据库连接、外部接口这类"另一个变化轴"应被隔离。

→ **Split Phase**（按阶段拆）、**Extract Class**（按职责拆）。与霰弹式修改互为镜像，看改动是"聚在一点但原因发散"还是"一点原因散落多处"。

## Shotgun Surgery（霰弹式修改）

> 每做一个改动，都要在许多不同的地方做许多小修改——改对了没有成就感，漏一处就是 bug。

与发散式变化相反：问题在于职责**放错了地方**，散在各处。

→ **Move Function / Move Field** 把总被一起修改的东西搬进同一个模块；四处散落的小函数/小类合并 → **Inline Class / Inline Function**。判断搬家方向的依据：看这段代码使用谁的数据、被谁调用（依恋情结）。

## Feature Envy（依恋情结）

> 函数对别的类比对它的家更感兴趣——反复读写别的对象的数据。

典型如某个函数一半篇幅在取 `other.getXxx()` 做计算。数据与操作该数据的行为应住在一起。

→ 先 **Extract Function** 圈出"羡慕"的部分，再 **Move Function** 搬过去。注意例外：**策略模式里策略对象天生羡慕上下文数据**，这是设计的本意，不是味道（GoF Strategy 同理，见 [../GoF/03-Behavioral-Patterns.md](../GoF/03-Behavioral-Patterns.md)）。

## Data Clumps（数据泥团）

同样的三四个数据项总是结伴出现：函数签名里、参数列表里、字段里。绑在一起出现的数据暗示一个缺失的概念。

→ **Introduce Parameter Object**（参数成对象）、**Preserve Whole Object**（传已有的对象）、**Extract Class**（字段成对象）。泥团一旦成类，行为自然会长出来（如日期范围就能校验 start ≤ end）。

## Primitive Obsession（基本类型偏执）

金额用 `double`、电话号用 `String`、开关状态用 `int`、范围用两个变量……基本类型无法携带约束与行为，语义只活在程序员的脑子里。

→ **Replace Primitive with Object**（语义类型化）；泥团参数成对象；类型码驱动的分支 → **Replace Type Code with Subclasses** 后以 **Replace Conditional with Polymorphism** 收编；字符串拼接的复合数据 → **Encapsulate Record** 换成类。

## Repeated Switches（重复的 switch）

> 重复的 switch 的本质问题在于：每当你想增加或修改一个分支，必须找到**所有**相似的 switch 并同步修改——而且它们往往散落在不同地方。

同样的"按类型分发"逻辑（switch/if-else 链）出现多次才是味道；孤身一处的 switch 无妨。

→ **Replace Conditional with Polymorphism**；无法引入子类时，至少 **Extract Function** 消除重复的分支体，把 switch 集中到一处。

## Loops（循环语句）

循环本身无罪，但 **for/while 的机械细节（下标、累加器）常常淹没"在过滤什么、在汇总什么"的意图**。

→ **Replace Loop with Pipeline**：filter/map/reduce 组成的集合管道把这些意图直接写出来（Java 的 Stream、JS 的数组方法同源）。

## Lazy Element（冗赘的元素）

只有一个字段、或函数体只有一行的结构——维护它的抽象成本超过了它带来的表达力。可能是当初过度设计的残留。

→ **Inline Function / Inline Class**（把身体放回调用处/调用方）。

## Speculative Generality（夸夸其谈通用性）

> "呃，我想将来总有一天会需要这个参数/钩子/抽象层"——为了想象中的未来，当前代码平白多了许多无人使用的参数、只被一处调用的"通用"框架。

常来自过度设计，也常是"看，我多聪明"的炫技。维护者每次都要绕着这些死设施理解真实逻辑。

→ 无人调用的参数/类/模块 → **Remove Dead Code**；无谓的间接层 → **Inline Function / Inline Class**；名不副实的抽象 → 改成诚实的名字（改名一族手法）。

## Temporary Field（令人迷惑的暂时字段）

> 对象的字段应该（概念上）一直在那儿；可有时你会看到，某几个字段只在特定状态下才有值，其余时刻是 null 或占位——代码可读性大打折扣，读者不明白为什么它们"看起来没用"。

典型于"算法用多个临时变量分步传递中间结果"的长函数。

→ **Extract Class** 把这几个字段与操作它们的代码圈成一个独立对象；空值特判满天飞时 → **Introduce Special Case**。

## Message Chains（过长的消息链）

> 客户端 `a.getB().getC().getD().doSomething()`——一长串取值再末端调用。

链条意味着客户端掌握了整条导航路径的**结构知识**：中间任何一环变化，链条就断（火车失事，train wreck）。

→ **Hide Delegate**：在链头（或中段）加一个委托方法 `a.doSomething()`。不必处处都藏——只藏**真正被依赖**的那条路径；藏过头就成了下一个味道（Middle Man）。

## Middle Man（中间人）

> 封装的本意是隐藏委托；但藏得太多，类就退化成一堆"转发器"——一半的方法只是把调用转手给别的对象。

→ **Remove Middle Man**：把委托对象直接交给调用方；若几乎全部方法都在转发，说明这个类本身多余 → **Inline Class**。委托与中间人之间的平衡随时可回拨——**Hide Delegate 与 Remove Middle Man 是一对可反复拉锯的拨盘**。

## Insider Trading（狎昵关系）

> 软件中的模块如同事：可以交谈，但**不应互相窥探对方的私室**。

两个模块绕过公共接口私通对方内部（直接摸对方的字段/私有结构），或"子类对超类内部知道得太多"。这种特殊耦合一旦扩散，任何一方的改动都会波及"知情者们"。

→ 双方共同的亲密代码 → **Move Function / Move Field** 挪到第三者，或 **Extract Class** 圈出去；继承造成的狎昵 → **Replace Subclass with Delegate**；确需密切协作时，把关系放进明面上的接口（"最不坏"的选择）。

## Large Class（过大的类）

一个类干了太多事：字段成堆（每个字段都是一份"它知道的事"）、方法成群。读者抓不住它的核心抽象。

→ **Extract Class**（先圈出彼此相关的字段+方法）、**Extract Superclass**（有可共享部分时）、**Replace Type Code with Subclasses**（类型码暗示的多个职责拆给子类）；GUI 类这类"天生巨大"的 → **Split Phase** + **Extract Class** 组合拳。

## Alternative Classes with Different Interfaces（异曲同工的类）

两个类做着同一件事（如两种"邮箱服务"），方法名却各起各的——使用方无法互换，重复逻辑各自为政。

→ 用 **Change Function Declaration / Move Function** 把签名对齐成同一套协议；确有公共部分 → **Extract Superclass**。

## Data Class（纯数据类）

只有字段和 getter/setter、没有行为的数据袋。它们是"被所有人摆布的傀儡"：与之相关的行为散落在各处调用点。

→ **Encapsulate Record**（先变成有封装的类）、**Remove Setting Method**（不该变的字段去掉 setter）、用 **Move Function** 把行为搬进类里（先 **Extract Function** 把散落的行为圈出来）。例外：作为中间层传递、行为确在别处的 DTO（如渲染数据），保持无行为反而是对的。

## Refused Bequest（被拒绝的馈赠）

> 子类继承了父类的一堆方法与数据，却只用其中一部分——继承来的遗产成了负担。注释"这只是复用，不是真 is-a"就是自首。

→ 真是"为复用而继承" → **Replace Superclass with Delegate**（改委托/组合）；是"层次放错了层" → **Push Down Method / Push Down Field** 把不需要的遗产下放给真正需要的子类，或 **Extract Superclass** 再造中间层；行为随状态切换 → **Replace Subclass with Delegate**。这与 GoF "优先组合而非继承"的告诫同源。

## Comments（注释）

> 注释不是坏味道——但它们常被当作**除臭剂**使用：写注释的冲动往往说明代码自己没把话说清楚。

一段代码需要长注释解释"它在干什么"，通常意味着应该 **Extract Function** + 起个好名字；神秘的命名 → 改名而不是补注释；含糊的条件 → 引入解释性变量/函数。当这些都做完，剩下的注释（解释"**为什么**这么做"的背景、约束、坑）才是好注释——它们值得写，且永不过时。

---

## 小结：味道之间的张力

好几个味道互为反题，重构时需要**拨盘式**权衡而非单边执行：

* Hide Delegate ↔ Remove Middle Man（封装 vs 转发噪音）
* Extract Class ↔ Inline Class（拆分 vs 归并）
* Change Reference to Value ↔ Change Value to Reference（复制 vs 共享）
* Long Function 的"切"与 Lazy Element 的"合"

Fowler 的态度始终是：**味道是线索，不是法律**。闻到味道 → 判断是否值得、何时动手 → 用小步手法消除它 → 让测试证明你没弄坏东西。
