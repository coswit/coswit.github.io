# 封装（Encapsulation，第 7 章）

封装是把"数据藏到函数后面"的一组手法：记录、集合、基本类型各有各的封装方式，外加委托关系的隐藏与撤销、算法的整体替换。核心目标只有一个——**让改动数据结构时只需要改一处**。

> 示例用 Java 改写（原书为 JavaScript）。

本章手法：

| 手法 | 一句话 |
| --- | --- |
| Encapsulate Record 封装记录 | 裸记录/Map 变成有类包装的结构 |
| Encapsulate Collection 封装集合 | getter 不再暴露可变集合，增删走成员方法 |
| Replace Primitive with Object 以对象取代基本类型 | 带语义的基本类型升级成类 |
| Replace Temp with Query 以查询取代临时变量 | 局部临时变量变成可复用的查询函数 |
| Extract Class 提炼类 | 一个类拆成两个 |
| Inline Class 内联类 | 两个类合成一个（互逆） |
| Hide Delegate 隐藏委托关系 | 在服务对象上加转发方法，斩断消息链 |
| Remove Middle Man 移除中间人 | 转发太多时反向撤销（互逆） |
| Substitute Algorithm 替换算法 | 整体换掉一个更清晰的实现 |

## Encapsulate Record（封装记录）

> 近似第 1 版的 Replace Record with Data Class（以数据类取代记录）

**意图**：让调用方不再直接操作记录结构（JSON、Map、struct），改为通过一个类访问。

### 动机

* 记录型结构（Map/JSON/关联数组）只有"形状约定"、没有行为与校验：字段拼错要到运行时才炸，调用点之间靠默契共享结构知识，改一个字段名要满世界搜索字符串键；
* 封装成类后：结构知识集中一处；可以区分"可变的字段"（收窄写点）与"派生的字段"（变成计算）；
* 只读的、在模块内部小范围使用的记录可以直接用；**会被共享、会被修改**的记录才值得封装（与坏味道 Global Data / Mutable Data 对应）。

### 做法

1. 创建一个类，持有该记录；先用构造函数接受裸记录；
2. 逐个把对记录字段的读写改为调用类上的方法（读 → getter，写 → setter/专门方法）；
3. 每个字段迁移完即测试；全部迁完后，类对记录内部结构的依赖收进私有；
4. 若字段来自外部数据源（JSON 反序列化），可在边界处一次性转换成类（Combine Functions into Transform 常配合使用）。

### 示例

```java
// before：裸 Map 当组织机构用，形状知识散落在所有调用点
Map<String, String> organization = new HashMap<>();
organization.put("name", "Acme Gooseberries");
organization.put("country", "GB");
String name = organization.get("nmae");   // 拼错编译器不管，运行期才翻车

// after：结构与命名收进类，字段可见性受控
class Organization {
    private String name;
    private String country;

    Organization(String name, String country) { this.name = name; this.country = country; }

    String name()    { return name; }
    String country() { return country; }
    void setCountry(String country) { this.country = country; }
}

Organization acme = new Organization("Acme Gooseberries", "GB");
acme.name();   // 拼错即编译错
```

## Encapsulate Collection（封装集合）

**意图**：集合字段不通过 getter 整体暴露，增删元素改走属主的成员方法。

### 动机

* 普通字段的 getter/setter 封装了"谁在改"，但**集合的 getter 一旦原样返回内部集合，封装就漏了**——调用方拿到引用后 `add/remove` 无人知晓，属主完全失控；
> 如果说 setter 是封装的字段级的关卡，集合需要的是**元素级**的关卡。
* 正确形态：提供 `addX`/`removeX`；getter 返回**不可变视图或副本**——想改只能走关卡，属主的约束（如不允许重复课程）得以执行；
* 随之而来的收益：`setCourses(整个列表)` 这种"整体倾倒"式接口被 `addCourse` 逐个添加取代，语义清晰。

### 做法

1. 在属主上添加 `addX`/`removeX` 方法，把已有的增删调用点改过来；
2. 让 getter 返回不可变包装（Java：`Collections.unmodifiableList`；或返回副本）；
3. 若存在"整体设置"的 setter：改为 `initializeCourses` 之类的初始化方法（内部逐个 add），或直接删除；
4. 测试。

### 示例

```java
// before：拿到 getter 就能绕过 Person 乱改课表
class Person {
    private List<Course> courses = new ArrayList<>();
    List<Course> getCourses() { return courses; }
    void setCourses(List<Course> list) { courses.addAll(list); }
}

// 调用方
person.getCourses().add(new Course("Snowboarding", false));   // 无人知晓的修改

// after：增删走关卡，读取拿到的是只读视图
class Person {
    private List<Course> courses = new ArrayList<>();

    void addCourse(Course course)    { courses.add(course); }
    void removeCourse(Course course) { courses.remove(course); }
    List<Course> getCourses()        { return Collections.unmodifiableList(courses); }
    long numberOfAdvancedCourses()   { return courses.stream().filter(Course::isAdvanced).count(); }
    long numberOfBasicCourses()      { return courses.size() - numberOfAdvancedCourses(); }
}

// 调用方：想改只能走关卡
person.addCourse(new Course("Snowboarding", false));
person.getCourses().add(new Course(...));   // 运行时 UnsupportedOperationException
```

> 注：返回副本 vs 不可变视图——副本允许调用方继续在本地改（不影响属主），视图完全禁止改动；原书（JavaScript）采用返回副本的写法，Java 生态惯用不可变视图；无论哪种，getter 名字保持不变。

## Replace Primitive with Object（以对象取代基本类型）

> 曾用名：Replace Type Code with Class（第 1 版）

**意图**：把承载特定语义的基本类型（String/int/double…）包装成有行为的小类。

### 动机

* 开发早期用基本类型图省事，后来语义越来越重：订单的"优先级"是个字符串，比较规则散落各处；金额是 double，币种与精度无人负责——这就是坏味道 Primitive Obsession；
* 一旦有了类，**行为就有了家**：校验（"high/low"之外的取值直接拒绝）、比较（`higherThan`）、格式化（`toString`）、单位（欧元≠美元）都长在类型上；
* 这类小类（value object）通常随后做成不可变的（Change Reference to Value）。

### 做法

1. 给这个"概念"建一个类，内部先持有原基本类型；
2. 用 **Change Function Declaration（迁移版）** 把相关字段/参数/返回值逐个换成新类；
3. 把散落在各处的行为（比较、校验、判断）**Move Function** 进新类；
4. 测试。

### 示例

```java
// before：优先级是裸字符串，比较规则在调用点各写各的
class Order {
    String priority;
    boolean isHighPriority() {
        return "high".equals(priority) || "rush".equals(priority);   // 规则会繁殖
    }
}

// after：优先级成类，规则有了唯一的家
class Priority {
    private final String value;
    private static final List<String> ORDER = List.of("low", "normal", "high", "rush");

    Priority(String value) { this.value = value; }
    boolean higherThan(Priority other) { return ORDER.indexOf(this.value) > ORDER.indexOf(other.value); }
    boolean atLeastHigh()  { return higherThan(new Priority("high")); }
    @Override public String toString() { return value; }
}

class Order {
    Priority priority;
    boolean isHighPriority() { return priority.atLeastHigh(); }
}
```

## Replace Temp with Query（以查询取代临时变量）

**意图**：把"只赋值一次、用来暂存表达式结果"的临时变量，换成随时可调用的查询函数。

### 动机

* 临时变量只在本函数可见——它是 Extract Function 的路障：想提炼的代码用了 temp，就得层层传参；
* 变成查询（函数）后：可被任意函数复用、自带名字、还能被覆写（子类换计算方式）；
* 常见顺序：先 Replace Temp with Query 清障，再 Extract Function 拆函数（第 1 章走读正是这么做的）；
* 性能担忧照例多虑：这类查询通常很便宜；真成热点再局部优化。

### 做法

1. 确认变量只赋值**一次**（赋值多次先 Split Variable），且赋值右侧是**无副作用**的表达式；
2. 用 **Extract Function** 把右侧表达式提炼成函数，以变量的意图命名（`basePrice` 而非 `getBasePrice`——它是个概念不是 getter 仪式）；
3. 用函数调用替换变量的所有引用点；
4. 逐变量进行，每步测试。

### 示例

```java
// before：basePrice、discountFactor 两个临时变量锁在函数体内
double getPrice() {
    int basePrice = quantity * itemPrice;
    double discountFactor;
    if (basePrice > 1000) discountFactor = 0.95;
    else discountFactor = 0.98;
    return basePrice * discountFactor;
}

// after：概念变成查询，主体一眼读懂；下一步 Extract Function 零阻力
double getPrice() { return basePrice() * discountFactor(); }

int basePrice()          { return quantity * itemPrice; }
double discountFactor()  { return basePrice() > 1000 ? 0.95 : 0.98; }
```

## Extract Class（提炼类）

**意图**：把一个类中"彼此相关的一组字段与方法"拆出去，形成新类；原类留一个引用。

### 动机

* 类长大了（Large Class）：一部分字段与方法跟另一部分明显不是一回事——比如"人"与"人的办公电话"；
> 拆分类的判断依据是**内聚**：如果某些字段总是一起被某些方法使用、而与类的其余部分几乎无关，它们就該独立。
* 拆出的部分可以独立演化、独立测试；新的抽象（TelephoneNumber 可复用于 Person、Contact、Company）随之出现；
* 拆分粒度宁小勿大——类之间用组合再接起来很容易（GoF：优先组合），一坨大类拆起来只会越来越贵。

### 做法

1. 决定拆分边界，新建类，以拆出的**概念**命名；
2. 把新类创建为原类的字段（先让两者并存）；
3. 用 **Move Field** 把字段逐个搬过去，**Move Method** 把方法搬过去（搬方法前先用 Extract Function 把"混在方法里的两摊职责"切开）；
4. 决定对调用方是否暴露新类：不暴露 → 原类加委托方法；暴露 → 原类公开新类访问器（并删掉委托）；
5. 每搬一个成员就测试。

### 示例

```java
// before："人"与"办公电话"混在一处
class Person {
    String name;
    String officeAreaCode;
    String officeNumber;

    String telephoneNumber() { return "(" + officeAreaCode + ") " + officeNumber; }
}

// after：电话号码独立成类（Person 保留委托，调用方无感）
class Person {
    String name;
    private final TelephoneNumber officeTelephone = new TelephoneNumber();

    String telephoneNumber()  { return officeTelephone.toString(); }
    String officeAreaCode()   { return officeTelephone.areaCode(); }
    void setOfficeAreaCode(String code) { officeTelephone.setAreaCode(code); }
}

class TelephoneNumber {
    String areaCode;
    String number;
    String toString() { return "(" + areaCode + ") " + number; }
}
```

## Inline Class（内联类）

**意图**：与 Extract Class 相反——把不再有独立价值的类并回它的使用者。

### 动机

* 随着功能搬移，某个类的职责被搬空了（Lazy Element），只剩转发；
* 或在重构中途（如 Inline Class + 重新 Extract Class）需要先拆散原有边界再重组。

### 做法

1. 在目标类（吸收者）上创建新类的字段；
2. 把新类的方法/字段逐个搬进目标类（Move Method/Field），调用点改指目标类；
3. 删除空类，测试。

### 示例

```java
// before：TelephoneNumber 已经名存实亡
class TelephoneNumber { String areaCode; String number; ... }

// after：并回 Person
class Person {
    String name;
    String officeAreaCode;   // 回到字段级，等下一次真正的边界出现再拆
    String officeNumber;
}
```

## Hide Delegate（隐藏委托关系）

**意图**：客户端通过 `a.getB().getC()` 使用中间对象时，在 a 上加一个委托方法 `a.getC()`。

### 动机

* 消息链（Message Chains / "火车失事"）意味着客户端掌握了**对象的内部布局**：Person 里有个 Department、Department 里有个 Manager——哪天 Department 没了，所有调用点一起塌；
> 封装的本质不是"藏字段"，而是**藏模块间的内部结构**——调用方只该知道自己要什么，不该知道东西放在几楼。
* 委托方法立起一道墙：内部怎么组织是 Person 的私事。

### 做法

1. 在服务对象（链头）上创建委托方法，转调链尾目标；
2. 把调用点改为使用委托方法；
3. 调用点迁完后，若中间对象再无他用，可用 **Change Function Declaration** 收掉对它的公开访问器。

### 示例

```java
// before：客户端知道"人在部门里、部门有经理"这整条路径
Person manager = person.getDepartment().getManager();

// after：Person 挡在中间
class Person {
    private Department department;
    Person getManager() { return department.getManager(); }   // 委托
}
Person manager = person.getManager();
```

## Remove Middle Man（移除中间人）

**意图**：与 Hide Delegate 相反——委托方法泛滥时，让客户端直接拿委托对象。

### 动机

* 封装做过了头：类的一半方法都是 `return delegate.xxx()`，这些**中间人**除了增加跳转什么也不干（坏味道 Middle Man）；
* 纯转发方法累积到拖累阅读时，就该考虑移除中间人；委托多了藏、藏多了又暴露——这是随需求摆动的拨盘，不是一次性的决定；
* 若类几乎全部方法都在转发，用 **Inline Class** 连类一起撤掉。

### 做法

1. 在服务对象上公开委托对象的访问器（`getDepartment()`）；
2. 把纯转发的委托方法逐个内联进调用点（客户端直接链式调用），删除委托方法；
3. 测试。

### 示例

```java
// before：Person 变成了 Department 的传声筒
class Person {
    private Department department;
    Person getManager()       { return department.getManager(); }
    String getDepartmentName(){ return department.getName(); }
}

// after：暴露部门，删掉转发（调用方自取所需）
class Person {
    private Department department;
    Department getDepartment() { return department; }
}

Person manager = person.getDepartment().getManager();
```

## Substitute Algorithm（替换算法）

**意图**：用实现更清晰的算法整体替换原有实现。

### 动机

* 有时问题换一个解法，代码量级地缩减：嵌套循环换成集合运算、手写查找换成标准库；
* 它是"消灭重复"的终极形式：**把做同一件事的多个糟糕实现，统一替换为一个清晰实现**（手法上先 Extract Function 立起函数边界，再整体换芯）。

### 做法

1. 把现有逻辑整理成一个边界清晰的函数（不清晰先 Extract Function）；
2. 用新算法重写函数体（可以借用新库/新语言特性）；
3. 用测试**对照**新旧行为一致——这是所有手法里对测试依赖最重的一个，测试没盖住的行为差异会悄悄溜走；
4. 若旧算法仍在别处使用，让它们调用同一个新实现。

### 示例

```java
// before：逐个名字硬比对
List<String> foundGuys(List<String> people) {
    List<String> found = new ArrayList<>();
    for (String p : people) {
        if (p.equals("Don") || p.equals("John") || p.equals("Kent")) {
            found.add(p);
        }
    }
    return found;
}

// after：意图（按名单过滤）直接写成声明
private static final Set<String> GENTS = Set.of("Don", "John", "Kent");

List<String> foundGuys(List<String> people) {
    return people.stream().filter(GENTS::contains).collect(Collectors.toList());
}
```

## 小结：封装的四个层次

本章在四个粒度上立关卡：

1. **字段/变量**（Encapsulate Variable，见 [02-第一组重构.md](02-第一组重构.md)）；
2. **记录与集合**（Encapsulate Record / Encapsulate Collection）——结构级；
3. **语义类型**（Replace Primitive with Object）——概念级；
4. **对象间结构**（Hide Delegate ↔ Remove Middle Man）——模块级。

Extract Class ↔ Inline Class 则是这些关卡在"类"粒度上的重新划分。下一章处理另一个维度的问题：**放错位置的东西怎么搬** → [04-搬移特性.md](04-搬移特性.md)。
