# 搬移特性（Moving Features，第 8 章）

重构的半数工作其实是**搬家**：函数、字段、语句搬到更合适的地方，让"数据与操作它的行为"住到一起。位置对了，很多坏味道（Feature Envy、Shotgun Surgery、Divergent Change）自然消解。

> 示例用 Java 改写（原书为 JavaScript）。

本章手法：

| 手法 | 一句话 |
| --- | --- |
| Move Function 搬移函数 | 函数搬到它真正关心的上下文 |
| Move Field 搬移字段 | 字段搬到主要使用它的类 |
| Move Statements into Function 将语句移入函数 | 调用方都在重复的前置语句，移进函数 |
| Move Statements to Callers 将语句移到调用者 | 函数的通用性变窄时，把语句还给调用方（互逆） |
| Replace Inline Code with Function Call 以函数调用取代内联代码 | 手写的内联逻辑换成现成函数 |
| Slide Statements 移动语句 | 相关语句聚拢，减少干扰 |
| Split Loop 拆分循环 | 一个循环干两件事 → 拆成两个 |
| Replace Loop with Pipeline 以管道取代循环 | 循环换成 filter/map/reduce |
| Remove Dead Code 移除死代码 | 删掉没人用的代码 |

## Move Function（搬移函数）

> 曾用名：Move Method（第 1 版）

**意图**：把函数从现在的模块搬到另一个更合适的模块，原处留委托或彻底删除。

### 动机

* 搬家的判断依据是**依恋情结（Feature Envy）**：函数引用哪个上下文更多、被谁调用更多，它就该住得离谁更近；
* 搬对位置的收益：数据与行为同住、函数能访问到目标上下文的内部结构（不再需要一堆 getter）、调用关系变短；
* 它是消除 Shotgun Surgery / Divergent Change 的主力：把总被一起修改的东西聚到一起，先搬字段（Move Field）再搬函数是常见顺序。

### 做法

1. 审查函数体，确认它依赖的上下文（字段、同模块函数）——依赖过散时先整理（Extract Function 圈出要搬的部分）；
2. 在目标上下文创建新函数（函数引用不到的宿主数据，转为参数或查询）；
3. 逐个把调用点改为新位置；调用点迁移期间，旧函数转调新函数保持兼容；
4. 全部迁完：删除旧函数，或保留一个薄委托（对外接口需要稳定时）。
5. 每迁一批调用点就测试。

### 示例

```java
// before：discountRateFor 挂在 Customer 上，眼里却只有 Contract
class Customer {
    private Contract contract;
    double discountRateFor(Contract c) {
        return c.isPreferred() ? 0.9 : 0.95;
    }
    double applyDiscount(double amount) {
        return discountRateFor(contract) * amount;
    }
}

// after：函数与它唯一关心的数据住到一起
class Contract {
    private boolean preferred;
    double discountRate() { return preferred ? 0.9 : 0.95; }
    boolean isPreferred() { return preferred; }
}

class Customer {
    private Contract contract;
    double applyDiscount(double amount) {
        return contract.discountRate() * amount;   // 调用点改指新家
    }
}
```

## Move Field（搬移字段）

**意图**：字段搬到更频繁使用它的类里。

### 动机

* "数据放错了地方"最直观的信号：一个字段大半的读写都发生在另一个类里；
* 字段搬对，函数常常**跟着归位**（方法总是围着数据转）——所以 Move Field 常是 Move Function 的前奏；
* 典型场景：Extract Class 拆类时逐字段搬家；发现"折扣率其实属于合同而非客户"这类概念错位时。

### 做法

1. 封装字段（Encapsulate Variable）：确保所有读写都经过访问函数；
2. 在目标类创建字段与访问函数；源类的访问函数转调目标（形成委托）；
3. 调用点逐批改指目标类；全部迁完后删除源类上的委托；
4. 测试。

### 示例

```java
// before：discountRate 住在 Customer，但读写都发生在 Contract 的逻辑里
class Customer {
    private double discountRate;          // ← 概念上属于合同
    double getDiscountRate() { return discountRate; }
    void setDiscountRate(double r) { discountRate = r; }
    Contract contract;
}

// after：字段归位
class Contract {
    private double discountRate;
    double getDiscountRate() { return discountRate; }
    void setDiscountRate(double r) { discountRate = r; }
}

class Customer {
    Contract contract;
    double applyDiscount(double amount) {
        return contract.getDiscountRate() * amount;
    }
}
```

## Move Statements into Function（将语句移入函数）

**意图**：调用某函数前总要执行的语句，把它移进函数体内。

### 动机

* 多个调用点每次都重复同一段"前奏/尾声"——重复且容易漏；
* 让函数把完整的事做完（连同前奏），调用方一行到位；
* 反向信号：如果这段语句只被**部分**调用方需要，那它不该进函数——那是 Move Statements to Callers 的场景。

### 做法

1. 若各调用点的语句长得不一样，先用 **Substitute Algorithm / Extract Function** 统一它们；
2. 把语句移进函数（放在函数体最前面或最后面，视它在前奏还是尾声）；
3. 删除调用点的这条语句；
4. 每迁一个调用点就测试；若语句影响函数签名（如引用了调用方变量），同步 **Change Function Declaration**。

### 示例

```java
// before：两个调用方都在 emitPhotoData 前打印 title —— 迟早有人漏打
void renderPerson(Person person) {
    out.println("<p>" + person.name() + "</p>");
    out.println("<p>title: " + person.photo().title() + "</p>");   // 前奏重复
    emitPhotoData(person.photo());
}
void listRecentPhotos(List<Photo> photos) {
    for (Photo photo : photos) {
        out.println("<div>");
        out.println("<p>title: " + photo.title() + "</p>");        // 前奏重复
        emitPhotoData(photo);
        out.println("</div>");
    }
}
void emitPhotoData(Photo photo) {
    out.println("<p>date: " + photo.date() + "</p>");
    out.println("<p>location: " + photo.location() + "</p>");
}

// after：title 移入函数，调用方各减一行
void emitPhotoData(Photo photo) {
    out.println("<p>title: " + photo.title() + "</p>");
    out.println("<p>date: " + photo.date() + "</p>");
    out.println("<p>location: " + photo.location() + "</p>");
}
```

## Move Statements to Callers（将语句移到调用者）

**意图**：与 Move Statements into Function 相反——函数里某条语句不再对所有调用方通用时，把它还出去。

### 动机

* 函数当初承载的"共同点"随演化消失了：现在只有部分调用方需要其中的某条语句；
> 函数的意义在于抽象出调用方的**共性**；共性缩水时硬撑着不拆，函数内部就得靠参数/开关区分调用方——那更糟。
* 拆出去之后，每个调用方拼装自己需要的行为；之后常常各自触发新一轮提炼。

### 做法

1. 最容易移的是**边界处的语句**（函数开头/结尾），先挑它们；
2. 把语句复制到需要它的调用方（紧贴调用前后），从函数体中删除；
3. 若语句引用了函数内部的变量，需要先调整（把变量带出/提炼查询）；
4. 每迁一个调用点就测试。

### 示例

```java
// before：listRecentPhotos 不想输出 location，却被迫吃进 emitPhotoData
void emitPhotoData(Photo photo) {
    out.println("<p>title: " + photo.title() + "</p>");
    out.println("<p>date: " + photo.date() + "</p>");
    out.println("<p>location: " + photo.location() + "</p>");   // ← 部分调用方不需要
}

// after：location 还给需要的调用方；emitPhotoData 回到全体共识
void emitPhotoData(Photo photo) {
    out.println("<p>title: " + photo.title() + "</p>");
    out.println("<p>date: " + photo.date() + "</p>");
}
void renderPerson(Person person) {
    out.println("<p>" + person.name() + "</p>");
    emitPhotoData(person.photo());
    out.println("<p>location: " + person.photo().location() + "</p>");   // 自取所需
}
```

## Replace Inline Code with Function Call（以函数调用取代内联代码）

**意图**：手写在调用方的逻辑，换成调用一个（已有的或提炼出的）函数。

### 动机

* 内联代码重复了既有函数的逻辑——两份代码必然漂移；
* 即便没有现成函数，也值得先 Extract Function 立起函数、再在调用方替换：意图命名、逻辑复用、单独测试三得；
* 常见形态：手写循环其实是 `contains`/`sum`/`max`，手写字符串拼接其实是 `String.format`。

### 做法

1. 若目标函数不存在，先提炼它；
2. 确认内联代码与函数语义一致（含边界行为）；
3. 用函数调用替换内联代码，测试。

### 示例

```java
// before：手写"是否包含管理员"
boolean hasAdmin = false;
for (User u : users) {
    if (u.isAdmin()) { hasAdmin = true; break; }
}

// after：标准库直说意图
boolean hasAdmin = users.stream().anyMatch(User::isAdmin);
```

## Slide Statements（移动语句）

**意图**：让相关的代码彼此靠近——声明靠近使用处、同属一件事的语句聚拢。

### 动机

* "让有关联的代码在一起"是所有搬移类手法的微观基础：语句聚拢后才能看清它们是不是该一起 Extract Function / Move Function；
* 相邻但无关的代码互相干扰：读代码的人被迫在无关的变量与语句间跳来跳去；
* 经典场景：函数开头的变量声明离首次使用隔了半屏。

### 做法

1. 确定要移动的语句与目标位置；
2. 检查移动路径上的语句与它**没有数据/副作用纠缠**（不读写同一变量、不依赖执行顺序）；
3. 小步移动（一次挪一行/一小段），测试；有纠缠先梳理（如把纠缠的语句一起挪、或先提炼变量）。

### 示例

```java
// before：pricingPlan 的声明与使用隔着 charge 的初始化
double pricingPlan = getContract().pricingPlan();
double charge = 0;
int units = getReading().units();
if (pricingPlan == BASIC) charge = units * 0.5;
else charge = units * 0.8;

// after：声明紧贴使用，读起来成对
double charge = 0;
double pricingPlan = getContract().pricingPlan();
int units = getReading().units();
if (pricingPlan == BASIC) charge = units * 0.5;
else charge = units * 0.8;
```

## Split Loop（拆分循环）

**意图**：一个循环身兼数职时，拆成多个各司其职的循环。

### 动机

* 一段循环里同时"求和"又"找最小值"，读者要在脑内同时追踪两个任务；
> 有人说"两个循环会慢"。但循环本身的负担通常远小于循环体，为清晰付这点开销几乎总是划算；真有性能问题，也可以后续再合并——**先清晰，再优化**。
* 拆开的循环常常正好触发下一步重构：每个循环体 **Extract Function** 成意图明确的查询，甚至整个被 **Replace Loop with Pipeline** 取代。

### 做法

1. 复制这个循环（一次复制一个职责）；
2. 从复制品中删掉"不属于它的职责"的语句，从原循环中删掉"属于它"的语句；
3. 重命名循环内的变量，让两个循环各自表意；
4. 测试；随后按需对每个循环继续 Extract Function。

### 示例

```java
// before：一次遍历干两件事
double totalSalary = 0;
double youngest = employees.isEmpty() ? 0 : employees.get(0).age;
for (Employee e : employees) {
    totalSalary += e.salary;
    if (e.age < youngest) youngest = e.age;
}

// after：两个单职责循环（各自可再提炼/管道化）
double totalSalary = 0;
for (Employee e : employees) totalSalary += e.salary;

double youngest = employees.isEmpty() ? 0 : employees.get(0).age;
for (Employee e : employees) if (e.age < youngest) youngest = e.age;
```

## Replace Loop with Pipeline（以管道取代循环）

**意图**：用集合管道（filter/map/reduce…）取代显式循环，声明式地表达"筛选—变换—汇总"。

### 动机

* 循环暴露的是**过程**（下标怎么走、累加器怎么更新），管道表达的是**意图**（留下什么、变成什么、聚成什么）；
> 逻辑相同的情况下，管道让人一眼看出"集合在流经哪些变换"；循环则要求你在脑内模拟执行。
* Java Stream / JS 数组方法 / Kotlin 集合操作本质同源；这一手法在现代语言里几乎总能直接落地；
* 注意：不是所有循环都该管道化——带复杂跳出/副作用交织的循环硬转反而更难读；先 Split Loop 让循环职责单一，再管道化才顺手。

### 做法

1. 一个循环里干几件事的，先 **Split Loop**；
2. 逐段把循环体翻译成管道操作：过滤条件 → filter、元素变换 → map、聚合 → reduce/collect；
3. 删除旧循环，测试。

### 示例

```java
// before：解析 CSV、过滤 India、抽取字段、组装对象，四件事挤在一个循环里
List<Office> result = new ArrayList<>();
String[] lines = csv.split("\n");
for (int i = 1; i < lines.length; i++) {           // 0 行是表头
    String[] record = lines[i].split(",");
    if ("India".equals(record[1].trim())) {
        result.add(new Office(record[0].trim(), record[2].trim()));
    }
}

// after：每一跳都是一步变换
List<Office> result = Arrays.stream(csv.split("\n")).skip(1)
        .map(line -> line.split(","))
        .filter(fields -> "India".equals(fields[1].trim()))
        .map(fields -> new Office(fields[0].trim(), fields[2].trim()))
        .collect(Collectors.toList());
```

## Remove Dead Code（移除死代码）

**意图**：删除不再被使用的代码。

### 动机

* 死代码（无人调用的函数、永假的分支、被注释掉的旧实现）不是无害的静态资产，而是**误导读者的噪音**——它暗示"也许还有人在用"；
> 版本控制系统记得一切——注释掉代码"以备后用"是把 VCS 当摆设。删！要用再从历史里捡回来。
* 常见来源：需求取消后残留、特性开关的旧分支、重构中途被绕开的旧路径。

### 做法

1. 确认真死了：搜索全部引用（含反射/配置注入等"看不见"的引用要重点排查）；可用覆盖率/静态分析辅助；
2. 删除；若是被注释掉的代码块，连注释一起删；
3. 测试；过段时间没人喊疼，就说明删对了（若真有人用，编译/运行会立刻告诉你）。

## 小结

本章是"搬家三件套"：**字段 → 函数 → 语句**，从粗到细三个粒度调整代码的位置，让数据与行为、调用与实现彼此靠拢；再配上 Split Loop / Replace Loop with Pipeline 重塑循环内部的形态。搬完之后下一类问题是**数据本身怎么组织** → [05-组织数据.md](05-组织数据.md)。
