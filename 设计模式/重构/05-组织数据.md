# 组织数据（Organizing Data，第 9 章）

数据比代码活得更久：字段名被到处引用、派生值会过期、值与引用的选型决定别名 bug 的有无。本章 5 个手法都在回答一个问题——**怎么组织数据，让"正确性"由结构保证而不是靠程序员记性**。

> 示例用 Java 改写（原书为 JavaScript）。

## Split Variable（拆分变量）

> 曾用名：Split Temporary Variable（第 1 版）

**意图**：一个变量承担了多个职责（被赋值多次、每次表示不同的东西）时，拆成各司其职的多个变量。

### 动机

* 变量的"一个职责"= 只被赋值一次（loop/累加器是唯一惯例）。多次赋值看似省了个名字，实则让读者无法确定"此刻它是什么"；
* 一变量多用还会挡住后续手法：Replace Temp with Query、Encapsulate Variable 都要求单次赋值；
* 典型症状：`temp`、`result`、`acc` 在函数中途"改行"。

### 做法

1. 找出变量的第 N 次赋值（N ≥ 2），确认这次赋值不是累加/收集（那属于同一职责）；
2. 在该赋值点声明一个新变量（以这一职责命名），后续引用改为新变量；
3. 以此为界，把前一职责的变量也改成符合自身的名字；
4. 每拆一次测试。

### 示例

```java
// before：acc 在函数中途"改行"——前半段是主推加速度，后半段是双引擎合加速度
double distanceTravelled(Scenario scenario, double time) {
    double result;
    double acc = scenario.primaryForce / scenario.mass;
    double primaryTime = Math.min(time, scenario.delay);
    result = 0.5 * acc * primaryTime * primaryTime;

    double secondaryTime = time - scenario.delay;
    if (secondaryTime > 0) {
        double primaryVelocity = acc * scenario.delay;
        acc = (scenario.primaryForce + scenario.secondaryForce) / scenario.mass;   // ← 二次赋值
        result += primaryVelocity * secondaryTime
                + 0.5 * acc * secondaryTime * secondaryTime;
    }
    return result;
}

// after：两个名字各自单次赋值，物理含义直接写在代码里
double distanceTravelled(Scenario scenario, double time) {
    double result;
    double primaryAcceleration = scenario.primaryForce / scenario.mass;
    double primaryTime = Math.min(time, scenario.delay);
    result = 0.5 * primaryAcceleration * primaryTime * primaryTime;

    double secondaryTime = time - scenario.delay;
    if (secondaryTime > 0) {
        double primaryVelocity = primaryAcceleration * scenario.delay;
        double secondaryAcceleration =
                (scenario.primaryForce + scenario.secondaryForce) / scenario.mass;
        result += primaryVelocity * secondaryTime
                + 0.5 * secondaryAcceleration * secondaryTime * secondaryTime;
    }
    return result;
}
```

## Rename Field（字段改名）

**意图**：给数据字段起一个能表意的名字。

### 动机

* 数据字段的名字是**数据字典**：它出现在记录、序列化格式、API 里，名字错了会误导每一个读到的人；
* 名字与含义错位是数据层的"神秘命名"——尤其字段名说了"是什么"，实际存的是"另一个东西"（存"顾客数"却叫 `count`）；
* 字段被广泛共享（数据库、JSON、公共 API）时改名成本高，因此更要趁早改、走封装与迁移路线。

### 做法

1. 若字段已有封装（访问器/记录类）：先给访问器改名（Change Function Declaration），再改字段本身；
2. 若字段被直接访问：先 **Encapsulate Record / Encapsulate Variable** 立起关卡，再在关卡内改名；
3. 对外格式（DB 列名、JSON 键）与内部字段解耦：边界处做一次映射，内部用诚实的名字。

### 示例

```java
// before：name 太泛——文章的"标题"才是它真正的概念
class Article {
    String name;
    int views;
}

// after
class Article {
    String title;    // 字段名与领域概念一致
    int views;
}
```

## Replace Derived Variable with Query（以查询取代派生变量）

**意图**：把"由源数据算出来、又存起来"的派生值，换成用时现算的查询函数。

### 动机

* 可变的派生数据是**过期 bug** 的温床：源数据改了、副本忘了改，程序拿着旧值继续算——而且没人知道错在哪一层；
* 好的代码应该把**可变状态压到最少**：源数据是唯一事实（single source of truth），派生值随问随算；
* 原书特别提到：良好的函数式风格不是"消灭可变性"这么教条——把"多个可变变量"收敛成"少量源 + 派生查询"就是务实的落地；
* 例外：计算昂贵或高频调用的派生值可以留缓存，但要意识到这是性能权衡，且缓存值要跟着源一起更新（必要时再配套 Change Reference to Value 等隔离别名）。

### 做法

1. 识别出所有对派生变量的赋值点；
2. 创建一个查询函数，从**源数据**当场计算该值（可先 **Extract Function** 提炼现有计算）；
3. 把对派生变量的读取改为调用查询；赋值点与字段随之删除；
4. 测试。

### 示例

```java
// before：production 被"增量调整"维护着——每改一处都要记得同步它
class ProductionPlan {
    private double production = 0;
    private final List<Double> adjustments = new ArrayList<>();

    void applyAdjustment(double adjustment) {
        adjustments.add(adjustment);
        production += adjustment;                 // ← 同步两处，迟早漏
    }
    double getProduction() { return production; }
}

// after：adjustments 是唯一事实，production 随问随算
class ProductionPlan {
    private final List<Double> adjustments = new ArrayList<>();

    void applyAdjustment(double adjustment) { adjustments.add(adjustment); }
    double getProduction() {
        return adjustments.stream().mapToDouble(Double::doubleValue).sum();
    }
}
```

## Change Reference to Value（将引用对象改为值对象）

**意图**：把"到处共享同一实例"的引用语义，改成"每个副本独立、按内容相等"的值语义。

### 动机

* 引用对象的代价：别名无处不在，一处改、处处变，还要操心线程安全与缓存一致性；
* 若对象的内容**不该变**（货币、日期范围、地址、电话号码），值语义更省心：副本独立、天然线程安全、不用共享；
* 值对象（value object）的关键契约：**不可变 + equals/hashCode 按内容**；Java 的 `record`、`String`、`LocalDate` 都是值对象。

### 做法

1. 把类做成不可变：删除所有 setter（**Remove Setting Method**），字段全 final；
2. 实现 `equals`/`hashCode`（Java 可用 record 直接获得）；
3. 若创建成本高/数量大，可配工厂 + 缓存共享（此时其实成了 Change Value to Reference 的回摆——按需权衡）；
4. 检查原来依赖"改共享实例"的调用点：它们必须改为"替换整个对象"，测试。

### 示例

```java
// before：TelephoneNumber 是引用对象——两处拿到同一个实例，一处 set 全局遭殃
class TelephoneNumber {
    private String areaCode;
    private String number;
    void setAreaCode(String code) { this.areaCode = code; }   // 可变 → 共享即风险
}

// after：不可变 + 按内容相等（record 一步到位）
record TelephoneNumber(String areaCode, String number) {
    TelephoneNumber {
        Objects.requireNonNull(areaCode);
        Objects.requireNonNull(number);
    }
}

TelephoneNumber a = new TelephoneNumber("021", "555-1234");
TelephoneNumber b = new TelephoneNumber("021", "555-1234");
a.equals(b);   // true：值语义
```

## Change Value to Reference（将值对象改为引用对象）

**意图**：与 Change Reference to Value 相反——把"每个持有者一份副本"改成"同一逻辑实体全局只有一个实例、大家共享引用"。

### 动机

* 值对象的副本语义在"**逻辑实体**"上会出事：系统里 `Customer("Acme")` 有三份副本，给其中一份升级 VIP，另两处看到的还是普通客户——更新被副本吞了；
> 判断标准：两个副本应该"始终同步"吗？是 → 引用；各归各的、内容相同只是巧合 → 值。
* 引用语义需要**单一来源**：注册表/仓库（repository）负责"同 key 拿到同实例"；
* 这正是 GoF **Flyweight / Singleton 家族**的共享思路在业务对象上的应用（见 [../GoF/01-Creational-Patterns.md](../GoF/01-Creational-Patterns.md)）；数据库的主键 = 天然的引用键。

### 做法

1. 为引用对象确定唯一键（id），把构造收进工厂（**Replace Constructor with Factory Function**）；
2. 建一个注册表（Map<key, instance>）：工厂先查表，命中返回既有实例，未命中创建并登记；
3. 所有创建点改走工厂；对象通常同时做成不可变，共享才安全；
4. 若实例需要更新：更新也经由注册表统一进行（或改回值语义再权衡），测试。

### 示例

```java
// before：每个订单 new 一个客户——同一个 Acme 有三份互不相干的副本
class Order {
    Customer customer = new Customer("Acme");   // 副本
}
acmeOrder.customer().upgradeToVip();            // 只改了这一份

// after：注册表保证"同一 id 即同一实例"
class CustomerRepository {
    private static final Map<String, Customer> instances = new ConcurrentHashMap<>();

    static Customer of(String id) {
        return instances.computeIfAbsent(id, Customer::new);
    }
}

class Order {
    Customer customer = CustomerRepository.of("Acme");   // 共享引用
}
acmeOrder.customer().upgradeToVip();            // 所有订单立刻可见
```

## 小结：可变数据的三板斧

本章贯穿一条主线——**可变状态是麻烦的根源**：

1. 变量本身：**Split Variable**（一个变量一个职责）；
2. 派生数据：**Replace Derived Variable with Query**（源数据是唯一事实）；
3. 共享方式：**Change Reference to Value ↔ Change Value to Reference**（该独立的不可变，该同步的共享——互为拨盘，按"副本该不该同步"拨）。
